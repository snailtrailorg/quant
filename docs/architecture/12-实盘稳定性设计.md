# 12 · 实盘稳定性设计（2026-08-17 实盘调试复盘产出）

> 背景：2026-08-17 实盘链路调试一天排雷 7 颗（unit 错位/polkit/OOM/停止语义/列漂移/ABRT/幽灵实例）。
> 结论：**链路能通 ≠ 能扛实盘**。本文按"实盘灾难等级"梳理风险，给出必须建的机制、监控清单、代码级优化与运行守则。
> 对应待办批次 ST1-ST6。

## 0. 实盘的灾难定义与设计原则

灾难 = ①非计划停机 ②重复/丢失下单 ③状态与券商漂移 ④控制面失明（不知道自己不知道）。

原则：
- **单一真相源**：持仓以券商查询为准，任务状态以 live_task 表为准，实例清单以 feishu_config 类 DB 表为准
- **防呆不防人**：机制保证安全（约束/闸门/看门狗），不依赖人记得规矩
- **故障自愈 + 必达告警**：自愈失败必须有人知道（飞书通道现成）
- **交易时段禁一切变更**：部署/迁移/unit 变更/重启

## 2. 必须建的机制（设计层）

### 2.1 下单 WAL + 启动对账（ST1，消 D1）
- 时序重排：`place_order` 内 **先写 order_log(status='submitting') → 发单 → 更新 submitted/rejected/failed**。崩溃后 submitting 残留即对账线索
- runner 启动时：`adapter.query_orders()+query_trades()` vs order_log 比对 → 认领孤儿委托、撤销未知在途单（或人工 gate）、不匹配即 critical 告警
- 这是 #7 三账对账的"在线版"：离线版查历史，在线版保重启安全

### 2.2 持仓真相源切换（ST2，消 D2）——✅ 2026-08-18 已实施（迁移 0043，N/O 审，详见 15 号同期报告）
- `position_snapshot` **当前状态表**（每批同事务 DELETE+INSERT，清仓空批可表示）+ `position_refresh` 心跳（stale≠空仓）
- runner/hub_worker 60s 循环取 `query_position()` 返回值单事务覆盖（**非** EVENT_POSITION handler——direct 模式 vnpy 每 4s 常推会散批）；TD 断线守卫内（不写假空仓）
- `/api/position` 读快照（stale/snapshot_ts 语义）；trade_log 推导挪 `/api/reconcile` 第四比对（符号 split_part 归一）做归因
- 生产首验：18 标的券商真值、direction=Net（A 股推 NET，端点不过滤 direction）

### 2.3 任务唯一性约束（ST3，消 D3）
- `start_live_task` 前置检查：同 (account, symbol) 已有 running 任务 → 拒绝（错误码）
- DB 兜底：live_task 部分唯一索引 `WHERE status='running'`（启动竞态双保险）

### 2.4 心跳 + 看门狗 + OnFailure 告警（ST4，消 S1；**S6 修订 2026-08-18**）
- runner 主循环写 Valkey `quant:hb:task:{id}`（pid/md_conn/td_conn/last_bar_ts/last_tick_ts，TTL 90s）
- systemd `WatchdogSec=120` + python `sd_notify(WATCHDOG=1)` —— 挂死（进程在但不转）自动重启
- runner 单元 `OnFailure=quant-task-failed@%i` → hook 脚本走 MessageChannel → 飞书
- beat 任务扫 hb 过期/snapshot 停更/tick 停更（交易时段）→ 告警
- **S6 修订（2026-08-18，详见 15-服务监控设计.md）**：断流自杀（hub+direct 的 300s os._exit）删除，
  只告警不动作——重启治不了平台/网络问题，基线跨日污染曾致每晨 09:31 必重启；安全判定改
  send_order 时刻（buy_ok），进程级故障仍由 watchdog/事件线程检查兜底

### 2.5 systemd 加固（ST4 一部分）
- `StartLimitIntervalSec=300` + `StartLimitBurst=5`：5 次/5 分钟后放弃进 Failed（今天无限风暴 restart counter=59 不可接受）→ 触发 OnFailure
- **SA4（CrashLoopBackOff，2026-08-23）**：
  - `Restart=on-failure`（原 always）：正常停止 exit(0) 不再拉起（F-36 churn 根修）
  - `RestartPreventExitStatus=78`：退出码 78（EX_CONFIG 永久配置错误）不重启，直接 Failed → OnFailure 人工
  - runner 退出码分类：0=正常停 / 75=EX_TEMPFAIL 瞬态 / 78=EX_CONFIG 永久 / 1=其他（watchdog/崩溃）
  - 启动依赖探活 + 进程内指数退避（5→60s 封顶共约 10min，期间喂 watchdog）：服务器重启序 PG 慢启不再 5 连崩打穿 StartLimit
  - celery reconciler（`sa4_reconciler`，beat 300s）：扫 Failed 单元 → live_task 已停/已删只清状态不拉起、PG 不可达整体跳过（fail-safe）、退避窗口（Valkey 计数 300s*2^(n-1) 封顶 1h，稳定 active>10min 清零）外自动 reset-failed + start
- `MemoryHigh=768M`（先限流）+ `MemoryMax=1G`（后击杀）
- `OOMScoreAdjust`：web-api `-500`（保护控制面）、runner `+100`（内存不够先牺牲策略，不牺牲 API）
- journald `SystemMaxUse=200M`

### 2.6 部署闸门 + 选择性重启（ST5，消 S2/S3）
- deploy-server.sh 开头：交易时段（A 股 9:15-11:35/12:55-15:05，加密 7×24 有任务则视为盘中）且有 active live-task → **拒绝执行**，`--force` 显式覆盖
- 选择性重启：比对 rsync 前后各服务代码目录 hash，只 restart 变更者；runner 类代码变更 → 提示"任务将在下次重启生效"并列为盘后动作
- 迁移（DDL）默认同样拒绝交易时段

### 2.7 容量定论（ST6，消 D4——需要用户决策）
实测预算：核心服务 ~800M-1G + **每 runner 稳态 400-600M**（XTP 全市场合约加载峰值 total-vm ~1G）。
- 1.8G + 2G swap：只够 1 个 runner 做**测试**（当前状态）
- 真实盘 N 策略：**4G 起（N≤3），建议 8G**；或策略 runner 独立小机分离部署
- 这是花钱决策，不是代码决策：真金白银之前必须定

### 2.8 运行时韧性分层模型（2026-08-24 故障驱动的设计决策）

两大故障（hub 僵尸会话 + 任务 8 停机 2.5 天）暴露根因：系统没有统一的故障处理框架，
各模块各管一段，数据流症状被用 L1 的钝器处理，DB/systemd 状态漂移无人负责。

**三层责任**：

| 层 | 责任 | 触发器 | 动作 | 已有件 |
|---|---|---|---|---|
| L1 机器层（systemd） | 进程活着 | 退出码/OOM/watchdog 挂死 | 重启+退避+Failed 告警 | watchdog、SA4、StartLimit、reconciler |
| L2 会话层（进程内） | 功能活着：连接/会话/订阅/流 | 数据流健康度（tick/bar 新鲜度）、登录态 | 进程内重登/重订阅/暖机 | MdSession 契约、XtpMdSession、EVENT_LOG |
| L3 意图层（调和器） | 该跑的在跑 | DB 期望状态 vs systemd 实际状态 + 心跳 | 调和（拉起/告警） | sa4_reconciler（扩展为期望状态调和器） |

**两条硬规则**（不可违反）：
1. **退出/重启只属于进程域故障**：崩溃、挂死（watchdog）、事件线程死、启动期配置错（exit 78）。
   **数据流症状（零 tick/断流/登录失败）永不杀死进程**。跨层滥用=SA4 之前每天 09:31 必重启的覆辙。
2. **外部世界故障 = 进程内无限重试 + 有界退避 + 告警，无退出路径**：断流、登录被拒、会话僵尸、
   依赖闪断，全部是同一个模式——`循环{探测症状→尝试恢复→退避等待}`，退避封顶（如 5min），
   重试次数无上限。平台恢复的下一秒就是自愈点。已知周期失效（如 XTP 日切 ≈23:53 丢会话）
   用**定时续航**（交易日 09:10 主动重登），未知失效用**反应式重登**（症状驱动，退避保护）。

**前提**：告警通道必须独立可达（channel_config 配置），否则自愈层是植物人。

**遗留安全阀**：当 L2 自愈正确但 SDK 对象坏死时（极罕见），由 watchdog/事件线程检查兜底真·进程死，
不因自愈逻辑自身 bug 导致重启风暴（SA4 的 StartLimit + reconciler 退避已在 L1 组合防死）。

### 2.9 2026-08-25 一日三事故：韧性模型的忠实实现缺口与运行时重构（已批准）

§2.8 模型本身经受住了考验（09:10 定时续航首战即胜、租约 fencing 正确让位、L3 拉起漂移任务），
但**实现层**一日三事故，证明模型与实现之间存在系统性缺口：

| 事故 | 实现 | 教训 |
|---|---|---|
| 反应式重登死路（09:31-10:13 零 tick） | runner 主循环缺「时段进沿写 sess_enter_ts」一行——hub/runner/worker **三份复制主循环**必然漂移 | 复制即负债：同一职责多份实现，修复同步靠人肉 |
| XTP 半开陷阱 | XTP 官方 Login 返回 -2 文档明示「已存在连接须先 logout」，序列从未被遵守；日切后半开 socket 上 login() 永远 EISCONN | SDK 调用序列必须被**状态机**包住，文档契约必须进代码 |
| **SEGV 崩溃循环（hub 停 20min，最重）** | setHeartBeatInterval 在 createQuoteApi 之前调用（凭文档推理、未经真机验证即盘中部署）→ C 对象未建即触 | **mock 单测（473 绿）拦不住 C 层**；「文档说可以调」≠「任何时刻可以调」 |

**决策：运行时服务层全面重构**（2026-08-25 用户批准，6 批，四道门验收——单测/本地真机冒烟/
事务化部署/盘外部署；XTP 测试平台 7×24 可达，冒烟随时可跑）。核心件：
- `md_api_guard.py`：SDK 生命周期状态机（IDLE→CREATED→LOGGED_IN→RELOGGING→DEAD），
  createQuoteApi→setHeartBeatInterval→login 官方时序只在守卫内发生，非法时刻调用抛 Python 异常
  永不到 C 层——SEGV 类事故结构性绝迹
- `strategy_framework/runtime/`：共享引擎骨架（到期驱动钩子/SessionCounters/MdSessionSupervisor/
  AlertPolicy/SubscriptionManager），三引擎退化为声明式钩子，复制漂移结构性绝迹
- `scripts/quant-release.sh`：8 阶段事务化部署（staging→verify→原子切换→分波重启→postverify，
  失败自动回滚；run-current 包装器钉死进程版本目录，「文件新+进程旧」结构性绝迹）
- L3 扩面（md-hub+strategy@*）+ polkit 配套 + hub 单元对齐 SA4

批次状态单一真相源：`flow/待办.md` 重构跟踪表。当日部署链三处止血已先行（c8326bd）。
