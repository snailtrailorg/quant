# 15 · 服务监控设计（S6 修订 2026-08-18）

> 触发事件：hub 每晨 09:31 必自杀重启（`断流 34627s`，昨夜回放 tick 污染今晨基线）。
> 根因复盘定调：**重启是 liveness 工具不是疗法**——数据缺席的原因在平台/网络/交易所规则，
> 重启一概治不了；把交易所时段规则编进守卫触发器必然在边界上翻车（三所规则不一、券商平台再叠一层偏差）。

## 0. 设计原则（六条）

1. **动作只基于事实信号**（连接回调/线程状态/watchdog/unit 状态），永不基于对数据节奏的预期推断
2. **重启是 liveness 工具不是疗法**——crash-only：进程随时可杀，状态可重建（gen/fencing/暖机/幂等订阅/启动对账已具备）
3. **安全判定在执行时刻**：下单前查输入新鲜度（buy_ok），不在后台猜
4. **日历/时段规则只用于告警抑制与展示，永不触发动作**
5. **告警走症状不走原因**，聚合判断交给监控层
6. **每条告警必须有 runbook**

## 1. 六平面职责

| 平面 | 职责 | 机制 | 归属 |
|---|---|---|---|
| A 进程域 | 进程活着吗 | WatchdogSec=90+喂狗；Restart+StartLimitBurst；OnFailure→SA3；事件线程自检 | systemd（**重启唯一合法 domain**） |
| B 连接域 | 线路通吗 | XTP onDisconnected→重连→重放订阅（60s 幂等）；TD/MD connect_status 分离 | 已有 |
| C 数据域 | 数据新鲜吗 | **只观测+告警，永不动作**（S6 修订：删 hub/direct 两处断流自杀）；基线=时段内首事件 | `src/health_monitor/` |
| D 安全域 | 现在下单安全吗 | send_order 时刻事实检查（`buy_ok_check`：bar<300s + hub 心跳）；sticky 冻结（untrusted/gap=污染事实）；SELL 放行 | `hub_worker.py` |
| E 监控域 | 聚合+触发告警 | 内部 health_monitor（30s beat）+ Zabbix 外部（NAS） | 本文 §3-4 |
| F 运维域 | 人怎么接手 | 每告警一条 runbook；手动重启通道（polkit/web/systemctl） | 本文 §5 |

## 3. 内部健康监控模块（`src/health_monitor/`）

- **collector**：`collect()` 单次快照（systemd unit 批量 show + Valkey 心跳族 + PG/Valkey 可达），
  子项失败不拖垮整体；`/metrics` 与 beat 任务共用
- **monitor**：症状型规则 + **沿检测**（触发/恢复翻转才告警，持续态不轰炸）+ `health_event` 落库
  （迁移 0041）+ MessageChannel 告警；**自身心跳 `quant:hm:health-monitor`（TTL 120s）供 Zabbix 反向监测（互监）**
- beat 调度：`health-monitor` 30s，risk 队列
- 规则表：R1 unit_down(critical) / R2 unit_restarted(warning, NRestarts 沿) / R3 dep_down(critical) /
  R4 hub_hb_lost(critical，Valkey 活但心跳键过期) / R5 task_blind(warning, frozen 聚合视角)
- 既有 `health_check`（LLM 探测）保留不动，职责互补

S6 修订配套（同批落地）：
- hub/direct 断流自杀 → 告警（文案带 runbook 指引）；基线改"时段内首 tick"（进入沿清零：
  跨日回放/假日/竞价静默窗口全部不再误判，心跳新增 `sess_ticks`）
- worker 冻结重构：`frozen_allows` 只判 sticky；动态新鲜度 `buy_ok_check` 在 send_order 时刻判定
  （BUY 需 bar<300s + hub 心跳；检查器缺失保守拒）；`frozen["now"]` 降为纯观测字段

## 4. Zabbix 外部层（Phase 2，NAS）

### 4.1 落地手册（SM1b-e，NAS=常在线）

**① NAS 侧（Zabbix server）**
- 推荐 Docker Compose：`zabbix/zabbix-server-pgsql` + `zabbix/zabbix-web-nginx-pgsql`（NAS 自带 PG 或容器起一个；数据与 quant 无关，独立库）
- 通知介质：webhook/自定义脚本 → 飞书群（建议 `[ZBX]` 前缀或独立群，与平台内部告警区分）
- 网络可达性**决策点**：NAS（家）→ 服务器（阿里云）有两条路——
  - **A. VPN（推荐）**：WireGuard 打通后 NAS 走服务器内网地址拉 `/metrics`（nginx allow 已含私网段），agent 主动上报 ServerActive=NAS 私网
  - B. 公网白名单：家宽动态 IP 是坑（nginx allow 不支持域名），需静态 IP/DDNS+定时改配置，不推荐
- NAS 侧需对服务器可达 10050（active 模式则只需 agent→NAS:10051，**首选 active**——服务器安全组少开一个口）

**② 服务器侧（zabbix-agent2）**
```bash
# al8：装 zabbix 仓库后
sudo dnf install zabbix-agent2
# /etc/zabbix/zabbix_agent2.conf 关键项：
#   Server=<NAS 私网 IP>（active 模式 ServerActive 同值）
#   Hostname=quant-server
sudo systemctl enable --now zabbix-agent2
```
- agent2 自带 systemd 插件（无需 userparameter）

**③ 监控项（Zabbix 配置清单）**
| 类别 | 项 | 形式 |
|---|---|---|
| 主机资源 | CPU/内存/磁盘/网卡 | 模板 "Linux by Zabbix agent 2"（标准） |
| 服务状态 | `systemd.unit.info[quant-md-hub@quant.service,ActiveState]` 等 5 常驻单元 | agent2 systemd 插件（**独立复核**：应用烂到报不出自己死时它仍能看见） |
| 端口 | web 443/80、PG 5432、Valkey 6379 | `net.tcp.service` |
| 外部探活 | `http://<域名>/healthz` | Zabbix web 场景（外部视角） |
| 应用指标 | `/metrics`（Prometheus 格式全套） | HTTP agent + **Prometheus pattern** 预处理（url 走 VPN 内网地址） |
| 监控自身 | hm 心跳键 `quant:hm:health-monitor` TTL 120s | `/metrics` 加暴露或 agent 检查 |

**④ Trigger（症状+依赖抑制）**——host down 压掉该机全部服务告警：
| Trigger | 阈值 | 级别 |
|---|---|---|
| 组件心跳年龄（hub/hm） | >120s（hm 放宽 **>10min**：risk worker 单并发可能延迟 beat 任务，D 陷阱 7） | 高 |
| unit 重启 | 24h 内 NRestarts>2 | 高 |
| 交易时段 bar 断流 | >5min（日历仅此处做抑制） | 高 |
| `/healthz` 外部不可达 | 连续 2 次 | 高 |

**⑤ 双通路归属**：运维级（进程/机器/网络/PG/Valkey）→ Zabbix→飞书[ZBX]；业务级（冻结/断流/熔断）→ 平台 alert_notify→飞书。SM3 再做去重调优。

## 5. 职责划分（内外归属）

| 对象 | 内部 | Zabbix | 告警主责 |
|---|---|---|---|
| 业务语义（frozen/断流/熔断/订单链） | ✅ 主 | /metrics 展示 | 内部→飞书 |
| unit 状态/重启数 | ✅ 主（业务解读） | ✅ 独立复核 | 内部为主，Zabbix 兜底 |
| CPU/内存/磁盘 | ✅ 采集（关联展示） | ✅ 标准+阈值 | Zabbix |
| 网络（连通/丢包/带宽/端口） | ❌ | ✅ 主 | Zabbix |
| PG/Valkey | ✅ readyz/metrics | ✅ 端口探测 | 内部主，Zabbix 兜底 |
| 监控自身死亡 | Zabbix 测 hm 心跳超时 | 内部测 agent 数据新鲜度 | 互监 |
| 证书/域名到期 | ❌ | ✅ web 场景 | Zabbix |

双通路约定：运维级（进程/机器/PG/Valkey）归 Zabbix 通道；业务级（冻结/断流/熔断/风控）归平台
alert_notify→飞书（MessageChannel）。

## 6. Runbook（每告警一条，F 域骨架）

| 告警 | 查 | 处置 | 升级 |
|---|---|---|---|
| unit_down | `journalctl -u <unit> -n 100` | 找到根因后 `systemctl restart <unit>` | 反复出现→人工介入 |
| unit_restarted | journal 09:xx 段（今晨 09:31 案例即此形态） | 判结构性误报 or 真故障 | 24h>2 次必查 |
| dep_down (postgres/valkey) | `systemctl status postgresql valkey`；磁盘/内存 | 重启对应服务 | 数据完整性→data_continuity_check |
| hub_hb_lost | `systemctl status quant-md-hub@quant` | restart（worker 自动暖机补缺，gen+1） | worker frozen 伴随→见 task_blind |
| task_blind (frozen) | `redis-cli -n 4 hgetall quant:hb:task:N`（lag/frozen）；hub 心跳 | hub 死→restart hub；sticky→重启任务 | BUY 已被下单时刻拦截，无资金风险 |
| 断流告警（hub/runner） | journal + XTP 链路 | 确认行情源问题后手动 restart | 平台故障→联系券商 |
| 零 tick | 订阅列表 + MD 连接 | 确认后 restart（重放订阅） | — |
