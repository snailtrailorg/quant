## 1. 全仓 DB 写路径盘点(第一步产出)

### 1.1 盘点方法与范围

grep 全 `server/src`(66 文件)的 `execute(`/`executemany`/`commit()`,逐处读上下文确认写语句类型、批量方式、事务边界。计数:全仓 execute 类调用 494 处;含写 SQL(INSERT/UPDATE/DELETE/DDL)约 160 处,分布在 25 个文件。web_api/main.py 实测 156 处 execute(含读)+auth.py 18 处。

六个符号约定(下表列含义):
- **批量方式**:逐行 = 循环内单条 `cur.execute`(N 行=N 次往返);executemany = 单语句批;单条 = 业务上就一行。
- **事务范围**:单条 / 整批(一批一事务)/ 跨调用(事务跨越函数调用边界,含网络往返)。
- **分段提交**:大批量是否按 N 行/事务切分。

### 1.2 基础设施层事实(所有写路径的公共底座)

| 位置 | 事实 | 影响 |

### 1.4 读路径的隐性事务(idle in transaction 全仓性根因)

psycopg 非 autocommit 下,`with get_conn()` 块内第一条 SELECT 即开事务,块退出归还池才被 SQLAlchemy reset 回滚。全仓大量只读函数(get_bars/_get_config/list_symbols/_desired_symbols/web 读端点等数十处)都是"SELECT 不 commit"——**块内任何慢操作期间,该会话就是 idle in transaction**。锁链事件中 19min idle in transaction 的来源即此类代码(§1.3-C 组两处是实测在案的跨网络变体;web 端点若在 with 块内同步调 LLM/外部 HTTP 属同族,当前 web 端点未发现此嵌套)。

结论:单靠"改写路径"治不完,必须叠加 §4 的 `idle_in_transaction_session_timeout` 服务端防线 + health_monitor 的 pg_stat_activity 长事务告警。

### 1.7 PG 参数防线清单(适用性论证)

前提约束:**所有服务共用同一 DB 用户(quant)**,ALTER ROLE 级设置无法按入口分层——参数必须走应用侧连接(engine options / 连接串),db.py 按入口建引擎预设(web/task/live),alembic env.py 独立设置。落地细节归 §4,本节定值与论证。

| 参数 | web 端点(uvicorn) | 同步/回补任务(celery) | 策略进程(runner/hub systemd) | alembic(migrate) |
|---|---|---|---|---|
| statement_timeout | **10s** | **60s** | **10s** | 不设(大迁移合法长跑;或 30min 上限) |
| lock_timeout | 5s | 10s | 5s | **10s**(核心) |
| idle_in_transaction_session_timeout | **60s** | **300s(5min)** | **60s** | 60s |
| transaction_timeout(PG17+) | — | 600s(可选) | — | — |

逐项论证:

- **web 10s**:实测 156 处 execute 全为单条/少条+立即 commit,无合法超 10s 语句;create_pool 千行逐行整改后回到秒级。10s 同时防慢查询占死 uvicorn 请求线程与池连接。lock_timeout 5s:web 写均为配置行级,拿锁超 5s 即该让位告警。
- **celery 60s**:最大合法单语句=save_bars 分钟段 executemany(≤8000 行)/backfill_adj_factor 按日 UPDATE(~5400 行带索引),均秒级实测,60s 给足 10x 余量;超出者即 §1.6 待整改目标(全表 DELETE),被杀是正确方向。**注意 statement_timeout 只计语句执行不计空闲**——Tushare 慢拉取杀不住,杀它的是下一行。
- **idle_in_tx 5min(celery)**:全仓合法写路径"事务内静止"时长=0(所有网络拉取本都应在事务外;§1.4 根因恰是违反此假设的代码)。5min 是宽容值:既能杀 49min 级跨网络事务(锁链事件量级),又给慢机器上批间执行留裕度。web/runner 收紧到 60s:请求/拍级周期内不存在合法的分钟级事务静止。
- **alembic lock_timeout 10s**:踩坑教训 2 的直接解——DDL 拿不到锁 10s 内快速失败,部署管道可见可重试,不再无声排队堆出 7 个 CREATE INDEX;配合索引迁移 CONCURRENTLY(事务外执行,不阻塞 DML)。idle_in_tx 60s 同拦"迁移中途挂起"。
- **相互关系**:statement_timeout(语句级)与 idle_in_tx(事务静止级)是两张网,前者拦慢 SQL 后者拦悬挂事务;lock_timeout 只管等锁,优先级低于已持有的死锁检测,10s 足以把"无限等"变"快速失败"。三者叠加后,锁链事件的三种形态(长写事务/跨网络事务/DDL 无限等)各有对应杀手。
- **观测先行**:上线参数前先以 health_monitor 采集基线(#9),防误杀;参数生效后告警阈值与参数值联动(告警<超时,留人工介入窗口)。

## 2. 写路径规范（2026-08-21 定稿,随整改批落地）

### 2.1 批量写范式
- **批量 upsert 一律 executemany**（psycopg3 pipeline，db.py `save_bars` 与 2026-08-21 整改后的 tier1 工厂/list 三 handler/pool_data 是范式）；禁逐行 `cur.execute` 循环（5000 行=5000 次往返）。
- 大 DataFrame→rows 构造优先向量化（`to_records`/列取向），避免 `iterrows`（现有存量逐步改，新代码不引入）。
- 分段提交：单事务建议 ≤5000 行；超大批（分钟线全量等）按日/按段提交（`_sync_by_trade_date`/`backfill_adj_factor` 范式）。

### 2.2 事务边界
- **事务内禁一切网络调用**（Tushare/HTTP/XTP 查询）——锁链事件根因。拉取在事务外，落库开短事务。2026-08-21 已修：static_list_sync / data_continuity_check（盘点重灾 #1/#2）。
- **SELECT 读块禁悬挂**：fetchall 后不再需要连接就退出 with（归还池）；读连接归还时池自动 rollback，不产生 idle in transaction。
- 同步任务软上限 = 事务从开到 commit ≤ 数秒；跨分钟的长流程必须拆成多个短事务。

### 2.3 DDL 规范
- alembic 唯一真相源（运行时零 DDL，既有铁律）；alembic 连接自带 `lock_timeout=15s`（2026-08-21 部署）——DDL 被长事务堵时快速失败，不再闷死部署管道。
- **新索引一律 `CREATE INDEX CONCURRENTLY`**（迁移内 `op.execute` + autocommit_block 或拆两步）；存量非 CONCURRENTLY 索引属历史惯性，高流量表改造前不动。
- 迁移文件必带 `if_not_exists`/幂等（0049 教训）。

### 2.4 连接与超时分层（§1.7 落地值）

| celery/sync 族（默认） | 60s | 5min | 10s |

### 4.3 运维诊断钥匙（锁链事件复盘沉淀）
```sql
-- 谁在持锁堵 DDL/长事务源头：
SELECT pid, state, wait_event_type||'/'||wait_event AS waiting,
       age(now(), xact_start) AS xact_age, left(query,55) AS q
FROM pg_stat_activity WHERE datname='quant' AND pid<>pg_backend_pid()
ORDER BY xact_start NULLS LAST;
-- 精确清锁：SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE pid IN (...);
-- 注意：kill 客户端进程 ≠ PG 释放锁（TCP 半开连接等 keepalive 数小时）——必须 PG 侧 terminate。
```
