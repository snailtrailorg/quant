# 19 · IM 统一接入设计(平台化 MessageChannel 补全)

> **定位**:补齐平台化铁律在即时通信面的承诺——"别人实现接口子类+配置即接入自己的 IM,不改平台代码"。
> 现状差距:MessageChannel(PT4)只是**出站告警喇叭**;feishu_bot 是**单例硬实现**(凭证半 DB 半 env/用户授权双轨/签名全局 env——2026-08-21 P0-2 修复时制造了倒退)。
> 用户裁定(2026-08-21):支持多平台接入;接入方式差异允许,但框架+界面统一支撑。
> 流程:八段法,审核=双盲对照。
> **v2(2026-08-21)**:双盲对照审(A/B 两独立评审)4+5 严重项全部吸收——A/B 同判:补 default_role 双轨授权/DROP 后移/运行模型;分歧项路由方案采 B(URL bid 为主,Encrypt Key 加密场景 body 无 app_id 可解)。

## 1. 抽象:IMBotProvider(与 MessageChannel 的边界)

**MessageChannel 保持不动**(单向告警出站);IMBotProvider 管**完整 IM 接入面**:

```python
class IMBotProvider(ABC):
    # ── 凭证声明(单一真相源=FIELD_SCHEMA;REQUIRED_FIELDS 由其中 secret 字段推导)──
    FIELD_SCHEMA: list[dict]   # [{key,type(text|secret|select|number|boolean|textarea),
                               #   label_key,secret,options?,option_label_key?}]
                               # 平台固定列(name/enabled/priority/description)不进此表
    # ── 运行模型(v2 补:飞书=hybrid——消息走 ws 长连接,卡片走 webhook,SDK 长连接丢卡片是现状)──
    MODE: str                  # webhook | websocket | long_poll | hybrid
    def connect(bot_id, on_message) -> None      # 长连接类:启动(平台管进程/会话)
    def shutdown(bot_id) -> None
    # ── 接入向导(状态机:pending→poll→credentials→test→done)──
    ONBOARDING: str = "manual" # manual | interactive
    def start_onboarding() -> dict
    def poll_onboarding(ticket) -> dict
    # ── 通道行为 ──
    def send_text(bot_id, receive_id, receive_id_type, text) -> bool   # v2 补 receive_id_type(open_id/chat_id)
    def send_card(bot_id, receive_id, receive_id_type, card) -> bool
    def verify_callback(bid, request) -> tuple[str, dict] | None
        # 返回 ("challenge", {...回显}) | ("message", InboundMessage) | None(验签失败)
    def build_confirm(tool, args, reason) -> card
    def parse_confirm(action_value) -> ConfirmRequest | None
    def test_connection(bot_id) -> bool

# 统一消息结构(v2 补全):
InboundMessage{bot_id, sender_id, receive_id, receive_id_type,
               text, event_id, chat_type(p2p|group), mentions: list[str]}
```

**职责分界(v2 补)**:验签/消息解析/卡片 schema = Provider;event_id 去重/60s 时效/角色门槛/challenge 路由 = 平台。去重键 `im:{provider}:{bid}:card:{event_id}`。

**授权决策链(v2 补,双盲同判 S1)**:`user_role = im_bot_users 行 → im_bot_config.default_role → 拒绝`(fail-closed)。扫码新 bot 落 default_role='viewer',管理员首授权走 /api/im-bots/{id}/users。

## 2. 表(迁移 0051——v2:只建表+迁数据,**不 DROP**)

```sql
im_bot_config(
  id SERIAL PK, provider text,
  name text, description text,
  default_role text CHECK (default_role IN ('viewer','analyst','trader','admin')),  -- v2:双轨授权(原 feishu_config.role)
  lang text DEFAULT 'zh',                                                          -- v2:N 语言
  enabled bool DEFAULT false, priority int DEFAULT 0,
  credentials_encrypted text,        -- 加密 JSON,仅 secret 字段(REQUIRED_FIELDS=FIELD_SCHEMA.secret 推导)
  params jsonb DEFAULT '{}'::jsonb,  -- 非敏感:route_key=app_id(明文)/默认群
  created_at/updated_at,
  UNIQUE (provider, params->>'route_key')   -- v2:防双存储漂移
)
im_bot_users(
  id SERIAL PK, bot_id int REFERENCES im_bot_config(id) ON DELETE CASCADE,
  im_user_id text, role text CHECK (role IN (...)),
  UNIQUE (bot_id, im_user_id)
)
```

- **数据迁移(全列,v2 修丢列)**:feishu_config 行 → im_bot_config(app_id→params.route_key+credentials / secret 加密 / role→default_role / lang / description / enabled 保值);`event_types` 死列明示丢弃
- **feishu_config 的 DROP 后移到 0052**(批 2 切完全部读路径后——双盲同判:批 1 DROP 即断 FeishuClient/ws_client/web 六端点主链路)
- **回调路由(v2 裁决,采 B)**:URL 带 bid 为主(`/api/im-bots/{bid}/callback`,每 bot 在飞书后台配自己的回调地址)——Encrypt Key 加密场景 body 解密前无 app_id 可解,body 路由有先天硬伤;body 的 header.app_id 仅作交叉校验(与该 bid 的 route_key 不匹配即拒);p1 格式拒;未命中 fail-closed

## 6. 风险与边界(v2 补)

- 扫码 register_app 拿不到 verification_token:扫码接入的 bot 卡片确认在管理员补录 token 前禁用(fail-closed 语义正确),ImBots.vue 提供补录即解
- env→im_bot_users 导入:独立幂等脚本(ON CONFLICT DO UPDATE),导入到全部迁移行;删除语义=表为准
- 长连接 SDK 丢卡片回调(lark_oapi MessageType.CARD→return):现状即 hybrid,接口 MODE 表达;升级 SDK 若支持卡片段再收敛
- 诚实边界:新平台固有复杂度不可消除;全新向导交互形态才需加步骤类型(罕见)
