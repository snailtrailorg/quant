## 一、参照系：五类系统各自的架构答案

### 1.1 kdb+ Tick Plant——行情基础设施二十年事实标准

```
feed handler（专用进程，只管收+重连）
   → ticker plant（唯一写入点：定序+落盘+转发）
   → RDB（当日）/ HDB（历史）——查询面与采集面物理分离
```

对本项目有意义的骨架原则：
- **数据面单向流，组件间只通过显式流协议说话**——没有组件直接伸手进另一个组件的内存状态。我们的 hub→Valkey Streams→worker 与此同型（方向正确）。
- **链内序号自证完整性**：每条消息带序号，下游断号即知缺口，不靠外部巡检发现"今天少了一段"。我们：bar 连续性靠事后 SQL 数数（昨天 09:30-11:01 缺口就是这么发现的——滞后一个上午）。
- **feed handler 的重连/心跳是一等公民**：专业 handler 的核心复杂度就在会话生命周期（登录/心跳/序号重同步/重连退避），不是解析。我们：直到昨天才把会话生命周期从引擎循环里剥出来（md_session/guard），此前混在主循环里。

### 1.2 LMAX——单写者原则（Mechanical Sympathy）

- **每个并发数据结构只有一个线程写**，其他线程只读快照；热路径无锁、无共享可变状态。
- 业务逻辑纯函数化，输入输出全部在边界处理。

对照我们：`stats`/`_tick_state`/`counters` 的并发安全论证是"GIL 原子 + 实证无 gil_scoped_release"——**这是"碰巧安全"不是"设计安全"**：正确性依赖 pybind 实现细节（今天双盲审做 `.so` 字符串分析才确认），换一个绑定版本论证即失效。LMAX 答案：事件线程只投递事件，状态只归引擎主循环线程写——结构上不需要论证。

### 1.3 NautilusTrader——现代开源交易引擎（结构与我们最接近）

- **统一组件生命周期**：DataClient / ExecutionClient / Strategy / Actor 全部实现同一个生命周期契约（start/stop/resume/deinitialize），消息总线解耦，任何组件不知道别的组件的存在。
- **数据客户端与执行客户端分离**（≈我们的 hub 数据面 vs runner 交易面）。
- 组件间故障隔离：一个 Actor 崩不倒引擎，由框架统一重启。

对照我们：**每个集成点各发明一套生命周期**——XTP SDK 的时序靠 guard 补、celery 靠 systemd 补、hub/runner 各自手写主循环。NautilusTrader 的答案是反过来的：先定义组件契约，所有东西往契约里装。我们的 runtime/ 骨架本质是在重新发明这个契约的一半（只覆盖了循环，没覆盖组件边界）。

### 1.4 Erlang/OTP——监督树（L1/L2/L3 的正版）

- supervisor 不是"重启器"，是**声明式监督策略**：重启强度（intensity/period，如 5 次/5s 内放弃并上报）、监督树层级（谁崩溃升级给谁）、一对一/一对多/全连重启策略。
- **let it crash**：进程内防御性编程最少化——状态不可信就死，让监督层以干净状态重启；与"外部世界坏了不重启"（我们的 L2 硬规则）恰好构成完整边界：**进程内状态坏了→死给监督层；外部世界坏了→进程内自愈**。我们 §2.8 两条硬规则其实就是这个边界的朴素表述，但我们的 L1 没有"重启强度声明"，StartLimit 5/300s 是 unit 文件里的隐式策略，没有与 L2/L3 统一的语义。

对照我们：L3 reconciler 是手搓的 level-triggered 调和（k8s 同型，方向正确），但 **desired state 没有单一声明源**——live_task.status 是半真相源（人 stop 了 DB 还 running，昨天任务 8 停 2.5 天的根因），unit 的 enabled、策略表的 enabled、任务表 status 三处各说各话。

### 1.5 交付：不可变工件 + releases 目录 + 门随工件走

- **Capistrano 式 releases/<id>/ + current 符号链接**：每次部署是完整新目录，切换=一次原子 rename，回滚=改回链接。50 年 Unix 传统，Rails 世界 20 年标准。
- **构建一次，处处运行**：CI 产出的工件（容器/包/目录）在 staging 冒烟后**原封不动**进生产——验证过的与运行的是同一字节。
- **门绑定在工件形态上，不绑定在人的自觉上**：不是"部署前记得跑冒烟"，是管道里 stage 没过冒烟就根本没有 promote 这一步。

对照我们：**没有工件概念**——部署=rsync 源码目录到运行树 + exclude 黑名单保护混在树里的数据（runtime//avatars//.env/venv）。exclude 名单就是"源码目录当工件"的补偿器，每个新目录都是新地雷（今天 runtime/ 包撞名爆雷）。批 5 计划了 releases 方案但**排在最后**——所有批次都先从危管道上过。

## 二、差距：为什么老出错（今天的每个错误 → 违反的原则 → 结构病灶）

| 错误（两天内） | 违反的业界原则 | 结构病灶 |
|---|---|---|
| SEGV：setHeartBeatInterval 在错误时刻调 C | 1.3 统一生命周期 | SDK 边界无生命周期抽象，"能不能调"与"什么时候能调"脱钩 |
| 反应式重登死路（sess_enter_ts 缺行） | 单一实现优先 | 同职责三份手写主循环，漂移靠人肉同步 |
| exclude 咬掉 runtime/ 包，hub 停 15min | 1.5 不可变工件 | 代码+数据混树；交付正确性依赖与代码形态无关的黑名单 |
| 盘中 --force 部署放大 SEGV | 变更窗口/冻结纪律 | 闸门存在但可被人格绕过——**纪律无机制兜底** |
| postverify 未跑即交付 | 门随工件走 | 交付物与验证不绑定；"我会记得"当机制 |
| 双盲审全部由用户触发，自发交卷两次都带 P1 | 四眼原则强制化 | 自我验收在结构上不可信（设计门的人绕过门） |
| stats/共享态"GIL 原子"论证 | 1.2 单写者 | 正确性依赖绑定实现细节，非设计保证 |
| 任务 8 停 2.5 天无人知（昨日） | 1.4 desired state 单一源 | status/enabled 三处各说各话，无声明式期望态 |

**三个结构性根源**（所有错误都是它们的表现）：
1. **没有工件边界**：repo=运行树 → 交付层任何新形态都是地雷，验证无从绑定。
2. **没有统一生命周期契约**：每个组件/集成点各自发明启动-重连-停止语义 → 每处都是特例，特例即 bug 温床。
3. **验证绑定在批次与人的自觉上，而非产物形态上**：门随人走，人就绕得开门；四道门是我设计的，我绕过了它两次。

## 三、方案重定向（方向稿——本文档只到方向，正式批次待评审）

| 方向 | 内容 | 对应根源 |
|---|---|---|
| **A. 工件化交付（最先做，原批 5 提前并扩展）** | releases/<id> + current 原子切换 + run-current；数据外置共享层（runtime//avatars//.env/venv 出版本树）；版本树纯代码 → **rsync 零 exclude、--delete 天然安全**；管道内置导入门+postverify（已止血的 verify_imports 转正）；包名评审（runtime/ 撞名） | 根源 1 |
| **B. 统一生命周期契约** | 把 guard/supervisor/EngineLoop 泛化为组件契约：所有长活组件（hub/worker/runner/未来新引擎）同构的 start/stop/health/事件接线；desired state 单一声明源（L3 调和的输入归一） | 根源 2 |
| **C. 验证矩阵规约化** | 一张「变更类型 × 必过门」矩阵写进 12 号/规范：代码=单测+冒烟；交付=导入门+postverify+盘外；配置/schema=各自检查——**门的触发写死在管道与模板里，不依赖执行者自觉** | 根源 3 |
| **D. direct 模式终局决策** | ST7 影子门禁过 → 切阶段 1（worker 消费 hub 流）→ direct 退役；批 3 缩窄为只迁 worker，不为过渡形态铺骨架 | 避免投资浪费 |

顺序：A（地基）→ 观察 → B（批 3 缩窄版）→ C 随 A/B 落 → D 按门禁节奏。
