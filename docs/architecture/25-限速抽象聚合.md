# 25 - 限速抽象聚合（数据源限速策略化）

> 状态：方案待双盲审（八步法步 1）。用户 2026-09-07 裁定：池保留、限速抽象聚合（高内聚低耦合）、积分档太特殊要去掉。本文是 24 号多数据源架构的**限速部分修订**。

## 一、调研结论（当前耦合点）

当前限速是「四层覆盖」耦合在 `DataSource` 基类 + `TushareDataSource`（`data_source.py`）：

| 层 | 机制 | 耦合度 |
|---|---|---|
| L0 | `DEFAULT_RATE_LIMITS`（类默认，代码写死） | 通用 |
| L1 | `params.points_tier` 积分档预设（`POINTS_PRESETS` 200/2000/5000 写死） | **Tushare 专属** |
| L2 | `params.rate_limits` 单参数覆写 | 通用 |
| L3 | `params.rate_time_overrides` 时段乘数（盘后放宽） | **Tushare 专属** |

问题（用户裁定）：
1. **多级耦合**：四层覆盖 + 时段乘数把「限速」的复杂度堆在基类，Tushare 的「间隔秒」模型和聚宽/米筐的「每日额度」模型无法统一表达。
2. **积分档太特殊**：`POINTS_PRESETS` 写死 Tushare 三档，`points_tier` 是 Tushare 专属概念，不通用。
3. **时段乘数**：盘后放宽是 Tushare 频控的优化，复杂度高收益低。

## 二、目标

限速**策略化**：不同平台不同的限速模块，抽象统一接口——高内聚（各平台限速逻辑在自己类里）、低耦合（engine 只依赖接口）。

## 三、核心设计：RateLimitPolicy 策略模式

### 3.1 抽象接口（`data_platform/rate_limit.py` 新增）

```python
class RateLimitPolicy(ABC):
    """限速策略：不同平台不同限速模型，抽象统一接口 get_interval(api_name) -> 间隔秒。

    Tushare=间隔秒模型；聚宽/米筐=每日额度模型（换算成平均间隔）。engine 只依赖此接口，
    不关心具体平台怎么算间隔。
    """
    @abstractmethod
    def get_interval(self, api_name: str) -> float:
        """两次调用最小间隔秒。0=不限。"""
```

### 3.2 两个实现

```python
class FixedIntervalPolicy(RateLimitPolicy):
    """固定间隔策略（Tushare）：api_name -> 间隔秒，两级（类默认 + DB 覆写）。"""
    def __init__(self, defaults: dict[str, float], overrides: dict[str, float]):
        self._defaults = defaults
        self._overrides = overrides
    def get_interval(self, api_name):
        v = self._overrides.get(api_name, self._defaults.get(api_name, 0.0))
        try:
            return float(v)
        except (TypeError, ValueError):
            return 0.0   # 非法值回落不限（原 get_rate_limit 同款容错）


class DailyQuotaPolicy(RateLimitPolicy):
    """每日额度策略（聚宽/米筐）：每日 N 次 → 平均间隔秒（86400/N），各 api 共享额度。"""
    def __init__(self, daily_quota: int):
        self._quota = max(1, int(daily_quota))
    def get_interval(self, api_name):
        return 86400.0 / self._quota
```

### 3.3 DataSource 持 policy（组合）

```python
class DataSource(ABC):
    def __init__(self, credentials_encrypted, params):
        ...
        self._policy = self._build_rate_policy()

    def _build_rate_policy(self) -> RateLimitPolicy:
        """子类覆写：构建限速策略（各平台自己实现，高内聚）。默认无覆写的固定间隔。"""
        return FixedIntervalPolicy({}, self._params.get("rate_limits") or {})

    def get_rate_limit(self, api_name: str) -> float:
        return self._policy.get_interval(api_name)
```

`TushareDataSource._build_rate_policy`：
```python
def _build_rate_policy(self) -> RateLimitPolicy:
    return FixedIntervalPolicy(self.DEFAULT_RATE_LIMITS, self._params.get("rate_limits") or {})
```

**engine/rate_limit_context 零改动**：仍调 `ds.get_rate_limit(api_name)`，内部委托 policy。

## 四、去掉积分档 + 时段乘数

| 删除 | 影响 |
|---|---|
| `POINTS_PRESETS`（200/2000/5000） | `TushareDataSource` 删类属性；限速值直接由 `DEFAULT_RATE_LIMITS`（L0）+ `params.rate_limits`（L1）两级决定 |
| `points_tier` 层（get_rate_limit L1） | `get_rate_limit` 从四层简化为委托 policy（两级） |
| `_apply_time_overrides` / `rate_time_overrides` | 删基类方法 + docstring；`FixedIntervalPolicy` 不含时段逻辑 |
| `PointsTierReq` + `_preset_cls` + 积分档端点 | `models.py`/`mgmt.py` 删积分档切换端点；保留 rate_limits 覆写端点（`RateLimitOverrideReq`） |

**迁移**：无 DDL（`data_source_config.params` 里的 `points_tier`/`rate_time_overrides` 键变遗留，不主动清理——旧配置行无害，读不到即忽略）。前端 DataSources.vue 的积分档下拉删，限速表保留（直接配 rate_limits）。

## 五、接口契约

**新类**：`RateLimitPolicy`（抽象）、`FixedIntervalPolicy`、`DailyQuotaPolicy`（`data_platform/rate_limit.py`）
**改动**：`DataSource._build_rate_policy`/`get_rate_limit`（组合 policy）；`TushareDataSource._build_rate_policy`（FixedIntervalPolicy）
**删除**：`POINTS_PRESETS`、`get_rate_limit` 四层逻辑、`_apply_time_overrides`、`PointsTierReq`、mgmt 积分档端点
**前端**：DataSources.vue 删积分档下拉

## 七、回滚/边界

1. **池保留不动**（用户裁定）：`pools`/`minute_symbols` 攒数据标记、回测池级/个股级入口，本次不碰。
2. **熔断保留**：`CircuitBreaker` 三态熔断是通用的（DataSource 级），不涉及「多级覆盖」，不改。
3. **限速值语义不变**：FixedIntervalPolicy 两级（默认 + 覆写）的限速值与现状 L0+L2 一致——删掉的 L1（积分档）/L3（时段乘数）是「切换档位/盘后放宽」的便捷层，删后限速值由 DB `rate_limits` 直接定（默认兜底）。
4. **越界回步 1**：只动「限速策略化 + 删积分档/时段乘数」，不碰熔断、池、同步引擎。
