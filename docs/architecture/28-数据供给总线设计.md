## 一、数据地图：系统有什么数据、谁在用

**人话**：把系统想象成一家餐厅——行情是食材，参考数据是菜谱，交易回报是小票。这张表列清每种食材谁用、什么时候买（定时进货 vs 现点现做）。

| 大类 | 数据（DataKind，§十一全量） | 消费方 | 时态 |
|---|---|---|---|
| 行情时序 | bar_daily / bar_minute / index_daily | 因子计算、回测、策略暖机、选股 | historical（定时同步） |
| 行情时序 | bar_minute（盘中生成） | 实盘策略实时计算 | streaming→historistic 双时态（盘中流生成、盘后权威回补，§8.4） |
| 实时行情 | snapshot（含 crypto 标记价字段） | 实盘决策、交易台、风控监控 | snapshot（拉取+TTL 缓存） |
| 实时行情 | stream_bar / stream_tick / depth | 实盘策略、盘口策略（Phase 2） | streaming（订阅推送） |
| 参考数据 | static_list / trade_cal / index_constituents / industry_class | 一切需要"标的清单/日历/归属"的地方 | historical（全量重建式同步） |
| 参考数据 | fundamental_daily / financial_stmt / featured_daily（资金流·融资融券·龙虎榜·筹码）/ stk_limit / adj_factor / funding_rate | 因子、选股、回测 | historical |
| 事件数据 | **suspend**（停复牌）/ **corporate_action**（分红除权·转债强赎下修） | 实盘下单硬约束、回测可成交性、转债策略生死线 | historical（事件流）+ snapshot（当前状态查询） |
| 交易运行时 | account_query / order_stream / trade_exec / **settlement**（交割单） | 实盘 worker、风控、对账 | snapshot + streaming |
| 市场参数 | margin_model / fee_model / fx_rate（挂账） | 风控（强平档位）、成本模型、跨市场计价 | security_master 引用（**非 DataKind**——参数域，§十一注） |

**不归总线管的**：因子值、信号、风控状态、股票池——它们是消费方产物（衍生数据），总线只管"从外部世界进来的数据"。

## 二、五层架构总览

**人话**：五层像一栋楼——一楼放法律（契约），二楼住搬运工（adapter），三楼是调度室（路由），四楼是大堂（门面），五楼是客房（消费方）。客人只跟大堂说话，永远不用知道后厨哪个供应商送了菜。

```
L5 消费层   回测引擎/因子计算/实盘 worker/选股/风控/对账 —— 只 import 门面接口
L4 门面层   DataBus（读数据） + TradeBus（做交易）—— 双门面，共享 L3 内核（CQS 分离）
L3 解析层   RoutingTable.resolve(req) → 有序候选链 + 决策审计
S  存储层   PG（本地仓+权威缓存）+ Valkey（流+快照缓存）—— 独立一层（v1 缺失，专家 P0-3）
L2 适配层   Source Adapter 插件族（Tushare/XTP/Tencent/Binance/OKX/Wind/…）
L1 契约层   数据形状/时点立法/错误模型/SecurityMaster/MarketHours 节奏域
```

**依赖铁律**（可用 CI 断言，对标 test_layering）：L5→L4 单向；L2 互不知晓；S 层只被 L3/L4 与消费方经门面触达（"L8"为 v2 笔误，本版修正）。

**五层 ↔ 项目四层映射**（三审 P3 成表——防实施期 test_layering 抓人）：

| 蓝图层 | 项目层（test_layering） | 内容 |
|---|---|---|
| L1 契约 | quant_common（层 0） | 类型/枚举/维度词典纯数据；SecurityMaster 的 DB 加载函数下沉数据层 |
| L2 adapter + L3 路由 + S 存储 | data_platform（数据层） | 注册表/resolve/对账/PG 仓 |
| L4 门面 | data_platform 对内 + web_api/策略框架按消费方 | DataBus 归数据层；TradeBus 契约在 quant_common、执行链在 strategy_framework |
| L5 消费 | 各消费方（应用层/入口层） | 只 import 门面
**解耦判据**（宪法定义"无缝"）：**加一个供应商 = 新增 1 个 adapter 文件 + DB 2 行（账号+能力启用），L3/L4/L5 与全部消费方零改动；CI 断言全仓无 `if provider ==` 分支。**

### 3.2 时间与时点立法（金融必修 16 条，升格 hub 现有实践）

| 法律 | 条文 | 实施义务（adapter） |
|---|---|---|
| tz | ts 一律 **UTC aware** 落库；展示按市场时区。**立法冲突标注（复审 N8）**：本条是对 23/24 号"+08:00"既有立法的**变更**——实施批须含存量迁移（timestamptz 等值改写零损失），迁移完成前两份文档以本条为准 | 源本地时区→UTC 归一 |
| 日界 | 日线 bar 的 ts 锚 = 市场收盘时刻：astock 15:00(+08:00 转 UTC)、crypto **UTC 00:00**（Binance 实证锚，v1 专家口误已纠） | MarketHours（§4.2）提供锚点 |
| **分钟时点** | **结束时刻标注**：桶 [10:00,10:01) → ts=10:01:00（Tushare 口径——hub MinuteAggregator 已实现，本条升格为契约） | 标开始时刻的源（腾讯分时）须 shift+1min |
| **竞价条** | 供应商分钟数据中的集合竞价统计条（如 Tushare stk_mins 09:30:00 条，内含开盘集合竞价撮合量）**并入首根（ts=09:31）**：volume/amount 累加、open 取竞价条 open、high/low 与竞价价取 max/min（跳空日竞价价即首根极值——漏并则分钟聚≠日线，又一生成 diff 源）——只滤条不归量=首根系统性缺竞价量，每天每标的触发固定对账 diff（v3 复审必修：v2 只挖了壳没填量） | adapter 归一义务（§5.3）；hub 侧 [09:30,09:31) 首桶同口径含竞价撮合量（聚合基线对齐） |
| bar 边界 | 开盘首根/午休切分/收盘末根的归属按 MarketHours 时段表切分 | 同上 |

### 3.3 错误模型（架构 P0-6：三分类决定能否重试）

```python
class ContractError(Exception): ...
class ParamError(ContractError):      # 请求本身错（未知 symbol/非法区间）→ 不 failover，直接抛
class SourceUnavailable(ContractError): # 源故障（超时/熔断/限速打满）→ 可 failover 到下一候选
class DataGap(ContractError):         # 源正常但无此数据（停牌/未上市/覆盖外）→ 可降级/换源补
```
**failover 的定义**：只有 `SourceUnavailable` 触发候选链下移；`ParamError` 重试无意义；`DataGap` 触发覆盖面更广的候选（§6.2）。

### 3.4 复权与修订（金融必修 17/18 条）

- **复权存储立法**：库中永远存**不复权原始价 + adj_factor 旁挂**；前/后/不复权三口径由消费侧现算（16 号逐行因子链升格契约）。**禁止任何 adapter 直接出口复权价**——CI 断言 adapter 输出列不含 `close_qfq` 之类。
- **修订事件化（PIT 双时间轴）**：财务/成分类数据表一律带 `ann_date`（披露日）列；上游回溯修正**写 restate_event 行，不静默覆盖**；消费侧显式选口径：
  ```python
  bus.get("financial_stmt", symbol=..., as_of=AsOf.PIT)      # 当时知道什么（回测防前视）
  bus.get("financial_stmt", symbol=..., as_of=AsOf.LATEST)   # 现在知道什么（当前决策）
  ```

## 四、SecurityMaster 与节奏域：标的属性库 + 市场时钟

**人话**：一本"户口本"（每个标的是什么、属于哪个市场、乘数多少、什么时候开盘）+ 一本"作息表"（每个市场几点竞价、几点午休、几点收盘）。路由和风控随时查这两本册子，永远不用在代码里写死。

### 4.1 security_master 表

```sql
CREATE TABLE security_master (
  vt_symbol     text PRIMARY KEY,            -- '600000.SHSE' / 'BTCUSDT.BINANCE'
  market        text NOT NULL,               -- astock | crypto（词典：markets.py 单源）
  exchange      text NOT NULL,
  category      text NOT NULL,               -- stock|etf|convertible|fund|reits|perp
  list_date     date, delist_date date,      -- 生命周期 → 路由覆盖过滤
  multiplier    numeric NOT NULL DEFAULT 1,  -- 交易语义（可转债 10 张/手 vs 股票 100 股——27 号勘误的根治）
  tick_size     numeric NOT NULL DEFAULT 0.01,
  fee_model_ref text,                        -- 费率模型外键（回测 set_fees 参数化收编）
  margin_model_ref text,                     -- 保证金档位外键（加密强平风控根参数——金融必修 20）
  session_id    text NOT NULL,               -- → market_hours（§4.2）
  trade_phase   text NOT NULL DEFAULT 'T+1',  -- T+0|T+1（转债/crypto T+0，股票/ETF T+1——回测可成交性契约位；柜台拒单是实盘兜底非回测依据）
  routing_hints jsonb NOT NULL DEFAULT '{}', -- 只放"事实例外"（该标的仅源 X 覆盖）；
                                              -- 立法：禁放规则（架构 P0-8b 防知识回迁 DB 后门）
);
-- 时变属性层（金融必修 26）：ST 戴帽改涨跌停幅度、转股价下修、margin_tier 保证金档位
-- （档位带生效期=历史回放取当期口径，v3：margin_model 的时变角由本层承载）——时变事实不进主档
CREATE TABLE security_state (
  vt_symbol text, effective_from date, kind text,   -- 'st'|'limit_band'|'conv_price'…
  value jsonb, PRIMARY KEY (vt_symbol, effective_from, kind)
);
```

**两级路由判据**（品类级默认 + 标的级例外）：`resolve()` 过滤覆盖面先按 (market, exchange, category) 匹配，再叠加 routing_hints 的标的级例外——代码零 if-symbol 分支。

### 4.2 market_hours 节奏域（金融必修 21 条：语义义务立法）

```sql
CREATE TABLE market_hours (
  session_id  text PRIMARY KEY,          -- 'astock_main'|'crypto_247'
  tz          text NOT NULL,             -- '+08:00' | 'UTC'
  calendar    text NOT NULL,             -- 日历真源引用（astock=trade_cal 表；crypto=none）
  sessions    jsonb NOT NULL,            -- 时段序列（下表 astock_main 示例）
);
-- astock_main.sessions:
-- [ {phase:"pre",      09:15-09:20, cancel:true },   // 开盘集合竞价·可撤单
--   {phase:"auction",  09:20-09:25, cancel:false},   // 竞价·不可撤单
--   {phase:"open",     09:30-11:30}, {phase:"lunch", 11:30-13:00},
--   {phase:"open",     13:00-14:57},
--   {phase:"close_auct",14:57-15:00, scope:"SZSE|BSE|SHSE:STAR"}, // 收盘集合竞价：深市全所+北交所+沪市仅科创板
--   {phase:"post_fix", 15:05-15:30, scope:"SHSE:STAR|SZSE:CHINEXT"} ]  // 盘后固定价格（仅科创/创业板；BSE 无）
-- scope 语法（v3 复审必修②）：`交易所[:板块]`——板块级例外不建 board 实体（27 号"board 暂不建"不变），
--   由 scope 表达式承载。表注：SHSE 主板无收盘竞价（连续竞价至 15:00，收盘价=14:57-15:00 加权均价——
--   §15.1 口径白名单第一条来源：加权均价 vs 集合竞价价两种收盘口径并存）
-- crypto_247.sessions: [{phase:"open", 00:00-24:00}]，calendar=none，日锚=UTC 00:00
```
**三个消费点**：路由（时段内该用流还是快照）、补齐（**停牌=合法缺失**，suspend 品类+日历双确认才报警）、对账（盘后定价成交是否计入日量——口径白名单条目，§15.2）。
现状衔接：xtp_session 参数化（连接窗）是本表的运行期切片，L3 深水区实施时统一。

## 五、L2 适配层：能力签名与 adapter 模板

**人话**：每个供应商一个"翻译官"，翻译官必须会说两种话——对供应商说方言，对系统只说普通话（契约）。加新供应商=雇一个新翻译，不动餐厅任何其他岗位。

### 5.1 能力声明与签名（代码级）

```python
# quant_common/capability.py（层 0：类型）+ data_platform/registry.py（注册表）
class PullCapability(Protocol):
    kind: ClassVar[DataKind]
    def fetch(self, req: FetchRequest, acct: AccountRef) -> ContractFrame | AsyncContractFrame: ...
class StreamCapability(Protocol):
    kind: ClassVar[DataKind]
    def subscribe(self, sub: Subscription, sink: Sink, acct: AccountRef) -> StreamHandle: ...

class StreamHandle(Protocol):
    def unsubscribe(self) -> None: ...
    def health(self) -> SourceHealth: ...      # {state, last_msg_ts, msg_rate} → 健康度回流（§6.4）

class Sink(Protocol):                          # 背压契约（架构建议 10，本仓现状立为缺省）
    def on_contract(self, evt: ContractEvent) -> None
    # 慢消费者处置=冻结告警（Valkey MAXLEN~5000 + worker 冻结语义——现状缺省，写死不再造）
```

### 5.2 adapter 模板（以 TushareAdapter 为例，代码级）

```python
@adapter(name="tushare", creds="token")
class TushareAdapter:
    implements = [
        Pull(kind="bar_daily",          scope=astock_all_exchanges),
        Pull(kind="bar_minute",         scope=astock_shse_szse),   # stk_mins 无 BSE——覆盖矩阵事实
        Pull(kind="fundamental_daily",  scope=astock_all),
        Pull(kind="featured_daily",     scope=astock_all),          # margin_detail/moneyflow/top_list/cyq_perf
        Pull(kind="financial_stmt",     scope=astock_all, pit=True),
        Pull(kind="trade_cal"), Pull(kind="static_list"), Pull(kind="stk_limit"),
        Pull(kind="adj_factor"), Pull(kind="index_constituents"), Pull(kind="industry_class"),
        Pull(kind="suspend"), Pull(kind="corporate_action"),
    ]
    quality = Quality(latency="T+1 盘后", coverage=0.999,
                      rate=RateProfile(window="积分档", burst="按 api_name"),
                      cost="按次计积分")      # → shadow 预算闸门输入（§15.3）

    # fetch 骨架：方言进、契约出；差异全部终结于此函数
    def fetch(self, req, acct):
        pro = tushare_pro(self._token(acct))            # 凭证经 AccountRef（§五.4），不落盘
        df = pro.stk_mins(ts_code=..., freq=..., ...)  # 方言：ts_code/参数形状
        df = merge_auction_into_first(df)  # 归一义务①：竞价条并入首根（§3.2 v3——volume/amount
                                          # 累加+open 取竞价条 open，非简单过滤）
        df["vol"]  *= 100                               # 归一义务②：手→股（24 号立法）
        df["amount"]*= 1000                             # 归一义务③：千元→元
        return to_contract(df, source="tushare")        # 归一义务④：结束时刻校验/UTC/11 字段
```

### 5.4 凭证获取（55a/55b 已落地链，总线沿用）

## 六、L3 解析层：RoutingTable 与路由决策

**人话**：调度室。收到点单（要什么数据、给谁用、多急），先筛掉不会做这道菜的厨子（硬过滤），再按手艺、排班表和今天的身体状态排顺序（软排序），最后把"为什么派了张三"记在值班日志（审计）。

### 6.1 resolve 全过程（代码级）

```python
def resolve(self, req: DataRequest) -> CandidateChain:
    # req = {kind, symbols, freq, temporality, consumer_tag, deadline_ms, as_of}

    # ① 硬过滤（全数据驱动，零代码分支）
    cands = self.registry.adapters_with(            # 代码注册表：能力+scope
        kind=req.kind, temporality=req.temporality) # 　＋组合表合法性（§十一）
    cands = [c for c in cands if c.account.enabled   # DB：external_interface 能力启用子集
             and c.covers(req.symbols)]              # scope 匹配：SM 解析 (market,exchange,category)
                                                     # 　　　　　＋security_master.routing_hints 例外
    cands = [c for c in cands if self.perms.allows(  # 权限过滤（架构专家补）：market_op 五键→
        req.consumer_tag, req.symbols, c.account)]   # (market,category,venue)（27 号 DECOMP 终态）

    # ② 软排序（三因子加权，权重=routing_policy 表）
    w = self.policy.weights(req.consumer_tag)       # backtest: completeness>cost；live: latency>…
    cands.sort(key=lambda c: (
        -c.account.position,                        # 人工序（Web 拖拽）
        -score(w, c.quality, self.health.of(c)),    # 质量档案×实时健康度（熔断态=−∞）
    ))
    # 风暴防护（架构 P0-补充）：熔断触发 failover 时按 per-source 并发闸门放行
    # （bulkhead：候选 i 的在途请求超闸门则直接跳候选 i+1，防止全量涌备源打死自己人）
    # v3 细则：闸门计数=共享存储（Valkey）——跨进程风暴同样防护；审计区分两种跳过
    # 　（skip_busy=闸门满 vs skip_unhealthy=熔断——"为什么没用 B"两种答案分开记）；
    # 　全链闸门满+deadline_ms 耗尽 → 抛 SourceUnavailable(timeout)——deadline 首个消费点；
    # 　"配置序 vs 事实序"漂移观测：probe 增加 per-source 实际服务占比
    # consumer_tag 缺省（v3）：未登记 consumer → routing_policy 默认行（completeness>cost 保守序）

    # ③ 审计（P0-5：采样式，见 §15.4）
    self.audit.maybe_record(req, cands, fingerprint_changed=True)
    return CandidateChain(cands, epoch=self.epoch)
```

### 6.2 三种切换语义（风险分级，v1 立法保留+补协议）

| 形态 | 触发 | 语义 | 适用 |
|---|---|---|---|
| 自动 failover | SourceUnavailable | 候选链下移+审计必记 | 一切读类 |
| 计划切换 | Web 改 position | 下个 resolve 生效；存储层执行版本冻结协议（§7.3） | 读类 |
| 交易切换 | 人工提名 | **状态机+确认卡**（§10.3），绝不自动 | trade_exec 专属 |

### 6.3 热更新与多进程一致性（架构 P0-4）

```
config_version（Valkey 单调整数，DB 变更时 +1；载体=Valkey pub/sub channel "cfg")
各进程（web/celery/hub/runner）：订阅 → 收到新版本 → 重建 RoutingTable（原子替换引用）
　resolve 结果缓存带 (fingerprint, version) 双键——版本变即全失效（架构建议 9）
观测面：/api/_probe 增加 route_epoch 段：{进程, epoch, lag_ms}——切换窗口可解释
在途语义：已开始的 fetch 用旧表完成；已建订阅按流切换协议处理（§8.2）
漏收兜底（v3 复审 N9）：pub/sub 漏收（进程重启窗口）→ 各进程周期性对账 config_version
　（滞后>阈值即主动重拉重建表）——自愈，不依赖人看 lag_ms
```

### 7.2 fetch-on-miss 语义

    try: return chain.fetch(source="local_pg")          # 仓即候选①

        frame = chain.fetch(skip="local_pg")             # 远端候选按序取

### 7.3 切换重建与版本冻结（读类计划切换的存储协议）

```

重建窗口内：get_bars 返回冻结的旧版本快照（读旧不读半新半旧——回测一致性，金融必修 25）；

　　并进重建回放队列（重建完成后按新源重拉覆盖）——杜绝"读旧写新"的版本污染

```

## 八、流与水位线：无缝切换的真语义（架构 P0-1/P0-2 补全）

**人话**：实时数据像直播。换台（换源）时观众不能看到断片或重播——需要一份"节目单"（流注册表）告诉大家现在哪个台在播、播到哪了（水位线），观众换台时从上次看到的地方继续。

### 8.1 两层订阅模型（hub 对源 ≠ worker 对流）

```
第一层（集中式）：Hub 进程持账号，对"源"订阅（StreamCapability.subscribe，AccountRef 来自 RoutingTable）
第二层（分布式）：worker 们对"分发流"消费（Valkey Streams，XREADGROUP）——worker 永不直连源
```

### 8.2 流切换协议（代码级时序）

```
stream_registry（DB 表）：
  stream_id | source_account | gen | state    # state ∈ shadow|live|draining|retired

计划切换（MD 源 A→B）：
  1. 起第二 Hub 实例持 B 账号，state=shadow（写影子流，不发布）
  2. 影子健康 N 分钟（StreamHandle.health 判据）→ 原子切：registry.gen+=1，B.state=live，A.state=draining
  3. 分发流消息内嵌元组 (gen, seq)：worker 见 gen 跳变 → 执行重暖机协议（§8.3）
  4. A 排空（drain TTL）→ retired，Hub-A 进程退出
故障 failover（源 A 猝死）：
  1. StreamHandle.health 超时 → 自动 gen+=1 切影子/备源（读类自动语义）
  2. 与计划切换唯一差别：无影子预热，冷启动窗口数据由盘后权威回补兜底（双时态，§8.4）
丢包/重复：at-least-once + 去重键 (vt_symbol, bar_ts)——worker 幂等消费（14 号现状继承）

**租约模型（v3 复审必修 N1——与 14 号单租约防脑裂调和）**：
- 分发写权 = 单租约（14 号 SET NX+Lua CAS 语义不变）：**任一时刻至多一个 Hub 持分发租约**；
- 影子 Hub **不参与分发权竞争**：shadow 态订阅源、写影子流（stream_id 后缀 ":shadow"），不写主流；
- 写权交接屏障 = fencing token：registry.gen+1 的同一事务把租约 token 绑定到 B——B 从 DB 读到
  (gen, token) 才开始写主流；A 的写操作校验 token 失配即 surrender（14 号 fencing 同款）；
  消除"gen 已推进但 B 未感知、A 已 draining"的写权真空窗；
- 故障 failover 冷切（无影子）：租约 TTL 过期 → 候选 Hub 抢租约成功者写 gen+1——与 14 号现行
  hub:lease/hub:gen 机制完全同构，不新发明。
```

### 8.3 水位线衔接（get_bars 与 subscribe 的缝隙，总线内建）

```python

stream = bus.subscribe(sub, from_watermark=watermark)
# 总线衔接器职责（消费方拿单流，拼接逻辑零泄漏）：
#   ① 流按 from_watermark 重放（XREVRANGE 起）
#   ② 去重键 (vt_symbol, ts) 丢弃仓内已有
#   ③ 顺序契约：消费方见到的序列单调不回退（14 号 §3.3 顺序钉死升格为总线义务）
```

### 8.4 双时态权威链（金融建议：盘中流生成 vs 盘后权威回补）

盘中 streaming 生成的 bar 是"快照聚合"；收盘后 historical 通道（官方日线/分钟源）**回补为权威**——盘后 sync 覆盖当日流生成版本（dataset_version 推进），消费方拿到的"最终事实"以回补后为准。bar_minute 是 hybrid 时态：**盘中 streaming、盘后 historical 权威**——两时态不矛盾，以时间阶段切换权威。

**当日 ongoing 日线 bar 归属**：实盘"今天这根日 K"需求（盘中画图/当日收益）由消费方从 stream_bar 聚合派生，不设品类、不入 historical 仓（historical 只存已闭合权威 bar）——显式归属防歧义。
**crypto 7×24 切刀（v3 复审必修 N2——"盘后"不存在时的边界立法）**：
- 回补**仅覆盖已闭合时段**（闭合=该 bar 的 bucket 已终结；三审 P3 简化：原"无活跃订阅"条件删除——已投递不撤回+回补只写 historical 已保证流侧安全，该条件反使持续订阅标的永不回补（historical 读到滞后版本）；
- **已投递流数据不撤回**——流侧已驱动过交易决策，回补只修 historical 读路径，不做流重放；
- 回补后 historical 与流生成版本 diff 超 per-field 容差 → diff 告警升级（数据质量事件，非静默覆盖决策产物）；
- 实操节奏：crypto 回补窗口锚市场小时（如每日 UTC 00:00 日界后回补前一日），等价 A 股"盘后"语义——market_hours（§4.2）为无收盘市场定义日锚即得"虚拟盘后"。

## 十四、操作流程闭环（六份 runbook）

**人话**：六本操作手册，每本从"谁发起"到"怎么验证"一步不缺。

**R1 加供应商**（如 Wind）
```
开发者：写 WindAdapter（§5.2 模板+§5.3 六项归一打钩+契约测试三样本）
　→ @adapter 注册+外部依赖档案加列（§十二）
管理员：Web 建账号行（凭证/能力启用/position）
验证：providers 目录出现 Wind→连接测试 ▶→shadow 影子跑 3 日→diff 达标→position 提前转正
```

**R2 加品类**（如 open_interest 实装）
```
改动账单（诚实）：DataKind 枚举+组合表+覆盖矩阵列+适配器实现+（有页面则）前端页签——四处中央变更
　枚举治理闸：无消费方的需求不立 kind（防枚举爆炸）
```

**R3 读类源切换（计划）**：Web 拖 position→dataset_version+1→后台重建（版本冻结中读旧）→重建毕新版本生效→shadow 观察一周→旧源账号停用。

**R3b MD 流源切换（v3 复审 N4——§8.2 协议的操作面）**：
```
①准备：registry 登记影子行（B 账号, state=shadow）→ 起 Hub-B（写影子流，不竞争分发租约）
②观察：影子流健康 N 分钟（msg_rate/last_msg_ts 达标）——不达标换候选重来（嵌套切换=影子行直接换 C，主链不动）
③原子切：单事务 {gen+=1, 租约 fencing token→B, B.state=live, A.state=draining}
④drain：A 排空 TTL → retired → Hub-A 退出；worker 侧 gen 跳变触发重暖机（§8.3 水位线协议）
⑤验证：probe route_epoch 各进程收敛 + 首日 shadow 对账（新旧源同桶 diff 入 §15.2）
```

**R4 交易账号切换**：§10.3 状态机全流程（提名信息包→确认卡→前置检查单→切→对账锚点留存）。

**R5 故障 failover**：SourceUnavailable→候选下移（并发闸门防风暴）→审计必记→IM 告警→恢复后自动回切 position 序（hysteresis 冷却窗防乒乓）。

**R6 数据修订**：上游 restate→restate_event 行落库→订阅该 kind 的因子任务收事件→按其口径声明（PIT/LATEST）决定是否重算→重算记 dataset_version。

## 十五、质量闭环与成本闸门

### 15.1 金标准纪律（继承）+ 口径白名单（金融必修 23）

“容忍一致地错、绝不各改各的”之上新增：**对账前口径归一**——收盘价取值口径（最后成交 vs 最后分钟加权，含 SHSE 主板=14:57-15:00 加权均价的口径事实，§4.2 表注）、日量含不含盘后定价/竞价量等“不一致但都可能对”的差异，登记口径白名单；对账引擎按白名单先归一再 diff，防止狼来了。

**白名单治理三条（v3 复审——防白名单退化成告警静音器）**：①条目版本化（代码仓管理，非 DB 手改）；②新条目带验证义务（定期抽样证明该差异真实存在）；③命中率监控（某条目长期 100% 命中=可疑，升级人工复核）。
**SecurityMaster 自身对账（v3 复审——架构建议 2 补全）**：SM 也是多源数据——static_list 多源不一致时以 routing_policy 指定的金标准源为准，diff 走 §15.2 同款采样对账（含 BSE 覆盖类覆盖差异）。

### 15.2 shadow 对账（采样式+预算闸门，架构 P0-5）

```
shadow_policy：{kind, 备源, 采样比例(如 bar_daily 每日 50 标的), 预算上限(积分/月)}
超预算自动降采样→告警；diff 超 per-field 容差 → 降级备源 + restate 排查
```

### 15.3 审计采样（防写放大）

RoutingDecision：决策指纹变化必记+failover 全记+稳态每 N 分钟采样一条。算术：50 标的×5s 轮询=86.4 万次/天决策，采样后 ≈千行级/天。

### 15.4 血缘贯穿（金融必修 19）

`bar.source` 列 → RoutingDecision 审计 → **signal_log/回测结果记 (source, fetched_at, dataset_version)**——监管问"这笔单依据哪个源哪版数据"链条闭合。

### 16.2 知识分层终版立法（架构挑战 a 精确化）

> **映射住代码（adapter），偏好住 DB（routing_policy/账号 position），例外住属性库（routing_hints）**——判据=变更频率×验证成本：偏好盘中可变须秒级生效，映射变更=发版。
> 逃生门（触发条件立法）：品类>50 且高度同构（tabular→tabular）时，允许构建时 schema 生成（声明式列映射+编译期校验）——仍非运行时 DSL。
> 字面量豁免四类：层级默认（DB 可覆写）/平台规则算法（client_id 1-99）/注册表键名/fallback 键名——此外 CI 断言零魔法值。
