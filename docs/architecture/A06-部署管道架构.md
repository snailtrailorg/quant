## 0. 一句话与一张图

**一句话**：控制机上一条 Ansible 命令，把仓库里的**不可变版本树**搬到目标机，用**符号链接原子切换**放量，全程只走 **12 只特权 wrapper**，最后用**进程 cwd 收敛断言**自证成功；失败自动翻回上一版。

```
┌─ 控制机（开发机，bernard 身份）───────────────────────────┐
│  ~/Projects/quant/                                       │
│   ├── server/          ← 发布源（rsync 白名单切片）        │
│   ├── web/dist/        ← 前端工件（preflight 现场 npm build）│
│   └── deploy/                                            │
│        ├── .venv/            ansible-core 2.17.14         │
│        ├── inventory/        quant-prod.yml / quant-staging.yml
│        ├── playbooks/        release.yml / rollback.yml / bootstrap.yml / wave.yml
│        ├── wrappers/   12 只（源码住仓库，装位到目标机 /usr/local/sbin）
│        ├── templates/        sudoers-quant-deploy.j2
│        └── collections/      ansible.posix vendor（CN 离线可复现）
└──────────────────────┬───────────────────────────────────┘
                       │ ssh（密钥 quant_deploy_ed25519，用户 deploy）
                       │ 生产: deploy@120.24.235.98 ｜ 彩排: deploy@127.0.0.1
                       ▼
┌─ 目标机（同一台机上的两个「环境」，路径完全相同）───────────┐
│  /data/websites/snailtrail.cc/quant/       ← deploy_root    │
│   ├── server -> releases/<id>          ← 原子切换（flip-server）
│   ├── web    -> releases/<id>/web      ← 原子切换（flip-web）
│   ├── releases/<id>/                   ← 不可变版本树（唯一写入物）
│   ├── shared/                          ← quant:quant 700（.env 600，deploy 不可读）
│   ├── var/                             ← deploy 状态（freeze 快照）
│   └── bin/run-current                  ← 钉版本入口（进程 cwd = releases/<id>）
└──────────────────────────────────────────────────────────┘
```

**三个「同」是本机制的地基**：staging 与 prod **同路径、同权限、同 sudoers**，且彩排走**真 ssh**（`deploy@127.0.0.1`，同一把密钥）。彩排不是模拟，是同一份 playbook 打到另一个「环境名」上——所以彩排能撞出的边界，上产一定也撞得出。

## 1. 设计目标与四条地基不变量

### 1.1 四个目标（批 3 立）

| # | 目标 | 反面（要避免的事故） |
|---|---|---|
| 1 | **声明式幂等交付** | 手敲 bash 部署链的 SEGV/引号/漏文件事故（旧 `scripts/` bash 链已于 2026-08-27 删除，git 史 `40fb5fa`） |
| 2 | **不可变工件 + 原子切换 + 自动回滚** | 就地改线上文件 → 无回滚点；`cp` 半途中断 → 半新半旧 |
| 3 | **权限独立**：deploy 用户 + sudo 原子白名单 + secrets 隔离 | root 直连 ssh、deploy 能 `systemctl restart` 任意单元、deploy 能读 `.env` |
| 4 | **彩排先行**：staging 零分叉 | 「彩排绿了上产挂」——若彩排与产上路径/权限不同就必然发生 |

### 1.2 四条地基不变量（改链前必先自检这四条）

**① 钉版本 = 进程 cwd（整个收敛断言体系的地基）**

`bin/run-current` 解析 `server` 链接后 `cd` 进 `releases/<id>` 再 `exec`：

```bash
CUR=$(readlink -f "$ROOT/server"); cd "$CUR"; exec "$ROOT/shared/venv/bin/python" "$@"
```

⇒ 每个 quant 进程的 `/proc/<pid>/cwd` 就是它实际在跑的 release。`quant-pinned` wrapper 读它，**postverify 版本收敛断言与 GC 的「被钉项跳过」共用这一条通道**（双盲审 P1 要求：两处若各走各的通道，会出现「收敛判过、GC 却把在跑的版本删了」的劈叉）。
⇒ 推论：进程存活期内钉住版本；**crash 后被 systemd 拉起 = 解析新链接 = 自动滚到新版**。

**② 版本树不可变**：`releases/<id>/` 一旦建就不改；所有变更产生新 id。回滚 = 换链接，不是改文件。
**推论**：`shared/`（`.env`/`venv`）是**管道外输入**——结构上不可指纹，改了它指纹照样一致。**改了 `shared/` 必须 `-e force_full=true` 重跑**（否则走快车道=不重启=旧进程读旧 venv）。

**③ 改 wrapper = 提权（故 wrapper deploy 不可写）**：所有特权操作（`systemctl`/`alembic`/`flip`/`pip`/`psql`）都收进 `/usr/local/sbin/quant-*`，属主 root 或 quant，`deploy` 无写权。父目录 `quant/` 是 `750` 且**组位无 w**——`deploy` 物理上无法自建/替换 `server` 链接，`flip-server` 是唯一修改通道。这是**权限独立的实现，不是约定**。

**④ 退出码语义**：rescue 路径一律以 `fail:` 收尾 ⇒ 中止/回滚 = **非零退出 + 告警**。CI 门不吃假绿。

### 3.3 sudo 白名单（唯一真源 = `templates/sudoers-quant-deploy.j2`）——共 12 只

**语法红线**（改前必读，写在模板头部）：
- sudoers **无 `|` 交替符** → 逐动词、逐行写 `Cmnd_Alias`
- **`*` 通配吃空格** → 凡带参命令一律 wrapper 化。`systemctl`/`journalctl` 族**绝不裸列白名单**：`systemctl restart quant-web sshd` 会整行匹配 `quant-*` = 任意 unit DoS 面
- 全部白名单命令 = **root/quant 属主、deploy 不可写**的脚本
- 每个 wrapper **严参校验**（无参校验的 wrapper = 允许任意提权）

| # | wrapper | 属主 | sudo 身份 | 严参 | 作用 |
|---|---|---|---|---|---|
| 1 | `quant-flip-server` | root | (root) | `release_id` 正则 + 目标须存在于 `releases/` | 原子切换 `server` 链接（`ln -sfn tmp` + `mv -T`） |
| 2 | `quant-flip-web` | root | (root) | 同上 **+ 目标须含 `web/` 子目录** + 拒实目录（引 bootstrap） | 原子切换 `web` 链接 |
| 3 | `quant-install-units` | root | (root) | `release_id` + 单元名 + **拒符号链接** + **realpath 须收敛在本次 release 内** + **逐单元须含 `User=quant`** | `cp` 单元 → `/etc/systemd/system` + `daemon-reload` |
| 4 | `quant-pinned` | root | (root) | **不收任何参数** | 读 `/proc/<pid>/cwd` → 输出「被钉 release_id 清单」 |
| 5 | `quant-journal` | root | (root) | `-u` 单元名锚定 `^quant-…\.service$`；只读 flags 白名单 `--since/--until/-n/-p/-q` | journalctl 只读诊断（读不到 auth/sshd） |
| 6 | `quant-emd-build` | root | (root) | `release_id` + cwd 锁定 | gcc-toolset-13 编 EMQ pybind11 `.so`（**须读 `shared/venv` 700 且写 staged，故 root**） |
| 7 | `quant-svc` | root | (root) | verb 白名单 `restart\|start\|stop\|status\|is-active\|daemon-reload\|disable\|enable\|unmask` + unit 正则 | `systemctl` 唯一通道；`restart/start` 前置 `reset-failed` |
| 8 | `quant-alembic-wrapper` | root | **(quant)** | `release_id` + `alembic.ini` 在位 | `cd releases/<id>` → `alembic upgrade head`（**读 `shared/.env` 靠 quant 身份**） |
| 9 | `quant-importsmoke-wrapper` | root | **(quant)** | `release_id` | `ast.parse` 全量 + 六入口导入冒烟 |
| 10 | `quant-pip-wrapper` | root | **(quant)** | `freeze` / `dry-run <id>` / `install <id>` | `pip install --require-hashes -r requirements.lock` |
| 11 | `quant-dbro` | **quant** | **(quant)** | `which ∈ live\|feishu\|hub`，恰一个参数 | 波次实例 **DB 真相源**（PG peer 免密，连接封装其内） |
| 12 | `quant-hbcheck` | **quant** | **(quant)** | 无参 | hub 心跳逐行验（TTL + 8 字段 + ts 判龄 ≤90s） |

**为什么 8-12 走 `(quant)` 而不是 `(root)`**：它们的共同需求是**读 `shared/.env`（属 quant 600）**与执行 `shared/venv`。让 deploy 持连串会破坏 secrets 隔离；**解法是把「连接」下沉到 wrapper 内部**，让 wrapper 本身以 quant 跑。`quant-dbro`/`quant-hbcheck` 因此连**文件属主**都是 `quant:quant`（全族唯一两只非 root 属主）。

`quant-svc` 的 `reset-failed` 前置是**真机踩出来的**（沙箱场景 3）：StartLimitBurst 耗尽后，`restart/start` 在 StartLimitIntervalSec 窗口内会被直接拒（`Start request repeated too quickly`）——回滚波次重启一个 crash-loop 单元时当场翻车。

### 3.4 信任链

```
bernard 私钥 ──ssh──▶ deploy（白名单受限） ──sudo/wrapper──▶ root 或 quant 身份
                                                              └─ 无裸 systemctl / 裸 alembic / 裸 psql
```

### 3.5 装位通道（**wrapper 与 sudoers 不进 release 管道**）

改了 wrapper 内容 = 改了提权面，**必须人工重装**才生效。三条路：

| 场景 | 命令 | 谁跑 |
|---|---|---|
| 新机首次 | `sudo bash deploy/scripts/bootstrap_server.sh`（读 `SRC=/home/michael/3b2`） | michael（服务器上） |
| 彩排环境 | `sudo bash deploy/scripts/bootstrap_staging.sh` | michael（本地） |
| 单件增量 | `sudo install -o root -g root -m 755 deploy/wrappers/quant-xxx /usr/local/sbin/` | michael |

`playbooks/bootstrap.yml` 是**声明式版本**（`ansible.posix.authorized_key` + `visudo -cf` 校验 + 目录权限矩阵），但**双闸默认关**：`bootstrap_dry_assert`（缺省 true，拒跑）+ `bootstrap_enabled`（缺省 false，任务体零动作）——误跑零副作用。

> ⚠ **已知不一致（2026-09-30 核准）**：`bootstrap.yml` 的 wrapper 安装清单是**批 63/web 工件化之前**的（8 只 + dbro/hbcheck），**缺 `quant-flip-web` 与 `quant-emd-build`**；而 `bootstrap_server.sh` 是完整的。⇒ 用 ansible bootstrap 装出的新机**会缺这两只**，阶段 6 才爆（`flip-web` 漏装 = server 已切后失败的无谓回滚——release.yml preflight 的 wrapper 在位检查正是为此存在）。**修法**：以 `bootstrap_server.sh` 为准补齐 `bootstrap.yml` 清单。

### 4.2 preflight 断言清单（`release.yml:25-224`）

| 断言 | 判据 | 为什么 |
|---|---|---|
| release_id 格式 | `^[0-9]{12}-[a-f0-9]{7,}$` | 与 wrapper 同款正则（防注入 + 可排序） |
| **交易窗口** | 非禁止启动时段，或 `-e force=true` | 见 §7.2 |
| 磁盘余量 | `≥ deploy_min_disk_mb`（500M） | venv/工件写不下会半途炸 |
| **前端构建** | `delegate_to: localhost` 跑 `npm run build`（`run_once`） | 前端是版本化工件的生产点 |
| rsync 在位 | `rsync --version` rc=0 | `synchronize` 前提（控制机+目标机都要） |
| 目录就位 | `releases/` + `var/` | — |
| 上一版指纹采集 | `readlink -f server` → 逐切片 md5（**先剥路径再哈希**） | 剥离路径否则 release_id 不同即误报变更 |
| **发布前被钉集合** | `quant-pinned`（失败→空串→**fail-closed**） | 快车道「零重启不变量」的断言基准 |
| DB 真相源接线 | `deploy_task_units_source=db` 时两条 cmd 非空 | v3.3 通道不得悬空 |
| **特权 wrapper 在位** | `quant-dbro/pinned/hbcheck/flip-web` 存在且可执行 | `flip-web` 漏装会在**阶段 6 server 已切后**才爆 |
| task 波清单 | `quant-dbro live`（`live_task.status='running'`，**不收 active 单元**——幽灵前科） | DB 才是真相源 |
| feishu 波清单 | `quant-dbro feishu`（`im_bot_config enabled AND provider='feishu'`） | 同上 |
| **hub 期望集** | `quant-dbro hub` → `id\|provider` → **provider 白名单过滤** → `quant-md-hub@<id>.service` | 批 66b：unit 换名窗 systemd 旧名单失效 |
| **hub 期望集非空** | `length > 0`（除非 `server_changed=false` / 显式 `-e deploy_hub_allow_empty=true`） | 空集 = DB 采集断链，发布须带期望集 |

**release_id 为什么 `set_fact` 物化**：`vars:` 段的 `lookup` 是**惰性求值**——play 跨分钟时 `date` 每次引用重算，会导致 staged 目录（16:08）与 wrapper 参数（16:09）错位 → 阶段 5「requirements 不存在」。2026-08-26 五跑实锤后改为首任务一次性物化。

### 4.3 批 8 变更感知快车道

**判据**：`server_changed = (无上一版) or force_full or req_changed or 任一切片指纹不同`。切片集 = `deploy_slices` = `src / migrations / scripts/systemd / requirements.txt / requirements.lock / alembic.ini`。

`server_changed=false`（纯 web 发布）⇒ **跳阶段 3 / 5 / 7**（导入冒烟 / pip+alembic / 波次重启），只走同步 + 双链 flip + postverify。

- **收敛断言换形态**：全量路径要求「被钉集 **恰为** {本次}」；快车道要求「被钉集 **⊆** 发布前钉集 ∪ {本次}」（零重启不变量 —— 进程钉旧目录跑**同内容**是期望态）
- 实测：prod 90s / staging 49s 全弧（原 8-10min / 3-4min）
- **逃生门**：`-e force_full=true`（改了 `shared/.env`/`venv` 必用）、`-e deploy_dwell_seconds=N`（压缩稳定窗）

**为什么带 `scripts/systemd` 单独成切片**：单元文件变更判据（决定是否走 `install-units` 通道）。**注意 `scripts/` 非 systemd 子树故意不入指纹**——那是按需脚本（backup/init 等），新起进程经 `run-current` 自然取新树。

### 4.4 回滚：三条路径与一个结构性缺口

| 路径 | 触发 | 行为 |
|---|---|---|
| **rescue(2-5)** | 未切换阶段失败 | 清 staged（`allow_contract=true` 时**保留**供人工处置）+ `fail:` |
| **rescue(6-8)** | 已切换阶段失败 | 翻链回 `prev_release_id` + 重启 `waves_touched` 波 + 收敛复验 + freeze diff + `fail:` |
| **`rollback.yml`** | 手动独立跑 | `-e confirm=true` 必需；缺省目标 = 字典序紧邻当前之前、**带 `.deployed`** 的版本；**不吃交易窗硬闸**（紧急回滚恰在盘中） |

**⚠ 结构性缺口（这是「批 84 回滚诚实性」的立法对象）**：`rollback-tasks.yml` 只翻**代码链**，**不含任何 alembic downgrade**。所以「回滚成功」的真实语义是「代码回旧版，**schema 留在新版**」。这套逻辑成立的前提是 **expand-only**——即新代码只加表/加列，旧代码在新 schema 上照样跑。

而这个前提**只有 DDL 门在守**（阶段 4 扫新增迁移的 `upgrade` 段，命中 `DROP TABLE/COLUMN`、`ALTER COLUMN ... TYPE`、`op.drop_*`、`alter_column...type_` 即 fail）。`-e allow_contract=true` 是唯一的放行通道，它置 `auto_rollback_disabled=true`：

- **rescue(2-5) 消费它** → allow_contract 时保留 staged，不清理；
- **rescue(6-8) 不消费它** → 仍然照常自动回滚。

⇒ 用 `allow_contract` 跑**破坏性**迁移时，若阶段 6-8 失败，会**自动翻代码到旧版、而 schema 已前进**——旧代码 + 新 schema 的组合**没有任何复验保护**。这就是「撕裂态」。**详见 `flow/任务/批84-回滚诚实性与schema一致性.md`。**

**已知的不可回滚边界（先例，2026-09-24 事故规约）**：`RENAME` 类破坏性迁移失败 = 代码/schema 分裂，**不能停在回滚混合态**——须立即手动 `quant-flip-server <新release>` + 全量重启恢复一致。且 **DDL 门正则不拦 RENAME（盲区）**，需显式 `allow_contract`。**IM 回滚另有专属形态闸**（`rollback-tasks.yml:84-121`：目标含 concrete unit = 66a 形态 → 先停新数字 unit 再复活旧 `@quant`；反序会造成双写裸流窗 → 打崩实盘任务）。

### 4.5 GC（`release.yml:621-671`，仅成功路径）

1. **孤儿 staged**：`releases/*` 中**无 `.deployed`** 的 = 从未切换成功的中断残留 → 删
2. **旧版保留**：已部署版按 release_id **字典序**保留 `deploy_keep_releases=5`，删最旧的超额部分
3. **跳过三类**：`server` 指向项、`web` 指向项的**目录本体**（`dirname(readlink)`）、**被钉项**（`quant-pinned`）
4. **fail-safe**：`quant-pinned` 通道故障（非零）→ **本轮 GC 整体跳过并告警**——绝不因探测失败把在跑的版本当孤儿删

## 5. 核心脚本说明

### 5.1 `run-current`（版本化入口，装到 `<root>/bin/`）

`root:root 755`，**固定路径、不经 `server` 链接自举**（避免「切链接导致下次 run-current 自身变化」的耦合）。单元文件里 `WorkingDirectory` 指 `shared/`，`ExecStart` 调 `bin/run-current`——**禁穿 `server` 链接**。所有 systemd 单元的 `User=quant`（由 `quant-install-units` 强制校验）。

### 5.2 `wave.yml`（波次 + dwell，release 与 rollback 共用）

**波次顺序（批 56b 翻转，不可随意改）**：`web → celery → feishu → task → hub`。
理由：**新 worker 必须先起、兼容旧 hub 的 `+08:00` 流**（`_epoch_key` 跨表示同键）。反序（新 hub + 旧 worker）⇒ ISO 字典序去重恒真 ⇒ **当日 bar 全丢锁死**。

**两层失败语义（设计稿注记③，修死）**：

| 层 | 失败 | 语义 |
|---|---|---|
| **命令层**（`quant-svc restart`） | `failed_when: false` **吞没**，登记 `wave_failed` 续行 | 续行只为「后续波跑完 = 回滚时受影响面全量」+ 信息收集；**终判在阶段 8** |
| **验证层**（dwell 稳定窗 / healthz） | **不吞没** | 直接穿透外层 block → rescue → 自动回滚 |

**dwell 稳定窗**（`deploy_dwell_seconds=30`，poll 2s，max_wait 120s）：要求单元**连续** `is-active` ≥30s；一旦进 `failed` = **StartLimit 判死，即刻中止**（不等满窗）。

**波次清单必须覆盖动态实例**（2026-09-24 事故规约）：hub 曾被硬编码 `[quant-md-hub@quant]`，漏掉 per-account 加密 hub → 版本收敛断言失败回滚。**新增任何 per-account / per-task 模板单元必须同步进波次采集**。

### 5.3 其余 wrapper 的关键实现点

- **`quant-dbro`**：唯一走**沙箱分支前置**的 wrapper（`QUANT_DBRO_SQL_DIR` 判定在选表探测**之前**，保证沙箱路径永不触库）。生产走 `psql -U quant -d quant -v ON_ERROR_STOP=1 -tAc`（**PG peer 免密，unix socket，无连串无密码**）。固定 SQL 内封，不收外部 SQL。
- **`quant-hbcheck`**：批 66b v2 **DB 驱动期望集 + 两代自适应**——per-account 键 `quant:hb:md-hub:<id>` 全缺且裸键在场 → 回落 legacy 单键并**显式输出「legacy 模式」**（解 wrapper 装位件不随 release 版本化的时序悖论）。判龄靠 **hash 内 `ts` ≤90s**，不只看 TTL（防旧心跳 90s 残留 TTL 假过）。
- **`quant-pinned`**：`systemctl list-units 'quant-*'` → `show -p MainPID` → `readlink /proc/<pid>/cwd` → 过滤 `*/releases/*` → `sort -u`。**无权读/无进程 = 跳过，不算失败**（探测语义）。
- **`quant-install-units`**：三重防夹带 —— ①单元名正则；②**拒符号链接** + `realpath` 必须收敛在本次 release 目录内（防 staged 树内藏链接把 `/etc` 敏感文件以 root 属主复制进单元目录）；③生产通道逐单元须含 `^User=quant`（**防发布源删 User 行使服务以 root 跑**）。
- **`quant-pip-wrapper`**：装 `requirements.lock` 而非 `requirements.txt`，**`--require-hashes`**（防 vnpy/PySide6 类依赖漂移）。`req_changed` 指纹判 **lock**。

### 5.4 TRANSITION-0115 双态 wrapper（过渡期哨兵）

`quant-dbro` 与 `quant-hbcheck` 内的 `select_trading_table()`：用 `to_regclass('external_interface')` / `to_regclass('trading_account')` 探两态 —— `10`→旧表（**保留 `'trading' = ANY(capabilities)` 域谓词**）、`01`→新表（无谓词）、`11`（并存）/`00`（皆缺）→ **rc=1 响亮拒绝**（不猜、不静默选一侧）。所选表打 stderr（`选表=…` 日志底）。

**为什么必须双态**（2026-09-30 prod 实查后定论）：`quant-dbro` 在 **preflight**（alembic **之前**）跑，`quant-hbcheck` 在**阶段 8**（alembic **之后**）跑。prod 现 DB=0115、新表在 0116 才建 ⇒ **单态 wrapper 无装位时序可解**：先装查新表 → preflight 撞未建的表拦停；不装 → postverify 撞已删的旧表失败**且回滚不动 schema**（撕裂态）。

**收口纪律**（写在两个 wrapper 文件头）：`TRANSITION-0115:收口=0116 全环境上产后` —— 重装位 + 删除 `select_trading_table()` + 标 `# TRANSITION-0115` 的旧态 SQL 行 + 文件头注记，回到单态 `trading_account`。**闸门**见 §6.1。

## 6. 闸门：谁在守着这套机制

### 6.1 `server/tests/test_deploy_blast_radius.py`（拆表/改表影响面）

**教训（2026-09-30 staging 彩排阻断实证）**：批 83a 拆表审核只扫了 `server/src` + `web/src`，**漏了 `deploy/wrappers/`** —— 两个 hub 期望集 wrapper 的 SQL 仍查旧表，彩排阶段 1 当场 `relation "external_interface" does not exist` 拦停。

⇒ **规矩**：任何「表拆分/改名/删除」的读点清单**必须显式包含部署链**：
`deploy/wrappers/`（服务器侧特权脚本，`/usr/local/sbin`，bootstrap 一次性装位）+ `server/scripts/`（随 rsync 上服务器的运维脚本）+ `deploy/playbooks|templates|inventory`。理由：这些位置 **pytest / src 扫描 / 前端构建全都看不见**。**读点定位按符号名（表名）grep，别按行号**（行号必漂）。

**闸门内容**：① wrapper SQL 表名必须命中 `schema_expectations.txt`；② `deploy/**` + `server/scripts/**` 的 SQL 行**不得再现退役 artifact**（除非在 `TRANSITION-0115` 哨兵块内）；③ 哨兵纪律（文件头须声明收口条件、BEGIN/END 成对、stale 声明报红）；④ 真源非空。

### 6.2 `server/tests/test_deploy_sync_ssh_hardening.py`（同步腿加固）

**教训（2026-09-30）**：`ansible.posix.synchronize` 的 rsync 腿**自起一个 ssh 进程，与 ansible 连接腿不共享配置** —— `use_ssh_args` 默认 `false`（配置静默丢失）、`verify_host` 默认 `false`（硬加 `StrictHostKeyChecking=no` + `UserKnownHostsFile=/dev/null`，**TOFU 完全绕过**，与连接腿的 `accept-new` 分叉）。而这条腿传的正是**即将上线的代码工件**。此前 `deploy/tests/` **一条 synchronize 断言都没有**，缺口才活到那天。

**闸门内容**：① 每个 `synchronize` 任务须显式 `use_ssh_args: true` 且 `verify_host: true`（递归扫 `block/rescue/always`，覆盖 `playbooks/` 全目录）；② 真源非空 + 反向禁 `:false`。

### 6.3 `deploy/tests/run_scenarios.sh`（六场景注入）

沙箱内用假单元（`quant-sbx-*`，`RestartSec=1` / `StartLimitBurst=2` 压缩时间尺度）真打真 `systemctl --user`，断言 `ansible-playbook` **退出码**：

| 场景 | 注入 | 期望 |
|---|---|---|
| 1 坏 requirements | 坏包名 | 非零（`pip dry-run` 拦截） |
| 2 坏迁移 | 破坏性 DDL | 非零（**DDL 门**拦截，alembic 不触库） |
| 3 crash-loop | 假单元必崩 | 非零 + 回滚恢复（dwell 判死） |
| 5 中断残留 | 孤儿 staged | 零（顺带 GC） |
| 6 单元变更 | 改单元文件 | 零 + 新单元落位 |
| 附加 A0/W/D/P | 交易窗闸 / install-units 负例 / dbro 负例 / pinned 假 proc 树 | wrapper 级直断 |

`flock` 互斥（沙箱树与 `systemd --user` 单元是共享可变状态）。

## 7. 操作规约

### 7.1 三命令（**一律在 `deploy/` 目录下跑**，否则 `ansible.cfg` 不生效）

```bash
# ① 彩排（强制先行——staging 不绿不上产）
.venv/bin/ansible-playbook -i inventory/quant-staging.yml playbooks/release.yml

# ② 上产
.venv/bin/ansible-playbook -i inventory/quant-prod.yml playbooks/release.yml

# ③ 手动回滚
.venv/bin/ansible-playbook -i inventory/quant-prod.yml playbooks/rollback.yml -e confirm=true
```

**`ansible.cfg` 的缺省 inventory 是沙箱** —— 这是安全缺省：忘写 `-i` 也打不到生产。生产**必须显式** `-i inventory/quant-prod.yml`。

**成功后核对三证**：

```bash
.venv/bin/ansible quant-prod -i inventory/quant-prod.yml -m shell -o -a \
  'readlink -f /data/websites/snailtrail.cc/quant/server; sudo -n -u quant /usr/local/sbin/quant-hbcheck; sudo -n /usr/local/sbin/quant-pinned'
# 预期：server → releases/<新 id>；hub 心跳全过；pinned = {新 id}（九单元收敛）
```

### 7.2 部署窗（2026-09-01 用户裁定）

`deploy_trading_windows` 记的是**禁止启动**的时段（命中 → 拒绝），仅周一~周五生效：
- `08:55 – 11:35`（开盘段）
- `12:40 – 15:05`（午盘段）

⇒ **允许启动**的时刻 = **08:55 前** / **11:35 – 12:39** / **15:05 后**。闸拦的是**启动时刻**（启动 ≠ 完成，边界已让出全弧时长）。逃生门 `-e force=true`（会打印「自担风险，操作者留痕」）。staging 是 `enforce: false`（随时可彩排，不碰生产）。

### 7.3 操作纪律（踩坑成规）

- **部署命令一律落文件**：`> /tmp/rel.log 2>&1`；输出为空**先验状态**（readlink 三证）再决定重跑
- **两环境连跑要拆开**（10min 硬杀会绕过 rescue）
- **系统 `python3.14` 不可用**：vnpy 4.4.0 硬 pin `pyside6==6.8.2.1`（`requires_python <3.14`）⇒ 控制机 ansible venv 用 python3.10

### 7.4 staging 与 prod 的差异（**三处有意 + 一处已对齐**，其余零分叉）

`inventory/group_vars/quant-staging.yml` 自述的设计意图是「镜像 prod 全集」，下列是唯一的例外：

1. 交易窗**不强制**（随时彩排）
2. 波次**缩减**：无 `task` 波道具、feishu 波在 staging 的 `quant-staging.yml` 已并入；沙箱另有 `deploy_waves` 全套假单元
3. XTP `md_host` 指向 `127.0.0.1`（连不上即刻拒绝，防黑洞挂起 > Watchdog）
4. `deploy_task_units_source: db` **已对齐 prod**（批 4b）——彩排即验证 DB 真相源通道，消盲区

### 7.5 控制机沙箱（本开发容器）的两条绕行

生产控制机 `/etc/ssh` 正常，**不需要**下面两条；这是**本沙箱容器**特有的元数据污染（`/etc` 是只读子卷、`/etc/ssh/*` 属主被映射成 `nobody`）：

```bash
# 连接腿：-F 只读用户配置，跳过系统 include
ANSIBLE_SSH_ARGS="-F /home/bernard/.ssh/config -o UserKnownHostsFile=/home/bernard/.ssh/known_hosts"
# 注意：rsync 腿能吃到这里注入的参数，靠的是 release.yml 已置 use_ssh_args: true
```

**根因与边界**：`/etc` 是 btrfs **只读子卷** → 修系统文件这条路**不存在**（chown 无门）。这不是设计边界，是容器元数据。
