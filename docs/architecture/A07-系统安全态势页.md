> 依据。写给「三个月后的你」和 AI——读完能维护、能正确扩展，不必逆向工程。

## 一、这个页面回答什么问题

三个，按用户看它的顺序：

1. **现在有没有事？**（状态卡：漏洞数/采集健康度/数据新鲜度）
2. **有什么事、多久了？**（漏洞表：每个洞首次发现日期——停留越久越扎眼）
3. **有没有新的变化？**（基线时间线：新端口/新包/配置翻转，只报变化不报静止）

AI 摘要（B 区）是把这三问的答案用人话再说一遍——**摘要员不是判定员**：
告警与否永远是确定性规则的输出，LLM 挂了只影响摘要区为空。

## 二、数据从哪来（六个采集面 + 各自的取舍）

| 面 | 怎么采 | 为什么这样采（取舍依据） |
|---|---|---|
| **应用组件** | `pip freeze` 全量（179 包） | 全量零成本（本地 venv 秒级）——不选白名单：新增包自动纳入，无需维护 |
| **漏洞比对** | `syft 扫 site-packages+rpmdb → grype sbom:` 单源（批 123） | **演进三段**（如实记）：批 120 pip-audit（OSV 单源，无 severity 输出——CVE 体系标准字段缺失）；批 123 初议三插件并列→返工分层→**终裁单源**（用户：「就用 grype，故障点太多」——回退/校正/优先级编排=故障面乘法，准入判据立：多源编排需证明单源不可忍受才立项）。现语义：①扫 site-packages dist-info（已装真身——release 树只含声明，扫它=SBOM 失真）；②severity 原生 CVSS 词表（单词表零归一层）；③alias 归一 vuln_id 优先 CVE 号（跨日键稳定）；④rc=1=有洞红线平移（曾因语义反致「有洞日永远查不出」P0）；⑤未装机/失联 ⇒ degraded 诚实显示，零回退。**alinux3 backport 已知噪点**：grype 按 CVE 原始版本比对，al8 回植补丁的 rpm 包可能误报——人工判读兜底，误报率观察期实测，不可忍再评估 errata 校正源（单独立项） |
| **系统组件版本** | 点名 8 只（nginx/openssl-rpm/pg/redis/python/pango/cairo/wqy 字体） | 只点名「quant 直接依赖且需人眼识别版本」的；其余系统包不需要版本展示——它们的**漏洞面**由下一行全覆盖 |
| **系统漏洞面** | 读部署管道落的 `shared/security/dnf-security.json` | **共享数据模式**：root 权限的 `dnf check-update --security` 在每次 release 时由 wrapper 执行落文件，采集器只读。不在采集时现查的原因：①需 root（采集器是 quant 身份）；②全库扫有成本。**可靠性保证**：wrapper 三态落文件（ok/ok-none/degraded），文件缺失=分区显式 degraded，绝不静默当 0 |
| **sshd 配置** | 直读 /etc/ssh/sshd_config；600 权限后降级读部署落的快照文件 | 同上共享模式——快照随每次 release 刷新 |
| **暴露面/安全头** | `ss -tln` 本机 + urllib 探本机 443 四安全头 | 本机自查零成本 |

**采集的身份与特权边界**：全程 quant 身份零 sudo——需要 root 的两件事（dnf/sshd）
都转为「root 在部署时落文件、quant 读文件」。这是本页最重要的架构决定：
**不为了安全页给运行时开任何新特权**。

## 三、何时扫、扫多全（窗口 vs 成本的实际账）

| 时机 | 触发 | 理由 |
|---|---|---|
| 每日 06:00 | beat 常规 | CVE 数据源（OSV/dnf repo）本身日级更新，更频繁的扫描是在重复读不变的数据 |
| **依赖变更即时** | release 收尾：req_changed 指纹变化 ⇒ 补一轮 | 新依赖上线=漏洞面变化时刻（盲窗从最长 24h 收敛到部署即时）。无变更日零成本——只在真需要时花 50s |

一轮全扫成本（批 123 后）：syft SBOM ~30s + grype 匹配 ~60s + 本机采集 ~5s；
**首日另加 DB 全量下载 106s**（v5 无增量机制=每日全量 296MB，anchore 源实测
2.8MB/s——任务 600s timeout 内预算：106+60+50 余量足）。一天 1-2 次。
**刻意不做**的：增量 CVE 缓存（复杂度>收益）；rpm 全量版本**展示**（漏洞面
grype+dnf 已覆盖；台账已入库版本史——展示仍只点名）；多源 CVE 编排（见 §二）。

## 四、落库与去重（避免重复判断的机制）

```
security_snapshot   一天一行（scan_date unique，同日复跑覆盖）
                    六分区 jsonb + status(ok/degraded) + ai_summary
security_finding    一洞一行（唯一键 source+pkg+vuln_id；批 123 +severity）
                    first_seen 首见告警一次 / last_seen 停更=已修复沉底
security_component  一组件一行（唯一键 source+name——批 123 台账）
                    version + first_seen + last_changed + last_seen
```

- **快照**管「当天的样子」：全量 jsonb，历史 30 天，基线 diff 拿它逐日比。
- **finding** 管「洞的档案」：grype 每天报出的洞按唯一键 upsert——同一个洞
  第二天再报只是刷新 last_seen，**不重复告警**；升级后不再报，last_seen 停更
  前端灰显沉底（存量 pip-audit/dnf 行同语义自然退役）。severity 词表=
  Critical/High/Medium/Low/Negligible/Unknown（CVSS 基准，NULL=未评级诚实显示）。
- **台账**管「版本变更史」（批 123——动态数据入库原则）：UPSERT 三态——
  新组件三日同值入库/版本未变只推 last_seen/变了同步 version+last_changed。
  治「距上次变更只能 30 天窗口反查」的打补丁思维；**暴露时长**=台账
  last_changed→当日（漏洞真实存在了多久——发现可晚于暴露，两数并列展示）。
  归源：pip（site-packages）/rpm（含 python3-* 系统 rpm，与 pip 域各自台账
  不双删）/system（8 个点名组件——不依赖 grype，未装机期照常滚动）。
  三表分工=展示态/档案态/变更史分离，互不膨胀。
- **降级红线**：任何分区采集失败 ⇒ 该分区 status=degraded 显式落库+前端黄点。
  空表=假绿是本页立法红线（曾因「无 JSON 主体被当空结果」出过 P0）。

## 五、告警哲学（只报变化，不报静止）

飞书告警只在这三件事发生时响：**新监听端口 / lock 外新增包 / 安全配置翻转**。
昨天的绿今天还是绿——不响。新洞 first_seen 响一次。理由：安全页的敌人是
狼来了效应——告警轰炸一周后没人再看。判据全部是确定性集合比较（纯函数
`_baseline_diff`），AI 不参与判定。

## 六、展示设计（五区与两表）

| 区 | 内容 | 设计依据 |
|---|---|---|
| A 状态卡 | 漏洞总数/状态/新鲜度(>26h 黄)/基线偏差 | 业界惯例（Trivy/GH Security 概览形态）：第一眼回答「有没有事」 |
| B AI 摘要 | 当日人话总结（纯文本转义渲染） | 纯文本=零 XSS 面（CVE 描述含注入可能，LLM 输出走 `{{ }}` 转义） |
| C 漏洞表 | **严重度降序**（Critical→Unknown；同级按暴露时长）；暴露时长列（发现 N 天副信息）；修复沉底灰显 | 批 123 前只有停留天数（pip-audit 无 severity——自建映射=第二真源不敢造）；grype 原生 severity 后**排序回归业界标准**（severity 是 CVE 体系行动语义），暴露时长（台账口径）次之、发现时长再次——三个时间维度按可行动性排序 |
| D 组件表 | 系统组件 8 行 + pip 关注包 10 行（行序=攻击面优先：公网认证/传输→数据→框架→策略运行时）；**上次变更日期**列（台账直读）；openssl 备注 al8 backport 语义 | 批 122 曾做「层级」tag 列——批 123 审判冗余（行序已表达优先级且覆盖不全）删除；「距上次变更天数」改直读日期（可关联"那天我升过什么"——天数做不到）。全部 179 包不展示——看清单去 lock 文件 |
| E 基线时间线 | 近 30 天逐日变更计数+当日明细 | 历史日只存计数不存明细（存储>回看价值，30 天前的「新增 3 包」没人看） |

样式全走本仓惯例：TableShell/var(--sp-*)/i18n 中英双语/令牌门。

### 「捆绑二进制库」这一类（批 124 记）

**现象**：findings 里大半是 ffmpeg（45 条中 40+）——但系统从未装过 ffmpeg。

**真相**：来自 PySide6 6.8.2.1（vnpy 硬 pin 的 Qt 绑定）**捆绑的 Qt Multimedia 库**
（`site-packages/PySide6/Qt/lib/libavcodec.so.61.19.100` = FFmpeg 7.1 全套）。
syft 识别为 `type=binary`。

**处置特点**（与系统包/pip 包都不同）：

| 维度 | 说明 |
|---|---|
| CVE 真实性 | 真实（库确实是 FFmpeg 7.1） |
| **升级路径** | **无独立路径**——只能等 PySide6/Qt 升版；`dnf update ffmpeg` 与它无关 |
| fix_version | 多为空或 7.1.2（Qt 上游未跟进） |
| 我们的选择 | 照常展示（不隐藏——隐藏=知情权损失）；**D 区「来源」列自动标注"PySide6 捆绑"**（origin 从 SBOM locations 首段推导，非人工备注）；不入 pip 台账语义域（source='binary'）⇒ 暴露时长走 ≈ 估计 |

**为什么记**：这是"组件来源自解释"需求（2026-10-15 用户）的原始触发点——
答案本该在表里，不该要用户问 AI。origin 推导规则在
`security_collector._component_origin`（单一真源）。

## 七、可靠性三支柱（怎么保证不出假数据）

1. **真源对齐**：grype 扫 site-packages（已装真身）+ rpmdb；dnf/sshd 读部署落
   文件（与机上状态同源同刻）；台账=版本变更史一等表（非快照反查）。
2. **降级显式**：单分区失败标 degraded 不静默；快照照落、告警照走、前端黄点。
3. **测试钉**：rc=1 语义/prev degraded 守卫/探针 Host 头/快照三态——历史出过
   的每个错都有反向用例钉死（全套 2668 例含安全页 60+）。
