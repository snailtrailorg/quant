# D25 · 三层能力模型（能力 → 能力集 → 接口）

> 状态：**设计定稿**（2026-09-25 三裁定收口：能力集 5 类 / 页签合并 / snapshot 归位；待双盲审后实施）

## 一、背景

用户在审视外部接口配置组织（数据源 vs 交易账户两页签）时，引出能力分层问题：

- **能力集**（粗粒度，用户配置视角）：历史数据、实时行情、交易
- **能力**（细粒度，后端处理视角）：A股列表、基本面、日线、tick、持仓、可用资金…

核心问题：这两张清单是什么关系？是「能力-能力集-接口」三层，还是「能力-接口」两层？

## 二、现状盘点（三路代码探索 + A03 理想态对照）

**已落地的能力相关构件**：

| 构件 | 位置 | 语义 | 数量 |
|---|---|---|---|
| **DataKind**（能力真源） | `quant_common/contract.py` | 细粒度能力枚举 | **26 词**（行情7+参考10+事件2+交易4+占位3） |
| Temporality（时态） | `contract.py` | historical/snapshot/streaming | 3 |
| **sync_id**（实现标识） | `migrations/0094` sync_kind_config | 数据同步具体项→kind+pg_table | **20 个** |
| **CAPABILITIES**（配置层能力集） | `quant_common/markets.py` | 粗粒度能力集 | **5 个**（daily/minute/snapshot/quote/trading） |
| SYNC_ID_CAP_MAP（映射） | `markets.py` | sync_id→能力集 | **5 个**（只映射 5 个 sync_id） |
| A03 DataKind（理想态） | `docs/architecture/A03` §十一 | 理想态能力清单 | 30 个（比 contract.py 多 4 个占位细化） |

**核心发现（三路探索实证）**：

1. **36 项数据能力，能力层只登记 5 项，31 项漏网**：
   - sync_id 20 个里 15 个没进 SYNC_ID_CAP_MAP（index_daily、astock_basic、astock_list、stk_limit、moneyflow、top_list、concept、trade_cal…）
   - pool_data 二档 10 项（income/balancesheet/cashflow/fina_indicator/cyq_chips/top10_holders/dividend/pledge_stat/share_float/stk_holdernumber）完全无限速、无能力登记
   - 独立 task 2 项（static_list_sync、convertible_terms_sync）
   - 实时/按需 4 项（quote 快照、intraday 分时、on-demand 财务/筹码、analyze 缓存）
2. **CAPABILITIES 是混合维度**：`daily/minute`（粒度）+ `snapshot/quote`（时态）+ `trading`（交易）——三个正交维度挤在一个 5 元组里，语义不清。
3. **snapshot 错位**：`snapshot` 枚举只配给 tencent（行情盘口快照），而 MD 网关的 5 档盘口 tick 被标成 `quote`；账户/持仓的 DB 快照是「交易面」而非「行情 snapshot」。
4. **交易/行情操作项全被两个枚举收口**：place_order/cancel/query_position/query_account/query_orders/query_trades/get_vt_orderid/set_leverage/对账/风控/任务生命周期 全归 `trading`；connect/subscribe/tick/盘口 全归 `quote`——无细粒度。

## 三、三层模型定义

答案是「能力 — 能力集 — 接口」三层，且**「能力」层已经落地（DataKind），「能力集」层现状是错的（独立建模 + 混合维度）**。

```
接口（external_interface 行）      标注能力集（用户配置时选）
   ↑ 标注
能力集（归类视图）                  从 DataKind 派生的「大类」，不是独立建模
   ↑ 派生
能力（DataKind 26 词）             代码真源，adapter 声明 implements
   ↓ 映射
sync_id（实现层，仅数据同步）      具体同步项 → kind + pg_table（0094 归置表已落地）
```

**关键澄清——三层里只有「能力」是真源**：
- 能力（DataKind）= 代码真源，adapter 声明「我实现 bar_daily / account_query / trade_exec」。
- 能力集 = 能力的**派生归类视图**（供用户配置理解），不独立建模——加能力只加条目，归类自动跟着变。
- sync_id = 数据同步的**实现层**（不是独立的能力维度，是「能力→具体同步任务→落表」的中间标识），只在数据侧存在；交易/行情侧没有 sync_id，直接是 DataKind（account_query/trade_exec/stream_tick/depth）。

## 四、设计决策

1. **能力真源 = DataKind**（contract.py 26 词，已落地）。三路探索发现的 36 项数据能力，应全部归入 DataKind 或其子类（sub_kind），不新建独立词表。
2. **能力集 = 5 类（用户裁定 2026-09-25 + 文案师审校定稿）**：**历史行情 / 实时行情 / 交易 / 参考数据 / 标的事件**——从 DataKind 派生归类，替代现状混合维度的 CAPABILITIES 5 元组。
   - 命名依据（文案师审校）：原「行情」与现行 `cap_quote: '行情'` 标签**撞车**、原「事件」与「事件时间线/健康事件流」**撞义**，均已消歧；「公司事件」改「**标的事件**」（用户质询 OKX 适用性引出——加密无「公司」，下架/换币/硬分叉装不进；「标的」是平台核心词，跨市场通吃）。
   - 「参考数据」确认容纳（用户裁定 2026-09-25）：主力资金/财务数据/年报季报全归此类——**细分无节制，太纠结就落能力层**：能力集是配置标签（用户选数据源时看一眼就懂），不是数据治理分类；标的静态/公司基本面/市场统计三种子性质的细分留给 DataKind 层。tooltip 配白话「股票列表、交易日历、财务指标、资金流向、龙虎榜等辅助分析数据」。
   - DataKind 26 词归类：**历史行情**（bar_daily/bar_minute/index_daily/adj_factor，4）｜**实时行情**（snapshot/stream_bar/stream_tick/depth，4）｜**交易**（account_query/order_stream/trade_exec/settlement，4）｜**参考数据**（static_list/trade_cal/index_constituents/industry_class/fundamental_daily/financial_stmt/featured_daily/stk_limit/funding_rate，9）｜**标的事件**（suspend/corporate_action，2）｜占位（open_interest/liquidation/fx_rate，3）。
   - 分类本质（三正交维度）：价格 vs 非价格、批量 vs 实时、数据 vs 操作。
3. **配置页签（UX）独立于能力集**：页签按用户视角组织（数据源 / 行情 / 交易，或单列表+能力筛选），是纯前端视图，不改数据模型——上一轮讨论的「合起来单列表」落在这一层。
4. **补全 SYNC_ID_CAP_MAP**：5 → 20 个 sync_id 全映射；pool_data/独立 task/实时按需的 31 项漏网能力补登记。
5. **snapshot/quote 语义归位**：`snapshot` = 拉取式快照（tencent 快照 + account_query 账户快照）；`stream_tick/depth` = 流式行情（MD 网关盘口），不再挤在 quote。

## 五、裁定记录（全部已定，2026-09-25）

1. ✅ **能力集粒度**：5 类 = 历史行情 / 实时行情 / 交易 / 参考数据 / 标的事件（命名经文案师审校定稿，见 §四.2）。
2. ✅ **配置页签组织（用户裁定：合并）**：**单列表 + 能力标注 + 可选能力筛选**——多能力接口（XTP/币安）只出现一次，消除「两页签配同一账号」的混淆；能力集从「强制页签」降级为「筛选」。前端改造：`InterfacesCard` 两页签视图 → 统一列表（能力列展示 5 类标签 + 筛选器）。
3. ✅ **snapshot 归位（用户裁定：方案 A）**：账户/持仓/委托查询归 `account_query`（**交易**类）——品类看业务不看获取方式：`DataKind(snapshot)×Temporality(snapshot)`（拉行情价）与 `DataKind(account_query)×Temporality(snapshot)`（查账户）以组合区分，`snapshot` 词只在「实时行情」类出现，五个能力集边界干净。

**收口状态：三裁定全落定，设计定稿，下一步=方案双盲审（八步法步 2）。**

## 七、能力层扩充（DataKind + sub_kind 双层）

**原则（用户裁定 2026-09-25）：能力集保持 5 类不动，细分全部落能力层——「细分无节制，太纠结就落能力层」。**

DataKind 层的正确形态 = **粗词 + sub_kind** 双层（0094 `sync_kind_config` 已有 kind+sub_kind 结构，天然承接）：

| DataKind（粗词） | sub_kind（细项，补全后） |
|---|---|
| financial_stmt | income / balancesheet / cashflow / fina_indicator / forecast |
| featured_daily | moneyflow / margin_detail / top_list / block_trade / cyq_perf / cyq_chips |
| static_list | stock / etf / convertible / namechange / concept |
| bar_minute | 1min / 5min / 15min / 30min / 60min（freq 维度） |

**需新立的 DataKind 词**：
- **`holder_structure`（股权结构族）**：top10_holders（十大股东）/ pledge_stat（质押）/ share_float（解禁）/ stk_holdernumber（股东户数）/ dividend（分红历史）——既不是财务报表也不是事件，是「公司股权维度」。
- **非结构化占位**：`announcement`（公告原文）/ `news`（新闻）——见 §八。
- **report_rc（分析师预期）**：可归 fundamental_daily 的 sub_kind（analyst_expect）——评级/目标价/EPS 预测，当前积分可拿（实测）。

## 八、非结构化数据（获得与存储）

**tushare 能力实测（2026-09-25，200 积分，实证）**：
- `news`（新闻快讯）：❌ 无权限（积分档不够）；
- `anns_d`（公告）：❌ 无权限；且接口设计是元数据（标题+URL），PDF 全文本就没有；
- `report_rc`（研报）：✅ 可用——**结构化摘要**（标题/机构/评级/目标价/EPS·PE·ROE 预测），非全文。可做「分析师一致预期因子」，起步即可用。

**获得渠道（修正后）**：非结构化**原文以自建抓取为主**——公告原文走巨潮资讯（官方 PDF 源）或东财 + PDF 文本提取；新闻快讯走东财/新浪直接抓（或 tushare 升积分，仅短文本）；研报全文版权敏感拿不到，退而用 report_rc 结构化预期。

**存储三层（复用现有选型，零新架构）**：
```
原文表（PG）：doc_id / kind / symbol / ts / title / content TEXT / url / source
向量（pgvector）：embedding 列——「弃重型向量库」选型正是为此
检索（RAG）：bge-m3 嵌入 worker——散项 #42 伏笔，torch ~2GB 按需启
```

**消费三景**：LLM 事件提取（公告→停牌/分红/强赎自动入 security_state）｜情绪因子（新闻情绪）｜智能问答（RAG：AI 助手基于公告回答）。

**定位**：非结构化不是新架构，是 DataKind 的扩展（`announcement`/`news` 立占位词，枚举治理：无消费不实装）。

**范围外（明确不做）**：A03 的完整五层架构（L1-L5 路由/门面）本次不实施，仅对齐「能力分层」这一层；sync_id 归置表（0094）不动，作为数据侧实现真源复用。
