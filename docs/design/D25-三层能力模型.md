# D25 · 三层能力模型（能力 → 能力集 → 接口）

> 状态：**v2 设计定稿**（2026-09-25 双盲审 A/B 共 11 项 P1 全修；原 v1 三裁定不变，新增 token 立法/存量迁移/实施语义三章）
> 原裁定：能力集 5 类 / 页签合并 / snapshot 归位（见 §五）——盲审后全部维持。

## 一、背景

用户审视「数据源 vs 交易账户」页签二分时发现跨市场失效（加密账号三位一体，页签撕两半），引出能力分层问题：细粒度能力（A股列表/基本面/日线/tick/持仓/资金）→ 能力集 → 接口是什么关系。

## 二、现状盘点（三路代码探索实证 + 双盲审核实）

**已落地构件**：

| 构件 | 位置 | 语义 | 数量 |
|---|---|---|---|
| **DataKind**（能力真源） | `quant_common/contract.py` | 细粒度能力枚举 | **26 词**（行情7+参考10+事件2+交易4+占位3；与 A03 §十一 完全一致——v1 称 A03 30 词系错报，实为同 26 词） |
| Temporality | `contract.py` | historical/snapshot/streaming | 3 |
| **sync_id** | `migrations/0094` sync_kind_config | 同步项→kind+sub_kind+pg_table | 20 个 |
| **CAPABILITIES** | `quant_common/markets.py:23` | 配置层能力集（混合维度） | 5（daily/minute/snapshot/quote/trading） |
| SYNC_ID_CAP_MAP | `markets.py:26` | sync_id→能力集 | 5（漏 15） |

**核心发现**：36 项数据能力**31 项漏网**（pool_data 10 + 独立 task 2 + 实时按需 4 + sync_id 15）；CAPABILITIES 混合维度（粒度+时态+交易三轴挤一组）；snapshot 错位（MD 五档盘口被标 quote）。

**消费面真相（B 审 P1-1，改动面的地基）**：CAPABILITIES 元组本体 server/src 零消费；真正消费词表的是**散布 8 模块的 `'trading'=ANY(capabilities)` SQL 字面量**：`mgmt.py:24/192/263/364`、`broker.py:94/230`（实盘选账号）、`trading.py:121`、`risk.py:26`、`strategy_runner/main.py:452`、`scheduler/tasks.py:1344`、`data_source.py:177`、历史迁移 0098/0100；另有 `routing.py:294 _CAP_KIND_ALIASES`（daily/minute→bar_*）一处非 trading 消费。

## 三、三层模型定义

```
接口（external_interface 行）      标注能力集 token（用户配置时选，中文标签渲染）
   ↑ 标注
能力集（归类视图）                  KIND_CAP_CLASS 派生映射（markets.py，非独立建模）
   ↑ 派生
能力（DataKind 26 词）             代码真源，adapter 声明 implements
   ↓ 映射
sync_id（实现层，仅数据侧）         同步项→kind+sub_kind+pg_table（0094 归置表）
```

三层里只有「能力」是真源：能力集是**派生归类视图**（`KIND_CAP_CLASS` 映射表 + 全覆盖互斥测试断言防漂移——31 项漏网的根因正是无此断言）；sync_id 是数据侧实现标识。

## 四、设计决策

1. **能力真源 = DataKind**（contract.py 26 词）。
2. **能力集 = 5 类（v1 裁定 + 文案师审校定稿）**：**历史行情 / 实时行情 / 交易 / 参考数据 / 标的事件**。
   - DataKind 26 词归类（**显式映射表**，落码即 `KIND_CAP_CLASS`）：

   | 能力集 token | 中文 | DataKind |
   |---|---|---|
   | `hist_quote` | 历史行情 | bar_daily / bar_minute / index_daily / **adj_factor**① |
   | `rt_quote` | 实时行情 | snapshot / stream_bar / stream_tick / depth |
   | `trading` | 交易 | account_query / order_stream / trade_exec / settlement |
   | `ref_data` | 参考数据 | static_list / trade_cal / index_constituents / industry_class / fundamental_daily / financial_stmt / featured_daily / stk_limit / funding_rate |
   | `inst_event` | 标的事件 | suspend / corporate_action |
   | （占位归类） | — | open_interest / liquidation / fx_rate → ref_data（占位，消费落地时重裁） |

   ① **adj_factor 显式挪类注记**：contract.py/A03 原分组在「参考数据」，本设计挪入「历史行情」——理由：随 bar 同步拉取、`BAR_COLUMNS` 旁挂列、消费方即 bar 读取链。实施时 contract.py 分组注释同步改（归类单源=KIND_CAP_CLASS，注释仅注记）。
   - 分类本质（三正交维度）：价格 vs 非价格、批量 vs 实时、数据 vs 操作。bar_minute hybrid 时态（盘中流生成）按主用途归 hist_quote；纯流式分钟源声明走 `stream_bar`（rt_quote）。
3. **`trading` 保词（B 审 P1-1 采纳，token 立法核心）**：新 token 集 = `hist_quote / rt_quote / trading / ref_data / inst_event`——**trading 原词保留**，8 处 SQL 域谓词零改动零实盘风险；仅 daily/minute/snapshot/quote 四词退役（其 SQL 消费唯 routing._CAP_KIND_ALIASES 一处，随派生表重写）。
4. **配置页签合并（v1 裁定）**：单列表 + 能力标注 + 可选能力筛选；能力集从「强制页签」降级为「筛选」。实施语义见 §九。
5. **snapshot 归位（v1 裁定，方案 A）**：账户/持仓/委托查询归 `account_query`（trading 类）——**品类看业务不看获取方式**：`DataKind(snapshot)×Temporality(snapshot)`（拉行情价，rt_quote）与 `DataKind(account_query)×Temporality(snapshot)`（查账户，trading）以组合区分。`snapshot` 词只在 rt_quote 出现。（v1 §四.5 旧表述「snapshot 含 account_query 账户快照」系裁定前残留，已废弃。）
6. **细粒度旋钮分家（B 审 P1-3 采纳）**：接口层只标**类**（5 token）；per-kind 排除（如单独把 tushare 踢出分钟路由）移交 `routing_policy` 偏好（对齐 A03「偏好住 DB」）。行为变化：现状接口编辑里的单能力取消勾，合并后改在路由偏好配置。
7. **能力层扩充走 DataKind+sub_kind 双层**（见 §七），**不新建独立词表**；交易操作细分映射到既有 4 词（下单→trade_exec、查持仓/资金→account_query、订单→order_stream、结算→settlement），不造 reconcile/risk 新词（风控/对账是平台内功能非外部接口能力）。

## 七、能力层扩充（DataKind + sub_kind 双层）

**原则（裁定）：能力集 5 类不动，细分全落能力层。** sub_kind 承接结构 = 0094 `sync_kind_config`（表机制不动，行数据经新迁移增改——v1「0094 不动」表述修正为此）。

| DataKind | sub_kind（补全后，与 0094 对齐修正） |
|---|---|
| financial_stmt | income / balancesheet / cashflow / fina_indicator / forecast（+analyst_expect＝report_rc 结构化预期，当前积分实测可用） |
| featured_daily | moneyflow / margin_detail / top_list / block_trade / cyq_perf / cyq_chips |
| static_list | stock / etf / convertible（**namechange 经新迁移补 sub_kind 单列**；**concept 留 industry_class 不动**——0094 与 aggregate_kinds 均以 industry_class 为聚合域，v1 误划 static_list 已修） |
| holder_structure（**新词，唯一**） | top10_holders / dividend / pledge_stat / share_float / stk_holdernumber——**有实现（pool_data 在拉）无登记**，非占位，立词正当；时态 {historical}；dividend 边界注记：corporate_action=事件动作流（inst_event），dividend=参考性历史全景（ref_data） |

**不做的**（盲审 P2 采纳）：bar_minute 频率不入 sub_kind（DataRequest.freq 一等字段已存在，双表示=请求构造歧义）；announcement/news **不立占位词**（无活跃契约可歧义，推迟到消费落地再进 Literal——v1 占位方案撤销，非结构化见 §八按需立词）。

## 八、非结构化数据（获得与存储）

**tushare 实测（200 积分）**：news/anns_d ❌ 无权限（anns_d 且仅元数据无全文）；report_rc ✅ 仅结构化摘要（分析师预期）。

**获得**：原文自建为主——公告走巨潮（官方 PDF）+ PDF 文本提取；新闻走东财/新浪抓取；研报全文版权敏感，用 report_rc 预期数据替代。**立词推迟**：announcement/news 待首个消费场景落地时进 DataKind（枚举治理）。

**存储三层（复用选型）**：PG 原文表（doc_id/kind/symbol/ts/title/content/url/source）+ pgvector 向量 + RAG（bge-m3）。

**落地约束（B 审 P2-7 补）**：① prod 内存 1.8G+swap vs torch ~2GB——bge-m3 worker **现 prod 跑不动**，落点=开发机/升配后跑嵌入、prod 只存向量与检索；② prod pgvector **无安装证据**（deploy playbooks 零命中）——实施前 ansible 核实+装扩展；③ PDF 提取库不在 requirements，接入时补。

## 九、页签合并实施语义（B 审 P1-4 补定义）

| 语义 | 决定 |
|---|---|
| position | 保持**全局单序列**（现状语义不变，合并后跨类统一排序） |
