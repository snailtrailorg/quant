# D28 · 数据收敛与对账（Reconciliation）

> 立：2026-11-05（批171 依据）。定位：**数据正确性的架构基线**——取代「游标驱动的增量同步」作为正确性依据。
> 一句话：**游标只是加速器；正确性来自「目标态 vs 实际态」的持续对账与幂等重放修复。**

## 一、问题：为什么「单次写幂等」不成立为正确性保证

现行同步以 `last_sync_date` 游标推进：只拉 `(游标, 今天]`。它把「过去已同步」当成事实，而事实是**假设**。

- 一次失败（网络/限流/半批写入/进程被杀）就在历史留洞；游标只会向前，**永不回头**。
- 数据被外部改坏（错价、错量、误删、错时区）没有任何机制发现与修复。
- 结论：单写幂等只保证「不产生重复」，不保证「最终正确」。

实证（2026-11-05 排查）：`2026-10-14` 有 2470 只标的数据未入库（当日仅 11 只真停牌），二十天后仍未补齐；近两年另有 3284 只标的存在缺口，其中仅 26% 可被停牌解释。

## 二、设计主张（四条，互相约束）

1. **目标态优先（declarative）**：每个同步项声明「应该存在什么」（标的域 × 频率 × 时间轴 × 豁免），目标态是**纯函数**，不存库、不随历史漂移。
2. **区间代数（interval algebra）**：差异一律用「区间集合」表达与运算，绝不以「逐键枚举」表达——10k 标的 × 4000 交易日 = 4000 万键不可行；区间表示下差异天然稀疏（实测缺口段仅数千）。
3. **单一对账器（one reconciler）**：一套通用算法覆盖所有同步项；数据源只提供 `contract`（声明）与 `fetch(range)`（取数），**新增数据源零对账代码**。
4. **幂等重放（idempotent replay）**：修复=对同一区间重复执行取数+upsert，任意多次结果一致；失败只影响本轮，不改写历史结论。

## 三、分层架构（五层，单向依赖）

```
L5 观测   收敛面板 / 对账台账查询            （只读）
L4 调度   quick(近N日) / full(全历史) 编排     （编排，无业务）
L3 执行   Reconciler：区间→fetch→upsert      （IO，唯一写数据处）
L2 对账   Diff：目标态 ∩ 实际态 → 三类差异      （纯算法，可单测）
L1 声明   CoverageContract 注册表             （纯数据，随代码走）
```

| 层 | 职责 | 禁止 |
|---|---|---|
| L1 声明 | 每个 sync_id 的覆盖契约：标的域、频率、时间轴、豁免集、容忍度 | 禁止读 DB、禁止含数据源细节 |
| L2 对账 | 输入「期望键集×实际键集」→ 输出 `missing/extra/suspect` 区间 | 禁止 IO、禁止知道表名 |
| L3 执行 | 差异 →（标的,区间）批次 → adapter.fetch → upsert；写 `reconcile_item` 台账 | 禁止决策「哪些算缺」（那是 L2） |
| L4 调度 | 决定本轮扫什么窗口、预算多少、优先级、可中断续跑 | 禁止业务判断 |
| L5 观测 | 汇总差异/修复/剩余，供看板与告警 | 禁止写数据 |

## 四、目标态（L1）

```python
@dataclass(frozen=True)
class CoverageContract:
    sync_id: str
    universe: str        # 'astock' | 'listed_fund' | 'crypto' | 'index' …（标的域真源）
    freq: str            # '1D' | '1min' | '5min'
    axis: str            # 'exchange_calendar' | 'continuous'
    exempt: tuple[str, ...] = ('suspended', 'pre_listing', 'post_delist')
    bars_per_day: int = 1
```

**规则**：
- `axis='exchange_calendar'` ⇒ 期望日 = `trade_cal(is_open=1)` ∩ `[list_date, delist_date]` − `suspend(全天)`
- `axis='continuous'` ⇒ 期望日 = 自然日（加密 24×7）
- 豁免是**可插拔数据**：`suspend` 由停牌日历提供（suspend_d）；缺该数据的标的域（如场外基金）自动退化为「不豁免」，契约里显式声明而不隐式猜测。
- 注册表一处：`src/data_platform/coverage.py` 的 `CONTRACTS: dict[str, CoverageContract]`，新增同步项=加一行。

## 五、对账算法（L2）

输入：`expected_runs`（每标的的期望区间集合，由 L1 展开）、`actual_runs`（每标的实际有数区间集合）。
输出三类差异（**全部以区间表达**）：

| 类型 | 定义 | 处置 |
|---|---|---|
| `missing` | `expected − actual` | 回补该区间 |
| `extra` | `actual − expected`（非交易日/停牌日有数；加密豁免） | 报告，人工确认后删；默认不动 |
| `suspect` | 区间内有数但违反不变量（`close<=0`、`high<low`、`volume<0`、重复主键） | 重拉该区间覆盖写 |

**效率设计（关键）**：
- 第一阶段（O(标的数)）：按 `symbol` 聚合 `count(*)`/`min`/`max`，与期望数比对 → 只有 `count < expected` 的标的是候选（实测 9923 → 4510）。
- 第二阶段（O(候选数)）：对候选做日历反连接（`generate_series(日历) EXCEPT SELECT 实际日`）取缺失日，Python 侧合并为连续区间（单标的平均 3~5 段）。
- 绝不把 4000 万键拉进内存；单轮内存占用 = 差异段数（万级）。

## 六、数据模型

```sql
-- 对账台账（每轮一条）：可追溯「何时扫了什么、差多少、修了什么」
reconcile_run(id bigserial PK, sync_id text, scope text /*quick|full*/,
              window_start date, window_end date, started_at timestamptz,
              finished_at timestamptz, status text /*running|ok|partial|failed*/,
              stats jsonb /*{expected,actual,missing_days,extra_days,suspect_days,repaired_n,remaining_n}*/);

-- 差异明细（按区间，不是按键）：resume 与审计的依据
reconcile_item(run_id bigint, symbol text, kind text, start_date date, end_date date,
               keys_n int, status text /*pending|repaired|failed|skipped*/, error text,
               PRIMARY KEY (run_id, symbol, kind, start_date, end_date));

-- 停牌日历（豁免真源；suspend_d 落库）
suspend_event(ts_code text, trade_date date, suspend_type char /*S|R*/, suspend_timing text,
              PRIMARY KEY (ts_code, trade_date, suspend_type));
```

**追溯**：任一数据行都能回答「它属于哪轮修复」（`reconcile_item`）；任一异常都能回答「哪轮扫出来、修没修、失败原因」。

## 七、调度与预算（L4）

| 模式 | 触发 | 窗口 | 预算 | 目标 |
|---|---|---|---|---|
| `incremental` | 现有日调度 | 游标→今日 | 数据源限速 | 日常增量（保留，作为加速器） |
| `quick` | 增量成功后 | 近 30 交易日 | ≤ 2 分钟 | 当天失败当日发现当日补 |
| `full` | 每周低峰 | 全历史 | 可跨多轮（断点续跑） | 历史腐蚀修复 |

**预算与退避**：复用 `RateLimitPolicy`（D23）令牌桶；单轮 `max_symbols`/`max_days` 上限；失败项按指数退避重排，不阻塞其他标的；整轮可被 `SIGTERM` 打断并从 `reconcile_item.status='pending'` 续跑。

## 八、修复语义（L3）

1. 区间合并：同标的相邻缺失段合并（上限 N 天/批），减少请求数。
2. 取数：`adapter.fetch(symbol, freq, start, end)` —— 与增量同步**同一取数契约**，不另写一套。
3. 写入：`upsert`（主键冲突覆盖）——幂等；重复修复结果一致。
4. 结果：`keys_n` 实收 vs 期望，写回 `reconcile_item`；实收为 0 且期望>0 ⇒ `failed`（不静默成功）。
5. 停牌豁免：若缺失日全部属于停牌/上市前/退市后 ⇒ `skipped(reason=exempt)`，**不重试**（避免对不存在的数据反复请求）。

## 九、观测（L5）

- 收敛指标：`expected_days / actual_days / missing_days / suspect_days / remaining`，按 sync_id 与时间序列。
- 健康判据：`quick` 轮 `remaining == 0`；`full` 轮 `remaining` 单调下降。
- 完整性看板从「比例」升级为「目标/实际/差异/上轮修复」，比例只是派生值。

## 十、明确不做（本架构不含）

- 不做跨源逐值比对（源 A vs 源 B 一致性）——属数据质量域，另行设计。
- 不做复权因子的收敛（因子链另有一套对齐规则，见 D16）。
- 不做实时/流数据的对账（流有水位线机制，见 D26/A03）。
- 不引入外部编排引擎（Airflow 等）——调度仍用现有 Celery，收敛逻辑自持。

## 十一、验收标准

1. 单测：区间差集（含跨月/跨年/全缺/全有/停牌边界）、契约展开（三市场）、修复批次合并。
2. 集成：dev 人为删 `2026-10-14` 全表该日数据 → `quick` 轮自动补齐，`reconcile_run.stats.remaining=0`。
3. 破坏测试：随机改坏 100 行的 `close` → `suspect` 检出并重拉修复。
4. 幂等测试：同一轮连跑 3 次，第 2、3 次 `missing=0/repaired=0`。
5. 性能：全历史 `full` 扫描 CPU 时间 < 5 分钟（不含取数），DB 无长事务（D18 约束）。
