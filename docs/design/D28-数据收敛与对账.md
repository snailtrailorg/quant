# D28 · 数据收敛与对账（Reconciliation）

> 立：2026-11-05（批171 依据；同日双盲审后**整篇重写**——首版被否：它在仓库已有对账体系之外另造一套状态机，属「换皮」，不是架构级修改）。
> 一句话：**正确性不来自游标，也不来自新造一套对账，而来自「一个状态真源 × 一个期望态展开 × 一个请求编译器」的收敛闭环。**

## 一、现状与真实缺口（先承认已有的）

仓库已有三层对账能力，**本设计全部复用，不另立**：

| 既有件 | 位置 | 能力 |
|---|---|---|
| `sync_gap` 五态表 | 迁移 0140 / `_upsert_sync_gap` | 缺口**状态真源**：`open/verified/ignored/exempt` + `first_seen/last_seen/hit_rounds` |
| `_reconcile_dates` | `engine.py`（同步收尾内联） | **按日**差集 + 内联重拉（per-date 族） |
| `_reconcile_symbols` + 周任务 `data_gap_reconcile` | `engine.py` / `tasks.py` | **按标的**缺口（有 scope 白名单 `_RECONCILE_SYMBOL_SCOPE`） |
| `data_continuity_check` | `tasks.py`（小时） | 连续性巡检 + 补采 |
| `_window_floors` / `publish_lag` / `available_range` | `engine.py` / `adapters/base.py` | 窗口四边界真源：`max(inception, retention, source_earliest)` 与发布滞后 |
| `save_bars` / `save_bars_overwrite` / `SyncLock` | `db.py` / `engine.py` | 写路径（跳过/覆盖）与串行化 |

**真实缺口只有三条**：
1. **日线族的标的级覆盖不完整**——`_RECONCILE_SYMBOL_SCOPE` 只覆盖少数 scope，`bar_1D` 的 9923 只标的没有系统性逐标的对账 ⇒ 2026-10-14（2470 只缺 1 天）二十天无人发现、无人修复。
2. **修复粒度只有 per-symbol**——同一天 2470 只缺，现在要 2470 次请求；而源原生支持「按日全市场一批」（`fetch_supply(kind, sub_kind, start=day, end=day)`）。粒度选错 ⇒ 修复在限速下永远跑不完（这正是现有小时补采「检测到但补不完」的原因）。
3. **缺三态语义贯通**——日历未覆盖/本地读失败/源不可达时必须 `uncertain`（不得主张缺口、不得过健康门）；停牌/上市前/退市后必须 `exempt`。否则对账器把「不知道」和「合法没有」都报成「缺」，修复风暴打爆配额。

## 二、设计主张（四条）

1. **单一状态真源**：缺口状态只写 `sync_gap`。任何新代码不得引入第二张「缺口表」；轮次统计另存 `reconcile_run`（append-only 审计，非状态）。
2. **期望态是纯函数**：`(kind, sub_kind, symbol, 窗口) → 期望日集合 | uncertain(reason) | exempt(reason)`。窗口四边界（inception/retention/retention_days/source_earliest/publish_lag）是入参，不是事后裁剪。
3. **区间表达差异，粒度由编译器决定**：差异一律「每标的的区间集合」；执行计划把区间编译成**请求批次**——同一交易日的多标的缺口合并为 1 次按日批；多年长洞走 per-symbol 区间。
4. **幂等重放**：修复=对同一批次重复取数+覆盖写，任意多次结果一致；失败只影响本轮，不改写历史结论。

## 三、分层（可实现的依赖图，非装饰）

```
L6 调度   既有 beat（周任务 / 增量后 quick 档）        tasks.py
L5 执行   Reconciler：批次→fetch→写→台账              data_sync/reconciler.py（层3）
L4 编译   Plan：区间 × 源能力 → 请求批次                data_sync/reconcile_plan.py（纯函数）
L3 差异   SQL 集合化反连接 → 区间 → 三态               data_platform/reconcile_diff.py（层1，只读 SQL）
L2 展开   契约 × 窗口四边界 × 日历 × 豁免 → 期望集       data_sync/coverage_expand.py（层3，读 DB）
L1 声明   CoverageContract 注册表                      data_platform/coverage.py（纯数据）
```

依赖方向：L1←L2←L3←L4←L5←L6，且 L3（层1）不 import L2/L4/L5（层3）——**差异计算下沉到层1，只吃「已展开的期望集」参数**，层3 负责展开与执行。这样既守住 `test_layering.py`，又让差异算法可脱离业务单测。

**明确取消首版的伪分层**：不再声称「L1 禁读 DB」「L2 禁 IO」——展开必须读 DB（日历/停牌/主档），干脆把它放 L2 并标明「唯一允许读 DB 的期望态层」；差异层只接受参数，做纯集合运算。

## 四、契约（L1）

```python
@dataclass(frozen=True)
class CoverageContract:
    kind: str                 # DataKind（第一公民；sync_id 不作为键）
    sub_kind: str | None
    freq: str                 # '1D' | '1min' | '5min'
    table: str                # 落地表（bar_1D / bar_1min …）
    tz: str                   # 'Asia/Shanghai' | 'UTC'（日期归属时区——缺它必 off-by-one）
    source_predicate: str     # 共写表的多源隔离谓词（如 "source='tushare'"；单源表为 "TRUE"）
    axis: str                 # 'exchange_calendar' | 'continuous'
    window: WindowPolicy      # inception/retention/retention_days/publish_lag/available_range 的来源
    exempt: tuple[str, ...]   # ('suspended','pre_listing','post_delist')
    repairable: bool          # 无源可补（积分不足/接口下线）⇒ False，只报不修
    batch_hint: str           # 'by_day'（源支持全市场按日） | 'per_symbol'
```

注册表 `CONTRACTS` 一处；新增同步项=加一行。`repairable=False` 的项只写 `uncertain/unrepairable`，不进入修复队列。

## 五、期望态展开（L2）

```
expected = axis_days(axis, 窗口下界, 窗口上界) − exempt_days − 排除段
```

- **窗口四边界**（合取，缺一即假缺口）：
  - 下界 = `max(inception, retention, source_earliest)`，另有 `retention_days ⇒ now() − retention_days` 作为**硬地板**（修复器绝不得复活被清道夫删除的区间）
  - 上界 = `min(source_latest, now() − publish_lag)`（否则 quick 在增量后立刻跑，当日必假缺）
- **日历覆盖门**：`trade_cal` 未覆盖该区间（任一端缺失）⇒ `uncertain(calendar_uncovered)`，不得产出缺口。
- **inception 未知门**：`list_date IS NULL` 且无 retention ⇒ `uncertain(unknown_inception)`，不得从盘古展开。
- **豁免**：`suspended`（停牌日历，171b 接入）、`pre_listing`、`post_delist`。豁免数据缺失 ⇒ 该 exempt 项**不生效**且契约标 `degraded_exempt`（在报告里显式声明，不静默）。

三态返回：`(days: list[date] | None, state: 'ok'|'uncertain'|'exempt', reason: str)`。

## 六、差异（L3，层1，只读、集合化）

**候选筛选**：按 `symbol` 聚合 **`count(DISTINCT (ts AT TIME ZONE tz)::date)`**（不是 `count(*)`——分钟线含 240 根/日，用行数比会 100% 落候选）。与期望日数比对，只对 `actual_days < expected_days` 的标的展开。

**缺失日**：单条集合化 SQL，`generate_series(窗口) CROSS JOIN 候选集 LEFT JOIN 实表 ... WHERE 实表 IS NULL`，一次取回全部（symbol, date）。

**区间化**：Python 侧把缺失日合并为连续段（同标的相邻 ≤3 自然日合并），单标的通常 1~5 段。

**extra**：`actual − expected` 同样集合化（非交易日/停牌日有数）。默认**只报不删**，状态入 `sync_gap(kind='extra')`。

**known/perf**：`bar_1D` 4000 万行级走现有索引；`bar_1min` 10^9 级只允许 `quick`（近 30 日）窗口，`full` 对分钟族默认跳过（契约 `repairable` + 窗口共同约束）。

## 七、请求编译（L4，纯函数）

输入：`[(symbol, start, end)]` + 契约 `batch_hint` + 源限速档
输出：`[Request(n_symbols, kind, start, end)]`

规则（按成本最小）：
1. 同一天缺 N 只 ⇒ **1 次按日批**（`fetch_supply(kind, sub_kind, start=day, end=day)`）——2470 只缺 1 天 = 1 次调用，而非 2470 次。
2. 同标的连续 ≥K 天 ⇒ per-symbol 区间（K 由契约给，默认 5）。
3. 批次总天数受源 `available_range` 与接口单次上限（如 `stk_mins` 8000 条）约束，超限切分。
4. 单轮总请求数上限（预算）按源限速档计算，超出部分留待下轮（差异不丢，状态仍在 `sync_gap`）。

**这一层是「简洁 × 高效 × 可移植」的支点**：换数据源只改契约与 hint，编译规则不变。

## 八、执行（L5）

1. 串行化：修复全程持 `SyncLock(sync_id)`，与增量互斥；按 `(table, trade_date)` advisory lock 防与其它写入方交错。
2. 取数：复用 `fetch` / `fetch_supply`（**不新写取数**），分钟族带 `preserve` 与增量一致。
3. 写入：`missing` 用 `save_bars`（跳过已存在）；`suspect` 用 `save_bars_overwrite`（覆盖）——**必须取 `rowcount` 记账**，禁止用 `len(rows)` 冒充写入数。
4. 账：`reconcile_run`（每轮：窗口/候选数/缺口段数/请求数/写入数/耗时/状态）＋ 每条动作 append 到 `sync_gap` 的 `last_seen/pull_count/hit_rounds`（状态真源）。
5. 失败：`failed` 只影响本轮；退避记在 `sync_gap.hit_rounds`，不新增表。

## 九、调度（L6）

| 档 | 触发 | 窗口 | 默认动作 |
|---|---|---|---|
| `quick` | 增量成功后 | 近 30 交易日 | **171a：只报不修**；171b（豁免齐备）后开自动修复 |
| `weekly` | 既有周日任务（复用） | 日线族全历史 | 只报，人工确认后按需修复 |
| `hourly` | 既有 `data_continuity_check` | 近期 | 保持现状，逐步收编到本引擎 |

**预算**：修复在单一 beat 进程内串行（现有 `RateLimiter` 是进程内固定间隔，非分布式桶——不引入分布式令牌桶，避免过度设计）；单轮请求数上限按源档位计算（`daily` 0.5s/次 ⇒ 预算内 ~240 次/2 分钟）。

## 十、观测与追溯

- 指标：`expected_days / actual_days / missing_days / extra_days / uncertain_n / repaired_n / remaining_n`，按 (kind, sub_kind) 与轮次。
- 健康门：`quick` 轮「**本轮新增** missing == 0」且 `uncertain_n == 0`；`remaining` 允许非零（历史存量走 weekly）。
- 追溯：`reconcile_run` 回答「哪轮扫了什么、差多少、修了多少」；`sync_gap` 回答「这个洞从哪天起、被拉过几次」。

## 十一、明确不做

- 不新建第二套缺口状态机（`sync_gap` 唯一）。
- 不做跨源逐值比对（源 A vs B 一致性）——数据质量域另议。
- 不做复权因子收敛（D16 因子链自有对齐）。
- 不做流/实时对账（水位线机制见 D26/A03）。
- 不引入外部编排引擎。

## 十二、迁移路径（三个小批，默认安全）

| 批 | 内容 | 默认开关 |
|---|---|---|
| **171a** | L1 契约（日线族 A 股/基金/指数/加密）+ L2 展开（含四边界与三态）+ L3 差异（集合化）+ L4 编译（by_day 优先）+ L5 执行器（**只写 sync_gap 与 run 台账，不写业务表**）+ L6 quick 档 | `repair_enabled=false`（report-only） |
| **171b** | 停牌日历（`suspend_d` 同步项 + `suspend_event` 表）+ 豁免生效 + 打开 `repair_enabled` | 修复打开；首轮目标=补齐 2026-10-14 |
| **171c** | `suspect`（行级不变量 + 日根数）覆盖写 + `full` 慢扫 + 收敛面板 | 小流量试跑 |

向后兼容：增量同步与既有周/小时对账不动；`last_sync_date` 降级为「上次成功推进点」，不再是正确性依据。

## 十三、验收（可证伪）

1. **单测**：期望态展开（四边界各一例 + 日历未覆盖 + inception 未知 + 停牌豁免）；区间合并/裁剪；编译器（同日 N 标的 → 1 次 by_day 请求）；三态传播。
2. **171a 集成（report-only）**：dev 删 `2026-10-14` 该日 A 股数据 → quick 轮报告 `missing=2470±`、`requests=0`、`repair_enabled=false` ⇒ 证明「测得准且不乱修」。
3. **171b 集成（开修复）**：同场景 → `requests==1`（按日批）、次日该日补齐、`remaining==0`；连跑 3 次，第 2/3 次 `missing=0/repaired=0`（幂等）。
4. **停牌不误报**：长停牌股（如 000002 万科 2015-12~2016-07）在 171b 后 `exempt`，不进 missing、不告警。
5. **并发安全**：修复与增量同时触发 → 不出现死锁/重复写；覆盖写 `rowcount` 与台账一致。
