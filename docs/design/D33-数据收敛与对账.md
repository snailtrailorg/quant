# D33 · 数据收敛与对账

> 立 2026-11-05；**三轮双盲审后整篇重写（v4）**。
> v1 否＝另造状态机；v2 否＝重写既有能力且写错事实；v3 否＝「加三行 scope」撑不住真实规模（内存 4.3GB / 预算整 scope 抑制 / 修复原语不存在）。
> 一句话：**既有对账器的三个隐含假设在 A 股日线族下全部失效；解法是把「巡检」与「回补」彻底分离，并对既有引擎做七处定向改造——不新建模块、不新建表、不新建状态机。**

## 二、根因：三个隐含假设

既有 per-symbol 对账器是为「小众 universe + 小表」设计的，三处假设在日线族下同时失效：

1. **内存假设**：日期集可全量驻留（真实 4.3GB vs 1.6GB 上限）；
2. **预算假设**：缺口行数 ≈ 当期新增（真实首轮 2.9 万段历史欠账 ⇒ 整 scope 抑制）；
3. **修复假设**：per-symbol 区间可取数（真实：日线族无 supply 条目、按日批只存在于闭包里）。

**结论**：靠「加 scope」必然失败；必须改造这三处，并把历史欠账从日常巡检中剥离。

## 三、架构主张：巡检 / 回补 分离

| | **巡检（ongoing）** | **回补（explicit）** |
|---|---|---|
| 目的 | 发现**近期新增**缺口 | 消化历史欠账 |
| 范围 | 固定近 N 交易日（默认 30，可配） | 指定日期或区间（含全历史） |
| 读取 | SQL 下推差集，只回缺口日期（万级） | 同 |
| 预算 | 只对**本轮新增**缺口计；超限抑制**超出部分**，不整 scope 作废 | 不走巡检预算，按源限速分片、断点续跑 |
| 告警 | 只响新增（沿用 `_alert_sync_gaps`） | 只出报告 |
| 修复 | 同日聚批（同日多标的 = 1 次） | 按日批 + 长洞区间 |

两者共用：同一 `sync_gap` 状态、同一取数原语、同一写路径、同一锁。**不新增模块与表。**

## 五、状态与数据

- 缺口状态：沿用 `sync_gap` 五态，**不新增状态**。停牌＝期望集里没有该日 ⇒ 不产生 gap 行（R5 保证既有行不被误判）。
- 轮次：沿用 `sync_log` 与 `_log_scope_summary`；不建 `reconcile_run`。
- 新增表只有一个（171c）：`suspend_event(ts_code, trade_date, suspend_type, suspend_timing)`，来自 tushare `suspend_d`（实测可用：按 `trade_date` 日增量，单次 5000 行封顶需分片）。

## 七、验收（可证伪，全部用 dev 真库）

1. **内存/耗时**：stock scope 巡检（30 日）峰值 RSS < 200MB、DB < 5s（对比现状 4.3GB / 12.9s）。
2. **检出**：删 `2026-10-14` → 巡检报告 `listed_fund≈2160 + convertible≈311`，`new_open` 段数与之匹配；`stock=0`（当日确实没丢）。
3. **预算**：同一轮历史欠账存在时，当期新增缺口仍能被主张（R2 生效）。
4. **修复**：171b 开修复 → 该日请求数 **1**（按日批）；补齐后 `sync_gap` 转 `closed`；连跑 3 次 `new_open=0`。

6. **停牌**：`000002.SZSE` 2015-12~2016-07 在 171c 后不产生 gap 行，且既有 open 行的 `first_seen` 不被重置（R5）。
7. **守门**：`test_batch109/110`、`test_layering`、`test_route_auth_gate` 全绿。
