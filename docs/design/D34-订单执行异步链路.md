# D34 订单执行异步链路（下单 / 撤单 / 清仓）

> 状态：**阶段 1/2 已实施（2026-11-23）**，阶段 3（OrderGateway 单写点 + 券商查询 + 事件驱动 UI）待做。
> 本文是订单异步链路的**唯一现行设计真源**；实施计划见 `flow/方案/批189-订单异步链路改造-方案.md`（仅存进度，不复制设计）。

## 1. 分层与实体

- **web-api**：鉴权/参数校验/入队，不持有 TD 会话。
- **td_exec**（每交易接口一个）：唯一持有该接口 TD 会话，唯一碰 adapter。
- **XTP SDK/券商**：异步应答（回调）。
- 通道：`td:cmd:<td_code>`（命令）、`risk:cmd:result:<req_id>`（回执）、`iface:hb:td:<td_code>`（心跳）。
- 账本：`order_log`（投影）、`order_event`（append-only 事件账，0195）、`trade_log`、`position_snapshot`。

## 2. 同步返回 ≠ 受理

| 动作 | 同步返回 | 语义 |
|---|---|---|
| XTP `insertOrder` | `order_xtp_id`（0=未发出） | 进入 SDK/本地序号，不是券商受理 |
| vnpy `send_order` | `XTP.<id>`（先本地推 SUBMITTING） | 本地已提交 |
| 撤单 `cancel_order` | 无返回 | 仅请求已发出 |
| 券商 | **异步回调** | `onOrderEvent`（状态/拒单 error）、`onTradeEvent`（成交）、`onCancelOrderError` |

## 3. 当前状态机（实现）

```
submitting --send ok--> submitted --broker--> partial / all_traded
     |                       |-------------> cancelled / rejected
     +--send fail--> send_failed
submitted/submitting/partial --timeout(reconciler)--> unknown
unknown --迟到终态--> all_traded / rejected / cancelled （可覆盖）
```

- 写点：`_wal_insert_order/manual_order_open/_close_order_open` 写 `submitting`；`_close_order_mark/execute_place_order` 写 `submitted/send_failed`；`write_order_status` 写券商终态；`reconcile_stale_orders` 写 `unknown`。
- `unknown` 不在 `ORDER_FINAL_STATES`，迟到终态可纠正；撤单 DB 兜底已包含 unknown。
- 目标态 `broker_accepted` 尚未引入（当前以券商首次 onOrderEvent 作为推进）。

## 4. 事件账 order_event（0195）

字段：`id, order_id, client_order_id, req_id, ts, stage, status, source, detail jsonb, error`。

已埋点：
- `wal`/`wal_error`：写单失败；
- `risk_reject`：风控拒；
- `send`/`close_send`：发单成功/网关拒/异常；
- `broker`：券商终态（含 error）；
- `trade`：成交（price 取券商回调，非委托价）；
- `cancel_request`：撤单请求成功/失败（via cache/db）；
- `timeout`：对账判超时。

排查：`GET /api/orders/{order_id}/events`（read 权限，按 id 升序）；或 SQL `SELECT ... FROM order_event WHERE req_id=... ORDER BY id`。

## 5. 各入口

- **策略单**：`strategy.py::_place_order_via_cmd` 写 signal_log + 入队 → td_exec `_place_order` → `execute_place_order`（risk → WAL → rules → send）。
- **手工单**：`/api/manual-order` → 入队 → td_exec `_manual_order` → `submit_manual_order`（SELL 先按 volume-frozen 截断；risk → WAL → send）。
- **撤单**：`/api/risk/cancel-all` → 入队 → td_exec `_cancel_all` → `_cancel_working_orders(adapter, account_id)`：
  - cache 在途单按 vt 撤；
  - 有券商在途清单时只撤清单内 vt；不在清单的单记 `cancel_skip`（防 vt 复用误撤）；
  - DB 兜底查 order_log（status 含 unknown，vt 非空）盲撤；
  - TD 断线拒绝（td_disconnected）。
- **清仓**：`/api/risk/close-all` → 先 halt → 入队 → td_exec 专用线程 `td-close-<code>` → `EmergencyWorker._close_all` → `trading._close_all_positions` 无限循环（每接口独立，无全局协调器）：
  - 撤在场单 → 查持仓 → T+1（volume-frozen≤0 → skipped_t1）→ hub 主备取价（MAPPING_MISSING/NO_QUOTE）→ 拆单 → risk → WAL → send → 撤/重定价/重挂；
  - 终局 `:final`+SSE 由 `hub_worker._final` 写（closed_requested/positions_remain/skipped_t1/rejected/no_quote）。

## 6. 超时对账（阶段 2）

- td_exec 每 30s：`reconcile_stale_orders(adapter, account_id, threshold_s=120)`。
- 缓存仍有在途 = 正常挂单，不判超时；券商在途清单确认在途的单也不误判；缓存无记录且超阈值 → `unknown` + `order_event(timeout)`。
- **unknown 收敛**（`resolve_unknown_orders`）：按 `trade_log` 汇总已成交量，达到委托量→`all_traded`、部分→`partial`，写 `order_event(stage=reconcile)`；无成交保持 unknown，等迟到回调或撤单。
- **partial 不判超时**（2026-11-24）：partial=券商已回报部分成交，不是“无回报”；只扫 submitted/submitting，否则会 unknown→resolve→partial 无限循环并刷事件。
- 局限：vnpy_xtp 未暴露 query_order，当前只证明“我们没收到回调”，**不能证明券商侧真实状态**；阶段 3 补券商在途查询/重启对账后才能恢复真值。

### 6.1 事故：查询参数传反致 XTP 库越界 SEGV（2026-11-24 已修）

- **现象**：开盘后 td_exec 每 1–10 分钟 SEGV core-dump，重启 19 次；伴随 terminal_id=2 有主 与 watchdog 假 core。
- **证据链**：dmesg 全部 SEGV 落在 libxtptraderapi.so+0x39a43/0x39a4d；符号表= XTP::Base::SessionMgr::GetSession() 的无边界取槽指令；反汇编 TraderPrivateApi::QueryUnfinishedOrdersEx(uint64 session, int request_id) 证明 session 是第 1 参。
- **根因**：query_unfinished_orders 传成 (request_id, session_id)，时间戳被当 session 查槽 → 数组越界；且首轮查询发生在登录完成前（connected 只判 TCP）。
- **修复**：参数改 (session_id, request_id)；session_id<=0 禁查；reconciler gate 改 logged_in；回调改永久 dispatcher；SessionBusy 改 os._exit(75)。
- **验证**：NRestarts=0、连续 5 分钟 0 次 SEGV、对账无 partial 循环；查询回调是否真被 pybind 分发待下一笔在途单确认。
