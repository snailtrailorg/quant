# 数据同步机制全景（人话版）

> 目的：把「数据从哪来、怎么进来、存在哪、怎么管、坏了怎么办」一次讲清。
> 读者：平台使用者与接手者。代码位置随批演进，以仓内实现为准（本文引用 2026-10-27 时点）。

## 一、一张图：数据流全貌

```
外部源                     进程                       数据库                  消费面
────────                  ────────                   ────────                ────────
Tushare(主/日线/清单)  ─┐
聚宽JQ(历史日线)       ─┤   celery-beat(每300s)      ┌─ sync_config(调度配置)
币安(永续4档)          ─┼─▶ data_sync_scheduler ───▶ ├─ sync_log(每次运行)
OKX(永续4档)           ─┤   (判周期/派发)            ├─ sync_cursor类:
                        │        │                   │   last_sync_date(主游标)
                        │        ▼                   │   pool_data_cursor(池级)
                        │   sync引擎(data_sync/      ├─ sync_gap(缺口台账)
                        │        engine.py)          ├─ sync_kind_config(归置)
                        │        │                   ├─ bar_1D/1min/5min/15min/1h/
                        │        ▼                   │   bar_index(行情六表)
                        │   adapter.pull_*/fetch ──▶ ├─ tier1十表(涨停/资金/融资
                        │   (upsert幂等落库)          │   /龙虎/大宗/筹码/预告/
                        │                            │   ST/更名/概念)
                        │   Valkey SyncLock(防重)     ├─ external_interface(源凭证)
                        │                            └─ proxy_config(代理池)
XTP(实时行情) ── vnpy_xtp hub MD 流 ──▶ Valkey Streams ──▶ 实盘worker（**不走本链**）
```

**一句话**：beat 每 5 分钟醒一次 → 对照每项的 cron 判断到没到点 → 到点就调引擎 → 引擎按「kind」找 adapter 拉数据 → 幂等落 PG → 游标和日志记账 → 缺口和对账任务事后找补。

## 二、进程与调度（谁在跑）

| 进程 | 职责 |
|---|---|
| `quant-celery-beat@quant` | 定时器：每 **300 秒**唤起一次调度任务（5 分钟粒度才能对上分钟级 cron 窗） |
| `quant-celery-worker@quant` | 干活的：data_sync_scheduler 在此运行，同步本体也在 worker 进程内执行 |
| 特例异步派发 | 超长任务（池数据 290s、池全量校准/crypto 日线 3600s）丢到 `data` 队列另开 celery 任务跑，不堵调度轮（track=False——防任务表一年 10 万行噪声） |
| 防重锁 | Valkey `SET NX EX` 心跳锁（TTL 60s/心跳 20s）——同一 sync 同时只有一份在跑；进程死了锁自然过期 |

**到点判断（人话）**：每项记录着「上次跑完的时刻」，用 cron 表达式从那个时刻算下次该跑的时间；还没到就 skip。交易日过滤（none/workday/trade_day 三档）让 cron 命中但非交易日时自动滚到下一窗口。卡死在「running」超 2 小时的项自动复位成 idle（僵尸复位，防一次崩溃永久堵路）。

## 三、注册表：30+ 同步项怎么组织

- **双注册表**：`_HANDLERS`（清单/池/crypto/聚宽切片等专项处理器）+ bar 族 6 键走 `_sync_via_kind` 统一路径 + tier1 批量注册 8 项 + 全量重建 2 项（更名/概念）。
- **归置表 `sync_kind_config`**：每项的 kind/子类/目标表/主键列/浮点列/重建模式（增量 or 全量重建）都在这——新增一类数据=加一行配置+一个 adapter 方法，引擎零改动。
- **adapter 契约**（`data_platform/adapters/base.py`）：`pull_daily/pull_minute`（统一 11 字段 bar）、`fetch`（按 kind 分派）、`available_range`（源可达区间——硬契约，没写就报错）。注册用装饰器，tushare/jq/binance/okx 四家在册。

## 四、数据库表（存哪、谁写谁读）

| 表 | 干什么 | 写 / 读 |
|---|---|---|
| `sync_config` | 每项的调度配置+游标+状态（name/schedule/cron/enabled/provider/last_sync_date/last_sync_ts/retention…） | 引擎与调度器写 / 调度器、管理页读 |
| `sync_log` | 每次运行的流水（起止日/拉了几行/存了几行/耗时/状态/失败日期清单） | 引擎写 / 进度页、断流检测读 |
| `sync_kind_config` | 归置：kind→表/主键/列型 | 迁移种子 / 引擎读 |
| `sync_gap` | 缺口台账（sync_id+symbol+起点，五态 open/closed/unreachable/policy_discard/uncertain） | 对账写 / 补拉与告警读 |
| `pool_data_cursor` | 池数据表级游标 | 池任务写 / 断流二档检测读 |
| `bar_1D/1min/5min/15min/1h/bar_index` | 行情六表（主键 symbol+ts） | adapter upsert / 回测、选股、hub 暖机读 |
| tier1 十表 | 涨停/资金流/融资融券/龙虎榜/大宗/筹码/业绩预告/ST/更名/概念 | 通用 handler upsert / 策略因子面读 |
| `external_interface` | 外部源账号凭证（Fernet 加密）+能力集 | 集成中心写 / 数据源工厂读 |
| `proxy_config`+`proxy_binding` | 代理池与绑定（consumer→代理开关+端点覆盖） | 管理页写 / 引擎构造 adapter 时注入 |

## 五、幂等机制（为什么可以放心重跑）

1. **upsert 主键幂等**：所有数据表按业务主键 `ON CONFLICT DO NOTHING`（bar 族=(symbol,ts)；tier1=pk_cols 来自归置表；清单=ts_code）——同一窗口拉十遍，表里只有一份。
2. **游标三态推进**（`sync()` 核心）：
   - 全失败 → 游标不动，标 failed → 下轮自动重拉整个窗口（这就是重试机制，无需专门重试器）
   - 部分失败 → 推到「连续成功的最后一天」，标 partial → 缺的日子留待对账补
   - 全成功 → 推到 end_date
   - 回补（backfill）不推游标——补历史不动增量节奏
3. **窗口重叠**：池数据游标窗口含起点重叠一天，宁重拉不漏拉（反正幂等）。
4. **分钟线族例外**：无条件推游标——防 beat 5 分钟轮把失败任务重试成风暴。
5. **防重锁**：同项并发跑被 Valkey 锁挡住；`last_status` 只是展示，防重真源在锁。

## 六、管理界面（在哪操作）

- **数据运维页**（DataOps.vue 五 tab）：同步 tab=同步配置表（改 cron/启停/换源/触发）+ 异步进度轮询；完整性/质量/调度/路由/安全各一 tab。
- **接口族**（/api/sync/*）：config 读写、trigger+progress（含池数据/复权因子回补/per-symbol 逐标的/整项重拉 all）、数据删除（按日期段/按项）、switch-provider 换源、log 查询。全部挂权限键。
- **触发语义**：手动触发=立即跑一次该项目的完整增量窗口（不推 cron 节奏，跑完 last_sync_ts 刷新）；长任务异步+进度条。

## 七、异常处理（坏了怎么办）

| 异常 | 机制 |
|---|---|
| 拉取失败 | 游标不动 → 下轮自动重拉窗口；告警一条（含失败日样本） |
| 部分标的失败 | 游标推到连续成功末日；缺口进 `sync_gap` 台账 |
| 进程崩溃 | 心跳锁 TTL 60s 自然过期；running 超 2h 僵尸复位 |
| 断流（没报错但也没新数据） | 一档 8 表按 sync_log 48h 无成功告警（清单单源 tier_tables.py）；二档池表按游标 8 天+任务心跳；enabled=false 的项不参与（「禁用=主动放弃」）。**电平语义过滤**：只告「新变 stale」和恢复，状态存 Valkey——不每小时重复轰炸 |
| 缺口累积 | **三层对账**：① 同步收尾内联 per-date（日期差集→预算内重拉→仍缺落台账）② 周日 03:33 per-symbol 旁路（10 键 scope；4 轮同缺口才自动判、快照过老判 uncertain 抑制假主张）③ 池族/tier1 分族对账（cyq 自愈/显式三元组/清单新鲜度/接口健康四族）。新 open 聚合告警每轮一条防疲劳 |
| 三账不平 | 每小时 `reconcile_three_books` 对账 |
| 源侧数据未发布 | crypto 批量站「没发布就不推游标」——游标=实际拿到数据的最后一天，不虚进 |
| 时钟回拨 | 游标在未来锚回 7 天前重算 |

## 八、窗口与保留（retention 的真实语义）

**retention=拉取窗口下界，不是删除**。窗口地板取三方最大：`max(标的上市日, retention, 源最早可达)`。低于 retention 的段登记为 `policy_discard`（主动不保留——台账可查，不静默丢）。**没有任何按 retention 删存量数据的任务**——数据只进不清（日志类 system_log/audit_log 例外，30 天清）。现值例：index_daily=2005-04-08、astock_basic=1990-12-19、crypto 盘中三档未声明=「从源头全要」（开用前必须显式填，引擎注释有闸）。**缺口台账（sync_gap）目前只有告警面可见，Web 无直接消费页**——要查存量缺口走数据库或等聚合告警。

另：策略冻结（freeze_event：ts_gap/seq_gap/untrusted）是**实盘域**机制，与数据同步无关，别混淆。

## 九、XTP 为什么不在这条链上

XTP=实时行情（vnpy_xtp 网关→hub MD 流→Valkey Streams→实盘 worker 消费），是**推**模式；本链全是**拉**模式（定时拉历史/日线）。XTP 在集成中心只有凭证与连接测试（InterfaceProvider），不注册为 data_sync 源。

## 十、速查：常见操作

| 想做什么 | 去哪 |
|---|---|
| 看某项跑没跑/上次结果 | 数据运维→同步 tab（或 /api/sync/log） |
| 手动跑一项 | 同步 tab 触发钮（长任务有进度条） |
| 改周期/停用/换源 | 同步 tab 行内编辑（provider 切换有校验） |
| 补历史窗口 | 触发页回补（adj-factor-backfill / per-symbol backfill / all 重拉） |
| 查缺口 | sync_gap 台账（对账任务维护） |
| 配代理 | 集成中心代理面（proxy_config+binding） |
| 看断流告警 | 告警通道（48h/8 天两档） |
