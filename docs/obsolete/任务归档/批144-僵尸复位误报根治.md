# 批 144 · 僵尸复位误报根治（running 心跳锚点修正）

> 立项 2026-10-24（用户裁定立项观察窗预核发现 1/2）。来源＝10-24 观察窗预核（`flow/稳定性检查/观察窗判据汇总.md` 发现 1）。
> 关联：批 116（crypto 日线异步派发引入运行时长 135~1669s）· 批 83b（async 派发通道）· 2026-08-20 双盲审 A2（僵尸复位机制本尊）

## 目标

消除 binance_perp_daily 每晨「僵尸 running 已复位」误报：调度器僵尸判定所读的时戳与 running 置位动作对齐，长任务运行中不再被误判为死进程。

## 现状（已实证 · prod，2026-10-24 预核）

| # | 事实 | 锚点 |
|---|---|---|
| 1 | `_mark_running(sync_id, True)` 只 UPDATE last_status='running'，**不刷 last_sync_ts** | `server/src/data_sync/engine.py:217-221` |
| 2 | 僵尸判定按 `last_sync_ts` 龄 >7200s 且 last_status='running' 即复位 idle；NULL ts 同判 | `server/src/scheduler/tasks.py:782-802`（阈值 :792） |
| 3 | 每日档 async 派发后任务运行 1069s（binance 10-22 实测），跨过多个 5min 调度轮；轮内读到「running + ts 停昨日」⇒ 误报「1369/1436 分钟未更新已复位」连续两晨 | prod journal 10-22 08:46:11 / 10-23 08:47:01；预核报告发现 1 |
| 4 | SyncLock 吸收复位后重复派发（`sync_via_celery` 0.007s 秒回 skipped），终态写回自愈——**无实害但每晨一条 WARNING 稀释真僵尸信号** | tasks.py:875-877 + journal 10-22 08:46:11 双 sync_via_celery 行 |
| 5 | okx_perp_daily 运行 ~59s 不跨轮，幸免 | journal 10-23 08:48:02 |

批 116 已上产（观察窗内）；批 83b async 通道现行；僵尸复位机制本身（A2 修复）不动。

## 产出

1. **engine.py `_mark_running`（:217-221）**：running=True 分支 UPDATE 同时刷 `last_sync_ts=now()`（单条 SQL：`SET last_status='running', last_sync_ts=now()`）；running=False 分支不动（终态由 `_update_sync_state` 随后覆盖，G-S2 顺序既有测试锁死）。
2. **tasks.py 僵尸判定（:782-802）**：注释补两行——「running 心跳锚点=置位/运行中刷新的 last_sync_ts（批 144）」+「last_sync_ts 语义=活跃时刻（running 中=置位时刻，DataManage「同步时间」列同此），防误当前端 bug（盲审 A-P1）」；判定逻辑本身零改动（ts 锚点对齐后 >7200s 语义即恢复「进程已死」本义）。
3. **回归钉（tests/）**：①`_mark_running(True)` 断言 UPDATE 语句含 last_sync_ts=now()（mock conn 捕 SQL）；②模拟「running + ts=23h 前」仍判僵尸复位（真僵尸不漏）；③「running + ts=10min 前」不再复位（本修目标态）。

## 限定范围

改：engine.py（_mark_running 一处）、tasks.py（注释）、tests/。**不碰**：僵尸阈值 7200s、SyncLock、_SYNC_ASYNC_DISPATCH、_update_sync_state 写序、调度器其余判定。

## 接口契约

- `_mark_running(sync_id: str, running: bool) -> None`（签名不变；行为变更=running 分支同刷 last_sync_ts）。
- 读写表：sync_config（UPDATE last_status/last_sync_ts）。
- 回滚：git revert（纯代码小批，无迁移无 DB 副作用）。
