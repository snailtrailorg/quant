# 批30 · 通知用户化+手机号+QR 倒计时修

> 2026-09-16 立项。用户三条裁定：**①系统通知只选用户（被选者邮箱/手机/IM 即通道，可多选，可用就发不可用不发，删用户自动出列表）②手机号短信验证码验证成功才改（对齐批20 邮箱先例）③多 bot 全发**。
> 三通道底数：smtp ✅（批7）/阿里云短信 ✅（批7，凭证 system_config）/用户 bot ✅（五轮后全用户化）。

## 一、现状与断点

| 项 | 现状 | 断点 |
|---|---|---|
| 订阅模型 | `alert_channel_sub(channel, target, categories, min_level, enabled)` 行级通道订阅（alerts.py:75-110 行 CRUD；AlertSettings.vue 选通道填目标） | 用户裁定改**选用户**——用户的三通道自动展开 |
| dispatch | `_load_channels()` 读表（dispatch.py:289-302）→ 逐行 `_send_one`（im=bot_id/email=地址/sms=手机号），三通道 Celery+claim 防双发+writeback 审计（批7 终态） | 展开层换用户 fan-out，通道层复用 |
| 手机号 | users 无 phone 列（0001 建，0003 加 email） | 迁移+验证码链路全新 |
| 验证码短信 | sms.py `send_sms(phone, level, title)` 钉告警模板 | 需独立验证码模板+发送函数 |
| QR 倒计时 | Profile.vue `startQrCountdown(expireAt)` 闭包捕获调用时 deadline（:490）；resume/BUSY 路径硬编码 600_000（:526/:554）；poll 的 d.ttl 真值只更新外层变量（:573）**可见倒计时永不校准** | 闭包改读活变量+占位值钳上界 |

## 二、子项

### 30-1 迁移 0080（数据面）
- `users` ADD `phone TEXT NULL`（不设唯一——同号多用户各收各的，通知按用户走）
- CREATE `alert_user_sub(id, user_id INT NOT NULL REFERENCES users(id), categories jsonb NOT NULL DEFAULT '[]', min_level TEXT NOT NULL DEFAULT 'warn' `**`CHECK (min_level IN ('warn','critical'))`**`（A-P2-4 保形旧表 0061 约束）`, enabled BOOLEAN NOT NULL DEFAULT true, created_at/updated_at timestamptz DEFAULT now(), UNIQUE(user_id))`
- **存量迁移**（im 行→owner）：`INSERT INTO alert_user_sub(user_id, categories, min_level, enabled) SELECT DISTINCT ON (b.owner_user_id) b.owner_user_id, a.categories, a.min_level, a.enabled FROM alert_channel_sub a JOIN im_bot_config b ON b.id::text=a.target AND a.channel='im' `**`JOIN users u ON u.id=b.owner_user_id`**`（A-P2-3：防御孤儿 owner 触 FK violation）` WHERE a.channel='im' `**`ORDER BY b.owner_user_id, a.id`**`（A-P1-1：DISTINCT ON 确定性） ON CONFLICT (user_id) DO NOTHING`；email/sms 行**不迁**（GET 响应带 legacy 清单提示 admin 自行转移）
- 旧表 `alert_channel_sub` **保留不读写**（非破坏优先——DROP 属破坏性 DDL 门拦截项，清理列下批）
- downgrade：DROP alert_user_sub + users DROP phone
- **复杂 SQL 离线冒烟测不出（A-P2-2）——staging 真库 up/down 由管道彩排覆盖，验收含此项**

### 30-2 后端订阅面（alerts.py）
- GET `/api/alerts/config` → `{subs:[...], users:[...], sms_configured, legacy:[{channel,target（_mask 脱敏）}]}`
- POST/PUT/DELETE 行级 CRUD 保形，target 换 `user_id`（校验用户存在且未软删）；**行数上限=全表 10 行（=最多 10 个订阅用户，per-channel 概念消失）**；前端"多选用户"= 循环 POST（B-P2-6，不做批量端点）
- **`/api/alerts/test` 端点适配（B-P1-1）**：原按单行 channel/target 测——改按订阅行用户的三通道各发一条测试（email 有则测邮箱/sms 有且配则测手机/名下 bot 逐个测），返回逐通道结果
- **短信凭证维护面扩展（B-P1-3②）**：`PUT/GET /api/alerts/sms-config` fields 加 `alert_sms_verify_template_code`（进 LIKE 'alert_sms_%' 面、**不入 `_CFG_KEYS` 四键 all() 校验**——防告警 sms_configured 被未配 verify 键误伤）
- 权限键 `alerts_config` 不变

### 30-3 dispatch fan-out（dispatch.py）
- `_load_channels()` → `_load_user_targets()`：
  ```sql
  SELECT s.user_id, s.categories, s.min_level, u.email, u.phone
  FROM alert_user_sub s JOIN users u ON u.id=s.user_id
    AND u.enabled AND u.deleted_at IS NULL WHERE s.enabled
  ```
  + `SELECT owner_user_id, id FROM im_bot_config WHERE enabled AND owner_user_id IS NOT NULL` → per 用户展开 targets：email 行（u.email 非空；smtp 未配=跳过+日志）、sms 行（u.phone 非空且 sms_configured；否则跳过）、im 行（**名下每个 enabled bot 全发**——裁定③）
- **展开行结构契约（A-P0-3+B-P1-2——dispatch.py:330-339 `row.get("id")` 缺失/同键=节流互撞+dkey 回写互覆+claim 失败连首行都不发）**：行字段 `{channel, target, categories, min_level, id, sub_id}`——**email/sms 行 id=user_id、im 行 id=bot_id**（同用户 5 bot=5 行各自唯一，保证 (ch,id) 全局唯一）；**sub_id=alert_user_sub 行 id**（供 worker 重查，配套 30-3b）
- 软删/停用用户 JOIN 过滤=**自然出列表**（裁定①删用户语义）
- `_send_one/_send_im/_send_email/_send_sms/claim/writeback/throttle/quota` 机制零改动（"通道层复用"指此层；实改面=dispatch.py+alert_tasks.py 两文件——A 总评修正）

### 30-3b worker 重查表切换（scheduler/alert_tasks.py，A-P0-2）
- `_still_enabled`（:30-42）现硬查 `alert_channel_sub`——新表切换后用 sub_id 查 **alert_user_sub**（展开行带 sub_id）；不切则新环境旧表空 → fetchall 空 → 全部 skip:disabled → **三通道全灭**；存量环境两表 id 撞行随机误杀/误放
- **fallback 分支删除（A-P1-2 裁定）**：dispatch.py:310-323"零 enabled 订阅→legacy webhook 外推"过渡兜底随切表退役（用户化终态：零订阅=不外推；防新表空环境重燃已失效 webhook）
- 测试补断言 `_still_enabled` 查询的表名（防回归）

### 30-4 手机号+验证码（后端）
- `sms.py` 加 `send_sms_code(phone: str, code: str) -> tuple[bool, str]`——模板键 **`alert_sms_verify_template_code`**（B-P1-3：带前缀进 `_sms_config()` LIKE 面；单独 SELECT 读该键+复用 `_sms_config()` 基础凭证；未配置=NOT_CONFIGURED；参数 `{"code": ...}`；复用 dysmsapi 签名 V1 通道）
- `auth_routes.py` + **`models.py`（B-P1-5：PhoneCodeReq/PhoneChangeReq pydantic 模型）**（批20 先例同构，require_authenticated）：
  - POST `/api/user/phone-request`：body `{phone, current_password}`——**密码验证（B-P1-4/A-P1-6：批20 邮箱先例验密码；不验=被盗会话可改他人通知手机+向任意号码发短信）**→ 格式校验（**`_PHONE_RE` 从 alerts.py import——A-P2-5 防第二份漂移**）→ 频控（`_RATE_RULES` 加 `phonechg: (3, 3600)`，桶键=str(uid) + 60s 发码间隔键）→ 6 位码，**Valkey `phone:chg:{uid}` 值存 `{code, phone}`（A-P0-1：码绑死手机号——request 收码手机即落库手机，change 端点从存侧取 phone 不收 body，批20"token 绑 email"同构；原方案 body 带 phone=验证语义空洞）** TTL 300s → send_sms_code
  - POST `/api/user/phone-change`：body `{code}`——**`secrets.compare_digest` 比对（A-P2-7 防时序逐位爆破）+ 码错 5 次作废（A-P1-6，Valkey 计数）**→ 码对→单事务 UPDATE users.phone=**存侧 phone**（审计 `phone_change`，old/new 脱敏）→ 作废码；码错/过期→400 `PHONE_CODE_INVALID`
  - web 侧 Valkey 走 **`redis_pool.redis_client()`**（A-P2-7：批27-2"新建连接池才是泄漏源"教训）
- `/api/user/profile` 响应加 `phone`（本人资料不脱敏；me 端点不加——对齐 email 先例不回）
- **用户前置（外部 gate，不阻塞编码）**：阿里云控制台创建验证码短信模板（**正文过文案师**，初稿：`您的验证码为${code}，5分钟内有效。若非本人操作请忽略。`）→ 模板 Code 填入设置→告警→短信凭证区新字段 `sms_verify_template_code`

### 30-5 前端
- `AlertSettings.vue`：订阅表改用户维度（用户下拉多选出多行/每行=用户+类别+级别+开关；channels 可用性 chips 展示"邮箱✓ 短信✗ 机器人×2"）；legacy 清单横条提示
- `Profile.vue`：信息台加手机行（无→"未设置"）+修改弹窗（**emailChgDlg 骨架参照**——批20 为邮件链接确认模式非验证码先例，phone 弹窗=输号+密码→发码→填码提交+60s 防重发，全新逻辑）——**词条过文案师（B-P2-9 三处：弹窗词条/err.PHONE_CODE_INVALID 词条/验证码短信正文）**
- **30-6 QR 倒计时修（Profile.vue）**：`startQrCountdown` tick 改读活变量 `pollDeadline`（d.ttl 校准自动生效——**顺带修真 bug**：resume 首查时 qrImg 尚空 → :574 `if(qrImg)` 不重启倒计时=恢复路径校准失效；改活变量后 :574 重启冗余可顺手删）；**占位/钳上界用 3600（A-P2-1：900 是 pending 键 TTL 非 SDK 真值——scanning 会话 expire_in 可达 ~1h，钳 900 会在首查慢时 pollDeadline 低估 → pollQr 提前自杀翻 timeout）**；startQr `expire_in` 钳 `min(expire_in||600, 3600)`

## 六、风险与已知
- 验证码模板外部 gate：未配置时 phone-request 返 NOT_CONFIGURED（清晰指引），不阻塞其他子项
- 多 bot 全发的扇出：单用户 5 bot×一条告警=5 条 IM（用户裁定接受；throttle/quota 面已有 INCR 配额兜底）
- legacy email/sms 订阅行不自动迁移——GET 带 legacy 清单，admin 手动转移后下批清理旧表
