# 多资产量化数据中台架构升级方案（V3.0 - 含细粒度限流治理）

> **文档版本**：V3.0  
> **核心目标**：在“三通道”数据管道基础上，引入**元数据驱动**、**数据域垂直切分**，并构建**声明式细粒度限流治理层**，实现多市场稳定接入，杜绝因限流导致的卡顿、锁死或账户封禁。

---

## 1. 架构全景回顾与限流挑战

当前架构（通道 A/B/C）已解决数据搬运问题，但**限流（Rate Limiting）是平台稳定性的头号风险**：

- **账户安全**：超限可能导致 API Key 封禁或降权（尤其 Tushare/OKX 计费严格）。
- **多维度细粒度**：限流针对 `(数据源, 接口名, 批量大小, 时间窗口)` 组合，无法用单一全局变量处理。
- **多实例竞争**：横向扩展时，本地内存限流失效，必须共享配额。

**设计铁律**：**限流逻辑绝对不写死在 Adapter 的 `pull_*` 函数内部，全部外置为可热加载的配置项。**

---

## 2. 四层元数据模型（数据资产抽象）

为支撑多市场，首先建立元数据注册中心（存入 PG），作为所有上层业务的基础。

| 层级 | 实体名 | 关键属性 | 示例 |
| :--- | :--- | :--- | :--- |
| **L1 接口层** | `DataGateway` | 连接配置、限速策略、状态 | `TUSHARE_PRO`, `OKX_PUBLIC` |
| **L2 交易场所** | `TradingVenue` | 时区、日历类型（`CN_23H`/`24X7`） | `SSE`, `OKX_VENUE` |
| **L3 资产大类** | `AssetClass` | 是否复权、是否到期、合约类型 | `EQUITY`, `CRYPTO_SWAP` |
| **L4 具体标的** | `Instrument` | 全局 URN、名称、到期日 | `SSE.EQUITY.600036`<br>`OKX_VENUE.CRYPTO_SWAP.BTC-USD` |

全局唯一标识符：`{Venue}.{AssetClass}.{LocalCode}`，策略配置全部使用此 URN。

---

## 3. 数据域垂直切分（Domain-Oriented）

按业务属性划分独立域，通过 `Instrument` 关联，避免宽表爆炸。

| 数据域 | 表族 | 适用 AssetClass | 存储介质 |
| :--- | :--- | :--- | :--- |
| **OHLCV** | `bar_{freq}` | 全市场 | PG（历史）+ Valkey（实时） |
| **复权因子** | `adj_factor` | 仅 EQUITY/ETF | PG |
| **财务/基本面** | `financial_*` | 仅 EQUITY | PG（列存） |
| **衍生品特有** | `funding_rate`, `open_interest` | 仅 CRYPTO_SWAP/FUTURES | PG + Valkey |
| **标的主数据** | `instrument_meta` | 全市场 | PG + Redis 缓存 |

域注册表（配置化）用于前置校验和适配器任务生成，硬编码仅此一处。

## 4. 细粒度限流治理层（Resilience Layer）

这是本次升级的核心韧性组件，独立于数据管道，通过声明式配置驱动。

### 4.1 配置层次（四级优先级覆盖）

配置存储于 PG 表 `rate_limit_config`，支持 JSON Schema 和热加载。

| 优先级 | 层级 | 作用域 | 示例 |
| :--- | :--- | :--- | :--- |
| 1（最低） | **全局默认** | 所有 Gateway | `default_qps: 0.5` |
| 2 | **Gateway 级** | 特定数据源 | Tushare 总 QPS=5，OKX=20 |
| 3 | **API/Endpoint 级** | 特定接口（最核心） | `stk_mins: 1/3600s`，`adj_factor: 1/0.3s` |
| 4（最高） | **动态覆盖规则** | 特定时段/标的列表 | 盘后乘数 2.0，VIP 标的 100 QPS |

### 4.2 限流器引擎（分布式令牌桶 + 滑动窗口）

- **存储**：Redis（原子 INCR + EXPIRE），实现多实例配额共享。
- **算法**：滑动窗口（Sliding Window），避免固定窗口边界突刺。
- **原子操作**：Lua 脚本一次性完成“检查 + 扣减 + 记录过期”，杜绝竞态。

### 4.3 智能退避与熔断（防止雪崩）

限流不只是 sleep，需引入三层递进保护：

| 触发条件 | 动作 | 退出机制 |
| :--- | :--- | :--- |
| **首次 429 / LimitExceeded** | 睡眠 `retry_after` + 10% jitter | 正常恢复 |
| **连续失败 > 3 次** | 指数退避（2s → 8s → 30s） | 连续成功 1 次重置 |
| **连续失败 > 10 次（熔断）** | **Open 状态**：直接快速失败，报错给 Engine | 定时半开探测（Half-open） |

### 4.4 舱壁隔离（Bulkheading）

防止一个接口的阻塞拖垮全部。按 `(Gateway, Endpoint)` 维度维护**独立的令牌桶**和**独立的信号量（max_concurrent）**。在配置中可分别设定并发上限。

### 4.5 Adapter 零侵入调用

Adapter 内不再硬编码 `time.sleep`，而是**声明式使用上下文管理器**：

```python
class TushareAdapter:
    def pull_daily(self, symbols, start, end):
        with RateLimitContext(gateway="TUSHARE_PRO", endpoint="stk_mins", symbols=symbols):
            return self.client.daily(ts_code=symbols, ...)
```

`RateLimitContext` 自动拆分批量、扣除配额、处理重试和熔断异常，上层 Engine 只需捕获 `CircuitBreakerError` 做统一调度。

### 4.6 配置热加载（无需重启）

后台线程监听 `rate_limit_config` 表的 `updated_at`（或利用 PG NOTIFY/LISTEN），检测到变更后原子替换内存配置，`acquire` 立即生效。

## 5. 跨市场差异化适配（由元数据驱动）

| 维度 | A股（XTP/Tushare） | 加密币（OKX） | 框架内统一机制 |
| :--- | :--- | :--- | :--- |
| **交易日历** | 仅工作日 9:30-15:00 | 7×24 | `TradingVenue.calendar_type` 决定调度切片 |

| **衍生品独有** | 无 | 资金费率、持仓量 | 单独域 `DERIVATIVE_METRICS`，策略显式订阅 |
| **合约到期** | 永续 | 有 `expiry_date` | 回测自动过滤过期合约 |
| **代码体系** | `000001.SZ` | `BTC-USDT-SWAP` | 全局 URN 统一标识 |

## 6. 通道改造要点（与限流集成）

- **通道 A（历史批处理）**：`sync_all` 根据 `Instrument.AssetClass` 动态生成任务列表，每个任务通过 `RateLimitContext` 包裹，限流配置决定并发和 QPS。
- **通道 B（实时流）**：替换具体 Session 实现（如 OKX WebSocket），但保持五层骨架。限流主要用于 WebSocket 订阅数限制（配置 `max_subscriptions`），由 Session 层在连接前检查。
- **通道 C（影子）**：共享同一限流引擎，但可配置独立配额（如影子链路限流更宽松），通过不同的 `endpoint` 名称区分。

## 7. 可观测性与告警（必备）

限流器必须暴露以下 Prometheus 指标：

| 指标名 | 含义 | 告警阈值 |
| :--- | :--- | :--- |
| `rate_limit_acquire_wait_seconds` | 获取令牌等待时长（P99） | > 5s 严重 |
| `rate_limit_circuit_open` | 熔断器是否打开（0/1） | 1 触发紧急 |
| `rate_limit_remaining_tokens` | 当前窗口剩余配额 | < 10% 预警 |
| `rate_limit_concurrent_usage` | 当前并发数 / `max_concurrent` | > 80% 预警 |

集成 Grafana 看板，运维可实时查看各 Gateway 配额使用率。

## 9. 总结

> **限流即配置，配置即代码；元数据定义资产，数据域划分边界。**

1. **开发侧**：写 Adapter 时只需标记 `endpoint` 名，限流数值全在配置中，无需硬编码。
2. **运维侧**：修改 `rate_limit_config` 表，服务实时生效，无需发布代码。
3. **架构侧**：分布式令牌桶保证多实例一致性，熔断器保护账户安全，舱壁隔离防止接口间互相影响。

此方案落地后，即使未来引入新数据源（如 Wind、币安），只需增加配置行和元数据记录，**核心管道、策略、回测代码保持零改动**，真正实现多资产、多市场的一体化数据中台。

## 评审记录（2026-08-27，Bernard + Claude）

> 本文档为外部参考（AI 生成的通用方案），非本平台架构决策。以下是对照代码库实况的逐节评审结论。

### ✅ 说对（可吸收）
- 限流逻辑不硬编码在 Adapter pull_* 内——方向正确（我们已部分做到但未完全）
- stk_mins 1/3600s / adj_factor 1/0.3s——数值与 data_source.py DEFAULT_RATE_LIMITS 一致
- XTP 实时流不走 HTTP 限流——判断正确（TCP 长连接 SDK，限流应在 Session 层）
- RateLimitContext 声明式上下文管理器——好模式，立项吸收
- 配置热加载无需重启——好实践（risk_rules 60s 热加载先例）
- 熔断+舱壁隔离——成熟模式（LLM 网关有熔断先例，数据管道缺）

### ❌ 说错（与代码实况不符）
- "多实例竞争，本地限流失效"——我们是**单服务器 1.8G RAM**，不存在多实例场景
- "PG（列存）"——PG 是行存数据库，非列存
- `common/config_loader/`/`common/rate_limiter/`——目录不存在（我们用 `quant_common`）
- `financial_*` 表族名——实际叫 income/balancesheet/cashflow/fina_indicator（tier_tables.py）
- `instrument_meta` 表——不存在（有 static_symbols + stock_basic）
- Phase 排序矛盾——§2 说元数据是基础，Phase 4 才建

### ⚠️ 过度设计（方向对但规模不对——YAGNI）
- 四层元数据模型（DataGateway/TradingVenue/AssetClass/Instrument URN）——单市场不需要
- Redis 分布式令牌桶+Lua 原子脚本——单实例 Valkey INCR+EXPIRE 足够
- Grafana 看板——/metrics 有 Prometheus 格式但 Prometheus server 未部署
- 动态覆盖规则（VIP 标的 100 QPS）——无 VIP 场景

### 立项（见 flow/待办.md 常规线第 5 条）
做三件：RateLimitContext 声明式限流 / 三级覆盖扩展 / 数据源熔断器。
不做三件（有理由）：四层元数据（等第 2 市场）/ 分布式限流（等第 2 实例）/ Grafana（等 SM1）。
