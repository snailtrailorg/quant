# 量化交易系统菜单重构方案（通用化设计版）

## 一、设计理念

### 核心原则
- 通用化优于具体化：菜单命名代表"能力分类"，而非"具体实现"
- 职责单一、边界清晰：每个模块只做一类事情，不混杂
- 配置与技术解耦，业务与实现隔离：接入配置归系统设置，业务使用归交易管理
- 预留扩展能力：即使当前只实现了一个具体服务（如飞书、Tushare），菜单设计也要能容纳同类服务的扩展

## 三、各子菜单详细设计

### 3.1 交易管理 → 数据源管理（业务视角）

职责：管理"业务上要用哪些数据、怎么用"，关注数据内容的完整性和时效性

核心功能：
- 数据表同步任务列表（表格形式）
  - 字段：数据表名、数据源来源、同步频率、当前状态、数据延迟、最后同步时间、手动触发按钮
- 新增同步任务
  - 选择数据源 → 选择数据表 → 配置同步频率（定时/实时）→ 配置同步策略（增量/全量）
- 数据源健康状态总览
  - 各数据源连接状态、今日同步量、API调用量、日限额使用率
- 同步日志
  - 最近24小时同步记录、失败重试情况

设计要点：
- 所有数据源（Tushare/Wind/聚宽等）在此统一管理同步任务
- 新增数据源只需在"选择数据源"下拉中增加选项，无需改动页面结构
- 数据延迟监控帮助用户判断"当前数据是否可用于交易"


### 3.2 交易管理 → 后台任务管理（新增核心模块）

职责：统一监控所有异步长时业务任务，提供任务级别的控制与故障定位能力

任务列表（关键字段）：
| 字段 | 说明 | 示例 |
|------|------|------|
| 任务ID | 唯一标识，可复制用于排查 | task_20260809_001 |
| 任务名称 | 业务可读名称 | 回测_策略Alpha_v3_2026Q2 |
| 任务类型 | 标签化展示 | 回测 / 数据同步 / 交易执行 / AI分析 |
| 触发方式 | 手动/定时/事件触发 | 手动 / 定时每日15:00 |
| 当前进度 | 进度条 + 百分比 + 当前步骤描述 | 75% (处理第1500/2000只股票) |
| 状态 | 带颜色标识 | 运行中 / 排队中 / 已完成 / 失败 / 已终止 / 已暂停 / 疑似卡死 |
| 开始时间/运行时长 | 任务启动时间与已运行时间 | 2026-08-09 10:23:15 / 1h 23min 45s |
| 操作 | 根据状态动态展示按钮 | [暂停] [继续] [终止] [重试] [强制删除] [查看详情] [日志] |

任务详情页（故障定位核心）：
- 基本信息（名称、类型、触发人、时间、状态、进度）
- 执行参数（策略ID、回测区间、股票池等业务参数）
- 实时状态（当前执行步骤、最后一条日志、当前执行的SQL/API调用、资源占用CPU/内存/连接池、子任务进度）
- 操作按钮（暂停/继续/终止/重试/强制删除/导出日志/刷新）
- 执行日志（实时滚动显示）

任务状态流转：
提交任务 → 排队中 → 运行中 ⇄ 已暂停 → 已完成
                          ↓
                      失败 → 重试 → 运行中
                          ↓
                      已终止 → 强制删除（卡死时清理）

卡死检测机制：
- 系统后台巡检进程定期检查所有 status='running' 的任务
- 如果 last_heartbeat 超过阈值（如5分钟未更新），自动标记为"疑似卡死"并在前端高亮提示
- 用户可对卡死任务执行"强制删除"（二次确认 + 操作日志记录）

权限设计：
- 普通用户：只能看到自己创建的任务
- 管理员：可查看所有任务，可执行终止/删除操作

与系统运维的职责边界：
| 对比项 | 后台任务管理（交易管理） | 系统运维（系统设置） |
|--------|------------------------|---------------------|
| 关注对象 | 业务任务（回测/交易/数据同步/AI分析） | 系统服务（数据库/消息队列/策略引擎/网关） |
| 用户视角 | "我的回测跑完没？卡在哪了？" | "系统服务还活着吗？响应慢不慢？" |
| 操作粒度 | 任务级别（暂停/终止/重试具体任务） | 服务级别（重启服务、扩缩容） |
| 故障定位 | 看任务日志、当前执行SQL/API | 看服务指标（CPU/内存/QPS/错误率） |

### 3.4 交易管理 → 审计日志

职责：交易操作全链路追溯（保持现有功能，仅做菜单归类）


### 3.5 系统设置 → 用户与权限

职责：用户、角色、权限管理（保持现有功能）


### 3.6 系统设置 → 数据服务（技术视角）

职责：管理所有数据源的技术接入层配置，与交易管理的"数据源管理"（业务层）严格分离

核心功能：
- 已接入数据源列表
  - 每个数据源显示：名称、接入状态、连接测试按钮、启用/停用开关
  - 配置参数（按数据源类型动态展示）：
    - 通用参数：API Key/Token、Base URL、超时时间、重试策略、代理配置
    - 各数据源特有参数按需展示
- 用量监控（关键新增）
  - 今日调用量 / 日限额（进度条展示）
  - 本月调用量 / 月限额
  - 峰值QPS / 限制QPS
  - 各接口调用分布（饼图/柱状图）
  - 调用趋势（近7天折线图）
- 预警配置
  - 日限额预警阈值（如达到80%时触发）
  - 月限额预警阈值（如达到70%时触发）
  - 异常调用告警（如单次拉取数据量超过阈值）
  - 告警通知渠道绑定（飞书/邮件等，复用AI服务平台的消息通道）
- 全局数据服务设置
  - 数据更新超时阈值
  - 数据质量校验开关（异常值检测、字段完整性）
  - 数据存储策略

设计要点：
- 新增数据源（如Wind）只需在列表中添加一行配置表单，无需新增菜单
- 用量监控UI模板可复用，仅数据源不同
- 流量耗尽时自动关联后台任务管理中的任务失败状态


### 3.7 系统设置 → AI服务平台

职责：统一管理AI能力（模型层 + 输出层 + 用量监控），消息通道作为AI的输出渠道归属本模块

三大子模块：

（1）模型管理
- LLM模型配置列表（支持多模型并存：GPT-4/Claude/通义千问/文心一言等）
- 每个模型配置：API Key、Base URL、Temperature、Max Tokens、超时时间
- 默认模型设置（不同场景使用不同模型的映射规则）
- 调用统计（Token用量、请求次数、成本、响应时间）

（2）消息通道（AI输出层）
- 统一消息通道列表（表格形式）
  - 飞书 [已启用] [配置Webhook/签名] [测试]
  - 企业微信 [未启用] [配置] [测试] ← 预留
  - 钉钉 [未启用] [配置] [测试] ← 预留
  - 微信 [未启用] [配置] [测试] ← 预留
  - WhatsApp [未启用] [配置] [测试] ← 预留
  - 邮件 [未启用] [配置] [测试] ← 预留
  - 短信 [未启用] [配置] [测试] ← 预留
- 新增消息通道时，只需在列表中添加一行配置表单
- 消息发送接口抽象：send(channel, title, content, level, receivers)

（3）用量监控与预算管理
- 用量总览（今日/本月）
  - 各模型请求次数、Token消耗（输入/输出拆分）、预估成本
- 成本详情
  - 月度预算使用进度（进度条）
  - 各场景调用分布（策略分析/风控告警/智能问答等）
  - 调用趋势（近7天折线图）
  - 平均响应延迟（P50/P95/P99）
- 预算与预警配置
  - 月度预算总额
  - 预算预警阈值（如达到80%时触发）
  - 单次Token上限（避免单次调用成本过高）
  - 日请求上限（避免滥用）
  - 预警通知渠道绑定（复用消息通道）

场景路由（AI输出 → 消息通道的绑定）：
- 风控告警 → 飞书（紧急） + 邮件（记录）
- 策略建议 → 飞书（仅指定人）
- 系统异常 → 飞书 + 短信
- 日报总结 → 邮件

设计要点：
- 消息通道不是独立模块，而是AI平台的能力输出层，统一在AI服务平台下管理
- 新增消息通道只需实现统一接口，无需改动上游业务代码
- 预算耗尽时自动影响相关AI任务的执行，并在后台任务管理中体现为"任务失败"


### 3.8 系统设置 → 交易通道

职责：统一管理各交易所/券商/机构的API网关配置（保持现有功能，建议将XTP/欧易/币安等统一整合到此菜单下）


### 3.9 系统设置 → 系统运维

职责：系统级服务状态监控与运维操作（保持现有功能，建议逐步增强可观测性能力）


## 四、跨层联动设计（关键）

### 4.1 数据服务流量监控 ↔ 后台任务管理

数据服务：Tushare日限额耗尽
        ↓
触发预警（飞书/邮件通知）
        ↓
数据同步任务失败（任务状态变为"失败"）
        ↓
后台任务管理列表高亮显示失败任务
        ↓
用户点击查看任务详情 → 失败原因："数据源限额耗尽"
        ↓
用户决策：调整同步频率 / 扩展限额 / 切换数据源

### 4.2 AI服务用量监控 ↔ 后台任务管理

AI服务：月度预算耗尽
        ↓
触发预警（飞书/邮件通知）
        ↓
AI分析任务失败（任务状态变为"失败"）
        ↓
后台任务管理列表高亮显示失败任务
        ↓
用户点击查看任务详情 → 失败原因："AI预算耗尽"
        ↓
用户决策：增加预算 / 切换更便宜的模型 / 减少调用频率

### 4.3 统一告警通知（消息通道复用）

所有监控项的告警（数据限额预警、AI预算预警、系统异常告警、风控告警）统一通过AI服务平台配置的消息通道发送，避免多处配置通知渠道。


## 五、通用化设计对照表

| 原菜单名称 | 问题 | 新菜单名称 | 通用化设计要点 |
|-----------|------|-----------|---------------|
| 风控 | 太笼统 | 风控规则 | 明确为规则配置，非实时监控 |
| 对账报告 | 像结果文件 | （归入资产管理，本方案暂未展开） | 强调核对动作，非静态报告 |
| 数据同步 | 技术术语，且混杂了接入配置 | 数据源管理（业务层） | 业务关注"同步哪些数据"，非同步机制 |

## 七、设计原则总结

| 原则 | 说明 |
|------|------|
| 关注点分离 | 接入配置（系统设置）与业务使用（交易管理）严格分离，运维人员和交易员各司其职 |
| 通用化抽象 | 菜单命名代表"能力分类"，新增具体实现（如新增消息通道/数据源/AI模型）不需要修改菜单结构 |
| 统一入口 | 同类能力集中管理（所有数据源接入在一个页面、所有消息通道在一个页面），避免配置散落各处 |
| 状态可视化 | 所有有状态的对象（任务、数据同步、服务）都必须有清晰的进度/状态展示 |
| 故障可定位 | 业务任务卡死时，用户能快速看到"卡在哪一步、当前在执行什么SQL/API" |
| 操作可控 | 用户有权对卡死任务执行强制删除，避免僵尸任务长期占用资源 |
| 跨层联动 | 底层监控预警（数据限额/预算耗尽）→ 上层任务失败 → 用户感知，形成完整闭环 |
| 权限隔离 | 普通用户与管理员的操作范围分离，符合安全合规要求 |
| 预留扩展 | 当前只实现了飞书/Tushare/LLM，但UI和代码层面要为微信/钉钉/Wind/Claude等预留扩展能力 |


## 八、附录：数据表结构建议（供开发参考）

### 后台任务表（tasks）
| 字段名 | 类型 | 说明 |
|--------|------|------|
| id | VARCHAR(64) | 任务唯一ID |
| name | VARCHAR(255) | 任务名称 |
| type | VARCHAR(32) | 任务类型枚举：backtest/trade_sync/data_sync/ai_analysis |
| trigger_type | VARCHAR(16) | 触发方式：manual/schedule/event |
| trigger_user | VARCHAR(64) | 触发人（手动时）或系统（定时/事件时） |
| status | VARCHAR(16) | 状态：queued/running/paused/completed/failed/terminated/stuck |
| progress | JSON | 结构化进度信息（当前步骤、总步骤、百分比、子任务状态等） |
| params | JSON | 任务执行参数（策略ID、回测区间、股票池等） |
| last_heartbeat | DATETIME | 最后一次心跳时间（用于检测卡死） |
| pid | INT | 进程ID（用于强制kill） |
| error_message | TEXT | 失败时的错误信息 |
| start_time | DATETIME | 开始时间 |
| end_time | DATETIME | 结束时间 |
| created_at | DATETIME | 创建时间 |
| updated_at | DATETIME | 更新时间 |

### 任务日志表（task_logs）
| 字段名 | 类型 | 说明 |
|--------|------|------|
| id | BIGINT | 自增ID |
| task_id | VARCHAR(64) | 关联任务ID |
| level | VARCHAR(8) | 日志级别：INFO/WARN/ERROR/DEBUG |
| message | TEXT | 日志内容 |
| step_name | VARCHAR(64) | 当前执行的步骤名称 |
| sql_or_api | TEXT | 当前执行的SQL或API调用（用于故障定位） |
| resource_usage | JSON | 资源占用快照（CPU/内存/连接池等） |
| created_at | DATETIME | 日志时间 |
