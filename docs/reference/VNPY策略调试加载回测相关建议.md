# 系统设计方案：基于 vnpy + XTP 的 Web 量化中台

## 1. 总体架构设计（前后端分离）

| 层级 | 技术选型/实现 | 职责 |
| :--- | :--- | :--- |
| **前端展示层** | Vue 3 / React + TypeScript + ECharts | 策略编辑、回测配置、实盘看板、图表渲染 |
| **网关接口层** | Nginx + WebSocket | 转发 HTTP 请求，维持行情/成交的实时推送 |
| **核心业务层** | Python 3.10 + vnpy 核心库（无界面模式） | 调度策略、管理订单、路由请求 |
| **策略执行层** | 独立子进程（Subprocess） | **进程隔离**运行用户策略，防止崩溃影响主引擎 |
| **数据服务层** | ClickHouse / MongoDB + Parquet 文件 | 存储海量历史 Tick/Bar 数据，供回测与独立调试使用 |
| **柜台接入层** | XTP Gateway（vnpy 官方接口） | 仅实盘运行时加载，连接中泰证券柜台 |

---

## 2. 策略开发与调试模块（“沙箱”模式）

**核心原则：策略逻辑与 vnpy 引擎完全解耦。**

### 2.1 代码组织结构
project/
│
├── strategy_core/               # 纯计算核心（不引入 vnpy）
│   ├── base.py                  # 定义策略基类（纯 Python）
│   └── boll_channel.py          # 布林带策略逻辑（只依赖 pandas/numpy）
│
├── vnpy_adapters/               # vnpy 适配层（薄封装）
│   └── vt_adapter.py            # 将 BarData 转为 DataFrame，调用核心逻辑
│
├── research/                    # 调试脚本（命令行专用）
│   └── debug_runner.py          # 直接读取 Parquet/DB 数据进行回放调试
│
└── strategies/                  # vnpy 官方策略目录（实盘/回测用）
    └── boll_vnpy_wrapper.py     # 继承 CtaTemplate，内部调用 strategy_core

### 2.2 命令行独立调试（完全不影响 vnpy 主进程）
- **操作方式**：直接在终端执行 `python research/debug_runner.py --symbol 000001`。
- **底层原理**：该脚本**绝不引入** `vnpy.trader` 或 `PyQt`，仅依赖数据分析库，运行在独立内存空间。
- **数据来源**：直接读取你的海量历史数据源（如 ClickHouse 或本地 Parquet），完全绕过 XTP 接口。
- **优势**：调试循环可达到毫秒级响应，且即使代码崩溃，也**丝毫不影响正在运行的实盘 vnpy 主引擎**。

## 3. 策略编辑与参数管理模块

### 3.1 策略文件定义规范
策略脚本遵循 vnpy 的标准类定义，**参数不写死，均可在 Web 端调节**：

```python
class BollChannelStrategy(CtaTemplate):
    # 参数（默认值仅作为基线，运行时可被前端传入值覆盖）
    bb_window = 20
    bb_dev = 2.0
    fixed_size = 100

    # 元数据声明（供 Web 前端自动生成表单）
    parameters = ["bb_window", "bb_dev", "fixed_size"]
    variables = ["pos", "mid_line", "up_line", "down_line"]
```

### 3.2 Web 界面交互逻辑
| 功能点 | 实现方案 |
| :--- | :--- |
| **动态表单生成** | 后端扫描 `strategies/` 目录，解析类的 `parameters` 列表，返回 JSON 结构，前端据此动态渲染输入框/滑块。 |
| **参数持久化** | 前端提交参数后，后端将其以 JSON 格式存入数据库（`strategy_instances` 表）。 |
| **版本管理** | 建议在数据库中保存参数修改的历史记录（`updated_at` 字段），便于回溯。 |

> **关键约束**：实盘环境不支持“热加载”。策略代码修改后，需重启对应的策略子进程（见第 5 节）。

## 4. 策略回测模块

### 4.1 动态加载机制
- 用户点击 Web 界面的“开始回测”按钮后，后端**启动一个独立子进程**。
- 该子进程内部通过 `importlib.import_module` **动态加载**策略文件，并传入用户在前端设定的参数。
- 回测数据源：从数据服务层拉取历史 K 线，注入 `CtaBacktestingEngine`。

### 4.2 参数优化（网格搜索）
- Web 界面支持设定参数范围（例如 `bb_window: 10~30，步长 5`）。
- 后端批量生成组合，循环提交回测。
- 结果按“夏普比率/收益率/最大回撤”排序，支持**一键应用到实盘实例**。

### 4.3 回测结果缓存
- 将回测任务记录存入数据库（`backtest_tasks` 表），包含参数快照、资金曲线 JSON、绩效指标。
- 便于用户随时查看历史回测报告，避免重复计算。

## 5. 实盘交易与进程隔离（解决热加载难题）

**痛点**：vnpy 原生不支持实盘策略热加载，修改代码必须重启整个 Trader。

**解决方案**：**策略进程隔离 + 冷重启策略**

| 模块 | 实现细节 |
| :--- | :--- |
| **主调度进程（Master）** | 只负责管理 WebSocket 连接、账户资金查询，不加载任何用户策略代码。 |
| **策略执行进程（Worker）** | 每个策略实例运行在**独立的子进程**中。该进程启动时才 `import` 策略文件。 |
| **修改策略/参数流程** | 1. 用户在 Web 修改代码或参数 → 保存至数据库。<br>2. 后端向对应子进程发送“停止”信号 → 进程销毁。<br>3. 后端立即新建子进程，加载最新代码和参数 → 重新订阅行情。 |
| **异常隔离** | 若策略代码有 `bug` 导致子进程崩溃，主进程会捕获退出信号并记录日志，**不影响其他策略实例和系统稳定性**。 |

## 6. 数据库设计建议（核心表）

| 表名 | 关键字段 | 说明 |
| :--- | :--- | :--- |
| `strategy_templates` | `id`, `class_name`, `file_path`, `params_schema` (JSON) | 存储策略类元数据，用于前端生成表单。 |
| `strategy_instances` | `id`, `template_id`, `instance_name`, `vt_symbol`, `param_values` (JSON), `status`, `pid` | 存储具体的策略实例及其当前参数，`pid` 记录子进程号用于监控。 |
| `backtest_tasks` | `id`, `instance_id`, `start_date`, `end_date`, `param_values` (JSON), `result` (JSON), `status` | 回测任务记录，便于结果追溯。 |
| `daily_quotes` | （时序数据库）`symbol`, `open`, `high`, `low`, `close`, `volume`, `datetime` | 历史行情数据表，用于回测和独立调试。 |

| 阶段 | 目标 | 关键产出 |

## 8. 总结与关键提醒

1. **绝对隔离**：实盘主引擎与策略代码严格隔离，杜绝单点崩溃风险。
2. **参数即数据**：策略参数作为数据管理，前端不写死，后端不硬编码，全部存库。
3. **调试自由**：利用海量数据在命令行独立调试，秒级迭代且零影响。
4. **热加载替代**：用“子进程冷重启”巧妙绕过 vnpy 原生热加载限制。

这套设计方案完全基于我们讨论的痛点和目标量身定制，既充分发挥了 vnpy 的交易接口优势，又通过架构解耦实现了高度自由的 Web 化管控。您可以直接将其作为技术方案文档的框架。
