## 1. 个人中心

### 1.1 入口：顶栏头像下拉 ✅ 基本达标
- **提供**：头像+昵称（nickname||username 回退链）、三项下拉（个人资料/我的权限/退出，退出 divided 分隔 ✓）
- **感知**：头像即本人、点击出菜单——惯例成立
- ⚠ **元素偏差**：10 号设计为五件套（含改密/语言），实现为三项——改密收进 Profile 第三 tab（**合理收纳，不算缺陷**）；语言在顶栏独立 110px select（MainLayout:28，未丢 ✓）但**不在下拉内**——两处入口分散（语言在左、头像在右），新用户找"设置"的第一直觉是点头像，扑空后才见语言 select。建议：下拉加"偏好设置"项或语言并入 Profile basic tab（二选一，勿两处都有造成三入口）
- **防呆**：退出无确认——可接受（低危、token 可重登），但若有未保存编辑（Profile 改昵称未保存时退出）会静默丢失：建议退出前 dirty check（低成本）

### 1.2 我的权限玻璃盒（480 dialog）⚠ 半透明
- **提供**：三组 tag——角色默认/用户覆盖（warning）/被拒（danger plain）+说明行
- **认知偏差（核心问题）**：**权限键裸代码上屏**（`im_bots_config`、`risk.halt` 这类）——结构透明了（来源/覆盖/拒绝分清了），**语义没透明**：非 admin 用户看到 20 个英文键，仍不知道"我到底能干什么"。六问里"用户感知"这一问不及格。**修法**：i18n 键映射表（`perm.im_bots_config=IM 机器人配置`），tag 显示中文、tooltip 显示原键——半天工作量
- ⚠ 空态 `—`：viewer 看到一条横线——"无任何权限"还是"加载失败"无法区分。空态应显式文案"你的角色无附加权限"+若 denied 有值仍应显示（当前 `!myPerms.length` 判断会把"全被拒"也显示成 —，**被拒组与空态互斥冲突**：myPerms 空+denied 非空时 denied 组被隐藏？——模板 denied 组不受 myPerms.length 门控（v-if 独立），但空态行 `v-if="!myPerms.length"` 会与 denied 组同屏——需实测确认，逻辑上有同屏歧义）
- ✅ 加载 catch 静默：玻璃盒失败无提示（低危可接受，但建议失败文案）

### 1.3 Basic tab：头像/资料 ✅ 标杆级
- **提供**：头像点击打开 chooser 双 tab（36 系统图标即点即选 + 上传 vue-cropper 220 方形裁剪）、title"点击更换"提示、昵称行内保存（20 字上限）、用户名/角色/邮箱只读信息行
- **感知/防呆均好**：图标库避免用户找图、裁剪固定方形免比例困惑、只读与可编辑视觉分区清晰
- ⚠ 小困扰：头像 hover 无视觉变化（仅 cursor:pointer + title）——加 hover 光晕/角标铅笔图标，affordance 更明确
- ⚠ 邮箱 `-` 占位（与全站 `—` 不一致，04 §3 空值规范）

### 1.4 改密 tab ⚠ 表单合格、反馈一半
- ✅ 确认框 mismatch **即时**红框（input 时即比对）——好；规则文案常驻
- ⚠ 密码强度无实时指示（仅一行规则文案，弱密码提交才被后端拒：PASSWORD_NO_LETTER 等）——加 zxcvbn 式三档强度条或至少实时规则勾选清单
- ⚠ 修改成功后未强制/提示重登录（JWT 24h 有效期内旧 token 仍活——安全敏感操作，业界惯例改密后吊销会话或提示重新登录；结合 10 号"JWT role 24h 不刷新"旧差距，此处应提示）

### 1.5 注销账号 ✅ 合格
- danger 按钮 + ElMessageBox warning 确认 + 后端 LAST_ADMIN_PROTECTED 兜底 + 成功清 token 跳登录
- ⚠ 建议：确认文案补影响说明（"注销后 IM 绑定与权限即时失效，不可恢复"）——当前 deactivateConfirm 文案未读，确认强度应对称于不可逆性

### 1.6 页面导航 ⚠ 迷路风险
Profile 是独立路由（不在 16 项菜单）——从下拉进入后**无返回按钮**（与 StockDetail 同病，19 号 §2.6 已列"返回上下文"修复包），靠浏览器后退或点菜单。建议页头加"← 返回"。

## 2. IM 通道 tab（用户侧自助，Profile 第二 tab）

### 2.1 列表 ✅ 结构合格
- **提供**：provider/名称/启停状态 tag/待绑 badge（warning 数字，点击开绑定弹窗）/启停/删除
- ✅ **文案是全站安全沟通标杆**：addHint"手动方式创建后默认停用（启用前请先在 IM 平台完成应用配置）；扫码方式创建后即刻启用"——把两条路径的后果差异讲透了；bindHint"未绑定不获任何权限"——最小权限原则的用户教育
- ⚠ **缺活性线索**：无"最后消息时间/在线状态"列——用户无法判断通道是否真的活着（enabled tag 只表示开关意图，不代表连接健康）。建议加 last_seen 列（后端 feishu 心跳已有基础）
- ⚠ pending_binds 为 0 显示 `—`：badge 位置显示横线，视觉噪音（空即空白更好，全站惯例审视）

### 2.2 启停/删除 ⚠ 确认不对称
- 启停无确认（低危 ✓ 合理）；删除有确认但**文案未说明后果**（"删除后该 IM 身份的权限即时失效，绑定关系清除"）——删除是三操作中唯一不可逆的，确认文案应对称
- ⚠ 删除自己的通道时若 pending_binds>0——绑定中身份何去何从未在文案中交代

### 2.3 添加弹窗 ✅ 注册表驱动设计优秀，3 处元素瑕疵
- **提供**：provider 下拉（过滤 methods 非空 ✓）+方式 radio（多方式才显示 ✓ 顺序无关）+manual 动态 FIELD_SCHEMA 表单（secret 自动掩码 ✓）/interactive 扫码向导
- ⚠ **provider 显示英文原名**（feishu/…）——中文界面应显示"飞书"（label 走 i18n 或后端给 display_name）
- ⚠ manual 表单上方 addHint 已讲"先在 IM 平台完成应用配置"，但**无指引链接**——用户不知道去哪个开放平台、配哪些字段（外部文档深链缺失，第一次接入必卡）
- ⚠ manual 创建成功后默认停用——弹窗关闭后的引导断线：应提示"下一步：去开放平台完成配置后回来启用"并给入口

## 3. 飞书扫码向导（interactive）

### 3.1 状态机 ✅ 工程完备（逐态六问）
| 态 | 提供 | 用户感知 | 判定 |
|---|---|---|---|
| ''/intro | qrIntro 文案+开始按钮 | "推荐、自动配置"预期建立 ✓ | ✅ |
| starting | "正在生成二维码…"文字 | 等待有告知 ✓（无图时只有文字，可加 skeleton 框占位） |
| pending→scanning | QR 220px+"请用手机扫码，并在手机上确认" | **动作指令明确**（扫码+确认两步都说了）✓ |
| done | 绑定码 32px 大字+15 分钟提示+成功 toast | 大字醒目 ✓ | ✅ |
| done+owned=false | "该应用为平台级/他人通道：已刷新凭证，未变更归属与启停" | **防接管歧义——全案最专业的一条文案** | ✅ 标杆 |
| timeout | "二维码已过期，请重新发起"+重开按钮 | 明确 ✓ | ⚠ 见 3.2 |
| error | err.code i18n 映射 fallback 裸 error | 映射不全时裸英文 ⚠ |

**工程防呆全齐**：10s 轮询+600s 前端兜底+连续 2 次网络错才判死+弹窗关停+组件卸载停（轮询三件套）；方式切换复位旧码区（防过期码误导）；后端 ticket 归属绑定（他人 ticket→404）、每用户 1 活 ticket 频控、bot≤5 配额、admin 面不泄露他人验证码（pop bind_code）、全程 audit_log。

### 3.2 元素级剩余问题 ❌×1 ⚠×2
1. ❌ **过期窗口错位（真实困扰）**：前端兜底 600s，但飞书二维码真实 TTL 更短（平台侧约 5 分钟）——**过期后到前端 timeout 前的窗口内，用户扫的是死码：手机端报错，Web 端仍显示"请扫码确认"**，用户不知道该信哪边。修法：TTL 对齐平台真实值（如 300s）或提供"刷新二维码"按钮常驻 scanning 态
2. ⚠ **绑定码无倒计时**："15 分钟内有效"只有静态文案——用户发码给机器人前若耽搁，过期无感知。建议 done 态加 mm:ss 倒计时（纯前端即可）；另"私聊发给机器人"若用户发到群里——失败路径的反馈文案未验证（建议群里误发时 bot 回一句"请私聊发送验证码"）
3. ⚠ **知情同意粒度**：qrIntro 说"凭证自动配置（推荐）"——但"这一扫=把我的飞书应用凭证交给本平台保管"的事前告知没有（owned=false 是事后补救）。对单人平台可接受，若开放多用户建议 intro 加一句凭证托管说明

### 3.2b 扫码前置环节增补（v1.1）⚠×3
4. ⚠ **"用哪个 App 扫"未提示**：用户第一直觉是微信扫（扫出开放平台网页体验异常）——qrIntro/scanning 文案应明示"请用**飞书 App** 扫码（消息页右上角 + →扫一扫）"
5. ⚠ **手机侧确认页无预告**：扫码后手机会出现"连接现有应用 / 重新创建应用"选择——用户不知该选哪个（选错=飞书后台堆积垃圾应用）。Web 侧应在 scanning 态预告："手机上若出现选择：企业内已有此应用选『连接现有』，没有则『重新创建』"
6. ⚠ **app_preset 应用名写死"量化交易助手"**：所有自助 bot 同名——用户建 3 个通道无法区分（列表/飞书侧皆同名）；且与平台 bot10 同名（→ §3.3-1 混淆链根因）。修法：预设名带后缀（如"量化-{用户名}"）或扫码前让用户输入应用名

### 3.3 码消费环节（v1.1 增补——v1.0 缺口，❌×3 ⚠×2）

> 审核对象：done 显示码 → 用户切飞书 → 找 bot → 发码 → 绑定反馈 → 首次使用。这段是全流程体验断点最密集处。

1. ❌ **同名混淆链（P0 复合链）**：生产已有平台 bot10 也叫"量化交易助手"——done 文案"私聊发给**该机器人**"未指名，用户飞书里有≥2 个同名 bot，**大概率把码发给 bot10** → 码是 bot 维度键、bot10 无此码 → 拒答。与下条复合成认知崩溃。
2. ❌ **发码失败反馈不区分（P0）**：码错/码过期/发错 bot/群发——**全部回通用"未绑定平台账号"拒答**（feishu_client 拒答分支无场景分支）。用户刚走完扫码流程再收"未绑定"，无从排障："我不是刚弄完吗？"修法：码存在（该 bot 键在）但不匹配 → 专属回复"验证码不匹配——请确认发给刚创建的机器人「{bot 名}」，剩余尝试 {n} 次"；键不在（过期/作废/发错 bot）→ "验证码已过期或发错了机器人——请回到网页查看"；错次>3 附剩余次数预警
3. ❌ **关弹窗=丢码（P0）**：done 码只存活在弹窗内——用户习惯性 ESC/点关闭后去手机操作，回来码没了（Valkey 里仍有效但页面无锚点）。用户被迫保持弹窗开着跨设备操作。修法：done 后把码落 IM 通道列表行（常驻"待绑定"横条显示码+倒计时，绑定完成/过期后消失），不依赖弹窗存活
4. ⚠ **频控 429 困局**：报错"已有进行中的接入会话，请先完成或等待过期"——但**无处查看那个会话、无法取消**（上次没扫完的用户被锁 15 分钟无路可走）。修法：报错时直接恢复显示那个活会话（同 ticket 轮询）或给"取消重来"按钮
5. ⚠ **绑定成功后引导断层（冷启动）**：bot 回"✅ 绑定成功"即止——用户不知道接下来能干嘛。修法：成功回复附示例命令（"试试：查一下风控状态"）；错 5 次作废机制也应在此处文案露出（剩余次数）

三处应作为全站文案/状态机范式：addHint（双路径后果差异）、bindHint（未绑定=零权限）、owned=false（防接管歧义）。

## 6. 贯穿性主线索（v1.1）

- **术语统一**：全流程五词漂移（通道/平台/方式/机器人/应用）——用户心智只有一个概念"机器人"。修复原则：面向用户文案统一说"机器人"，"通道/平台/方式"仅留在开发者语境
- **错误反馈的场景区分**是本区最大系统性短板：拒答/频控/码错/过期共用通用文案，每次都把用户推回"从头排查"。原则：**每个失败路径都要能被用户独立排障**（说出错在哪+下一步去哪）
