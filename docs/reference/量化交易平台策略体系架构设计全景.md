# 量化交易平台策略体系架构设计全景（最终定稿）

本文档全面梳理了从因子定义、策略构建、信号生成到最终执行的整套机制。核心设计原则为：**因子与策略分离、风控绝对优先、双引擎模式并行**。

---

## 一、总体分层架构（四层模型）

平台从底层到顶层划分为四个独立的逻辑层级，任何策略（无论拖拽还是代码）都必须严格经过此四层流转：

1. **因子层（共享算力层）**：负责计算指标（如MA、MACD或自定义机器学习预测值）。**无状态**，输入时间戳与标的，输出数值序列。
2. **策略决策层（业务逻辑层）**：负责根据因子值判断“该买还是该卖”，并生成**理想的**下单指令（Signal）。此层分为“拖拽配置”和“高级代码”两种引擎。
3. **风控校验层（硬截断网关）**：系统级黑盒，**优先级最高**。强制校验策略生成的指令，一旦触及止损止盈或仓位红线，直接暴力修正或否决指令。
4. **执行撮合层（报单层）**：接收风控层输出的最终指令，对接实盘或回测撮合引擎，执行下单。

---

## 二、核心数据契约：标准动作信号体（ActionSignal）

**极其重要**：无论使用界面配置还是高级代码，策略层**绝不**能返回简单的`True/False`或`BUY/SELL`字符串，必须返回结构化的信号对象。该对象是连接策略层与风控层的唯一数据标准。

class ActionSignal:
    action: str              # 必填，枚举值：'BUY' | 'SELL' | 'HOLD'
    volume_type: str         # 必填，枚举值：'PERCENT' | 'SHARES' | 'ALL_IN'
    volume_value: float      # 必填，PERCENT时为0~1比例，SHARES时为具体股数
    price_type: str          # 必填，枚举值：'MARKET'（市价） | 'LIMIT'（限价）
    limit_price: float       # 可选，price_type为LIMIT时必填
    order_validity: str      # 必填，枚举值：'DAY'（当日有效） | 'GTC'（撤销前有效）
    extra: dict = None       # 可选，扩展字段（如附加止盈止损标记）

## 三、策略决策层：双引擎并行机制

用户可在策略编辑页面选择“普通模式（拖拽）”或“高级模式（代码框）”。两种模式**相互独立，不进行双向转化**，但共享底层的因子库。

### 1. 普通模式（拖拉拽配置）
- **买入/卖出分离**：界面提供独立的“买入策略配置画布”和“卖出策略配置画布”，用户通过拖拽`IF...AND...OR...`条件组件构建逻辑。
- **仓位UI绑定**：界面强制配备“买入仓位”（如总资金的20%）和“卖出仓位”（如持仓的50%）滑块或输入框。拖拽逻辑生成的判定结果，将自动与UI仓位拼接，组装成上述`ActionSignal`对象。
- **适用场景**：经典双均线、MACD金叉死叉、固定阈值风控策略。

### 2. 高级模式（原生Python代码框）
- **预置函数框架**：平台提供两个必须实现的函数模板，用户只需填写函数体：
  - `handle_buy_signal(context, data)` -> 返回 `ActionSignal` 或 `None`。
  - `handle_sell_signal(context, data)` -> 返回 `ActionSignal` 或 `None`。
- **自由度特权**：允许引入第三方库（如Pandas、Sklearn），允许调用外部API，允许动态计算`volume_value`（例如根据账户现金动态算出买入37.5%）。
- **适用场景**：涉及机器学习推理、复杂状态机（网格）、实时抓取另类数据的策略。

## 四、共享因子层：绝对统一的底层算力

无论策略采用哪种模式，所有因子（平台内置与用户自定义）在底层**完全等价且全局共享**。

- **统一注册机制**：所有因子代码必须通过`@register_factor`装饰器挂载。平台内置的`MA5`本质上与用户写的`My_AI_Score`是同一套代码结构。
- **调用句柄强制统一**：
  - 拖拽模式生成的DSL，底层解析为`get_factor('MA5')`。
  - 高级代码模式，必须通过`context.get_factor('MA5')`调用。
- **工厂模式与参数哈希**：同一算法不同参数（如MA5与MA10）视为不同实例，平台自动进行参数Hash作为缓存Key。若10个策略同时调用`My_AI_Score`，因子层**全局只计算1次**。
- **数据喂养形式**：为保证性能，策略层`handle_bar`接收的必须是**全标的池的因子DataFrame**，严禁在Python循环内逐标逐个请求因子，从调度上强制用户使用向量化思维。

## 五、最高优先级：全局风控校验网关（硬截断）

这是平台安全性的命脉。系统底层设有一个**不可跳过的拦截器**，按固定流水线处理策略发来的原始信号。

**处理优先级（由高到低）**：

1. **硬止损（Hard Stop-Loss）**：若账户权益相对历史峰值回撤达到UI设定的阈值（如-5%），无视策略信号，**强制覆写**为`ActionSignal(action='SELL', volume_type='ALL_IN')`，并标记`reason='STOP_LOSS'`。
2. **动态止盈（Trailing Stop）**：若持仓浮盈曾达+10%，现回落至+8%（回撤2%），同样强制平仓离场。
3. **单笔仓位硬顶（Position Cap）**：若UI设定“单笔最大20%”，但策略输出了`BUY 30%`，网关直接截断，将`volume_value`由0.3修改为0.2，并打上`adjusted_by='RISK_CAP'`标记。
4. **现金/持仓可用性校验**：若`BUY`指令所需资金超过可用现金，自动降级为“可买最大数量”；若`SELL`指令超出持仓量，自动修正为全平。

**最终铁律**：风控层的输出是执行层接收的**唯一指令来源**。策略层仅提供“建议”，风控层拥有最终决定权，确保用户永不爆仓。

## 六、全流程串联执行时序

系统在每一个`Bar`（K线周期）的调度顺序如下：

1. 数据模块推送最新行情及历史数据至**因子层**。
2. 因子层批量计算所有策略依赖的因子值，存入缓存。
3. **策略决策层**获取因子值，执行普通拖拽逻辑或高级代码逻辑，生成原始的`ActionSignal`对象。
4. 原始信号流入**风控校验网关**（见第五节），信号被校验、修正或覆盖。
5. 风控网关输出最终合规的`ActionSignal`。
6. **执行撮合层**解析最终信号，根据`price_type`（市价/限价）和`volume_type`发往券商接口或回测撮合队列。

## 七、架构优势总结

| 维度 | 实现效果 |
| :--- | :--- |
| **易用性** | 小白用户零代码拖拽，极速上手；专业用户直接写Python，不受UI限制。 |
| **安全性** | 风控层物理隔离于策略逻辑之上，无论用户代码多激进，平台硬顶永远生效。 |
| **性能** | 因子全局缓存仅算一次；DSL编译为C++高速执行，高级代码按Bar向量化传参，规避慢循环。 |
| **扩展性** | 新因子注册即用；未来接入AI生成策略，只需让大模型输出标准`ActionSignal`对象即可。 |

**最终结语**：这套机制将“自由度”与“安全性”这对矛盾体完美解耦。因子、策略、风控三者边界清晰，职责单一，可支撑平台从初创期平稳演进至百亿级资产管理规模。
