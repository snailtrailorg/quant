# 批25 · 全局日志三套体系（Apache 式）

> 2026-09-15 立项，方案双盲审（A 1P0+3P1+5P2 / B 3P0+5P1+2P2）后 v2 修订。起因：批24 迭代十六的邮件日志整合暴露架构问题——日志职责散落四张表，前端被迫映射合成。
> **用户设计哲学（裁定）**：像 Apache（access/auth 分文件）——三套全局日志单一职责，**从设计上契合，不分表合表**：
> ①系统运行日志（全模块+邮件发送事件）②用户操作审计日志 ③系统发送通知日志。
> 用户三裁定：落库=logger 统一 handler 异步批量；保留=运行 30 天/审计永久/通知 90 天；存量不迁（旧表冻结）。
> **UI 简化收益（用户裁定）**：日志为系统记录——运行/审计页签的删除所选/删除所有功能**退役**（系统简化）。
> **关机冲刷（用户要求"完美"条件）**：SIGTERM/atexit/FastAPI shutdown 三钩子把缓冲批量刷库。

## 一、目标

| 套 | 表 | 职责 | 写入 |
|---|---|---|---|
| ①运行日志 | `system_log`（新） | 全模块运行事件（level/source/module/message）+ 邮件发送事件（module=email） | logger 统一 handler |
| ②操作审计 | `audit_log`（现有不动） | 用户操作留痕 | 现有 audit_log() |
| ③通知发送 | `notify_log`（新） | email/im/sms 投递终态（channel/target/subject/status/error/level/category/关联 alert_id） | dispatch 终态点+outbox 终态点 |

- `email_outbox` 回归**纯队列**职责（重试调度 next_attempt_at），发送终态另落 notify_log。
- `task_logs` 冻结只读（live-task 时间线继续用），运行日志页切 system_log。

## 二、后端设计

### 2.1 表结构（alembic 0077：两新表+email_outbox 加 ref_alert_id 列）
```sql
CREATE TABLE system_log (
  id BIGSERIAL PRIMARY KEY,
  ts TIMESTAMPTZ NOT NULL DEFAULT now(),
  level VARCHAR(8) NOT NULL,          -- DEBUG/INFO/WARN/ERROR
  source VARCHAR(40) NOT NULL,        -- 进程/单元：web-api/worker/beat/live:1/hub
  module VARCHAR(60) NOT NULL DEFAULT '', -- email/scheduler/risk/...（自由）
  message TEXT NOT NULL
);
CREATE INDEX idx_system_log_ts ON system_log (ts DESC);
CREATE INDEX idx_system_log_level ON system_log (level);

CREATE TABLE notify_log (
  id BIGSERIAL PRIMARY KEY,
  ts TIMESTAMPTZ NOT NULL DEFAULT now(),
  channel VARCHAR(8) NOT NULL,        -- email/im/sms
  target VARCHAR(200) NOT NULL,       -- 收件人邮箱/bot 标识/手机号（im=bot 维度，per-user 结局不展开）
  subject VARCHAR(200) NOT NULL DEFAULT '',
  status VARCHAR(12) NOT NULL,        -- sent/failed（终态；pending 在 outbox/claim；stuck sending 永缺=known-limit）
  level VARCHAR(8), category VARCHAR(30), alert_id BIGINT,
  error TEXT
);
CREATE INDEX idx_notify_log_ts ON notify_log (ts DESC);
ALTER TABLE email_outbox ADD COLUMN ref_alert_id BIGINT NULL;   -- dispatch enqueue 带（终态关联）
```

### 2.2 SystemLogHandler（`src/data_platform/log_sink.py` 新）——按进程分型（盲审 A-P0/B-P0-2：celery prefork 三连击）
- `logging.Handler` 子类：内存队列（deque maxlen=2000）+ 后台线程 5s/100 条批量 `executemany`；flush 用 `threading.Lock`+drain-while（后台线程与关机钩子并发安全）。
- **装配按进程分型**：
  - **web-api**：import 期装 root handler；冲刷=FastAPI `lifespan shutdown`+`atexit`（**不裸抢 SIGTERM**——uvicorn 自装优雅退出，盲审 B-P0-2①）。
  - **celery worker/beat/risk**：`worker_process_init` 信号内**每子进程重启 flush 线程**（线程不跨 fork；celery `hijack_root_logger=True` 摘 root handler → 装配用 celery `setup_logging` 信号挂回，A-P0①）+`worker_shutdown` 子进程自冲刷（billiard `os._exit` 绕过 atexit，A-P0③；`--max-tasks-per-child=100` 高频再生下每子进程自洽）。
  - **live-task（`src/strategy_runner/main.py`）/md-hub（`src/md_hub/main.py`）**：入口自持 SIGTERM（链式调原 handler 后 sys.exit 让 atexit 跑）；source=`live:{task_id}`（--task-id 推导）。注意两入口 `logging.basicConfig` 在装配后变 no-op（root 已有 handler）需自验（A-P2-9）。
  - **im-pool（`src/im_bot/pool.py`）+feishu ws_client 子进程**（A-P1-3 补）：pool 装配+Popen spawn 的 ws_client 子进程环境变量继承 source，若不落库显式声明排除。
- **source 取值**：env `QUANT_LOG_SOURCE`（.env+systemd 单元 `Environment=` 双写；缺省按进程名兜底 `unknown`）——盲审 B-P1-8 钉死。
- 连接：批量写复用 `get_conn()` 每批短连接（全仓一致性优先，5s 频次可接受）。
- level ≥INFO 落库；access log 不落（uvicorn.access propagate=false 实证，A-P2-8 ✓ 零噪音）。
- DB 故障降级：批量写失败丢批次+stderr 告警。

### 2.3 写入面改造
- `main.py`：装配 handler（web-api source）。
- worker/beat/hub：各入口装配（source 对应单元名）。
- **邮件链事件写 system_log（module=email）**：入队/发送成功/失败/重试耗尽四事件（`alert_notify/dispatch.py` + outbox sweep）。
- **notify_log 写入（盲审 A-P1-2 修正：email 单点）**：
  - **email 唯一写入点=`email_service/_try_row_sync` 终态两分支**（sent UPDATE/failed MAX_ATTEMPTS——立即试发/worker 任务/beat sweep/web try_row 四路径必经；`_send_email` 返回"已入 outbox"非终态不写）。
  - **alert 关联**：`email_outbox` 加参考列 `ref_alert_id BIGINT NULL`（dispatch enqueue 时带上；sweep 终态行经此关联——三互斥中选加列，保留关联能力）。
  - **im/sms**：`alert_tasks.py` 三任务终态返回处写（im 通道 target=bot 维度；`im_partial` 聚合结果整行记，per-user 结局不展开——known-limit）。
  - **known-limit 写明**：stuck `sending` 行（worker 死亡窗）永无终态→notify_log 永缺该行（批7 已有语义，不新增机制）。
- 邮件四事件写 system_log（module=email）：入队=dispatch enqueue 处；成功/失败/重试耗尽=_try_row_sync 两 UPDATE 分支（A-P1-5 锚定）。
- 现有 logger 调用零改动（handler 统一捕获）。

### 2.4 GC（beat 任务）
`cleanup_logs` 日频（beat_schedule 注册，app.py——email-outbox-sweep/notifications_cleanup 同构并轨）：system_log>30d 删/notify_log>90d 删/audit_log 只插不删零 GC。批次形态（PG 无 DELETE LIMIT，盲审修正）：`DELETE FROM x WHERE id IN (SELECT id FROM x WHERE ts<now()-interval '30 days' LIMIT 5000)` 循环至 0 行、每批独立短事务（18 号规范 §批次）。

### 2.5 端点
- `GET /api/log`：**无参分支切 system_log**（200 条）；**task_id 参数分支保留读 task_logs**（live-task 时间线唯一消费 LiveTask.vue:303——盲审 B-P0-1，不可整体切）。
  - **可感知取舍（向用户披露）**：数据同步任务的 step 过程日志（task_manager.log_task 显式写 task_logs）从运行日志页消失——运行日志页=logger 面（system_log），step 过程保留在任务详情（task_logs）。任务过程日志若也要上运行日志页=log_task 双写 system_log（编码时实现，成本一行）。
- `GET /api/notify-log`：require_perm("user_mgmt")（发送记录含收件人邮箱——盲审 A-P2-7 钉死，与前端 admin 可见一致）。
- `GET /api/audit` 不动。
- **退役（盲审去幽灵：运行日志删除从未存在）**：`POST /api/audit/delete`（risk.py:254）+Audit.vue 删除钮+api.js deleteAudit+测试（test_batch23_delete_endpoints.py 拆 notifications 部分保留）。**通知收件箱删除（/api/notifications/delete）保留**（收件箱=用户自己的消息，语义不同——待用户确认）。
- 词条 deleteSelected/deleteAll 为 NotificationTable 共用**保留勿删**。

## 三、前端设计

- **三页签**：运行日志（system_log）/审计日志/通知消息。
- 通知消息页签内两块：我的通知（收件箱，现状 NotificationTable）/发送日志（notify_log 只读表，admin 可见）。
- 运行日志页：撤 hotfix4 的 outbox 映射（task_logs→system_log 数据源切换即天然含 email 事件行）；**删除钮退役**（RowFilter 筛选+导出保留）。
- 审计页：删除钮退役（筛选+导出保留）。
- 动作序维持：筛选→导出→（列设置）。
