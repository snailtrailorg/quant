## 三、发现

1. **usage_limit 是死列**：grep 全仓，运行期零读取（L1-L4 无一层消费）——仅 models.py:119 Pydantic + mgmt.py 五处 CRUD 透传 + 前端列/弹窗。设计意图"日限额（Tushare 积分）"从未实施（积分档已随 24 号废除）。方案一 v2 列清单不含 → 丢弃无功能损失（tests 全目录零 usage_limit 引用——盲审 B 实证）。
2. **L4 用量层近似空转**：唯一生产调用 `engine.py:33 record_usage(provider="tushare", api_name="get_pro")` 只记"客户端构造了一次"；真正的 API 调用（daily/stk_mins/…）在 `rate_limit_context` 内不计数。盲审 A 纠量：`_get_pro` 有 5 个调用点（engine.py:336/354/397/445/997），**每任务一行非每日一行**。→ 55a 只迁键不加语义（勘察范围=保迁移不破）；**计数接入 rate_limit_context 挂账待裁**（收益=真配额监控，成本=L4 从空转转活的告警面）。
3. **熔断/限速进程内键的 D2 语义裂缝（边界外记录）**：`rate_limit_context` 进程内键=`ds.provider`——熔断器 `_BREAKERS[provider]` **与限速节奏 `_LIMITERS[(provider, api_name)]`（盲审 A 补：同病）**均跨账号共享。external_interface 后同 provider 多账号（两个 tushare token）将共享——账号 A 打穿封/拖慢账号 B，与 D2 立法"配额共享体=账号"在多账号下矛盾。55a 单行语义下无实害；随深水区选源批一起解（键升级=行 id）。同构问题存于 `broker_usage` 表（盲审 A 边界外观察，provider 键多账号混账）。

## 四、0090 迁移处置汇总（供 ② 直接引用）

- `data_source_usage` **加列** `interface_id bigint NULL` + 存量按 provider 回填（数据域首行）+ 保留 provider 列（写侧经 #5 注入双填，读侧零改）。
- `usage_limit` **不迁移**（死列丢弃）；后端透传同批删（B-a）；存量 position=分域按旧表 id 序 0..n（B-d）。
- `params` 升 **jsonb**（终裁列类型）；读边界 `get_data_source`/`get_broker` 做 dict→json.dumps 转换喂 `__init__(params: str)` 契约。
- `params.rate_limits` / `params.circuit_breaker` 原样随行迁入（L2/L3 载体不变，端点选行序改 #1）。
- 旧表 `data_source_config`/`broker_config` **同版 drop**（终裁，批43 channel_config 先例；drop 前置=端点/测试绿+staging 彩排）；旧端点契约以垫片过渡（#10/#11），55b 前端切 `/api/interfaces` 后同车删。
