## 二、两个关键设计决策（**不要改，除非重审 29 号**）

> **用户裁定（2026-09-21，收编开工时）**——两隐患抓在埋雷前：
> ① sync_id 不得复活为分派键（24 号时代第一公民，28 号已让位 DataKind）；
> ② 不得制造两个 fetch（28 §5.2 的 adapter.fetch(req,acct) 是唯一契约，同步/消费共用）。

### 决策 1：单一 fetch 契约 `fetch(req, acct)`，分派键=(kind, sub_kind)

- **只有 28 §5.2 的 `fetch(req, acct)`**——同步引擎循环与消费面 DataBus 共用，区别只在 `req`：
  - 同步：`mode=supply` + symbols 域 + range_ 回补区间
  - 消费：`mode=consume` + 用户 symbols + 查询区间
- **分派键=(kind, sub_kind)**（DataKind 第一公民）。bar_daily 三品类靠 **sub_kind=stock/etf/convertible** 判别
  （0094 已补全），**不靠 sync_id**。
- **sync_id 只做过渡期调度 id**（游标 last_sync_date 的键），不进 fetch 签名；收编后随 `_HANDLERS` 一起退役，
  DataKind+sub_kind 是第一公民。
- **拉取粒度（逐日批/per-symbol/区间）是 adapter 内部批量优化策略**（sub_kind=stock/etf 的 bar_daily 用
  `pull_daily_batch` 按日批，cb 用 `pull_cb_daily` 区间），不改 fetch 签名——29 号验收①"行为等价"约束下，
  改拉取粒度=破坏等价，禁止。
- 返回 ContractFrame（`to_contract` 产物——58 同批建，抽象先占位）。

### 决策 2：通用引擎循环按 rebuild 分叉（行为等价优先）

- `incremental` → **逐日循环**（现状 `_sync_by_trade_date` 泛化，游标 last_sync_date）
- `full_rebuild` → **区间/全量拉**（现状 `_make_full_rebuild_handler` / 手写全量）
- **行为等价生死线**（29 号验收①）：改造前后同交易日全量同步，按 pk 排序全字段精确等值，排除列=代理键/摄取时间戳/dataset_version；`preserve_current_normalization=True` 下必然成立（bug-for-bug）。

## 四、灰度机制（55a 式，按 sync_id 逐项切）

- flag 载体：`system_config` 键（如 `sync_kind_routing` 值=逗号分隔的 sync_id 白名单；空=off 全走 _HANDLERS）。
- 切换序：先 `cb_daily`（区间粒度，最简）→ `astock_daily`/`etf_daily`（逐日 batch）→ 逐步覆盖 20 项。
- 每个 sync_id 切过去后：跑行为等价对照（改造前后 diff），绿了才切下一个。
- 全绿后：`_HANDLERS` 删除 + `tushare_api` 列 drop（与 fetch 分派表同车）。
