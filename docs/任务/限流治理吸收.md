# 限流治理吸收（参考文档评审三件，2026-08-27 立项）

> 来源：`docs/reference/多资产量化数据中台架构升级方案.md` 评审（对 60%/错 40%/过度 100%）。
> 评审结论：三件做（声明式限流/三级覆盖/熔断器）、三件不做有理由（四层元数据等第 2 市场/分布式限流等第 2 实例/Grafana 等 SM1）。
> 八步法（本文件=步 1）。

## 目标
1. **RateLimitContext 声明式上下文管理器**：收编 engine.py 五处散点 `time.sleep`（0.15/0.3/0.5s）+ adapter 内如有——统一为一处声明式调用，限速值从 DataSource 取
2. **限流三级覆盖**：现有两级（`DataSource.DEFAULT_RATE_LIMITS` 类默认 → `params.rate_limits` DB 覆盖）扩第三级"动态时段规则"（如盘后放宽×2/竞价降速×0.1）
3. **数据源熔断器**：连续失败>阈值 → Open 快速失败（Engine 只捕 CircuitOpenError 跳过本轮）→ 半开探测恢复——模式同 LLM 网关熔断（`_failed_counts + threading.Lock`）

## 依赖（就绪）

## 限定范围
不碰：adapter 的 pull_* 函数签名（零侵入——limit 在 engine 侧包裹，不改 adapter）；hub/runner（实时链不走 HTTP 限流）；分布式（单实例内存计数足够）。

## 设计决策

### D1：限速在 engine 侧（调用方）不在 adapter 侧（被调方）
- **理由**：adapter 的 pull_* 已是"一调一拉"纯函数（12 个 pull 函数零 sleep 实证）——限速是**编排节奏**（engine 循环间等待），不是单次调用属性
- 参考文档的 `RateLimitContext` 包在 adapter 内（`with ... : return self.client.daily(...)`）——**对我们不适用**：我们 engine 是"循环逐 symbol 拉"，限速在循环间而非调用内

### D2：熔断器按 DataSource 实例级（非 API 级）
- **理由**：Tushare 账号是配额共享体——任何接口打穿配额都封整个账号，熔断粒度应对齐封禁粒度
- 实现：`CircuitBreaker(fail_threshold=5, reset_timeout=60)`——连续失败 5 次 Open，60s 后 Half-open 放一次探测，成功关/失败再开

### D3：时段覆盖第三级用 multiplier（非绝对值）
- **理由**：`DEFAULT_RATE_LIMITS` 已有基础间隔（如 0.3s），时段规则只改"多快/多慢"不改"是什么"——盘后 ×2 意味着间隔÷2（更快），竞价 ×0.1 意味着间隔×10（更慢）
- 格式：`params.rate_time_overrides = [{"window": "16:00-20:00", "multiplier": 2.5}]`——乘在 QPS 上（间隔除以 multiplier）

## 验收标准
1. `pytest tests/test_rate_limit.py -q` 全绿（≥10 测）；全量绿；分层绿；pyflakes 零新增
2. `grep -c 'time\.sleep' src/data_sync/engine.py` 从 7 降到 ≤2（保留的须是 sleep_s 参数默认路径）
3. 三级覆盖实跑验证：mock `params.rate_time_overrides`，断言不同时段返回不同间隔
4. 熔断三态测试：连续失败 5 次→Open→60s 后 Half-open→成功关→失败再开
