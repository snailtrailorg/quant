# 批 121：管道收敛——地图、规约、清账与人话文档

> 立项：2026-10-12。触发：安全态势页（批 120）上产过程中，部署管道同一根因
> （改了输入、不认识它的消费者）三连断：lock 丢 hash / dev 文件不进切片 /
> 判据只盯 lock。以及 staging 与 prod wrapper 版本分叉（彩排价值削弱）。
> 用户裁定：收敛而非重写；文档要"人话"。

## 背景（为什么是这一批）

部署链近 30 天 44 个提交，闸门体系经实战检验（hash 门拦过丢 hash 的 lock、
交易窗门拒过盘中发布、DDL 门管过两步走立法）——机制本身是成熟的。但：

1. **三断环同根因**：管道的每个输入（切片/指纹/lock/wrapper/sudoers/nginx
   conf）都有消费者，散在 15 个文件的注释里。改输入的人（包括我自己）
   无法廉价地知道"改这个会断谁"——只能断一次、修一次、补一个检查。
   检查越补越多（用户已警觉：这是解决问题的正确思路吗）。
2. **环境一致性无机制**：wrapper 装位是 bootstrap 的活（一次性 root），
   但实际靠人肉——prod 手工装了新版、staging 落后（2026-10-12 实证分叉）。
3. **文档密度高但入口陡**：A06 架构文档 467 行是好的，但写给"已经在context
   里的人"。新会话/三个月后的自己，第一眼需要的是"人话版"：这条链是什么、
   我要改 X 应该看哪、出事了先查哪。

## 目标（判据可见）

1. **「输入→消费者」地图**：A06 增机器可查表（每行=输入文件/清单 × 消费者
   文件:行 × 改动前必查项）。判据：任何管道输入变更，查表可得全部下游。
2. **wrapper 生命周期规约**：一行规则进 runbook + bootstrap 幂等性验证
   （重跑不产生副作用）——「wrapper 变更 ⇒ 重跑 bootstrap」成为唯一装位通道，
   手工 install 定为违规操作。
3. **A06 §8 清账**：9 项已知边界逐项处置——收口 / 明确挂账含期限 / 判定
   接受现状（三条路选一，不许"待裁定"悬空）。
4. **staging 彩排完整性恢复**：wrapper 三件（pip-wrapper 新版 + dnf/ssh 快照
   两 wrapper）staging 装位 + sudoers 对齐，md5 与 prod 一致实证。
5. **人话文档**：A06 前置一章「五分钟读懂这条链」（无批号、无历史、只有
   现在时态的机制描述 + 三张图：数据流/权限流/失败时的行为）。
   判据：一个没有本仓上下文的人读完能回答——发布分几步、每步谁在守、
   改依赖/改wrapper/改nginx 分别要动哪几个文件。

## 限定范围

- **不重写 release.yml**；不删除任何不变量类检查。
- 不做 CI 外部化（单机仓库形态不变）。
- §8 四项的"收口"若涉及大改（如回滚含 schema），本批只裁定方向与立项，
  不实施。
- 文档全部中文人话，禁用"批号引用代替机制描述"（历史批号只进脚注）。

## 契约

- 地图表 schema：`输入 | 属主文件 | 消费者(file:line) | 改动前必查 | 关联闸门`。
- 人话章长度 ≤ 150 行；无前置知识依赖；每个机制描述配"为什么"一句话。
- staging 对齐以 md5 双向实证入进展日志。

   抽 3 行核 file:line 真实性。
