## 0. 契约（自包含）

- **问题**（DEF-13 原文）：`SyncLock` 全仓仅 3 处实例化；`_reconcile_symbols`（engine :2741，周日 03:33 beat `data_gap_reconcile`）与 `data_continuity_check`（tasks.py :555，每小时 :17 beat）**均无锁**，且后者直接写 `bar_1D`（per-symbol `pull_daily`→`save_bars`）。与 16:35 增量波次/手动回补/手动触发对账并发时：同表同窗并发写（upsert 幂等 ⇒ 数据面无重复行，但**重拉浪费**——两边各拉同一缺口一次；`factor:recalc:triggered` 重复触发；`sync_gap` 行读写竞态——open 行两边同时 repull 同时 closed）。
- **修复形态＝锁粒度对齐写粒度**（不发明新锁类型——复用 `SyncLock` 语义：`with SyncLock(key)` 未获 ⇒ 语义化跳过）：
  1. `data_continuity_check` 补采段（写 bar_1D）：`SyncLock("reconcile:continuity")`——**只罩补采段**（断线检测/新鲜度检测只读不罩，:577-595 段在锁外）。未获 ⇒ 本轮跳过补采（issues 记「补采锁被持，跳过」——只读检测照常）。
  2. `_reconcile_symbols`（tasks.py `data_gap_reconcile` 入口罩，engine 函数零改）：`SyncLock("reconcile:symbols")`。未获 ⇒ 返回 `{"status": "skipped", "reason": "上次对账仍在运行"}`（与 sync() 同词）。**不与 sync_id 锁互斥**——重拉走 adapter 限速（rate_limit_context 进程内）+ upsert 幂等，跨进程并发拉同一标的的最坏代价＝重复 API 调用，per-symbol 重拉候选有限频（`_GAP_REPULL_MAX`），锁目标是**防同任务双跑**（beat 重叠/手动+beat 并发），不是防与增量轮并发（增量轮与本任务写窗口天然不同——03:33 vs 16:35，交集=手动触发场景，由 upsert 幂等兜底）。
  3. **心跳续期**：两任务均长任务（慢轮 1664-2093s >> TTL 60s）——`with SyncLock(...)` 的 `__enter__` 已自动起心跳线程（sync_lock.py :108）⇒ 零额外代码；验证断言锁在 60s 后仍持（守门测试模拟）。
- **明确不做**：①不给 `_reconcile_symbols` 体内逐 scope 加锁（单任务内串行无竞态）；②不改 `pool_data`/jq 已有锁；③不做跨 sync_id 的「对账×同步」全局互斥（代价=16:35 波次被 03:33 长对账卡死的风险，收益=省重复拉——不划算，upsert 幂等已兜）。
