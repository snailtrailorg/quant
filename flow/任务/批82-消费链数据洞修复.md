# 批 82 · 消费链数据洞修复（P0-2 + P1-2，实盘核心）

> 立项 2026-09-29 深夜（批 81 第三梯队，用户拍板「做」）。实盘消费链核心，**改前必跑 staging `scripts/test-live-pipeline.sh`**。

## 一、根因（已确认）

`hub_worker.handle_msg`（`@make_guard` 保护）顺序：**副作用先行 + 无条件 xack**：

```
332-337  state.max_ts = ts_key + r.set(_mts_key)   ← 去重水位（副作用）
345      sig = strategy.on_bar(bar, history)       ← 业务（on_bar 内同步 place_order）
346-347  stats["bars"] += 1 + history.append
362      r.xack(...)                                ← process_batch 无条件
```

`on_bar` 抛异常 → guard 吞（`guard.py` 返回 None）→ `process_batch` 看到「正常返回」→ 无条件 xack。三重不可逆：
1. bar 被 ACK → 不可重放
2. `state.max_ts` 已推进 → 永久去重（重放也跳过）
3. `history` 未 append → 下根因子窗口缺一根
→ 静默数据洞 + `last_bar_wall` 已更新 → 心跳报健康，零告警。

**C-F1 已厘清**（`docs/design/D15:150`）：下单新鲜度锚是 `stats["last_bar_wall"]`（329 行，bar 墙钟），**不是** `state.max_ts`。所以 `state.max_ts`（去重水位）可安全后移，不碰 C-F1。

## 二、修复方案（三处）

1. **state.max_ts 后移**：332-337 的去重水位推进，从 on_bar **前** 移到 on_bar **成功后**。`stats["last_bar_wall"]`（329）/`sess_bar_wall`（331）保持在前（C-F1 不动）。
2. **guard 失败标志**（P1-2）：`guard.py` 的 `wrapped` 异常时 `return False`（正常返回 fn 值）。调用方用 `is False` 区分成败。
3. **xack 条件化**：`process_batch` 里 `handle_msg` 返回 `False` 的 bar 不 xack（流保留重放），其余（None/True=成功或跳过）照常 xack。

## 三、关键风险：下单重放（必须防护）

`on_bar` 内 `place_order`（strategy.py:261）同步下单。修复后：`place_order` 下单成功但后续异常 → 不推进水位 + 不 xack → **重放重复下单**（`trading.py:38` 注释已知此风险；`client_order_id` 唯一索引是下单后去重，非下单前幂等）。

**方案（二选一，盲审定）**：
- A：`place_order` 用 bar ts（`_last_bar` 的 ts）做**下单前幂等键**（下单前查 order_log 是否已有该 bar 的委托，有则跳过）。
- B：`on_bar` 内 `place_order` 包 try/except——下单失败（拒单）才算「业务失败」不推水位；下单成功后的异常（写 order_log 等）算「成功」，照推水位 + xack。

## 四、验收判据

1. 构造 `on_bar` 抛异常 → 断言（a）该 bar 未被 xack 或可重放；（b）`state.max_ts` 未推进；（c）告警/ERROR 日志（guard 已 logger.exception）。
2. 构造「下单成功 + on_bar 后续异常」→ 断言不重复下单（幂等防护生效）。
3. staging `test-live-pipeline.sh` 真跑绿（消费链顺序改动，行为级验收）。
4. 全量 pytest 绿 + ruff 绿。
