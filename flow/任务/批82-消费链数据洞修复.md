# 批 82 · 消费链数据洞修复（P0-2，实盘核心）

> 立项 2026-09-29 深夜（批 81 第三梯队，用户拍板「做」）。**方案经盲审推翻重定向：放弃「重放」路线，改「finally 补 history」最小修复**。

## 一、根因（已确认）

`hub_worker.handle_msg` 顺序：`state.max_ts` 推进 + 持久化（副作用先行）→ `on_bar`（业务）→ `history.append`（347）。`on_bar` 抛异常 → guard 吞 → 返回 None → process_batch 无条件 xack。

**真实问题**（盲审厘清）：`on_bar` 异常时 `history.append`（347）未执行 → 下根因子窗口缺一根。所谓「静默数据洞」部分误述——guard 已 `logger.exception` + `safe_notify critical` 告警（非静默）；bar 被 xack + max_ts 推进是「bar 已接收」的正确语义，不是 bug。

## 二、盲审 P0 发现（推翻「重放」路线）

方案盲审发现「不 xack 重放」路线两个 P0：

- **P0-A 重放空转**：`state.classify`（296）在 on_bar 前推进 `state.seq`；on_bar 失败不 xack 后，消息经 `_zombie_claim` 重投，classify 判 `dup_or_reorder`（307-309）直接丢——on_bar 从未被重试，PEL 永久滞留。
- **P0-B 误冻结**：max_ts 不推进 → 下一根 bar gap=120s>60 → `_ts_gap_frozen` 误冻结 sticky + 丢下一根 + 误报「源侧丢根」。修复比现状更糟。

## 三、最终方案（放弃重放，最小修复）

**只改一处**：`handle_msg` 的 `history.append` 包进 `try/finally`——on_bar 异常也补 history（护后续因子窗口）。其余（max_ts 前推、无条件 xack、guard 告警）全部保持。

```python
try:
    sig = strategy.on_bar(bar, list(history))
finally:
    stats["bars"] += 1
    history.append(bar)
    if len(history) > 100:
        history.pop(0)
```

**代价**（接受）：on_bar 异常的该 bar 信号未算出（因子/聚合异常），信号丢失。guard 已告警（critical），下一根 bar 正常。零重复发单、零冻结回归。

3. 行为级：构造 on_bar 抛异常 → 断言 history 仍 append（下根因子窗口不缺）——handle_msg 闭包难测，此判据由 staging 真跑覆盖。
