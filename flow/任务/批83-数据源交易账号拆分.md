# 阶段一 · 83a 拆表（重构，行为不变）

## 现状（揉合问题）

`external_interface` 单表（12 字段）用能力集 5 token 强行统一两类账号：

| 维度 | 数据源账号 | 交易账号 |
|---|---|---|
| 凭证 | token | 账号密码/API key |
| 能力 | hist_quote/ref_data/inst_event | rt_quote/trading |
| 处理 | 同步引擎 pull | hub/TD 长连接 |
| 插件 | DataSource | Broker/TD |
| params | rate_limits | 连接参数 |
| account_key | 无意义 | 资金账号 |

## 表结构

- **data_source**：`id, name, provider, market, credentials_encrypted, params(rate_limits/熔断), capabilities(hist_quote/ref_data/inst_event), position, enabled, created_at, updated_at`。`exchanges` 可删（routing 对 NULL 兼容全所）、`account_key` 删。
- **trading_account**：`id, name, provider, market, exchanges, account_key, credentials_encrypted, params(连接参数), capabilities(rt_quote/trading), position, enabled, created_at, updated_at`。

# 阶段二 · 83b 多源激活（功能，行为变化）

> 承接原批 74。前置=83a 拆表完成（在拆好的 data_source 表上做 provider 真路由）。

## 目标

`sync_config.provider` 从「摆设」激活为真路由：数据表选同步来源 = 注册的、有对应能力的 data_source 插件集合。

## 内容（原批 74 五点）

1. **provider 真路由**：sync_config.provider → handler 读 provider 选数据源（拆表后查 data_source）。现状「仅 K 线真路由」，其余同步项不读 provider。
2. **模块注册制**：数据源模块注册（TushareSyncModule 等），新增数据源=注册模块 + 实现 fetch 契约，引擎零改动（分层判据落地）。
3. **四条硬编码 beat 收编**：static-list-sync / convertible-terms / pool-data / full-calibrate 四条独立 beat 收编到注册制（现 tier1 9 键已配置驱动 0045 起，真硬编码=这四条）。

## 83b 盲审结论（agent a114057f）——可编码，先补 5 P1

### P1-1/P1-2 新增源须三处各注册一类（砍「SyncModule」新词）

现存三个 provider→类注册表，新增源须三处各注册一类，否则**串源**（确定性 bug）：
1. `data_source.py:169 _REGISTRY`（DataSource：连接/限速/熔断/用量/pacer）
2. `adapters/base.py:95 _ADAPTERS`（BaseDataAdapter：fetch 契约 + capabilities 真源）
3. `interfaces/base.py:21 _REGISTRY`（InterfaceProvider：配置表单 schema）

串源路径：新源只注册 adapter → `_get_rate_ds` → `get_data_source` 返回 None → 回落 `TushareDataSource()`（provider="tushare"）→ 熔断键 `rl:cb:tushare:0` → 新源失败/限速/用量全记 tushare 头上。**修法**：`get_data_source` 对「adapter 已注册但 DataSource 未注册」fail-fast（EX_CONFIG），不静默回落。砍掉「TushareSyncModule」新词——就是复用三个既有注册表各注册一类。

### P1-3 真路由在 engine.py（handler 分派），不在 routing.py

83b 点 1 的「provider 真路由」= **engine.py handler 分派**读 `cfg["provider"]`（tier1/静态/日历 handler 从硬编码 tushare 改读 provider），**不动 `routing.py` 的 `resolve()`**（那是 M2 试点，routing_kline_pilot 开关）。方案原「routing 上做真路由」表述误导，已纠正。

### P1-4 切换重建范围须界定

`delete_by_sync_item` 只支持 5 个 bar 族 sync_id（`_PER_SYMBOL_META`，不含 index_daily），`switch_provider_api` 对 tier1/静态/日历/index_daily 会 rollback+500。**裁定**：83b 只对 bar 族提供切换，非 bar 项 provider 恒 tushare 且前端下拉禁用（现状 `DataManage.vue:31` 已禁用态），不扩 delete_by_sync_item。

### P1-5 两维正交：provider 维 vs kind 维

模块注册制（管「数据源 provider 维」）与 `sync_kind_config`（0094 的 20 行 + 0106 的 10 行，管「同步项 kind 维」）+ `_HANDLERS`/`_VIA_KIND_IDS`（批 72 静态路由）**正交**，不是重建 sync_id 注册。新增源=三注册表各注册一类（provider 维），不动 sync_kind_config（kind 维）。

### P2 顺带

- index_daily / backfill_adj_factor 恒 tushare（`_get_kline_adapter({})`），显式声明为例外。
- 步 0 3 键须枚举到字面 + 连带 schedule/trade_day_filter/enabled 种子值 + 须在 `_HANDLERS`/`_VIA_KIND_IDS` 内可调度。
- 83a 遗留：`routing._load_state` SELECT 须去掉 exchanges 列（83a 删了 data_source.exchanges），否则 resolve SQL 报错——补进 83a 验收。
- 4 beat 收编（pool-data 是独立子系统：硬编码 tushare + pool_data_cursor + timebox + SyncLock）范围须界定（仅进注册表可路由，还是 fetch 契约重写）。
- **无第二数据源**：83b 上产后 provider 下拉仍只有 tushare（joinquant/ricequant 是 stub 空能力集），「选源真生效」无法行为级验证——验收须注入第二 stub 源或直改 DB provider 断言 fail-fast 而非静默回落（防 mock 绿）。
