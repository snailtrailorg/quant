# 批 83 · 数据源/交易账号拆分（external_interface 拆两张表 + 前端两页签）

> 立项 2026-09-29 深夜（用户裁定）。**抽象判据**：功能类似或有继承关系才抽象成一类实体；数据源账号（Tushare 拉取）与交易账号（XTP/EMT 下单+行情）完全不同、无继承，强行揉合=过度统一，拆分更简洁。

## 一、现状（揉合问题）

`external_interface` 单表（12 字段）：`id, name, provider, market, exchanges, credentials_encrypted, params, capabilities, position, enabled, created_at, updated_at, account_key`。用能力集 5 token 强行统一两类账号：

| 维度 | 数据源账号 | 交易账号 |
|---|---|---|
| 凭证 | token | 账号密码/API key |
| 能力 | hist_quote/ref_data/inst_event | rt_quote/trading |
| 处理 | 同步引擎 pull（短连接） | hub/TD 长连接 |
| 插件 | DataSource（data_source.py） | Broker/TD（broker.py/td_registry.py） |
| params | rate_limits | 连接参数（host/port） |
| account_key | 无意义 | 资金账号 |

**两域立法**（requirement-audit-rules 记忆）此前只做到「业务逻辑分离」，本批推进到「配置/表分离」。

## 二、拆分方案（方向，细节方案双盲定）

1. **表拆分**：`external_interface` → `data_source`（数据源）+ `trading_account`（交易账号）两张，各自字段清晰。
2. **能力模型**：5 token 保留（XTP 一个交易账号仍多能力 rt_quote+trading），但各表只用自己子集；`trading` 保词立法退役（8 处 SQL 域谓词 `'trading'=ANY(capabilities)` 改为直接查 trading_account 表）。
3. **后端**：15 个读表点分叉（`rate_limit`/`routing`/`data_source`/`interfaces`/`broker`/`md_gateway`/`md_hub`/`engine`/`monitor`/`tasks` + 路由 `risk`/`trading`/`chat`/`mgmt`）。数据源侧读 data_source，交易侧读 trading_account。
4. **前端**：集成中心单列表 + 能力筛选 → 两个页签（数据源 / 交易账号）。

## 三、影响面

- **迁移**：拆表 + 存量数据搬迁（现 external_interface 行按 provider 归入两表）。破坏性 DROP 需 allow_contract。
- **后端**：15 文件读表逻辑分叉 + `data_source.get_data_source`/`broker`/`md_gateway` 等取数路径。
- **前端**：集成中心页签拆分 + 能力筛选逻辑（每页签能力集收窄）。
- **能力模型**：D25 三层能力模型文档 + 集成中心 UI 能力筛选的语义调整。

## 四、验收判据

1. 迁移双向（拆表 + 搬迁数据零丢失）。
2. 全量 pytest 绿 + ruff 绿 + 前端 build 绿。
3. 行为级：数据源（Tushare）同步链 + 交易账号（XTP/EMT）hub/TD 链各真跑通（staging）。
4. 前端两页签各自正确显示 + 能力筛选。
