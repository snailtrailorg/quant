# 批 83 · 数据源/交易账号拆分（external_interface 拆两张表 + 前端两页签）

> 立项 2026-09-29 深夜（用户裁定）。**抽象判据**：功能类似或有继承关系才抽象成一类实体；数据源账号（Tushare 拉取）与交易账号（XTP/EMT 下单+行情）完全不同、无继承，强行揉合=过度统一，拆分更简洁。

## 一、现状（揉合问题）

`external_interface` 单表（12 字段）：`id, name, provider, market, exchanges, credentials_encrypted, params, capabilities, position, enabled, created_at, updated_at, account_key`。用能力集 5 token 强行统一两类账号：

| 维度 | 数据源账号 | 交易账号 |
|---|---|---|
| 凭证 | token | 账号密码/API key |
| 能力 | hist_quote/ref_data/inst_event | rt_quote/trading |
| 处理 | 同步引擎 pull（短连接） | hub/TD 长连接 |
| 插件 | DataSource（data_source.py） | Broker/TD（broker.py/td_registry.py） |
| params | rate_limits | 连接参数（host/port） |
| account_key | 无意义 | 资金账号 |

**两域立法**（requirement-audit-rules 记忆）此前只做到「业务逻辑分离」，本批推进到「配置/表分离」。

## 二、拆分方案（方向，细节方案双盲定）

1. **表拆分**：`external_interface` → `data_source`（数据源）+ `trading_account`（交易账号）两张，各自字段清晰。
2. **能力模型**：5 token 保留（XTP 一个交易账号仍多能力 rt_quote+trading），但各表只用自己子集；`trading` 保词立法退役（8 处 SQL 域谓词 `'trading'=ANY(capabilities)` 改为直接查 trading_account 表）。
3. **后端**：15 个读表点分叉（`rate_limit`/`routing`/`data_source`/`interfaces`/`broker`/`md_gateway`/`md_hub`/`engine`/`monitor`/`tasks` + 路由 `risk`/`trading`/`chat`/`mgmt`）。数据源侧读 data_source，交易侧读 trading_account。
4. **前端**：集成中心单列表 + 能力筛选 → 两个页签（数据源 / 交易账号）。

## 二·详细方案（勘察结果）

### 表结构

- **data_source**（数据源账号）：`id, name, provider, credentials_encrypted, params(rate_limits/熔断), capabilities(hist_quote/ref_data/inst_event), position, enabled, created_at, updated_at`。去掉 `market/exchanges/account_key`（数据源无市场维度/资金账号）。
- **trading_account**（交易账号）：`id, name, provider, market, exchanges, account_key, credentials_encrypted, params(连接参数 host/port), capabilities(rt_quote/trading), position, enabled, created_at, updated_at`。

### 关键决策点（方案双盲定）

1. **interfaces/base.py 抽象**：`InterfaceProvider` 基类（FIELD_SCHEMA/PARAMS_SCHEMA 配置自描述机制）对两类通用，**保留基类**；`_PROVIDER_MODULES` 注册表（56 行混合 tushare/xtp/...）拆成数据源 provider 注册表 + 交易 provider 注册表。
2. **迁移**：拆表 + 存量搬迁（按 provider 归入两表：tushare/tencent→data_source；xtp/emt_emq/binance/okx→trading_account）。破坏性 DROP external_interface 需 allow_contract。
3. **能力 token**：保留 5 token 常量（markets.CAPABILITIES），但每张表的能力子集在读取/校验处收窄。`trading` 保词 8 处 SQL 改为直接查 trading_account。
4. **前端页签**：集成中心「数据源」「交易账号」两页签，各自动态表单（据各自 provider 注册表的 schema）。

## 二·盲审结论（agent a9dd9e50）——方向对，补 4 点后编码

### P0-1 迁移须重指向 9 个 FK + 交易行保留原 id（关键）

8 表 FK 挂 external_interface.id，全交易侧语义：
- `live_task.account_id` RESTRICT（0100/0104）
- `position_snapshot.account_id` CASCADE（PK 组成）
- `position_refresh.account_id` CASCADE
- `account_snapshot.account_id` CASCADE
- `order_log.account_id` SET NULL
- `trade_log.account_id` SET NULL
- `account_permission.account_id` CASCADE（0097/0104）
- `trade_switch_session.from_account`+`to_account` RESTRICT（0107/0111）

**迁移设计**：①交易行**保留原 id** 迁入 trading_account（两表不各起新序列）→ 8 表 account_id 零重映射 + `data_source_usage.interface_id` 零迁移；②上述 FK 重指向 trading_account.id；③`account_key UNIQUE(provider,account_key)`（0099）重建到 trading_account；④DROP external_interface 不能裸 DROP（CASCADE 会静默删 FK），须显式先 drop FK 再 drop 表，走 allow_contract。

### P1-1 data_source 保留 market（误删）

tushare 有 `market='astock'`，三处依赖：`routing.py:313-322` `_row_covers` 用 market/exchanges 做 scope 覆盖（删后 market="" 回落全市场，tushare 误成 crypto 候选 + `routing.py:283` 权限过滤空资源 fail-closed 滤掉全部数据源）。**修法**：data_source 保留 `market`；`exchanges` 可删（routing 对 NULL 兼容全所语义）；`account_key` 删正确。

### P1-2 tencent 归类裁定

tencent 唯一能力 `{rt_quote}`（0096 分钟退役后），功能已硬编码 `qt.gtimg.cn` 不读表，是「僵尸行」。**裁定**：tencent 行**整体退役**（迁移不搬，直接删）——能力分区保持 hist_quote/ref_data/inst_event 纯粹。

### P1-3 读点清单补全 + 「9+1 处」修正

真实 SQL 读点仅 **9 文件**（非 15——databus/rate_limit/md_gateway/md_hub/engine/interfaces 是 docstring/传递点，无真实 SQL）。漏 3 处真实读点：`trading.py:31/37`（list_live_tasks JOIN 取账号名）、`mgmt.py:565`（put_account_permission 的 trading 谓词）、`scripts/verify_integration.py:121`。`trading` 保词实际 **src 内 9 处 + scripts 1 处**（markets.py:8 注释「8 处」同步改）。

### P2 顺带

- 前端能力筛选：每页签能力集已收窄，capabilities 列对 trading_account 近似常量；reorder/create 的 position 从「全局单序列」改「单表单序列」（mgmt.py:203/228）。
- `schema_expectations.txt` 重新生成（新两表 + 删旧表）。
- D25/A02 文档 + markets.py:8 注释更新。
