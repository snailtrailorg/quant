# 批 85 · 破坏性迁移两步走立法（expand → contract）

> 立项 2026-09-30（威廉姆裁定「立」）。来源＝批 83a 拆表过渡期勘察：`0116` **一步到位**
> （`op.drop_table("external_interface")` + `op.drop_index(...)`），而整条部署管道的自动回滚
> **建立在「迁移 expand-only（旧代码可读新 schema）」这个前提上**（`release.yml:582` 自陈）。
> 一步到位的 contract 型迁移**打破了这个前提**，于是有了批 83a 那场手工双态兜底。
> 本批＝**把前提变成纪律 + 闸门**，让将来不再需要那种兜底。
> 姊妹批：`flow/任务/批84-回滚诚实性与schema一致性.md`（84＝管道不许撒谎，85＝迁移不许违规）。

## 目标

把「破坏性 DDL 必须两步走（expand → 双读双写/回填 → contract）」从**口头前提**变为
**可执行的立法 + 自动化闸门**；并给现有违规迁移（`0116` 等）一个明确的处置结论。

## 背景（为什么是「前提」而不是「偏好」）

- `rollback-tasks.yml` 不含 alembic/downgrade → **回滚只回代码、不回 schema**。
- 因此管道「失败自动回滚」的**唯一合法性**来自：新 schema 仍能被旧代码读（expand-only）。
- contract 型迁移（DROP/RENAME/类型收窄）**恰好**破坏这一点。而阶段 4 的 DDL 门只认
  `-e allow_contract=true` 开关就放行（`release.yml:315-350`），**不校验迁移是否真 expand-only**
  ——即「前提」在门里**没有实现**，只是被文字声称。
- 结论：**要么让 DDL 门真的守住 expand-only，要么把 contract 型从管道里拿掉**。本批做前者 +
  给出合规的两步走通道。

## 依赖（就绪）

`deploy/playbooks/release.yml`（阶段 4 门 `:315-350`）✅｜迁移链 `server/migrations/versions/`（head 可跑、
双向往返已复现）✅｜`flow/规范/`（任务模板/八步法则等既有规范）✅｜静态扫迁移目录的闸门先例
`server/tests/test_jsonb_columns_guarded.py`（枚举 + 白名单 + 反证手法）✅

## 产出

1. **新规范** `flow/规范/破坏性迁移-两步走.md`：
   - **判定表**：哪些 `op` 属 expand / contract（至少覆盖 `drop_table`/`drop_column`/`drop_index`/
     `alter_column(type_=)`/`add_column(nullable=False 无 server_default)`/`create_index`（非 CONCURRENTLY）/
     列改名；每条给「为何危险」一句）；
   - **两步节奏**：expand 上产 → （可选）双读双写/回填 → **观察窗** → contract 上产；每步的闸门要求与回滚后果；
   - **声明格式**（见下 §接口契约）+ **收口条件**（contract 上产后 expand 侧残留必须清理，否则 = 债）；
   - 与**八步法**的挂接（哪一步产出声明、哪一步校验）、与 **D18 §2.3 DDL 规范**的关系（D18 讲 DDL 怎么写，本规范讲 DDL 何时写）。
2. `docs/design/D18-数据库操作规范.md` §2.3 加**一行指针**（指向本规范；不重写该节）。
3. **迁移声明**：迁移文件头加机器可读声明行——
   `# EXPAND-CONTRACT: phase=expand|contract pair=<另一半迁移 id>`（非破坏性迁移可不写）。
   本批**只给现有违规迁移补声明或标「历史遗留·一步到位」**，**不改任何既有 DDL 语义**。
4. **闸门** `server/tests/test_migration_expand_contract.py`（新）：
   - ① 扫 `migrations/versions/`：命中破坏性 op 而**无声明** → 红；
   - ② `pair` 必须指向**真实存在**的迁移文件，且该文件声明的 phase 相反 → 否则红；
   - ③ **孤儿检测**：只有 contract 无 expand（或缺另一半）→ 红；
   - ④ 历史遗留白名单（`0116` 等）逐条写明状态与理由，白名单**反向校验**（防止白名单腐化——同 `test_jsonb_columns_guarded.py` 手法）；

## 接口契约

- 迁移文件头声明行（约定，非代码 API）：
  `# EXPAND-CONTRACT: phase=<expand|contract> pair=<迁移 id>`
  —— `phase=contract` 必须带 `pair`；`phase=expand` 的 `pair` 可暂缺（后续 contract 补齐），但**闸门③**
  会把「expand 侧声明了却始终无 contract」列为**待收口项**（不做红、进报告，避免半成品迁移被误卡）。
- 新测试文件对外无 API；仅被 `pytest tests/` 收集。

## 验收标准

- `pytest server/tests/test_migration_expand_contract.py -q` → 全绿
- `pytest server/tests/ -q` → 不回归
- `cd server && QUANT_DB_URL=... venv/bin/python -m alembic upgrade head` + `downgrade -1` + `upgrade head`
  双向往返仍绿（**证明加注释行零副作用**）
- `ruff check .` 全绿
- **反证钉**（三项）：① 撤掉某迁移的声明行 → 闸门①红；② 把 `pair` 改成不存在的 id → 闸门②红；
  ③ 删掉 expand 侧 → 闸门③红。恢复即绿。
- 交付物含**处置结论表**：现有破坏性迁移逐条（`0116` 及其它）→ 「补两步走 / 有意识接受并标遗留」二选一，
  由审核方裁定；**不得留空**。

## mock 方式

纯静态扫描（读迁移文件文本 + 正则/AST 识别破坏性 op），**不连 DB、不跑迁移**；
双向往返验收用真实迁移链（scratch schema，`PGOPTIONS=search_path=...`，同批 83a 手法）。
