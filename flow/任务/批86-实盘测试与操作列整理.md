> 立项 2026-10-02（威廉姆提出四问 → 当场裁定）。来源＝实盘任务列表页 UX 走查。
> 本批＝**两件独立的事捆在一起交付**：① 新功能「实盘测试」（paper 模式）；② 操作列一致性整理。

## 一、威廉姆的四问与裁定（原文要点）

| # | 问题 | 裁定 |
|---|------|------|
| 1 | 实盘测试该放这里还是策略中心？缺省角色功能宜集中在一个菜单组 | **实盘测试 = 用实盘真实数据验证策略，但不真实下单**（= paper trading）。产品里**不存在**，需新建 |
| 2 | 操作列没用图标按钮+title；新按钮颜色是预定义 token 吗？ | 确认是缺陷（详见 §二） |

| 4 | 「更多」点了是删除 | 确认是名不副实的 bug。**裁定：展开**成 启动/停止/查看结果/编辑/删除 等 |

**关键澄清（问题 1 的前提）**：菜单里**没有**「实盘测试」页面，代码库与 i18n **零命中**。
它是批 77 时威廉姆口述的原则词（「analyst 只能回测和实盘测试，不能执行实盘交易」），
**从未落地成产品功能**。⇒ 本批要**先把它造成功能**，才谈得上放哪个菜单。

### ⭐ 威廉姆的治理原则（2026-10-02 当场裁定，本批最重要的输入）

> **「analyst 把策略提交 trader 跑测试。这里的不透明会显得很严格——对策略的实测结果很重视，
> 避免策略在 analyst 的全面掌控下，很容易落入噪声之中。」**

这条**不是随手决定，是一条职责分离原则**，直接改变本批设计：

- **造策略的人 ≠ 验策略的人**。analyst 造，trader 验。
- **不透明是刻意的特性，不是缺陷**：analyst **看不到**实盘任务的运行细节，
  是防「为了通过而调参」（Goodhart 定律）的防火墙。
- ⇒ **analyst 连实盘任务列表都不该看到**（不只是不能操作）。

**这推翻了初版方案的两处设定**（初版写「analyst 可读、保持现状」与「实盘测试做成 tab」），
两处均已按新原则改写。

## 二、现状勘察（逐条实证）

### 2.1 菜单分组现状（问题 1）

`web/src/layouts/MainLayout.vue:72-105`，四组：

```
研究面 research : 选股 · 股票池 · 因子 · 策略 · 回测 · 每日洞察     ← 权限键 strategy_control
实盘面 live     : 实盘任务 · 交易台                                  ← 权限键 live_control
风控   riskgrp  : 风控 · 对账 · 风控规则
运维   ops      : 用户 · 数据中心 · 集成 · 监控 · 路由 · 权限资源 · 设置
```

**实盘任务已在「实盘」组内**（与交易台同组），符合威廉姆「一个角色的功能集中在一组」的偏好。
`router.js:24` 把 `live-task` 写在第 22 行 `// 策略` 注释段下，是**注释归属错误**（实际渲染走 `live` 组），
顺手修正注释。

### 2.2 nav 维现状（决定 analyst 可见性的机制）

`perm_registry.NAV_ITEMS_BASE`（`perm_registry.py:37-57`）是 nav 条目的**唯一字面量层**，
`live-task` 登记为 `{"id": "live-task", "group": "live", "order": 1}`。

`perms.load_nav_map`（`perms.py:196-222`）直读 `permission` 表 nav 维，
**无字典兜底**，且注释明写「**无配置={}（=readwrite 缺省，前端现行为）**」。

⇒ **现状：`live-task` 对 analyst 是可见的**（表里无该行 ⇒ 缺省 readwrite）。
⇒ 这正是威廉姆要改的——**且改法是纯数据（补 nav 维行），零代码**。

⚠️ **nav 维也有「加项 ≠ 加行」问题**：新增 nav 项后，若要对某角色设 `hidden`，
必须**补 `permission` 表 nav 维行**（同批 77 P0 同型病）。本批用迁移 + 闸门双保险。

`router.js:89-104` 的守卫证明 nav 与 api 是**两套独立维**：`state === 'hidden'` 直接 `next('/')`，
与 `read` 键无关。

### 2.2.1 ⚠️ 初版「tab 方案」被否决（本批第一个自查出的设计缺陷）

初版方案倾向「实盘测试做成实盘任务页的 tab，不新增菜单项」。**按威廉姆的治理原则重审，
此方案有一个致命问题**：

`live-task` 是**一个页面 = 一个 nav 项**。tab 切换**不经过路由** ⇒ nav 维**管不到 tab 级**。
于是 analyst 的可见性陷入两难：

- nav 把 `live-task` 设 `hidden` ⇒ **连实盘测试 tab 也进不去**（两者同页）
- nav 保留 ⇒ analyst 看到「实盘任务」菜单，点进去是「实盘测试」⇒ **名字与内容不符**

⇒ **改为独立路由 `/live-test` + 独立 nav 项**，放 `live` 组。收益：

- `live-task` / `trading` 对 analyst `hidden`（干净，符合治理原则）
- `live-test` 对 analyst `readwrite`
- **analyst 的「实盘」组里只剩「实盘测试」一项** ⇒ 威廉姆要的「一个角色功能集中一组」**达成**

### 2.3 「实盘测试」在现有链路里的位置（问题 1 的技术核心）

`server/src/strategy_framework/adapters.py:5-11` 记载了**实盘下单三级开关（AND）**：

```
1. .env ENABLE_LIVE_TRADING                    ← 全局总闸（settings.is_live_trading_enabled）
2. live_trading_config 分项                    ← 市场级（convertible/etf/astock/binance_perp/okx_perp）
3. strategy_config.enabled + backtest_verified ← 策略级（scheduler 层）
```

**缺口定位**：链路是 `回测 → [缺] → 实盘`。第 3 层的 `backtest_verified` 就是「回测通过」，
下一级直接是全局实盘闸。**「用实盘数据验证但不下单」这一级没有载体。**

**建设成本比预想低**：`server/src/strategy_runner/main.py:211` 已有现成的「不下单」分支：

```python
stub_adapter = create_adapter(provider)   # stub（is_live 关时仅启动不下单）
```

即：**「跑真实行情流 + 不下单」的机制已存在**，只是它绑定在**全局总闸关闭**时（`is_live` 关），
而不是 per-task 的 paper 模式。⇒ 本批要做的是**把这个能力从「全局兜底态」提升为「per-task 显式模式」**。

**为什么不能复用全局总闸**：`is_live` 关时**所有**任务都不下单——无法同时「A 任务 paper、B 任务实盘」。
且全局闸一关，`main.py:200-205` 的加密 stub 硬闸也失效。⇒ 必须是**任务级**开关。


### 2.3 操作列的四个缺陷（问题 2/3/4）

`web/src/views/LiveTask.vue:100-116` 现状：

```vue
<el-button v-if="row.status !== 'running' && canLive" type="success" @click="onStart(row.id)">启动</el-button>
<el-button v-if="row.status === 'running' && canLive" type="danger" @click="onStop(row)">停止</el-button>
<IconBtn size="small" type="warning" :icon="Unlock" :title="..." v-if="..." />       ← 唯一合规的
<el-button @click="gotoDetail(row.symbol)">个股</el-button>
<el-button v-if="..." @click="openMore(row)">更多</el-button>
```

**(a) 图标按钮不一致**：`IconBtn` 是批 21 立的**全站统一图标按钮组件**（当时威廉姆裁定「统一风格，
尺寸唯一源=--icon-btn 令牌」）。`Backtest.vue:68-69` 操作列已**全用 IconBtn**。而 LiveTask 的
四个按钮是**批 16 写的，早于批 21** ⇒ 这一列现在是**混血**（一个圆图标 + 四个方文字）。

**(b) 颜色不是项目 token —— 比表面严重**：
`type="success"` / `type="danger"` 走 **Element Plus 默认色**（≈`#67C23A`/`#F56C6C`），
**不是**项目 `tokens.css` 的语义色：

```css
--critical: #7F1D1D;   /* 独立深红，区别于 --up；强制配图标+背景 */
--success:  #0E8388;   /* 青绿系，仅 toast/操作反馈，必配 ✓ 图标 */
--up:       #C8102E;   /* 涨/盈利 */
--down:     #0A7A54;   /* 跌/亏损 */
```

且 `tokens.css:41-43` 写明设计纪律：「**--success/--critical 只用于操作反馈与系统状态，互不借用**」。
EP 的 `danger` 红 ≈ `#F56C6C`，与项目 `--critical` `#7F1D1D` **不是一回事**。

**闸门盲区**：`scripts/check-tokens.sh` 只数 **px / hex / font-size** 三类（`count_px`/`count_hex`/`count_fs`），
**管不到 `type=` 属性** ⇒ 这类色彩漂移**永不报警**。本批顺手在闸门里加一维（见 §四 产出 4）。

**(c) 「个股」文案**：`locales/index.js:369` `symbolDetail: '个股'`。**名词而非动词**，
且这是**跳转到个股详情页**（`/stock/:symbol`）的导航动作。威廉姆裁定**移出操作列**。

**(d) 「更多」名不副实**：弹窗（`LiveTask.vue:120-130`）里**只有一个输入框 + 一个删除按钮**。
对照 `Backtest.vue:69` 的「更多」有**两个操作**（终止/删除）⇒ 名副其实。
LiveTask 的注释自称「对齐 Backtest 同批『更多』模式」——**抄了壳没抄内容**。
威廉姆裁定：**展开**操作列（启动/停止/查看结果/编辑/删除），不再用「更多」收纳。

## 三、方案

### 3.1 实盘测试（paper 模式）—— 数据模型与运行语义

**权限键**：新增 **`live_test`**（API 键 14→**15**）。理由见下「为什么不是复用 live_control」。

**⚠️ 必须遵守批 76b/77 的立法「加键 ≠ 加行」——四条齐动**（缺一即静默失效）：
1. `perm_registry.API_PERM_KEYS`
2. `perms.PERMISSIONS`（**仅新环境兜底**）
3. **seed 迁移补 `permission` 表行（prod 唯一真源）** ← 批 77 漏的就是这条，直接导致 P0
4. 前端 `permGroups`

**缺省持有者**（依威廉姆原则「analyst 只能回测和实盘测试」）：

| 角色 | `live_test` | 理由 |
|------|-------------|------|
| analyst | ✅ | 原则原文点名 |
| trader  | ✅ | 实盘交易的下位能力，trader 必有 |
| admin   | ✅ | 地板 |
| viewer  | ❌ | 只读 |

**数据模型**：`live_task` 加一列 **`mode`**（`expand` 步，`TEXT NOT NULL DEFAULT 'live'`，
值域 `live` / `paper`，由 CHECK 锁）。**不改表名、不拆表**——paper 与 live 共用任务生命周期
（创建/启停/冻结/心跳/日志），差异**只在「是否真下单」一个点**。拆表会把 8 个端点、
冻结史、心跳、单元安装全部复制一遍 ⇒ 明确否决。

**运行语义**：`mode='paper'` 时，`main.py` 走**已有的 stub 分支**（`main.py:211`），
但**不再依赖全局 `is_live` 关**，而是按 per-task `mode` 判定：
- `mode='live'` → 现有逻辑（三级闸 AND，一字不改）
- `mode='paper'` → 走 stub adapter，**真实行情流入 + 真实策略计算 + 真实风控判定 + 不下单**

**⭐ 关键设计点：paper 必须走完整风控链，只是最后一步不下单。**
否则「验证」是假的——若 paper 绕过 `check_order`，它验证的不是真实链路。
⇒ stub adapter 的 `send_order` **仍触发** `RiskControl.check_order`，
`check_order` 通过后才「假装成交」（记 paper 成交到日志/内存，不落真单）。

**为什么不是复用 `live_control`**：
- 语义不同面：`live_control` = **执行实盘交易**；`live_test` = **不执行的验证**。
- 威廉姆原则**明确区分**这两者（「能实盘测试，不能实盘交易」）⇒ 拆键是原则的直接落点。
- 风险面：`live_test` 不下单 ⇒ 危险度**低于** `live_control` ⇒ 可给 analyst（而同组 `live_control` 不可）。

**⚠️ 与批 77 裁定的兼容性说明**：批 77 裁定「解冻与起停同属实盘面同键，合并不拆分」——
本批**不违反**该裁定。批 77 说的是 `live_control` **内部**不再拆（同为执行面）；
本批新增的是**另一个面**（非执行面），不是把 `live_control` 拆开。

### 3.2 菜单归属与可见性（问题 1 的答案）—— ✅ 已裁定

**入口形态：独立路由 `/live-test` + 独立 nav 项，放 `live` 组**（非 tab，理由见 §2.2.1）。

**nav 维缺省矩阵（本批要设的目标态）**：

| nav 项 | analyst | trader | admin | viewer |
|--------|---------|--------|-------|--------|
| `live-task`（实盘任务） | **hidden** ← 本批改 | readwrite | readwrite | hidden |
| `trading`（交易台） | hidden（现状？待核） | readwrite | readwrite | — |
| **`live-test`（实盘测试）** | **readwrite** ← 新增 | readwrite | readwrite | hidden |

⇒ **analyst 的「实盘」组里只剩「实盘测试」一项**，达成威廉姆「一个缺省角色的功能集中在一组」。

**⚠️ 治理原则的另一面（必须同时处理）**：

「analyst 看不到实盘任务」这条**只在 UI/nav 层实现是不够的**——`live-task` 页面本身
（`web/src/views/LiveTask.vue`）**无 api 维门槛**（列表端点只要求 `read`，analyst 有 `read`）
⇒ **analyst 直接敲 URL `/live-task` 仍能看到**。

两个处置选项：
- **A（推荐）**：给实盘任务列表/详情端点加**新的读取面**门槛——不能只靠 `read`。
  但 `live_control` 是「执行」键，用它当读门槛会语义混淆。
  ⇒ 建议新增 **`live_view`** 键（看实盘任务），或复用 `live_control` 作为**读写同门**（更简）。
- **B**：只在 nav 层隐藏 + 路由守卫加 `meta.perm`（前端门，绕过=直连 API 仍可读，**不严**）。

⇒ 本批**取 A**：实盘任务的**读与写同门 `live_control`**（有实盘权的人才有必要看实盘任务）。
理由：① 语义干净（实盘面一件事一个键）；② analyst 天然看不到（无 `live_control`）；
③ 不新增键，避开「加键 ≠ 加行」风险。**副作用**：`viewer`/`analyst` 连只读都看不到——
但这**正是威廉姆要的严格性**。

⇒ 于是 `live-test` 成为 analyst 唯一的实盘面入口，**`live_test` 键独立**（见 §3.1）。

即：§3.3 的完整六钮是**批 B 收敛后的终态**；批 A 只落**能真跑的四钮**（启/停/解冻/删）+「个股」移出 + 拆「更多」。

理由：它是导航动作，与被操作对象（任务）无关；放名称列符合「点名字看它是什么」的直觉。

**不改 strategy_id/symbol/account_id**——它们决定已启动进程的身份，改它们须删重建）。

**⚠️ 编辑的权限门**：paper 任务须 `live_test`、live 任务须 `live_control`——
**按任务 mode 分档判**，避免 analyst 通过「编辑」绕到实盘任务上。

#### 3.3.1 颜色令牌核查结论（问题 2 的后半：颜色是预定义 token 吗？）

**答：不是。** 改前操作列的 `type="success"|"danger"` 是 **Element Plus 内置语义色**
（`--el-color-success` 等），不是本仓金融令牌（`--up/--down/--warn/--critical/--success`）。

关键点：**令牌门结构上看不见它**。`scripts/check-tokens.sh` 原只数三维——
`count_px`（内联 px）/`count_hex`（hex，排除 `#defa*` 数据面色）/`count_fs`（font-size）。
它扫的是**样式值**，看不见 `type=` 这种**属性**。⇒ 用 EP 语义色替代令牌，计数永不变，**永不告警**。

**批 A 修法（两手）**：
1. **收敛到 `IconBtn` 的 tone**——`IconBtn` 是批 21 用户裁定的全站统一圆形图标按钮，
   tone 分档（`''`=品牌蓝 / `success` / `warning` / `danger`）是**唯一受批的语义色入口**，
   内部用 EP 变量但不产生 `type=` 字面量；
2. **令牌门补第四维 `count_btn_type`**：数 `<el-button ... type="(success|warning|danger)">` 字面量，
   基线只许降（`--update` 落库，旧基线无 `BASE_BTN` 键时兜底 0）。
   `primary`/`info` 不计——前者是 EP 主色非语义分档，后者是中性，都不承担「这动作有多危险」的语义。

> 实测基线变化：`PX=43→39`（本批顺手减员）、`HEX=18`、`FS=0`、**`BTN` 首采 20**。
> 这 20 处是**存量**（其余页面的 el-button 语义色），不是本批新增——门只保证「不再涨」，
> 存量清理是后续的独立活（不在批 86 范围，避免本批变成全站改造）。

## 六、风险与边界

- **paper 不得绕过风控**（§3.1 ⭐）——否则「验证」是假的。这是本批最易做错的一点。
- **`live_test` 加键必须四条齐动**——批 77 的 P0 就是漏了第 3 条（seed 迁移），
  本批用 `0126` + 新闸门双保险。
- **不给 `paper` 开 `live_control`**：paper 任务**永不能**切换成 live（要 live 请新建 live 任务）
  ——避免「验证着验证着就实盘了」的意外升级路径。
- **冻结/心跳语义对 paper 同样适用**：paper 也消费实盘流 ⇒ 也会有 gap/污染 ⇒
  冻结史必须照记（否则 paper 的验证结论不可信）。
