# 批189-M1 十个 P0 的根因分析（2026-11-19）

> 目的：不是解释这 10 条，而是找出**产生它们的机制**，并确认同类问题在 M2–M8 不会再以同样方式出现。

## 一、10 个 P0 的症状归并

| 症状 | 涉及 P0 |
|---|---|
| 把既有对象当新建 | data_source（0116 已有）、provider_session_slot（0179 已有） |
| 存量数据形态假设错 | 虚拟纸账户 `capabilities={}` 落 0 行；`quote_account_id` 无条件自指 |
| 枚举清单漏项 | 8 处引用漏 `freeze_event`（第 9 处）、漏 `account_permission` |
| 顺序靠直觉 | PK 含 account_id → 先建后删/先删后建都错 |
| 规则与取值域未交叉 | C1 正则 `^[a-z][a-z0-9-]` vs provider `emt_emq` |
| 契约与部署链脱节 | release.yml 无停服阶段；波次仍按旧 id；hbcheck 新态未定义 |

## 二、根因（5 条，按贡献度排序）

1. **写作输入错位（贡献 5/10）**：M1 是从 M0 契约「推演」出来的，不是从 `server/migrations/versions/`、`deploy/wrappers/`、`release.yml`「核对」出来的。凡是"表/列/键/阶段"的存在性，都在凭印象。
2. **观测面有偏（2/10）**：profiling 用列表 API（过滤 `is_virtual=false`）+ `-t` 子集 dump，把"看得见的"当成全集——恰好漏掉会崩迁移的那类行。
3. **枚举式清单（2/10）**：靠人列"8 处引用""3 张新表"，清单天生会漏，且无人对"清单完整性"负责。
4. **规则与数据不交叉（1/10）**：契约写了正则/枚举语义，但没有拿真实取值跑一遍（`emt_emq`、`id=51`、`id=502`）。
5. **顺序无依赖图（1/10）**：PK/FK/触发器/索引互相牵连，凭"先建后删"的直觉必然错。

## 四、还没机械化的两处（明确承认）

- **DB 级数据形态**：`is_virtual` 行、slot 现存行、usage 实际分布，API 看不到；当前只能靠 michael 跑 SQL。已在 M1 §1 写成前置检查项，不靠记忆。
- **运行期语义**（断连竞态、窗边界、告警时序）：静态检查抓不到，靠 E1–E9 + staging 彩排。

## 五、审核模板（把「抽样审」变「按类核」）

后续迁移类方案的双盲审，固定六类必查对象，每类必须给 `file:line` 证据，缺证据视为未审：
`①表/列来源（create/rename/alter）` `②约束与依赖（PK/UK/FK/trigger/index）` `③存量数据形态（空值/异常枚举/隐藏行）` `④键与单元（写入点+读点）` `⑤部署阶段与 wrapper` `⑥契约取值域（正则/枚举 vs 真实数据）`。

## 六、结论

- 10 个 P0 是 **5 个根因的 10 个症状**；表层改完不解决，机制补上才能复用。
- 已补 5 个可执行机制（2 个新脚本 + 3 类断言/清单），M2–M8 沿用同一套门禁。
