# 批189 订单/清仓异常 RCA（2026-11-23 盘中实测）

> 原则：先查清再改。本文只记录证据与结论，不含代码修改。

## 1. 现象

- 用户在 UI 清仓，前端显示“清单为空（全部平仓完成）”，但仓位仍在。
- 部分买单价格优于撮合价却一直 submitted；撤单返回 requested=0/items=[]。
- 低价买单（002594 @72.40、300760 @148.00，市价约 79/183）却立即 all_traded。
- 603118 新买单券商拒：代码 11110000，信息 10000。
- 今日买入的 3 只持仓 close-all 返回 skipped_t1、positions_remain=2300。

## 2. 证据

### F1 清仓“失败”= T+1（系统行为正确，UI 文案错误）

- GET /api/risk/close-result/recent：closed_requested=0、skipped_t1=["300760.XSHE","002594.XSHE","688018.XSHG"]、positions_remain=2300、final_reason="final:done"。
- 三只均为当日买入（A 股 T+1），交易所不允许当日卖出；后端按规则跳过。
- 前端 Emergency.vue::fmtFinal 原只认 closed_requested=0 + 空清单 ⇒ 追加 finalClean（“清单为空（全部平仓完成）”），未读 skipped_t1/positions_remain。
- 已修并上产 202611231405-be3263d：有 T+1/剩余仓位时不显示“完成”。

### F2 撤单 requested=0 的根因：撤单只扫缓存且漏 SUBMITTING

- _cancel_working_orders（trading.py:335-368）只遍历 adapter.query_orders()，而 XTP 的 query_orders() 只返回进程内 _orders 缓存（providers/xtp/td.py:229-234），不查券商。
- working 集合 = SUBMITTED/NOT_TRADED/PARTIAL，不含 SUBMITTING。
- 订单发出后网关先回调 SUBMITTING；若券商后续没有 NOT_TRADED/REJECTED 回报，缓存里就停在 SUBMITTING ⇒ 撤单扫描不到 ⇒ requested=0；DB 的 order_log 却仍显示 submitted（提交侧写的）。
- 结论：撤单链路与 order_log 状态机之间存在断层；不是“没有单”，而是“单不在可撤集合里”。
- 补充实测（2026-11-23 15:2x）：DB 兜底初版带 `ts >= now()-1 day`，psql 同条件 count=0；手工单的 `ts` 可能为 NULL（order_log 默认未生效/历史行），导致“有 vt 却查不到”。已改为按 status+vt 查询、去 ts 过滤，并加 rows 日志；待下一交易时段复测。

### F3 submitted 长期不终态：缺超时对账

- write_order_status（trading.py:91-108）只回写 PARTIAL/ALL_TRADED/CANCELLED/REJECTED；SUBMITTED/NOT_TRADED 视为非推进，不写。
- 没有对 submitted/submitting 的超时巡检或券商在途委托查询；券商无回调时永远悬挂。
- 4 笔 UI 订单（603118、002142、688018、001309）即此形态；其中 603118 后续新单能拿到券商拒单码，说明回调并非全断，而是部分单无后续事件。

### F4 低价买单“成交”：XTP 测试撮合行为，不是成交价取值 bug

- write_trade_log（trading.py:180-184）价格取 Trade.price（券商成交回调），不是订单价。
- 002594 @72.40、300760 @148.00 均回调 all_traded，trade_log.price 同为 72.40/148.00；持仓随后增加（300760 500→600，成本被拉低到 178.616）。
- 说明 XTP 测试环境撮合按委托价成交/模拟撮合，与真实市场撮合语义不一致；因此：
  - 不能用测试账号验证“限价单不成交/排队/撤单”；
  - E1/E5 的成交/撤单语义必须在真实柜台或仿真环境验证。
- 不是 trade_log 抄订单价的 bug（代码读的是回调价）。

### F5 券商拒单可落库，但无错误明细

- 603118 13.10 返回 rejected + “交易委托失败，代码：11110000，信息：10000”。
- 但部分拒单（如昨日 600177/300760 等）error 为 None，说明拒单错误透传不一致（pop_order_error 取到的时机/匹配键可能丢失）。

## 3. 结论分级

| # | 结论 | 性质 |
|---|---|---|
| F1 | 清仓未执行=T+1，系统按规则跳过；前端误报完成 | UI bug（已修） |
| F2 | 撤单只扫缓存 + 漏 SUBMITTING ⇒ 撤不到悬挂单 | 状态机/撤单链路 bug |
| F3 | submitted 无超时对账，券商无回报即永久悬挂 | 可观测性/对账缺口 |
| F4 | 低价单成交=测试撮合按委托价成交 | 测试环境限制，非代码 bug |
| F5 | 拒单错误透传不一致 | 错误映射 bug |

## 5. 修复方向（待确认后动手）

1. 撤单：_cancel_working_orders 增加 DB 在途单（order_log.status IN submitted/submitting/partial）按 vt_orderid 盲撤；working 集合纳入 SUBMITTING。
2. 对账：定时把超过 N 秒仍 submitted 的单标记 unknown/查询券商；禁止长期悬挂。
3. 错误映射：拒单回调按 vt_orderid/client_id 双键匹配，统一写 error。
4. close-all UI：已修；再把 skipped_t1 文案明确为“T+1 明日可卖”。
5. 测试策略：限价/撤单/排队语义移至真实仿真环境；测试账号只验证链路可达与状态机。
