## 三、数据正确性契约（4 条核对 + 1 个 P0）

### 3.1 11 字段结构 ✅
`(symbol, freq, ts, open, high, low, close, volume, amount, adj_factor, source)` 结构一致（base.py:176-182）；source=self.provider；ts 读 trade_time/trade_date 按 freq 分支正确。

### 3.2 单位换算 ❌ P0（本轮最重要发现）

**契约**（24 §2.1 + 附对照表）：`volume=股、amount=元`，**各源在 to_bar_rows 内换算**（Tushare vol 手×100、amount 千元×1000）。

**实现**（base.py:180）：
```python
_safe_float(row.get("vol", 0)), _safe_float(row.get("amount", 0)),   # ← 无 ×100/×1000
```
金标准 to_save_rows/to_save_rows_min（tushare_adapter.py:227-262）**同样无换算**。全仓检索确认：bar 写入路径（data_sync/data_platform/db.save_bars）零处 vol×100/amount×1000；而 market_snapshot.py:95-96、stock_detail.py:173-177 对**腾讯**数据明确做了 ×100/×10000 归一到股/元。

**后果链**（若 Tushare 确实返回手/千元——24 号附对照表自证）：
1. bar 表存的是「手/千元」，与 23 §6.1 schema 声明「股/元」矛盾
2. 与 hub XTP（股/元）、腾讯实时（已归一股/元）**量纲差 100/1000 倍**
3. 动摇 06 号核心原则「回测实盘 schema 对齐、20 天零迁移切 live」——schema 对齐了、**量纲没对齐**，切 live 瞬间 volume 突变 100 倍

**定性**：要么代码错（漏换算，回测/因子量纲错 100/1000 倍），要么文档错（实际口径一直是手/千元，则「股/元」是理想宣言）。无论哪种，**契约与实现不一致，且金标准兜底把错误固化**。必须立即定性并修——这是「三合一 + 金标准逐字节一致」掩盖了一致性错误，双盲审的兜底设计在此失效。

## 五、总评与建议

**架构与工程品质高**：10 裁定全落地、双层抽象干净、策略模式正确、5 盲审 bug 全修、切换重建原语带防护、诚实标注边界（不虚报「已做」）。这套抽象是真接聚宽/米筐的合格地基。

**唯一 P0（必须立即定性）**：§3.2 单位换算缺失。建议动作：
1. **定性**：查生产 bar 表现值 + Tushare 实际返回单位，判定是「代码漏换算」还是「文档宣言错」
2. 若代码错：to_bar_rows 补换算（Tushare ×100/×1000），**同步修金标准 to_save_rows**，加单位回归测试（对照 hub XTP 同标的 volume 量级）
3. 若文档错（实际口径就是手/千元）：改 23 §6.1 与 24 §2.1 的 schema 声明 + 附对照表，并**显式声明「bar 表=手/千元、bar_hub=股/元」这一跨表量纲差异**——但此路径会动摇「零迁移切 live」，需你拍板

**次要（低优先）**：转债 adj_factor 恒 NULL 补一句设计声明；test_symbol_segment.py 是否已建需确认；ts aware 化并入任务 C。
