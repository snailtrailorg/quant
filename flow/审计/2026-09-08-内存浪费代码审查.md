# 内存浪费代码审查（2026-09-08 上午）

> 触发：双观察日 zram 99.8% 满溢出磁盘 ~190M，用户提问「各服务 import 相同内容能否共享」延伸出的定向审查。
> **原则（用户原话）**：不能为节约内存牺牲效率，但找「浪费了内存也没有提升效率」的代码。
> 方法：107 文件 22K 行定向模式扫描（iterrows/read_sql/SELECT */deepcopy/无界缓存/大对象序列化）+ import 链追溯（sys.meta_path spy 实证）+ 本地 RSS 实测。

## 结论速览

| 级别 | 发现 | 量化 | 性质 |
|---|------|------|------|
| **P1** | web-api 启动即常驻 pandas，唯一用途 2 个 `pd.notna()` | **~57MB 常驻**（实测 64292-7280KB） | 浪费且零效率收益 |
| P2 | `iterrows()` ×14 处（grep 实数，批10 盲审勘误）（同步引擎热循环在内） | 每行多造一个 Series，慢 5-10× | 更慢**且**更费，改了双赢 |
| P2 | worker 无 `--max-tasks-per-child` | 任务峰值 RSS 高水位永久驻留 | 只涨不跌的慢性泄漏面 |
| P3 | `get_bars` 逐列 to_numeric 循环=7 次列拷贝 | 微 | 卫生改善 |

## P1：web-api 的 pandas 承载（根治项）

**实证链**：`sys.meta_path` spy 抓到启动载入链 `main.py:94 → routes/stock.py:6 → import pandas`，**单一载体**。全路由模块级 import 扫描确认其余 11 个路由文件只 import `data_platform.db`（批 9 已函数级下沉）。

**荒谬点**：`stock.py:6` 模块级 `import pandas as pd`，全部用途是 `get_kline_api`（stock.py:142-144）里两个 `pd.notna()` 判空。K 线路由本质是「SQL 行 → JSON records」，现状路径却绕道 DataFrame：`get_bars` 内部 `fetchall → DataFrame → to_numeric 逐列`，路由再 `to_dict("records")` 转回来。**pandas 在这条链上是纯搬运工**。

**改法（根治，非 lazy 化）**：
1. db.py 加 records-native 查询（或路由内直查）：`fetchall → 直接构造 [{ts,ohlcv}]`，Decimal 用 `float()`、None 用 `is None`，ts 用 `strftime`——零 pandas。
2. `stock.py:6` 模块级 import 删除。

**效果与边界**：
- web-api 开机零 pandas，DataManage/日志/风控/任务/权限等高频管理页**永远**不载。
- 用户首次触发真需要 pandas 的路由（回测/分析选股——均已是函数级 import）时才载入并驻留（sys.modules 缓存）——「用时付出」合理，「不用也付出」消除。
- 本地实测 import pandas+numpy 的 RSS 代价 **~57MB**（64292 vs 7280 KB）。生产 web-api 是最大常驻进程、此前 swap 元凶，此改等于直接扩容。

## P2-a：iterrows() ×14（grep 实数，批10 方案盲审勘误）（双赢改造清单）

每行构造 pandas Series（含索引对齐开销），比 `to_dict("records")`/`itertuples()` 慢 5-10× 且费内存。全部改法机械：`for _, r in df.iterrows()` → `for r in df.to_dict("records")`（字段访问 `r.get()` 不变，改动面极小）。

| 位置 | 热度 | 备注 |
|---|---|---|
| `data_sync/engine.py:729` | ★★★ | bar 同步批构建，每标的×每天×几百行，15:20 腾讯攒与日常同步热路径 |
| `data_sync/engine.py:358/404/449` | ★★ | 股票/转债/基金列表全量同步（5000 行级） |
| `adapters/tushare_adapter.py:232/259/296/377`、`adapters/base.py:164` | ★★ | to_bar_rows/to_save_rows 归一化路径 |
| `data_sync/pool_data.py:98`、`scheduler/tasks.py:1192` | ★ | 每日一次小任务 |
| `astock_analysis/analysis.py:139`（top-N 小循环）、`strategy_runner/main.py:83`（tail 500） | ☆ | 顺手改 |

## P2-b：worker 无 max-tasks-per-child（高水位驻留）

`quant-celery-worker@.service` 的 ExecStart 无 `--max-tasks-per-child`。celery prefork 子进程处理过大任务（全市场回填/大 df 峰值）后，Python arena 不归还 OS，RSS 高水位**永久驻留**。1.8G 机器上这是「内存只涨不跌」的结构性面。

改法：`--max-tasks-per-child=100`（每百任务回收子进程，fork 成本百 ms 级可忽略；worker 任务间无跨任务暖缓存，回收零损失）。`quant-celery-risk@` 队列轻任务可同配保守值（200）或不动。**属于 systemd 单元改动，走部署管道**（units 指纹变化触发重启波次，需挑部署窗）。

- K 线路由 `days=0` 全历史 ~4000 行/标的，瞬时 ~400KB，量级无害。

## 附：共享与压缩的结论（审查中澄清的概念）

- 只读代码段/`.pyc` 经 page cache **早已跨进程共享**；不共享的是各进程 Python 对象堆——这是「每任务独立子进程」架构的固有代价。
- zram 不共享，压缩冷页；多服务换出页内容相似使 zstd 压缩比利好（实测 5.6:1）。
- KSM/prefork-COW 等真共享技术对本负载不适用；**lazy import（批 9 已做）+ 不加载（本审查 P1）比共享更彻底**。
