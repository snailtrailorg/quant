**产出**：

- `flow/审计/单一真源扫描-20260929.txt` — 本次人类可读输出
- `flow/审计/单一真源基线-20260929.json` — 基线（后续只报新增）

## 一、先把「同类问题」抽象成可机械识别的形状

个案给的是结论，排查需要**定义**。这批问题的共同本质是：

> 同一语义事实（缺省值 / 校验规则 / 常量 / 归一化方式）在仓库里有 N 份副本，且没有任何机制保证它们一致。

这个定义下的 6 种可检形状：

| # | 形状 | 判据 | 本次命中 |
|---|---|---|---|
| A | 跨文件重复字面量容器 | 同一组常量在多文件各写一份（dict/list，含 ≥1 数字） | 7 组 |
| B | 兜底分支引用字面量 | `x or <字面量>`，上游若已保证非空则该字面量为第二真源 | 51 处 |
| C | 兜底粒度错配 | `v = x or {…}` 之后 `v[k]` —— 上游缺任一 k 即 KeyError | 3 处（2 高置信） |
| D | 静默兜底键 | `.get("k", 默认值)` 同一键名多文件各有默认值 | 18 键 |
| E | 键集分层漂移 | seed（DB 默认值）/ bounds（写入校验）/ 代码映射 三层键集互差 | 0（全对齐） |
| F | 同名符号多实现 | 同名函数跨模块定义（语义分歧候选，低置信） | 6 组 |
| G | 调参散落 | 同一参数名在调用点有 ≥3 种字面量取值 | 3 个 |

**C 是真的 bug 形状，不是风格问题**——它直接对应上一轮复核的 `monitor.py:195` 那处。

## 二、锚点选对，是一半的功夫

按数值 grep 查不准，本次实测：

- `grep '0.6' server/src` → **3 处，其中 1 处是注释**（`strategy.py:73` 的示例值），另有 2 处只是同一事实的两份拷贝
- 改用标识符锚点 `VALKEY_URL` → **23 个文件 / 34 处**，每一份都各写一遍默认连接串 `redis://127.0.0.1:6379/0`

同一件事，换个锚点，规模从 3 变成 23。原因是：

| 锚点类型 | 示例 | 问题 |
|---|---|---|
| 数值字面量 | `0.6` | 会写成 `0.60` / `60%` / `0.6*100`；注释里也有假阳性 |
| **标识符** | `VALKEY_URL`、`alert_mem_warn`、`_DEF_THRESHOLDS` | 唯一、可枚举、无同形写法 |

**结论：锚点选标识符（配置键名 / 常量名 / 环境变量名 / 函数名），不选数值。**

## 三、本次分诊结果（工具给形状，人给判断）

### 三条分诊判据

1. **这些副本必须同时改变吗？** 必须 → 真源；可以各自演化 → 合法重复
2. **当前是否已经不一致？** 不一致 → 立刻是 bug；一致 → 定时炸弹
3. **有没有一条测试会在副本漂移时报红？** 有 → 已被守门；无 → 待守门

### 按判据筛出的真账（值得动）

**头号真账：`VALKEY_URL` —— 一个变量名承载两个语义，导致飞书库隔离静默失效**

证据链（每一环都实测）：

| 环 | 位置 | 内容 |
|---|---|---|
| 声明 | `web_api/redis_pool.py:17` | 注释：「飞书长连接专用库（db4）：ws_client 心跳/重连状态等，**与业务库隔离**」 |
| 声明 | `web_api/redis_pool.py:4` | docstring：「实际在用的两处（sync 端点 **db0** / im_bots 飞书长连接 **db4**）」 |
| 实现 | `web_api/redis_pool.py:12-21` | **两行相邻代码靠不同默认值区分目标库，但读的是同一个环境变量**：业务池 `.get("VALKEY_URL", ".../0")`、飞书池 `.get("VALKEY_URL", ".../4")` |
| 实现 | `feishu_bot/tasks.py:25` | 同一模式再来一份：`.get("VALKEY_URL", ".../4")` |
| 部署实况 | `server/.env:8` | `VALKEY_URL=redis://127.0.0.1:6379/0` |
| 示例文件 | `server/.env.example:13` | `VALKEY_URL=redis://127.0.0.1:6379/4`（**与 .env 相反**） |

后果分三种情形：

- `VALKEY_URL` **未设** → 业务池 db0、飞书池 db4，隔离成立
- `VALKEY_URL` = db0（**仓库内 `.env` 的写法**）→ 两个池**都连 db0**，注释声明的隔离**静默失效**，飞书心跳与业务键混装（而 `scheduler/app.py:19` 的注释正警告过「db0 与业务键混装——一次故障全带走」）
- `VALKEY_URL` = db4（**`.env.example` 的写法**）→ 22 个文件 / 32 处业务连接点**全部落到 db4**，业务键与飞书键互换

全仓 `VALKEY_URL` 共 **34 处 / 23 文件**，无任何集中定义（无 helper、无常量），每处各自内联默认值。判定：**必须同时改／已经不一致／无测试钉住 → 真 bug（设计级）**。

根因不是"漏改一处"，而是**用默认值来区分语义**：一个变量名无法同时表达"业务库"和"飞书专用库"，无论默认值取哪个，另一方在某个环境下必然失效。修法是拆成两个变量（如 `VALKEY_URL` + `FEISHU_VALKEY_URL`）或让飞书池显式指库号，而不是调默认值。

**次位：`monitor.py:195,205,206`** —— 阈值缺省第二真源 + 全有或全无兜底（由 A/B/C 三项独立指向，详 `2026-09-29-缺省值真源与阈值兜底-复核.md`）。

### 工具报出但人判为假阳性的（重要，不能省）

| 位置 | 工具为何报 | 实际判定 |
|---|---|---|
| `web_api/routes/backtest.py:186` `.get("capital", 1_000_000)` vs `scheduler/tasks.py:1036` `.get("capital", 100000)` | 同一键 `capital` 两处默认值差 10 倍 | **假阳性**。`backtest.py:186` 在 `_chk_money` 里，该值仅用于走 `float()` 与 `1e4~1e10` 值域校验，随后丢弃，**不参与执行**；真默认值只有 `tasks.py:1036` 一处。属命名债（探针值长得像默认值），非行为 bug |
| `migrations/env.py:54` `.get("QUANT_DB_STMT_TIMEOUT_MS", '3600000')` vs `data_platform/db.py:44` `.get(..., '60000')` | 同一环境变量默认值差 60 倍 | **假阳性**。`env.py:54` 同行已有注释「`# 迁移本身放宽 1h`」——有意为之且写明理由。判定：**合法重复（已注释）** |
| `web_api/main.py:48` vs `routes/auth_routes.py:28` `.get("AVATAR_DIR", ...)` | 路径串不同 | **假阳性**。`parents[2]` 与 `parents[3]` 取自不同深度的文件（`main.py` 与 `routes/auth_routes.py`），解析结果**同一目录**，等价 |
| `strategies/convertible_doublelow.py:37` `shares_per_trade=100` vs `crypto_cta_trend.py:42` `=1` | 同一键默认值不同 | **假阳性**。可转债 100 股/手 vs 加密 1 张，品种差异 |

**这一节是方法论的核心**：工具报 18 个键、51 处兜底，人判之后真账 1 个。工具的价值在于**把注意力从"找"移到"判"**，而不在于"找出所有问题"。假阳性的共同形态是「**字面量同形但语义不同**」——这正是三条判据里第 1 条（必须同时改吗？）要拦的东西。

### 按判据筛出的合法重复（不要动）

- **B 项绝大多数**：`or '未知'`、`or '(空)'`、`or '（LLM 无响应）'` —— 纯展示文案兜底，各调用点本就可独立措辞
- **F 项同包多实现**（`im_bot` 的 `send_text`/`send_card`/`verify_callback`）：基类 + 各渠道实现，是设计不是重复
- **G 项** `timeout` 8 种值 / `ex` 8 种值：不同调用点的不同超时，有意为之
- **A 项 `(None,None,0)` / `(None,0)`**：空值哨兵元组，只是恰好同形（工具的同形误报，需人工剔除）

### 仍需一次决策（不由本工具判定）

`strategy_framework` 的两条聚合路径语义不同：`astock_analysis/analysis.py:125-130` 是**加权平均**（`score / w_sum`，分数恒在 `[-1,1]`）；`strategy_framework/strategy.py:49-60` 的 `SignalAggregator.aggregate` 是**裸加权和**（不除 `w_sum`，分数无界）。阈值 `0.3/-0.3` 是绝对量纲——加减一个因子或调一次权重，买卖触发点会被静默改变。上一轮已记，改前须确认存量策略配置的阈值含义与回测基准。

### E 项全绿，是个重要对照

三层键集（seed 35 / bounds 22 / 代码映射 11）**互相零差集**。也就是说：

> **配置键这一层本来就没有洞——因为 `SYSTEM_CONFIG_BOUNDS` 那张表本身就是单源**（写侧查表 / GET 下发 / 消费侧钳位同源引用，批36b-α 立法）。

而「阈值缺省值」那一层有洞，原因正是它**没有对应的单源表**，靠 `_DEF_THRESHOLDS` 与内联 dict 两份人工同步。

**所以：这类问题的分布不是随机的，它精确地出现在"没有单源表 + 没有守门测试"的地方。** 这直接给出了排查的优先级——先查那些"同一事实却查不到一张权威表"的概念。

## 四、排查 SOP（五步闭环）

### ① 定义形状
用第一节的 6 种形状表框定范围。不要用"注意一致性"这种不可执行的表述。

### ② 选锚点
标识符，不是数值。锚点必须可枚举（DB 里的配置键、注册表 dict 的键、常量名）。

### ③ 工具出候选
```bash
python scripts/audit-single-source.py                 # 全量
python scripts/audit-single-source.py -c A,C          # 只跑指定检查
python scripts/audit-single-source.py --json 基线.json   # 首次：建基线
python scripts/audit-single-source.py --baseline 基线.json  # 之后：只报新增
```
工具的价值不是"找出所有问题"（做不到），而是**把人的注意力从"找"移到"判"**。

### ④ 人工分诊
用三条判据过一遍。工具给形状，判断必须人做——本次 51 处 B 里只有 1 处是真账。

### ⑤ 基线 + 反证
- **基线只许调低不许调高**：`--baseline` 模式下新增条目必须在 diff 里显式出现，等于强制一次架构决策 review。与 `test_no_sql_in_routes` 同一个模式。
- **反证**：往扫描范围埋一个已知缺陷，确认工具能抓出来。本次已做——见下节。

## 五、工具本身的坑：它自己被查出 6 次假阴性

写这个扫描器的过程中，它先后 6 次给出**自信的错误报告**，每一次都靠「已知答案反查」才发现：

| # | 症状 | 根因 |
|---|---|---|
| 1 | A–D 四项全部返回 0 | `visit_Module` 覆盖了默认遍历却没回调 `generic_visit`，整个 AST 遍历没启动 |
| 2 | A 项漏掉 `monitor.py:195` | A 只扫模块级赋值，而那份复制体在函数体内 |
| 3 | E 项报"bounds 有 seed 缺 11 个" | 只认单引号，`0112` 用双引号；且 seed 列表在 `INSERT` 语句**上方**，只往下扫 |
| 4 | E 项再报"7 个键从未 seed" | 实际有 **5 种** seed 写法：四元组 / 三元组 / 匿名内联列表 / 内联 SQL 字面量 / `.sql` |
| 5 | E 项 `bound: 0`（整张表被判空） | `(-1440, 1440, ...)` 首元素是 `ast.UnaryOp`（负号）不是 `Constant` → `all()` 判 false → **整张表被静默丢弃** |
| 6 | E 项报 20 个假键 | `bounds` 名字匹配过宽，把 `_REGISTRY_CACHE = {"at": 0.0, "data": None}` 和 `_TIER1_BATCH` 表名映射都收进来了 |

**第 5 条尤其值得记**：一条不合规的条目让整个容器被 `all()` 静默判否，工具不说话、不报错、给出一份看起来正常的空结果——**这正是本次要治的病的同一个形状**（`_dispatch_async` 签名错配让外推链断十天无人知、`trading.py` 那段 `SELECT 1` 探测写了等于没写）。写工具的人会犯同样的错。

所以 SOP 的第 ⑤ 步不是可选项：

```bash
# 反证：埋一个已知缺陷，确认被抓出
cat > scripts/.audit-selftest.py <<'EOF'
_DEF_THRESHOLDS_COPY = {"mem": {"warn": 0.6, "crit": 0.9}, ...}
def selftest(cfg):
    thr = cfg.get("thresholds") or {"mem": {"warn": 0.6, "crit": 0.9}, ...}
    for kind in ("mem", "cpu"):
        if thr[kind]["crit"]: pass
EOF
python scripts/audit-single-source.py --baseline 基线.json -c A,B,C,D
# 期望：B +1 / C +1（并带 dup_of 指向 collector），A 显示为 3 文件重复组
rm scripts/.audit-selftest.py
```

本次实测结果：B +1、C +1、D +1，全部命中，A 正确显示该文件加入了已存在的重复组。**反证通过后工具才可用。**

## 六、与上一轮技术债体检的连接

本次三处结论补充/修正了前一轮：

1. **「多份缺省值真源」是 ruff 抓不到的**。它不是语法或风格问题，而是语义一致性——只能靠自定义 AST 检查或手写守门测试。这解释了为什么项目已有 `test_layering.py` / `perm_registry` 键集守卫 / `verify.sh` 仍会漏这一类。
2. **本项目已有的守门模式正好可以复用**：`perm_registry` 键集守卫、router-walk 防漂移闸、`test_no_sql_in_routes` 的「基线只许调低」，三者都是同一招。本次的 `--baseline` 是第四例。
3. **优先级判据**：本次实证了「有单源表的层没洞，没单源表的层有洞」（E 全绿 vs A/B/C 命中）。所以排查顺序应按「这个概念有没有一张权威表」排序，而不是按文件或模块排序。
