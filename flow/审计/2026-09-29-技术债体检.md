## 二、具体问题（按严重度）

### 1. 静默吞异常 90 处 —— 交易系统里的 P0 级可观测性窟窿

分布：`scheduler/tasks.py` 13 / `health_monitor/collector.py` 8 / `strategy_runner/hub_worker.py` 6 / `data_platform/stock_detail.py` 6 / 其余散落 15 个文件。

对量化系统，`except: pass` 的杀伤力不是「代码难看」，而是**把故障变成静默**。项目内已有实证：2026-09-28 发现的 `_dispatch_async` 签名错配导致「**外推链自 09-18 起全断十天**」，正是这类模式掩盖出来的。

更刺眼的是**「写了自检但自检无效」**的形态——`web_api/routes/trading.py:347-350` 与 `363-366`：

```python
try:
    conn.execute("SELECT 1 FROM order_log LIMIT 1")
except Exception:
    logger.warning("get_orders: order_log 表不存在（需运行 alembic upgrade head）")
cur = conn.execute("SELECT ts, strategy_id, ... FROM order_log ...")   # 探测完照跑，warning 毫无作用
```

探测分支既没 `return` 也没降级，纯粹是**用一行 warning 换心理安慰**。同文件 `POST/GET/PUT/DELETE /api/account` 四个端点连这行安慰都没有。

**建议**：把 90 处分成三类处理——(a) 真该忽略的（进程退出时的清理）→ 加注释说明为什么可以吞；(b) 该记日志的 → `logger.warning(..., exc_info=True)`；(c) 该炸的 → 直接抛。用 `ruff` 的 `S110`/`BLE001` 规则把它锁死，而不是靠下一次人工盲审。

### 2. 零自动化质量闸门 —— 用流程替代工具，是 AI 协作的典型债

现状：守门靠「八步法 + 方案双盲 + 代码双盲 + 稳定性检查矩阵 + 48 种失败注入」。这套流程写得极其认真（`flow/规范/` 9 篇），代价是**每批任务都要消耗大量人力和 token 去做机器一秒能干完的事**：格式、未使用变量、错别字、类型不匹配、循环导入、死代码。

`flow/稳定性检查/` 下 15 份代理盲审报告，本质是**用 LLM 当 linter**。而盲审报告已经反复抓出同类问题（P1×N、P2×N 的措辞高度重复），说明**这类问题是机械可检的**，却每次靠新开一个盲审代理重新发现。

**建议**（排序即收益排序）：

1. `pyproject.toml` + `ruff`（`E,F,W,I,B,S,UP,SIM` + `S110`/`BLE001`），先只跑 `ruff check --statistics` 看存量，不阻塞；
2. `mypy --ignore-missing-imports` 只对 `quant_common` + `server/src/web_api/services`（新增层）开；
3. `.pre-commit-config.yaml`（ruff + ruff-format + 尾随空白 + 大文件拒绝）；
4. `requirements.txt` 生成 `requirements.lock`（`pip-compile`/`pip freeze`），**AGENTS.md 里那两条手写注释的 pin 原因，改成锁文件 + 注释双写**；
5. 一个最小 CI（gitea/cnb action 或本地 `verify.sh` 扩展）：`ruff` + `pytest` + `test_layering.py`。

### 3. 规范与代码脱节 —— 规则写在文档里，没人（也没工具）守

AGENTS.md 明写两条铁律，实测都被违反：

| 规范原文 | 实测 |
|---|---|
| 「业务逻辑不寄生 HTTP 入口」 | `web_api/routes/*.py` 里 SQL 密集：`auth_routes.py` 53 处 / `trading.py` 28 处 / `backtest.py` 27 处 / `alerts.py` 26 处 / `system.py` 24 处。HTTP handler = 参数校验 + 业务规则 + SQL + 事务 + 响应整形 |
| 「下层禁 import 上层」 | 有 `tests/test_layering.py` 守门——**但只断言 import 方向，不断言逻辑归属**，所以路由层塞满业务不会被拦 |

`trading.py` 直接 CRUD `live_task` / `live_trading_config` / `position_snapshot` / `order_log` / `accounts` / `backtest_runs` 六张表；`alerts.py` 直接 CRUD `alert_user_sub` / `sms_provider` / `im_bot_config` / `users`。**这是全仓唯一真正的架构级债务**：接口层与持久化层之间没有 service 层，未来任何 schema 变更都要同时改路由。

**建议**：不要大重构。**新代码强制走 `web_api/services/`，老路由冻结**——出个 `test_no_sql_in_new_routes.py`，对基线文件白名单放行、新增路由文件禁止出现 SQL 字面量。让存量随自然迭代缩减。

### 4. 概念返修被打进 schema —— 迁移链 0099→0104 是六连号改名

```
0100 venue_backfill
0101 retire_strategy_account      ← 建了又退役
0102 retire_live_task_account_id
0103 direction_resource_id
0104 rename_venue_to_account      ← venue 改名成 account
```

六个连续迁移在做同一件事的反复：`venue` 概念引入 → 回填 → 退役旧表 → 再改名 `account`。（公平地说：每个迁移文件的 docstring 都写清了 rationale 和取舍，`0104` 还专门解释了「PG18 的 NOT NULL 是 pg_constraint 行，rename 后约束名不自动跟随」——**这是好实践**。债务不在迁移写法，在概念未定型就上产。）

**建议**：上产前的「术语定稿」做成方案双盲的固定一环（现在双盲只审实现，不审命名）。`venue` vs `account` vs `exchange` 这种词，一次定死比六次迁移便宜得多。

### 5. 文档体量失控 —— 「真相源在文件里」正在变成「真相埋在文件里」

`flow/进展.md` **388 KB / 2,814 行单文件无界追加**。AGENTS.md 规定开工必读其「顶部一条」，意味着**每开一个会话都要加载一个 388 KB 的巨物**才能读那一条。同理 `待办.md` 86 KB。

更麻烦的是**语言已经不可解析**。实测顶部一条进展原文：

> 「**当班全弧**（方案 v2 **过门**→编码→**双盲 A/B** 全处置）……**施工自曝**（已修+列审单重点）：hset 位置参数被 mapping 形参吞→fail-open 静默吞回写（测试抓出）」

`当班全弧` / `过门` / `挂账` / `典` / `收编` 这些自造压缩词，**对新会话（以及三个月后的你自己）等价于密文**。写的时候省了字，读的时候要用一个 LLM 会话去解码。这笔账是亏的。

**建议**：

1. `进展.md` 按月切分（`进展/2026-09.md`），`flow/进展.md` 只留索引 + 最近 3 条；
2. 交接条目恢复「主谓宾」——缩写只在 `flow/规范/术语表.md` 定义后使用；
3. `flow/tasks/`（空目录）与 `flow/任务/` 并存 → 删空的那个；
4. `server/logs_emt/`、`.pytest_cache/` 加 `.gitignore`；312 个 `.pyc` 从 tests 清掉。

### 6. 前端：一个 2,810 行的多语言字典 + 没有组件沉淀

`web/src/locales/index.js` **2,810 行**（占全部前端行的 19%）——多语言词典单文件，应拆成 `locales/{en,zh,...}.json` 并按模块分节。`Profile.vue` 831 行同类问题。

同时 92 个文件里，20 个 `views/*.vue` 都是 200-400 行，各自实现表格+表单+弹窗。**没有抽取公共 CRUD 表格组件**是前端主要债源——`InterfacesCard.vue` / `SmsCard.vue` 这类已被抽出的卡片证明方向对，但覆盖率不够。

## 三、建议：先做这 4 件，别做别的

| # | 动作 | 为什么先做这个 | 预期影响面 |
|---|---|---|---|
| 1 | **上 `ruff` + `pre-commit`** | 一次性把格式/未使用/裸 except/静默 S110/未排序 import 挤出水面。**没有这个，后面所有人工评审都在重复劳动** | 机械问题不再进盲审 |
| 2 | **清 90 处 `except pass`** | 交易系统的静默失败 = 未来的「全断十天」 | 直接提升故障可见性 |
| 3 | **`requirements` 上锁 + 新增 `web_api/services/` 冻结路由 SQL** | 两条都是「防复发」，低成本高杠杆 | 依赖漂移 + 架构腐化双止血 |
| 4 | **`进展.md` 按月切分 + 恢复主谓宾** | 让下一个会话（人和 AI）读得懂交接 | 直接降低每会话的加载与理解成本 |

**暂时不要做的**：

- 不要重写 `scheduler/tasks.py`（1,709 行确实胖，但拆它风险高于收益，等 3 号做完 service 层再说）；
- 不要再新增 `flow/规范/` 文档、不要再开新的盲审代理——**边际收益已递减，该换成工具了**；
- 不要「全仓重构」。代码重复率 22 处证明它不是烂在结构上，**大重构会把仅有的秩序毁掉**。

## 四、一句话总结

代码本体是**健康**的：低重复、测试足、迁移有据、分层有守门。
真正的债是：**该用工具守的地方用了流程，该设上限的地方没有上限，概念没定死就打进了 schema。**
修 1-4 四项，这个仓库就从「靠人（和 AI）的记忆与纪律维持」变成「靠机器守门」——这才是 AI 大规模写代码唯一可行的可持续模式。
