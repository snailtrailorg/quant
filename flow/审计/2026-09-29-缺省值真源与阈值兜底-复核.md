# 复核：`grep -r '0.6' server/src` 命中三处的缺陷分析

**日期**：2026-09-29
**触发**：用户在 `server/src` 执行 `grep -r '0.6' *`，命中 3 处，问「有什么毛病」
**结论**：三处命中分别暴露三个独立缺陷，共同根因是「同一业务缺省值多份真源 + 取值侧对部分缺失不设防」。

---

## 0. 三处命中的定性

| # | 位置 | 性质 | 严重度 |
|---|---|---|---|
| 1 | `health_monitor/collector.py:39-40` | 运行期权威缺省（`_DEF_THRESHOLDS`） | 基准 |
| 2 | `health_monitor/monitor.py:195-198` | **第二份运行期真源**，生产永不执行 | P1 |
| 3 | `strategy_framework/strategy.py:73` | 注释里的示例值（grep 假阳性），但指向因子权重多真源 | P2 |

---

## 1. `0.6` 不是 3 处，是 5 处（同一业务缺省值）

| 位置 | 内容 | 性质 |
|---|---|---|
| `server/src/health_monitor/collector.py:39-40` | `_DEF_THRESHOLDS`：mem 0.6/0.9、disk 0.8/0.9、swap 0.8、cpu 0.7/0.9 | **运行期权威真源** |
| `server/src/health_monitor/monitor.py:195-198` | 内联同值 dict（全 4 kind） | **第二份运行期真源** |
| `server/migrations/versions/0076_resource_cfg.py:22-31` | DB seed：`alert_mem_*`/`alert_disk_*`/`alert_swap_*` + 3 个 `collect_period_*` | DB 侧真源（mem/disk/swap） |
| `server/migrations/versions/0112_metric_cpu_fir.py:21-23` | DB seed：`alert_cpu_warn=0.7`/`alert_cpu_crit=0.9`/`collect_period_cpu=30` | DB 侧真源（cpu，**另一次迁移**） |
| `server/src/web_api/routes/system.py:21-29` | `SYSTEM_CONFIG_BOUNDS`：只存边界 `(0,1,True,True)` | 正例——不复制默认值，只存约束 |

**目前 5 处数值一致，所以还没炸。但没有任何机制保证它们一致：**

- `tests/test_health_monitor.py:675` 只断言 collector 那份的 cpu：`thr["cpu"] == {"warn": 0.7, "crit": 0.9}`
- `tests/test_batch36a_input_governance.py:299` 只断言钳位回落行为
- **全仓没有任何一条测试断言 collector 的 `_DEF_THRESHOLDS` 与 monitor 的内联 dict 相等**，也没有断言两份与迁移 seed 的 kind 键集一致

即：键集与数值的同步，完全靠人记。

---

## 2. `monitor.py` 那份是「生产永不执行、只服务测试」的第二真源

调用链：

```
collector.collect()  :231   snap["thresholds"] = _read_cfg()[0]     ← 无条件写入
collector._read_cfg() :96-97  if thresholds is None: thresholds = _DEF_THRESHOLDS
                              → 永不返回 None（DB 挂了也返回权威缺省）
monitor.run_check()  :256   snap = collect()                       ← 生产唯一入口
monitor.evaluate()   :195   thr = snap.get("thresholds") or {内联 dict}
                              → 右半边在生产路径永远不执行
```

**它只被 4 条测试走到**（`TestBatch78CpuRules.test_cpu_warning_at_075` 等，靠 `_snap_cpu`(:591-600) 构造的不含 `thresholds` 键的 synthetic snap）。

这是最坏的一种重复：**一份不参与生产、因此改错不会被生产发现，但一旦改错就会让 4 条测试给出与生产不同结论的平行实现**。此时测试验证的不是生产行为，而是另一份实现——测试通过不代表生产正确。

---

## 3. 取值兜底用 `or`：修的是数据不是查找逻辑（P1 真问题）

`monitor.py:195` 的 `snap.get("thresholds") or {全部四 kind}` 是**全有或全无**语义。而 `:199-206` 的循环逐 kind 取 `thr[kind]`：

```python
for kind, comp, rule in (("mem", ...), ("swap", ...), ("cpu", ...)):
    r = res.get(kind)
    if not r or r.get("pct") is None:
        continue
    sev = "critical" if (... and pct > thr[kind]["crit"]) \
        else ("warning" if pct > thr[kind]["warn"] else None)   # ← thr[kind] 无兜底
```

只要 `snap["thresholds"]` 存在但**缺任一 kind** → `KeyError` → `run_check` 的 30s 判定链整个崩。

### 这个故障模式已经发生过一次

`tests/test_health_monitor.py:669` 的注释是实锤：

> `"""P0-2 回归钉：_CFG_KEYS/_DEF_THRESHOLDS 缺 cpu → thr["cpu"] KeyError → 30s 链崩。"""`

**当时的修法是给两份 dict 各补一个 cpu 键**（`_DEF_THRESHOLDS` 与内联 dict 同时加 `"cpu": {"warn": 0.7, "crit": 0.9}`）。这等价于：水管漏了，补的是墙上的洞，不是换管子。所以：

1. **新增任何 kind 会原样复现**——下次加 `load`/`io`/`net` 监控，同样两个地方漏加 → 同一个 KeyError。
2. **缓存路径是开放口子**：`_read_cfg():64-65` 在 TTL 内**原样返回 `_CFG_CACHE["thresholds"]`**，而 `_CFG_CACHE` 是进程级可变全局。`tests/test_health_monitor.py:707` 就真的往里写入了单 kind dict `{"cpu": {"warn": 0.7, "crit": 0.9}}`（该用例走路由层不触发 evaluate，故未炸）。

### 正确写法：缺失由查找侧补齐

```python
# monitor.py —— 一份缺省（从 collector 取，不复制），per-kind 深合并
from .collector import _DEF_THRESHOLDS as _DEF

_snap_thr = snap.get("thresholds") or {}
thr = {k: {**v, **(_snap_thr.get(k) or {})} for k, v in _DEF.items()}
```

效果：新增 kind 只加一行数据，`thr[kind]` 恒存在；同时 `monitor.py:195-198` 那份复制体消失。

## 4. `strategy.py:73` 的 `0.6` —— 注释假阳性，但因子权重有 4 套真源

`factors: list[dict] = field(default_factory=list)  # [{"name":"ma_dev","weight":0.6,"params":{}}, ...]`

这行是注释，本身只是 grep 噪音。但它旁边的字段是裸 `list[dict]`，而权重实际散在 4 处：

| # | 位置 | 性质 |
|---|---|---|
| 1 | `strategy_config.factors[].weight`（DB，Web 可配）→ `strategy.py:181` 消费 | 名义真源 |
| 2 | `astock_analysis/analysis.py:36-41` `SELECTION_FACTORS`：`net_mf_pct 2.0 / lg_flow_pct 1.0 / winner_rate 1.5 / ma_dev 1.5` | **硬编码，完全绕过 DB** |
| 3 | `signal_framework.SignalAggregator.weights` 字段默认 `{}`（`strategy.py:44`） | 构建时被 1 覆盖，形似真源实非 |
| 4 | `strategy.py:73` 注释示例 `0.6` + `strategy.py:74` `aggregator` 默认阈值 `0.3 / -0.3` | 示例值 |

### 实质缺陷：两条聚合路径数学语义不同

- `astock_analysis/analysis.py:125-130`：**加权平均** —— `score = score + r * weight * valid`，`w_sum += weight * valid`，最后 `score / w_sum`；行级按可用因子重分配权重。分数恒在 `[-1, 1]`。
- `strategy_framework/strategy.py:49-60` `SignalAggregator.aggregate`：**裸加权和** —— `score += val * w`，不除 `w_sum`。分数无界。

阈值 `threshold_buy=0.3 / threshold_sell=-0.3` 是**绝对量纲**。后果：

> 用户在 Web 上新增一个因子、或把某因子权重从 0.6 调成 1.2，裸加权和的分数尺度整体漂移，**买卖阈值被静默改变**——一个参数都没动，策略却变得更激进/更保守。

配置项是暴露了，但语义不是不变量——与 AGENTS.md「配置驱动非硬编码」的本意相反。

### 同源小缺陷：权重兜底与因子名校验强度不一致

```python
# strategy.py:181   权重缺失 → 静默 1.0
weights={f["name"]: f.get("weight", 1.0) for f in config.factors},
# strategy.py:212   因子名错误 → fail-closed
raise ValueError(f"未知因子: {name}")
```

同一份配置：**因子名打错会炸，权重键打错（`wieght`）静默按 1.0 全权重入模**。校验强度不一致，而松的那一侧恰是更危险的（权重直接决定下单方向）。

## 5. 建议（按性价比排序）

### 立即可做（低风险，纯止血）

1. **拆掉 `monitor.py:195-198` 的第二真源**，改为从 `collector` 取，同时把兜底改成 per-kind 深合并（§3 代码）。
   一处改动同时消掉「第二份真源」与「全有或全无兜底」两个问题。
2. **加键集一致性测试**（复用项目已有 `perm_registry` 键集守卫范式，放 `tests/`）：
   - `set(_DEF_THRESHOLDS) == {_CFG_KEYS["thresholds"] 里出现的 kind} == {0076+0112 seed 的 kind}`
   - 迁移 seed 的键集 ⊆ `SYSTEM_CONFIG_BOUNDS` 键集
   效果：**新增 kind 忘同步 → 测试红**，而不是生产 30s 链崩。

### 需一次决策后再动

3. **因子权重校验 fail-closed**：`weight` 缺失/非数 → 配置保存时即报错，而非兜 1.0；`StrategyConfig.factors` 用 `TypedDict` 或 pydantic 收窄。
4. **两条聚合路径语义统一**：推荐 `SignalAggregator` 也除 `w_sum`（与 `analysis.py` 对齐，阈值才可比）。
   **⚠️ 前置**：线上已有策略配置的买卖判定系在此语义上，改前须确认存量策略的阈值含义与回测基准是否受影响，需产品/策略侧确认，不可静默改。

## 6. 方法论附注

`grep -r '0.6'` 这类**按数值字面量检索真源**的做法查不准：同一缺省值可能写成 `0.6 / 0.60 / 60% / 0.6*100`，还有注释假阳性（本次 3 命中里 1 个是注释）。

要查「同一个缺省值有几份」，**锚点应该是配置键名**（`alert_mem_warn` 等），不是数值。本次用键名检索即暴露 5 处。

这条也正是上一轮技术债体检的延伸：**「多份缺省值真源」是 ruff 抓不到的**（它不是语法/风格问题，是语义一致性），只能靠一条自定义守门测试——与 §5.2 对应。
