## 三、五条根因

散点归并后，全部 P0 收敛到五条。按根因改，比逐条打补丁稳。

### R1 「另起一套」而非「收编既有」——最大的一条（覆盖 #1/#4/#5/#10/#17）

D32 假设自己从零建注册表、规格表、能力表，但仓内已有 **8 处 provider 注册点**（`data_source._REGISTRY`、`adapters/base._ADAPTERS`、`interfaces/base._PROVIDER_MODULES`、`md_gateway._REGISTRY`、`td_registry.TD_BUILDERS`、`broker._REGISTRY`、`create_adapter` 映射、markets 四张能力表）、**3 套规则存储**（`system_config close_policy.*`、`band_rules`、`MARKETS` 骨架）、**1 套运营真源**（`market_hours` + `security_master`）。`data_source.py:415-423` 的报错文案自己写着「加新源须三处各注册一类」——这是既存债务，D32 不是消除它，而是加第 9 处。

**后果**：manifest 与 `provider_capabilities()` 不同步时，集成中心写侧 ⊆ 校验与插件运行时协商结论相反；S3「删包即失效」落空（旧注册点仍能解析）。

**改法**：§十 改为「单注册表 + 投影」——`REGISTRY` 为唯一声明处，8 处 legacy 注册点在 P1 降为**只读投影**，P3/P4 逐项删除；新增守门「REGISTRY 与 legacy 投影的能力集必须相等，或显式标 legacy-only」。

### R2 契约丢了「进程角色」与「编排上下文」（覆盖 #2/#6/#11/#12）

`build(account)` 只有一个入参。但本仓的进程语义是硬隔离的：hub 零 TD、worker 零 MD（R-TD1，`ThinGateway.send_order` 直接 raise），订单前缀 `t{tid}:e{boot_epoch}:` 由编排层派生、靠 0040 唯一索引防撞，号段按 tid 派生跨进程唯一。`build(account)` 既拿不到 role 也拿不到 tid/epoch → hub 会建 TD、worker 各建一套 MD、订单号断链。

同源问题：端口只有 `query_*` 轮询，而真实交易链是事件驱动的（`main.py:355-366` 注册 EVENT_ORDER、`hub_worker.py:455` `__import__` 注册 EVENT_TRADE）；hub 主循环依赖 `start_ready/connected/poll_supervise` 这套生命周期面，端口里一个都没有。

**改法**：`build(account, role: md|td|pull, need) -> Runtime`，Runtime 按 role 只暴露合法端口，越界抛 `UnsupportedCapability`；订单号前缀仍归编排层；端口补 `subscribe_order/subscribe_trade` + `connected/start_ready/poll/health`。

### R3 失败语义没分维（覆盖 #9/#13）

D32 §7.3 一句「规则缺失 → fail-closed」把三种情况合并了：①开仓缺规则（可拒，代价是错过交易）②平仓/减仓缺规则（不可拒，代价是持仓暴露）③读失败（DB 抖动，不是配置缺失）。现行为是 fail-open（`hub_quote._CLOSE_POLICY_DEFAULTS` 回落 + warning），急停照样挂单；一刀切 fail-closed 会让新品种/DB 抖动时**平不掉仓**。

**改法**：三分语义写死 —— 开仓 fail-closed 拒单并标「规则未配置」；平仓/减仓 fail-open 到「行情可得的硬约束」（跌停线/对手价）+ 高优告警；读失败降级 fail-open 并留痕。`RuleSet` 增 `mode: open|reduce` 分流。

### R4 迁移期没有技术强制，且部署模型不支持插件级交付（覆盖 #7/#15）

两件事被当成了承诺但工程上不存在：

- **插件级回滚/热插拔**：唯一部署单元是 release（A06 版本树不可变、venv 跨 release 共享且不可指纹）。插件升级 = 全量发布 + 波次重启，盘中禁用；per-plugin `requirements.txt` 装进 shared venv 会同时炸掉待回滚的旧版。
- **同账号单套生效**：`trading_account` 只有 `UNIQUE(provider, account_key)` 且 `account_key` 可空 → 同一物理账号可以 `('xtp','X')`+`('emt_emq','X')` 两行双开；`REGISTRY` 是 provider→plugin，没有「实现版本」这一维，挡不住旧路径与新插件同时跑。

**改法**：删「热插拔/插件级回滚」承诺，改「插件随 release 交付」；删 per-plugin requirements；`trading_account` 加 `impl` 列 + `account_key` 部分唯一索引 + per-(account, role) Valkey 租约，拿不到即 EX_CONFIG。P1 拆 a（纯骨架+存量 vnpy 基线棘轮）/ b（事件端口接线）。

### R5 维度与词表不完备（覆盖 #3/#8/#14/#16）

- **四维缺 Account**：账户准入（`perms.account_allows` 五级 + `market_op`）、可用资金/保证金、行情数据授权、停牌态全无归属。
- **CAPABILITIES 是 DataKind 派生视图**，不是通用能力枚举；research 是端口能力，硬塞会撞「值域 = CAPABILITIES」守门。
- **RuleSet 只有 4 个固定方法 + 静态字段**，表达不了可转债临停状态机、以最优价为基准的申报范围、券商口径的可卖量 —— 表达不了的必然回流成插件里的 `if category ==`。

**改法**：四维 → 五维（加 Account）；`CAPABILITIES`（数据域）不动，新增 `PORT_CAPS`（端口域）；承认三层「静态 spec / 动态约束（按 category 注册的 RuleSet 子类）/ 交易所态（插件事件流）」，给动态约束留 `register_rule(category, predicate)` 扩展位。

## 五、需要用户拍板（4 项）

1. **四维 → 五维？** 加 Account 维（entitlements/cash_margin/data_license/halt_state），还是保留四维、在 §五表下逐项钉归属与消费点。前者结构干净，后者改动小。
2. **接受 P1 拆 a/b？** 「P1 零 vnpy」在当前结构下不可能（8 文件 4900 行，含 trading/hub_worker/main 三个行为核心）。必须拆成 P1a（骨架 + 基线棘轮）/ P1b（接线）。
3. **接受「插件=随 release 交付」？** 即删除「插件级热插拔 / provider 级回滚」承诺 —— 部署模型不支持，写了就是空头承诺。
4. **双轨防双写方案确认**：`trading_account.impl` 列 + `account_key` 部分唯一索引 + 租约（要动 DDL）。这是唯一能挡住 P3/P4 双下单的机制。
