# 方案 · 分钟数据源重构（腾讯攒过渡 + Tushare 终极 + bar_hub 缩小）

> 状态：方案定稿（双盲审修订后）。本文是任务自包含入口——做任务只读本文 + 接口契约 §Bar + 模块契约 `data_platform`/`data_sync`。

## 一、背景与目标

**现状**（2026-09-04 已核实）：
- 分钟数据两条路径，只有一条在跑：`bar_hub`（XTP 实时自攒，✅ 已验证正确）有数据；`bar_1min`（Tushare 池同步）空——200 积分 `stk_mins` 限流 1 次/小时 + 2 次/天，池同步跑不动。
- `bar_hub` 订阅范围过宽：`md_hub._desired_symbols` 四源里含「池源」（minute_history_start 池成员），为攒历史数据订阅大量非实盘标的，占 XTP 订阅额度 + 实时流资源。
- 攒数据标记只有**池级** `pools.minute_history_start`，无个股级，与回测双入口（pool_id / symbols）不对齐。

**目标**（用户 2026-09-04 裁定）：
1. 历史分钟数据改由 **腾讯攒**（免费、每天每只取一次、不占 XTP 额度），将来 **Tushare 分钟线（2000 元/年）开通后切换**，腾讯攒关闭（互斥）。
2. 攒数据标记做成 **池级 ∪ 个股级统一**，落一张「展开表」，与回测双入口对齐。
3. `bar_hub` 订阅**缩小**为只实盘在跑/实盘测试的标的，仍落库回溯。

## 二、终态数据架构

| 表 | 用途 | 标的范围 | 数据源 |
|---|---|---|---|
| `bar_hub` | 实盘实时 + 回溯 | 只 live_task running + 白名单 + 临时订阅 | XTP 实时流 |
| `bar_1min` | 历史回测 | `minute_symbols` 展开表 | 腾讯（现在）→ Tushare（将来） |

> 消费者澄清（盲审 A 核实）：回测引擎 `backtest_symbol_task` 读 `get_bars("1D")`（日线）；分钟数据真实消费者是**盘中研判 `astock_minute_analysis`（读 bar_1min 最新 20 根）+ live 暖机（读 bar_1min 30 天）**，两者当前都在读空表。本方案填 `bar_1min` 的直接受益方是研判/暖机；深度历史回测待任务 C（Tushare）。

## 三、分模块设计

### 3.1 展开表 `minute_symbols`（后端数据模型，核心）

**迁移**：`minute_symbols(symbol varchar PRIMARY KEY, source varchar NOT NULL, updated_at timestamptz DEFAULT now())`
- `source`：`'direct'`（个股直标）或 `'pool:{id}'`（池成员展开）——纯信息列，`symbol` 唯一（一标的只一行，满足用户「只单个标的」）。
- **优先级**：`direct` > `pool`（一标的既直标又在池，source 记 `direct`）。

**同步函数**（幂等，只重算 pool 部分，direct 行不动）：
```sql
-- refresh_minute_symbols() 的 SQL：
-- 1. DELETE FROM minute_symbols WHERE source LIKE 'pool:%'
-- 2. INSERT INTO minute_symbols (symbol, source)
--    SELECT DISTINCT ON (ps.symbol) ps.symbol, 'pool:' || p.id
--    FROM pool_symbols ps JOIN pools p ON p.id = ps.pool_id
--    WHERE p.minute_history_start IS NOT NULL AND p.category = 'astock'
--    ON CONFLICT (symbol) DO NOTHING   -- direct 行先存在则跳过（direct 优先）
```
- `DISTINCT ON (ps.symbol)` 保证同一标的进多个 mhs 池只产一行（消 PK 冲突，盲审 A-P0/B-P1 同根）；`ON CONFLICT DO NOTHING` 保证 direct 优先。
- `category='astock'` 过滤（盲审 P2：加密/ETF 池标的腾讯拉不到，不展开）。

**触发点**（这些端点末尾调 `refresh_minute_symbols()`）：
- `POST /api/pool`（create_pool，含 minute_history_start）— backtest.py:52
- `DELETE /api/pool/{pid}`（删整池，盲审 P1：漏了会残留僵尸行）— backtest.py:144
- `POST /api/pool/{pid}/symbol`（池加标的）— backtest.py:79
- `DELETE /api/pool/{pid}/symbol`（池删标的）
- **新端点** `POST/DELETE /api/minute-symbol/{symbol}`（个股直标：`INSERT ... ON CONFLICT (symbol) DO UPDATE SET source='direct'` / `DELETE WHERE symbol=%s AND source='direct'`）

**minute_history_start 取消通道**（盲审 P1：COALESCE 保留旧值，全仓无取消路径）：
- `create_pool` 的 upsert 改「空串 `''` → NULL」显式约定（传空串即取消），前端取消时传空串。

### 3.2 腾讯攒分钟任务（后端采集）

**新模块** `data_sync/tencent_minute.py`（参考 `pool_minute.py` 的 SyncLock + sync_log 模式）。

**拉取**（口径 2026-09-04 核对实证）：
- 接口：`https://ifzq.gtimg.cn/appstock/app/kline/mkline?param={tencent_sym},m1,,320`
- `tencent_sym` 复用 `_tencent_sym(ts_code)`（market_snapshot.py:39）；**注意 `minute_symbols` 存 vt（600000.SHSE），循环内先 `vt_to_ts` 转 ts_code 再喂 `_tencent_sym`**（盲审 P2）
- HTTP：`User-Agent: Mozilla/5.0`、`timeout=5`、失败重试 1 次；响应是 **UTF-8 JSON**（与 market_snapshot 的 qt.gtimg.cn gbk 不同，盲审 P2）
- 返回字段顺序：`[时间 yyyyMMddHHmm, open, close, high, low, volume(手), {}, 涨跌]`——**按位置解析**（close 在 high/low 前），尾部 `{}`/涨跌字段忽略
- 返回上限 320 根（1min），**滚动窗口**

**字段映射** → `bar_1min` 11 字段 `(symbol, '1min', ts, open, high, low, close, volume, amount, adj_factor, source)`：
- `volume = 腾讯volume × 100`（手→股）；`amount = NULL`（腾讯无成交额，统一 NULL 口径）；`adj_factor = NULL`、`source = 'tencent'`
- **ts 标注（盲审 B-P0 实测定案）**：
  - **中间段 0931~1459：腾讯 HHMM 与 bar_hub/bar_1min 分钟末直接对齐**（腾讯 0931 = bar_hub 09:31 同一分钟，已 79 根 0 差异实证）
  - **收盘竞价 1500 → 写 15:01**（腾讯标 1500、bar_hub 分钟末标 1501）
  - **开盘竞价 0930 → 丢弃**（腾讯单独标竞价根 vol 小量，bar_hub 首根 0931 已含竞价；丢弃不影响回测）

**调度**：Celery beat 每天收盘后一次（`crontab(hour=15, minute=20)`，**需显式注册到 scheduler/app.py 的 beat_schedule**——pool_minute 的 beat 是注释掉的，无活样板可抄，盲审 P2）。
- 扫描 `minute_symbols` 全表，`save_bars('1min', rows)` 落库（`overwrite=False`，UNIQUE 幂等）。
- **游标轮转公平性**（盲审 P1）：记上次扫到哪（Valkey 或表内 `updated_at`），下次断点续扫，防尾部标的永久排不上。

**漏取检测**（盲审 A-P1：320 窗口「漏一天可补」是错的）：
- 320 根 = 当天 241 + 前日尾部 79（13:42 后）。**漏一天即断 ~4 小时（早盘 09:30~13:42）**，不是「下次补上」。
- 漏取 = 异常 → **告警 + 人工处理**（不自动降采样腾讯 5min 补，粒度不一致污染回测）。检测：`MAX(ts)` 落后昨天即告警。

### 3.3 bar_hub 订阅缩小（后端）

`md_hub/main.py:179 _desired_symbols` 四源里**删除「池源」**（第 200-213 行 `pool_symbols JOIN pools WHERE minute_history_start IS NOT NULL` 一段）。
- 保留：① running 任务标的 ② `hub_shadow_symbols` 白名单 ③ 临时订阅（hub_transient_subs）。
- **安全**（盲审 A 核实读路径）：回测读 `bar_1D`、研判读 `bar_1min`、暖机读 `bar_1min`，都不依赖 bar_hub 多日历史；bar_hub 多日历史只被「当日分时」兜底读（且腾讯已是分时首选）。删池源只影响部分非实盘标的的当日分时兜底。

### 3.4 数据源开关（后端）

`system_config` 加键 `minute_data_source` ∈ `{'tencent', 'tushare'}`，默认 `'tencent'`。
- 腾讯任务：开关 = `'tencent'` 才跑。
- Tushare 池同步（`pool_minute.sync_pools_minute`）：任务 C 时改开关 = `'tushare'` 才跑，扫描源从 `pools` 改成 `minute_symbols`。
- **切换 Tushare 时清空 `bar_1min` 里 `source='tencent'` 行**（盲审 A-P1：bar_1min 唯一键 `(symbol,ts)`，保留 tencent 行会让 Tushare `ON CONFLICT DO NOTHING` 无法回补重叠段；且 ts 标注可能不同，保留=同一分钟两行冲突）。现定「切换即清空重建」，不悬置到任务 C。

### 3.5 前端 UI（Vue3）

- **池管理页**：`minute_history_start` 设置保留 + 取消（空串）；池增删标的后端自动 refresh；展示该池展开标的数（`list_pools` 加 `minute_count` = `minute_symbols` 中该池 source 计数）。
- **标的直标**：批量直标（对标 pool 的 `symbolsStr` 多行粘贴）+ 单标的开关 → 调 `POST/DELETE /api/minute-symbol/{symbol}`。
- **展开表页**：`GET /api/minute-symbol` 展示（含 source 分组、每个标的 `last_ts`/漏取状态，弱化漏取盲区，盲审 P2）。

## 七、风险与坑

1. **腾讯滚动窗口断档**：320 根 ≈ 1.33 天，**漏一天断 ~4 小时、漏两天断更久**。→ 收盘后定时雷打不动 + 漏取告警 + 人工处理。
2. **字段顺序陷阱**：腾讯 `[开收高低]`（close 在 high/low 前），按位置解析，别按标准 OHLC；尾部 `{}`/涨跌字段忽略。
3. **竞价两根特殊**：收盘 1500→1501（错位）、开盘 0930 丢弃（竞价根）。
4. **amount 缺省**：腾讯无成交额，bar_1min.amount 写 NULL（不是 0，与 Tushare `to_save_rows_min` 的 0 分叉——统一 NULL 口径，盲审 P2）。
5. **validate_bars 剔 ohlc=0**：冷门标的腾讯某分钟可能全 0，被剔后 `MAX(ts)` 误判缺口 → 漏取检测需区分「真缺」与「全 0 被剔」（盲审 P2）。
6. **切换互斥**：现定「切 Tushare 清空 tencent 行重建」；切换是任务 C。
7. **北交所/编码**：`_tencent_sym` 对北交所（bj 前缀）腾讯大概率不支持，展开表 category 过滤 astock 规避；mkline 是 UTF-8 JSON（非 gbk），单独确认。
8. **bar_hub 回溯**：缩小订阅后非实盘标的 bar_hub 不再积累（属预期，历史分钟走 bar_1min/腾讯）。
