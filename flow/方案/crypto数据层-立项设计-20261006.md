## 一、一次纠正与一次实测：真 gate 是网络，不是鉴权

威廉姆的判断**是对的**——交易所的**公开行情端点无鉴权**，`exchangeInfo` / `klines` / `depth` 等完全开放，只有下单/账户类要签名。所以「等账号、等 key」从来不是数据层的真实阻碍。

但据「不需 key」直接开工同样是错的，因为真阻碍是**网络可达性**：prod 在大陆阿里云（`120.24.235.98`，深圳），交易所域名在网络层被阻断。本节用 **prod 实测**把可达面钉死（这是开工的唯一依据）。

## 二、可达性实测矩阵

实测机：`quant.snailtrail.cc`（prod，大陆阿里云深圳）；时间 2026-10-06 00:1x CST；`curl -m 8~12`。

|---|---|---|---|
| 1 | `data-api.binance.vision/api/v3/{ping,exchangeInfo,klines}` | 币安**现货**公开行情 REST（CDN） | **200 / 0.25–0.30s** ✅ |
| 2 | `data.binance.vision/data/{spot,futures/um}/{daily,monthly}/klines/...` | 币安**官方批量历史** ZIP（现货 + **USDT 永续**） | **200** ✅ |

| 5 | `www.okx.com` / `okx.com` / `aws.okx.com` | OKX 全部 | `000`（DNS 污染至 `169.254.0.2`＝`awscn.okpool.top` + IP 层 RST；`--resolve` 绕 DNS 亦秒断）❌ |
| 6 | `api.exchange.coinbase.com` / `api.kraken.com` / `www.bitstamp.net` / `api.coingecko.com` / `api.bitget.com` | 备选公开源 | 全部 `000` ❌ |

**结论**：prod 可达的加密数据面**唯一敞口 = 币安的两个 `binance.vision` 域**。而这两个域恰好覆盖「**非实时**（历史批量 + T+1 增量）」的全部需求——与威廉姆「不做实时就开放」的判断严丝合缝。**实时 + OKX + 其他所**，全部不可达。

> 附注（排除环境噪声）：`aws.okx.com` 一度解析到 prod 自身 IP `120.24.235.98`，根因是解析器 `search snailtrail.cc` + 通配 `*.snailtrail.cc`（`ndots` 先试带后缀名），**非** OKX 有内容；用 `RES_OPTIONS=ndots:1` 复核后仍指向污染地址。

## 三、数据形状与覆盖深度（实测）

- **成员**：`BTCUSDT-1m-2026-10-04.zip` → `BTCUSDT-1m-2026-10-04.csv`。
- **表头**：`open_time, open, high, low, close, volume, close_time, quote_volume, count, taker_buy_volume, taker_buy_quote_volume, ignore`（12 列，日线同理、无 `count` 之外的差异）。
- **行数**：1m 日包 **1441 行**（1440 分钟 + 边界行）。
- **历史深度**：USDT 永续（um）月度包 `2021-01` ✅；早于 `2019-09` 404（永续 2019-09-08 上线）；现货日线自 2017-08。
- **T+1 语义**：UTC 当日文件 `404`、前一日 `200` ⇒ **日线在次日 UTC 可得**（天然 T+1，无盘中数据）。
- **非日线 bar 表**：`bar_1min/5min/15min/30min/1h/4h/60min` 全部 **0 行**（研究稿确认「纯为 crypto 预留」）；`bar_1d` 1747 万行全 astock。
- **币安无 4h 周期**：只有 1s/1m/3m/5m/15m/30m/1h/2h/4h/6h/8h/12h/1d/3d/1w/1M —— 实测口径含 4h，故 `bar_4h` 可用；但保留窗口与日线不同（见 §五）。

## 四、与平台目标的匹配：一个必须点破的错配

平台的加密腿**交易**目标是**币安 USDT 永续**（证据：`md_gateway.BinanceMdGateway`→`vnpy_binance.BinanceLinearGateway`；`markets.PROVIDER_MARKET["binance_perp"]="crypto"`；`contract` 的 `_SWAP_BINANCE`）。

| 需求 | 可达路径 | 结论 |
|---|---|---|
| 永续历史 K 线（回测/因子） | `data.binance.vision` um 批量 ZIP | ✅ **零依赖，可立即做** |
| 永续 T+1 增量 | 同上，日包次日可得 | ✅ 零依赖 |
| 永续**实时** tick / 下单 | `fapi.binance.com`（堵） | ❌ 需境外代理 |
| OKX 任意（现货/永续/实时） | `www.okx.com`（堵） | ❌ 需境外代理 |

**⇒ 数据层（非实时）与实盘腿（实时）可干净解耦**：先做数据层（本立项），实时腿待代理方案定后另批（批 102）。这是本立项成立的技术前提。

## 六、供给端口：复用批 100 刚建的 `fetch_supply`

批 100 把供给面统一到 `BaseDataAdapter.fetch_supply(kind, sub_kind=None, **params) -> DataFrame`，正是为「新 provider 插拔」准备的。加密数据层**不改端口**，只加实现：

- **`BinanceAdapter`**（新，`provider="binance"`）——实况（与初稿的差异已就地更正）：
  - `capabilities = {"crypto_perp_daily"}`——**sync_id 级**（初稿写的 `("hist_quote","ref_data")` 是**能力集 token 级，键错**：
    该字段的消费点 `_validate_provider` 要的是 sync_id 串；token 归一由 `SYNC_ID_CAP_MAP` 承担）。
    不含 `rt_quote`（非实时是真实能力，不许虚报）。
  - `capability_decls = [CapabilityDecl("bar_daily", "historical", CRYPTO_ALL)]`——`bar_daily` **非聚合域**
    ⇒ `sub_kinds` **必须为空**（`contract.validate_capability_decls` 硬约束）；初稿写的 `bar_minute`/`ref_data.symbols`
    属批 101b/后续，未声明（**只声明真实现的**）。
  - **单一批量后端**：`data.binance.vision` ZIP → 解压 → DataFrame。CDN 后端（`data-api.binance.vision`）
    **未实现**——批量站已覆盖历史，CDN 只对「近端校验」有价值，留作后续。
  - **形态**：crypto 属「按标的 + 连续时间窗口」形态（无「全市场单日」概念）⇒ 引擎新增 **by-symbol 窗口 handler**
    （`_sync_crypto_perp_daily`，**不**入 `_VIA_KIND_IDS`，不复用 A 股 by-trade_date 任何路径）。
- **符号主体**：`S3 ListObjectsV2`（`s3.ap-northeast-1.amazonaws.com/data.binance.vision`，分页）**全枚举**——
  实测 1056 条目 = 1004 永续 + 52 交割合约（`_YYMMDD` 后缀排除）；含 5 个中文名符号（须 URL 编码）。
  **放弃初稿的 Top-N 白名单**（威廉姆裁决：所有标的都要）。
- **两把键不混**：数据源 `binance`（hist_quote，0 密钥）≠ 交易通道 `binance_perp`（trading/rt_quote）。
  混用 ⇒ `_get_supply_adapter` 找不到 adapter 而**静默回落 tushare 拉错源**。
- **三处各注册一类**（批 83b 立法）：`adapters._ADAPTERS`（+ `adapters/__init__.py` 显式导入）
  + `data_source._REGISTRY`（`BinanceDataSource`，`DEFAULT_RATE_LIMITS={}` 刻意不接限速体系）
  + `interfaces._REGISTRY`/`_PROVIDER_MODULES`（`BinanceProvider`，两 schema 皆空＝0 密钥的正确表达）。
- **限速两制落点修正**：初稿说「`rate_limit` 需支持无速率档」——实况是**根本不进** `rate_limit_context`
  （`_get_rate_ds("binance")` 无 DataSource 行会回落 tushare 兜底源并告警「串源风险」＝把币安下载
  计进 tushare 的熔断器，是错的）；礼貌性由 adapter 内 ≤8 并发表达。

## 七、落库设计

| 数据 | 目标表 | 键 |
|---|---|---|
| 永续**日线**（批 101 已落地） | `bar_1d` | `symbol='BTCUSDT.BINANCE'`、`freq='1D'`、**`ts=open_time`**(bar 起始, **UTC aware**, timestamptz)、`source='binance'`、`adj_factor=NULL`、`amount=quote_volume` |
| 永续/现货**分钟·小时**（批 101b） | `bar_1min/5min/15min/30min/1h/4h`（现全空，crypto 预留） | 同形 |

> **`ts=open_time`（更正初稿的 `close_time`）**：bar 的语义起点是开盘时刻；更关键的是 `ts` **必须 UTC aware**
> ——`db.validate_bars` 对 naive 值走 `as_utc`（按 Asia/Shanghai 解释）⇒ **静默错 8h**。
>
> `bar_1d` 唯一键 `(symbol, ts)` 天然支持 upsert；`source` 列区分 `tushare`/`binance`，两市场同行不冲突。
> 写入口：增量 `db.save_bars`（冲突跳过）；回补 `db.save_bars_overwrite`（手动回补优先级最高）。

## 八、死构件处置（研究稿 §七-4）

`data_increment_crypto`（`scheduler/tasks.py:97`）现为「每 15min 被 beat 唤醒、永远 `return {"status":"skipped"}`」的死构件。**本立项处置＝删除 + 收编**（更正初稿的「真实现」）：

- `scheduler/tasks.py` 的 `data_increment_crypto` task **删除**；`scheduler/app.py` 的 beat `data-increment-crypto` 条目**删除**。
- 功能改由 **`sync_config` 行 `crypto_perp_daily`** 承载（迁移 0132），经 `data_sync_scheduler` 调度
  → `engine._sync_crypto_perp_daily`；cron `'30 8 * * *'`（**北京时区解释** ⇒ 00:30 UTC，正落 UTC 昨日文件之后）。
  理由：与批 83b 收编四条硬编码 beat 的范式一致——**beat 是调度形态、`sync_config` 才是能力真源**；
  T+1 语义下 15min 周期本就无意义。
- 同批修 `strategies/crypto_cta_trend.py:5` 的过期断言「外部 gate：币安/OKX API 未开通」→
  「**误判**：公开端点本就无鉴权，真阻碍是网络可达性；实时腿待批 102」。
- 新增 `sync_config` 行须同步登记 `SYNC_ID_CAP_MAP`（**批 99 已立完备性闸**）——这正是那道闸第一次真拦新项。
