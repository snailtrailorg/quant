## 一、问题陈述

同步窗口的起点今天由**游标**（`last_sync_date`）单方面决定，而配置层里那个看起来像「数据起点」的字段（`start_floor`）**执行时不读**。由此三类问题：

1. **声明 ≠ 执行**：`start_floor` / `supports_backfill` 住在定义层，却只被前端读去渲染（回补日期下限、回补表单显隐）；`engine._get_config` 的 SELECT 里根本没有这两列。
2. **窗口策略没有家**：真正决定回看多远的是 engine 模块级常量（`first_run_days` / `default_days` / `20050408` / `_PARTIAL_FREEZE_MAX_DAYS` / `_TIER1_OVERLAP_DAYS` / `_CRYPTO_TAIL_GRACE`），不随任务、不随 kind、不可配。
3. **自愈靠启发式堆叠**：四条互不知道的常量在各自领域打补丁（§二），语义重叠、边界不清，且都治不了「真实起点之外的老洞」——OKX 7/485 的 19 天洞即此症。

本稿要定的是：**同步窗口由哪些边界决定、这些参数各归哪一层、现有四条启发式如何收编。**

## 三、判据：一个参数该放哪一层

> **换一个任务就不同 ⇒ 定义层（DB）；同类任务共享 ⇒ 代码按 kind 给默认；连上某源才需要 ⇒ 接入层。**

两条铁律：

- **声明面必须被执行面消费**——只声明不读的键是装饰（§2.2 两列即反例）。
- **事实进代码，值进 DB**——能力/形状是**代码事实**（进 DB 即双真源、必漂移，如批 107 抓到的 `etf_list.pg_table` 漂移）；连接值/凭证是**运维事实**（进 DB）。

## 四、参数的三层归属（目标态）

### 定义层 · DB（系统数据）

| 承载 | 表 |
|---|---|
| 任务身份 / 调度 / 开关 / 交易日过滤 / provider / 游标 | `sync_config` |
| 结构 + **列形状**（kind/sub_kind/pg_table/列清单/rebuild） | `sync_kind_config` |
| **数据起点**（`start_floor`）+ **窗口策略** | `sync_config`（升格，见下） |

使用方：scheduler（派发）+ engine（分派 / 写目标 / 窗口计算）。
**升格**：窗口策略下沉——`first_run_days` / `_PARTIAL_FREEZE_MAX_DAYS` / `_CRYPTO_TAIL_GRACE` / `20050408` 收成**按 kind 的默认表（代码）+ 任务行覆写（DB）**。默认跟 kind 走，因为「表有没有时间轴」由 kind 决定；个别源特殊才落任务行。

### 能力层 · 纯代码（绝不进 DB）

`adapter.capabilities`（sync_id 级）/ `capability_decls`（kind 级）/ `SYNC_ID_CAP_MAP`（归一）/ `_SUPPLY_PULL`（分派）。
使用方：写侧 `_validate_provider`（白名单）+ 前端 provider 下拉 + 域路由。
**理由**：能力是代码事实；进 DB ⇒ 双真源漂移。

### 接入层 · schema 代码 + 值 DB

`interfaces/*.py` 的 FIELD_SCHEMA / PARAMS_SCHEMA（**schema 是代码**）；`data_source` / `trading_account` 表的 credentials_encrypted / params（**值是运维事实**）；`proxy_binding`（出口）。
使用方：DataSource（get_client / 限速 / 熔断 / 用量）+ 组装时注入出口。

### 逐项归位表

| 参数 / 机制 | 现在 | 目标层 | 动作 |
|---|---|---|---|
| `id` / `name` / `schedule` / `enabled` / `trade_day_filter` | `sync_config` | 定义层 ✓ | — |
| `provider`（选哪家源） | `sync_config` | 定义层 ✓（桥到能力层） | — |
| `kind` / `sub_kind` / `pg_table` / 列清单 / `rebuild` | `sync_kind_config` | 定义层 ✓ | 列形状唯一真源 |
| 游标 `last_sync_date` / `ts` / `count` / `status` | `sync_config` | 定义层 ✓（运行态） | — |
| **`start_floor`** | `sync_config`（只前端读） | 定义层 | **升格为执行参数**（engine 读，当 retention） |
| **`supports_backfill`** | `sync_config`（只前端读） | 定义层 | **改为从 handler 派生**（是否消费 `backfill_from` ＝ 代码事实） |

| `FIELD_SCHEMA` / `PARAMS_SCHEMA` | 代码 | 接入层 ✓ | — |
| `credentials` / `params` / `proxy` | DB | 接入层 ✓ | — |

## 五、窗口边界模型（目标态）

### 5.1 两个地板 + 一个源上限

```
窗口 = [ max(inception, retention) , source_upper − publish_lag ]
```

| 边界 | 含义 | 性质 | 落点 |
|---|---|---|---|
| **inception（产生时间）** | 数据**可能**存在的**最早**时点 | **事实**，每标的不同 | 从列表快照派生（`list_date`） |
| **retention（保留下限）** | 我们**关心**的**最早**时点 | **策略**，每任务 | `sync_config.start_floor`（升格为执行参数） |
| **source_upper − publish_lag** | 源**能给**的最晚时点 | **源属性** | adapter 新增 `available_range(kind)` |

**为什么要两个地板而不是一个**：全史都留时 ①② 重合（所以看起来只需一个）；但分钟线/大表早晚要 retention 控成本（不可能真从 1990 拉 1min）。**正确做法是都显式化取 max**——`first_run_days=30` 正是「用一个假值同时冒充两者」的坏样本：既不是真 inception（30 天太短），也不是有依据的 retention（30 天太随意）。

### 5.2 「缺」的定义随类别变

| 类别 | 「缺」＝ | 可否自愈 |
|---|---|---|
| 时序（incremental） | 预期日无数据（astock 用 `trade_cal`；crypto 用 UTC 连续轴） | **可**（差集重拉，幂等） |
| 快照（full_rebuild） | 与上游当前快照不一致 | 只能重跑，**无「补历史」概念** |
| `trade_cal`（生成族） | 覆盖 `[下限, 今天]` 的年份区间 | 按年增量生成 |

## 六、四条启发式的收编

| 启发式 | 类型 | 归宿 |
|---|---|---|
| `_PARTIAL_FREEZE_MAX_DAYS=10` | 被动冻结 | **删**——标的级对账既替代其功能，又消除粒度错配（全族游标退回 → 单标的差集） |
| `_TIER1_OVERLAP_DAYS=3` | 主动重叠 | **删**——日期级对账覆盖全区间，不再只回看 3 天 |
| `_CRYPTO_TAIL_GRACE=2` + `_TIER1_LAG_TRADING_DAYS` | 发布滞后 | **并入 §5.1 的 publish_lag**（源属性，非 kind 属性） |
| `first_run_days` / `default_days=30` / `20050408` | 假首跑地板 | **换** `max(inception, retention)` |

**为什么「统一」不是「删一件事」**：四条分属三种类型、散在不同族。对 astock per-date 族是**加**日期级对账（它们连冻结都没有，比 crypto 更差，只有 3 天主动重叠兜迟发布）；只有 crypto 那 2 个族才是**删**。

## 七、分族治法

| 族 | 粒度 | 期望集 | 治法 |
|---|---|---|---|
| per-date 整市场（`astock_daily` / `etf_daily` / `cb_daily`） | 日期 | `trade_cal` 交易日集合 | **日期级差集**：`SELECT DISTINCT trade_date` vs 预期，差集重拉。**判据已存在、无前置依赖** ⇒ 是同步主路径的收尾步骤（非独立维护任务） |
| per-symbol（`bar_minute` / crypto bar / `pool_data` 财报股东） | 标的×日 | 每标的 `[inception, end−lag]` | **标的级差集**：O(标的数)，低频或按需（现成 `_find_gaps`） |
| 快照（`static_list` / `industry_class` / `holder_structure`） | — | 上游当前全集 | 清表重灌；**无 reconciliation** |
| `trade_cal` | — | 年份区间 | 按年增量生成 |

**关键区分**：`astock_daily` 走 `pro.daily(trade_date=X)` **按日整市场**拉，上游只返当日存活标的 ⇒ **lifecycle 不产生缺口**；其洞是**整日失败**（连接抖动丢一天）⇒ 必须靠日期级差集。**lifecycle 只对 per-symbol 族是正解。**

## 八、实施序（五步，含删除门）

1. **前置：源可达区间**——给 adapter 加 `available_range(kind) -> (earliest, latest)`，把散落的「源边界」收进来（`_TUSHARE_MIN_DATE=2010` 硬底 / 聚宽 `account_window()` / binance 月包 floor 2019-09 / okx 分页触顶）。**这是跨源地板的前提**——否则 `_get_list_date` 的 tushare 专属回退会「吃掉」换源后的窗口。
2. **crypto perp 生命周期**——**扩 `security_master`（`market='crypto'`）并给 crypto bar handler 接 SM 填充链**，把 OKX `listTime`（已在响应内）与 Binance 月包下限解析成 `list_date`，**使 inception 对 crypto 非空**。**这道门决定第 5 步能不能做。**
   *排除「新建 perp 表」（造第二真源）与「从数据表 `min(ts)` 推导」——后者对「整窗 0 行」的标的天生失明（推导源为空 ⇒ 永不报缺），正是 OKX 7/485 的形状。*
3. **双地板取 max**——`inception`（从列表快照派生，**带新鲜度前置**，见 §九）+ `retention`（`start_floor` 升格，engine 真读），替换 `first_run_days` / `default_days` / `20050408`。
4. **分族对账**——per-date 族走日期级差集；per-symbol 族走标的级差集（低频 / 按需）。
5. **删 `freeze_on_partial`**——**门控**：①②③④ 落地 **且**对账在 prod 证明覆盖同一缺口。

**为什么删除是最后一步、且门控**：冻结今天**独家**护住「某标的整窗 0 行」（OKX 7/485）——该缺口**只有 inception 能检出**（无行 ⇒ 期望集为空 ⇒ 对账不可见）。在 crypto 有生命周期前删冻结 ＝ 重开此洞。过渡期并存只是**有界冗余**（全族重拉 11 天，幂等），**无正确性损失**，故安全。

## 九、边界与风险

1. **🔴 依赖倒置**：inception 是**派生数据**（来自 `asset_static_info` / `security_master`，本身是快照族同步项）。用时序族的完整性依赖快照族新鲜度 ⇒ **列表快照一过期（新上市股未入），时序族完整性就系统性静默漏报**。必须显式化前置 + 快照 stale 时判「**不确定**」而非「无缺」。同族前科：清单驱动检测点不看 `enabled` ⇒ 停用数据源永 stale（P1-A）。
2. **只对 per-symbol 族有效**（见 §七）——不是通解。
3. **`_get_list_date` 是 tushare 专属**：硬编码 `_TUSHARE_MIN_DATE`（`SYNC_START_DATE` 默认 `20100101`）当回退 + 下限 ⇒ 换源即错。升格前必须先落第 1 步。
4. **crypto 生命周期空白**（§2.6）——第 2 步不做，整个模型对 crypto 空转（inception 无从取得 ⇒ 标的级对账对 crypto 无期望集）。
5. **分钟族 retention**：全区间对账对高频族成本不可接受（受 G-S1 约束）⇒ 只能标的级、低频 / 按需。
6. **不做**：不重写游标契约（刚稳）；不把 full/incremental 压成一个 bool；不追求「所有设置都进 DB」。

| C | 对账调度频率 | 每轮 ／ 每日低峰 ／ 周级 | **不设全局值**，按族/kind 定义 |
| D | per-date 族对账优先级 | 与 per-symbol 同批 ／ **先 per-date** | **先 per-date** |
| E | 孤儿参数键闸门 | 立 ／ 不立 | **立**（列级 + 带理由豁免） |

### A. → 扩 `security_master`

- **单一真源**：SM 已是系统**唯一跨市场标的元数据真源**（`vt_symbol` 主键；`_market_of_suffix` 已认 crypto；`covers()` 已声明「SM 未回填 ≠ 不可用」）。新建表 ＝ **第二真源**（同族前科：批 107 `etf_list.pg_table` 漂移）。
- **形状匹配**：crypto 永续需要的 `multiplier`（合约面值）/ `tick_size` / `fee_model_ref` / `session_id` / `trade_phase` **只有 SM 有列**；`list_date`（上币日）与 astock 上市日**同语义**，天然复用。
- **容器已备**：`market_hours` 有 `crypto_247`、`security_state` 已按 `vt_symbol` 组织 ⇒ 扩 SM 是「接进已有体系」，新建表要重接一遍。
- **排除「推导规则」是架构理由**：「从数据表 `min(ts)` 推」对**整窗 0 行**的标的天生失明 ⇒ 正是 OKX 7/485 的形状（见 §八 删除门）。
- **必须连带**（正确性，非成本）：crypto handler 接 SM 填充链；`upsert_rows` 补 `session_id` 通道（现 12 列签名缺，否则落 `astock_main`）；crypto 行显式传 `trade_phase='T+0'` 与真实 `multiplier` / `tick_size`（否则落 astock 默认 ＝ 语义污染）。

### B. → 任务列为准 + kind 默认作默认值来源

- **判据**「换任务才变 ⇒ DB」：retention 换任务就不同 ⇒ 必须**任务级可表达**；仅 kind 默认**表达不了**个别任务的差异。
- **值已存在**：`start_floor` 列在、且 crypto 项**已填**（§2.6）——缺的只是执行面读它。
- **不构成双真源**：kind 默认在**读入时合并**（列 NULL ⇒ 取 kind 默认），运行时只有一个有效值。前提：明写「**任务行为准**」。
- **须正名**（§5.1）：现 crypto `start_floor` 填的是「源下限」，属 §③；`retention`（我们关心多早）与 ③ 语义不同，落地时要分清——**族级 retention（`start_floor`）与标的级 inception（SM）并存**，前者治「整族下界」，后者治「单标的产生时间」，OKX 那 7 标的正是后者才能表达的洞。

### C. → 不设全局值，按族/kind 定义

- **做成全局单选 ＝ 又开一个「没有家」的全局常量**（§一.2 的同构缺陷）。
- **per-date：每轮**——「本轮声称完成的区间必须真实完整」是**同步器的固有职责**（属主路径收尾，非独立节拍）；判据 `trade_cal` 已存在。
- **per-symbol：低峰 / 周级**——依赖 inception（第 2 步）、属**旁路深度修复**。
- **快照族：不对账**——无「补历史」概念。

### D. → 先 per-date

- **依赖闭合度**：per-date 判据 `trade_cal` 已存在、**不依赖 A / 第 1 步**；per-symbol 依赖 A（crypto 行）与第 1 步（跨源、源下限）⇒ per-date 是**可独立成立的最小完备子集**。
- **职责层级**：per-date 是**同步语义自洽**（主路径）；per-symbol 是**深度修复**（旁路）。主路径职责先于旁路工具。
- **收敛方向**：per-date 对账**替代正在起作用的 `_TIER1_OVERLAP_DAYS`** ⇒ 先替换在跑的启发式，使「启发式只减不增」，与 §六 收编方向一致。
- **非二选一**：两者治**不同类别**的洞（§七），是排序不是取舍。

### E. → 立（列级 + 带理由豁免）

- **它是铁律一的可执行形式**（§三）：没有它，「声明必须被执行面消费」只是口号——实证即 §2.2 两列。同族先例：批 107 的对账门（注册表 ↔ 真源）。
- **列级粒度**：`sync_config` 的策略 / 声明列必须在 `src/**`（非测试）有读取点；运行态 / 审计列豁免。
- **豁免须显式 + 带理由**，否则退化成垃圾场（门就没有牙）。
- **启红先于修复**：先让现有孤儿列在 CI 全暴露，再逐条「读数 / 删列 / 豁免 + 理由」。

---

## 十一、结论

**一句话**：同步窗口应从「游标单源 + 四条启发式兜底」改为 **`[max(inception, retention), 源上限 − 发布滞后]` 的三边界交集**；参数按「换任务才变 → DB、同类共享 → 代码 kind 默认、连源才需 → 接入层」三层归位；四条启发式分别**删 / 删 / 并入源边界 / 换真地板**。**冻结的删除是收尾步，门控在 crypto 生命周期落地**——否则重开 OKX 那类洞。
