## 一、问题陈述

同步窗口的起点今天由**游标**（`last_sync_date`）单方面决定，而配置层里那个看起来像「数据起点」的字段（`start_floor`）**执行时不读**。由此三类问题：

1. **声明 ≠ 执行**：`start_floor` / `supports_backfill` 住在定义层，却只被前端读去渲染（回补日期下限、回补表单显隐）；`engine._get_config` 的 SELECT 里根本没有这两列。
2. **窗口策略没有家**：真正决定回看多远的是 engine 模块级常量（`first_run_days` / `default_days` / `20050408` / `_PARTIAL_FREEZE_MAX_DAYS` / `_TIER1_OVERLAP_DAYS` / `_CRYPTO_TAIL_GRACE`），不随任务、不随 kind、不可配；**且窗口起点有四处各自为政的站点**（§2.1）。
3. **自愈靠启发式堆叠**：四条互不知道的常量在各自领域打补丁（§2.3），语义重叠、边界不清，且都治不了「真实起点之外的老洞」——OKX 7/485 的 19 天洞即此症。

本稿要定的是：**同步窗口由哪些边界决定、这些参数各归哪一层、现有四条启发式如何收编。**

## 三、判据：一个参数该放哪一层

> **换一个任务就不同 ⇒ 定义层（DB）；同类任务共享 ⇒ 代码按 kind 给默认；连上某源才需要 ⇒ 接入层。**

两条铁律：

- **声明面必须被执行面消费**——只声明不读的键是装饰（§2.2 两列即反例）。**可执行形式＝E 闸门（CI 强制）**（§十 E）。
- **事实进代码，值进 DB**——能力/形状是**代码事实**（进 DB 即双真源、必漂移，如批 107 抓到的 `etf_list.pg_table` 漂移）；连接值/凭证是**运维事实**（进 DB）。

## 四、参数的三层归属（目标态）

### 定义层 · DB（系统数据）

| 承载 | 表 |
|---|---|
| 任务身份 / 调度 / 开关 / 交易日过滤 / provider / 游标 | `sync_config` |
| 结构 + **列形状**（kind/sub_kind/pg_table/列清单/rebuild） | `sync_kind_config` |
| **数据起点**（`start_floor` = retention）+ **窗口策略** | `sync_config`（升格，见下） |
| **对账缺口**（per-symbol 缺口行：同步目标 / 缺口区间 / 状态 / 重拉次数） | **新表 `sync_gap`**（§7.2） |

使用方：scheduler（派发）+ engine（分派 / 写目标 / 窗口计算）+ 对账（§7.2）。
**升格**：窗口策略下沉——`first_run_days` / `_PARTIAL_FREEZE_MAX_DAYS` / `_CRYPTO_TAIL_GRACE` / `20050408` 收成**按 kind 的默认表（代码）+ 任务行覆写（DB）**。默认跟 kind 走，因为「表有没有时间轴」由 kind 决定；个别源特殊才落任务行。

### 能力层 · 纯代码（绝不进 DB）

`adapter.capabilities`（sync_id 级）/ `capability_decls`（kind 级）/ `SYNC_ID_CAP_MAP`（归一）/ `_SUPPLY_PULL`（分派）。
使用方：写侧 `_validate_provider`（白名单）+ 前端 provider 下拉 + 域路由。
**理由**：能力是代码事实；进 DB ⇒ 双真源漂移。

### 接入层 · schema 代码 + 值 DB

`interfaces/*.py` 的 FIELD_SCHEMA / PARAMS_SCHEMA（**schema 是代码**）；`data_source` / `trading_account` 表的 credentials_encrypted / params（**值是运维事实**）；`proxy_binding`（出口）；**`adapter.available_range(kind)`（源可达边界，代码）**。
使用方：DataSource（get_client / 限速 / 熔断 / 用量）+ 组装时注入出口 + **窗口计算（§5.1 的源上下界）**。

### 逐项归位表

| 参数 / 机制 | 现在 | 目标层 | 动作 |
|---|---|---|---|
| `id` / `name` / `schedule` / `enabled` / `trade_day_filter` | `sync_config` | 定义层 ✓ | — |
| `provider`（选哪家源） | `sync_config` | 定义层 ✓（桥到能力层） | — |
| `kind` / `sub_kind` / `pg_table` / 列清单 / `rebuild` | `sync_kind_config` | 定义层 ✓ | 列形状唯一真源 |

## 五、窗口边界模型（目标态）

### 5.1 三个地板 + 一个源上限

```
窗口 = [ max(inception, retention, source_earliest) , source_latest − publish_lag ]
```

| 边界 | 含义 | 性质 | 落点 |
|---|---|---|---|
| **inception（产生时间）** | 数据**可能**存在的**最早**时点 | **事实**，每标的不同 | 生命周期主档（`security_master.list_date`，§八.2） |
| **retention（保留下限）** | 我们**关心**的**最早**时点 | **策略**，每任务 | `sync_config.start_floor`（升格为执行参数） |
| **source_earliest（源可达下界）** | 源**整体**能给到的**最早**时点（kind 级） | **源属性** | `adapter.available_range(kind)`（新建硬契约） |
| **source_latest − publish_lag** | 源**能给**的最晚时点（扣发布滞后） | **源属性** | 同上（双返回） |

**为什么要有源下界（本轮新增，双盲审 P0 病灶）**：只有上界时，适配器会**在内部私自收窄起点**（`binance_adapter._pull` :242-250 的省流阀即此），于是「模型窗口 ≠ 真实窗口」，**对账层无法信任上游**：模型认为该拉 2019-09 起，适配器默默从 2020-01 起，最终「拉回了空」与「源本来就没有」**同形**。

**为什么要有两个地板（inception / retention）**：全史都留时两者重合（所以看起来只需一个）；但分钟族不可能对「从 1990 起的每一分钟」都负有完整性义务——**这是职责范围的界定**。**正确做法是都显式化取 max**——`first_run_days=30` 正是「用一个假值同时冒充两者」的坏样本：既不是真 inception（30 天太短），也不是有依据的 retention（30 天太随意）。

**`source_earliest` 的粒度陷阱（必须明写）**：`available_range` 是 **kind 级**，而 Binance 的**日包可达性逐标的不同**（2023 年上市的永续，日包自然自 2023 起）。⇒ **per-symbol 的那一段绑定由 `inception` 承担**（对 crypto，上币日恰恰就是该标的的数据可达起点），`source_earliest` 只处理「**源整体**拿不到更早」。**特别地**：`binance_perp_daily` 的源级 earliest 是 **`2019-09-08`（日包可达，`_pull` docstring 自证）**，**不是**月包 floor `2020-01`——后者只是批量路径的**优化边界**，既不是源级下界，更不是任何标的的 inception。

### 5.2 「缺」的定义随类别变

| 类别 | 「缺」＝ | 可否自愈 |
|---|---|---|
| 时序（incremental） | 预期日无数据（astock 用 `trade_cal`；crypto 用 **UTC 连续轴**——与 `bar_1D` 的 `ts`＝`00:00 UTC` 源原生日界一致） | **可**（差集重拉，幂等） |
| 快照（full_rebuild） | 与上游当前快照不一致 | 只能重跑，**无「补历史」概念** |
| `trade_cal`（生成族） | 覆盖 `[下限, 今天]` 的年份区间 | 按年增量生成 |

### 5.3 期望集下界 ≡ 窗口下界（不许各算一套）

对上表「时序」类，**期望集下界必须等于窗口下界 `max(inception, retention, source_earliest)`**：

- 若 `retention > 某标的 inception`（如 OKX `start_floor=2020-01-01` vs 2019 上市的永续），**retention 同时封顶期望集**——不能「拉取从 2020-01 起、期望却含 2019」⇒ 否则要么**永久缺口告警**、要么「对账认亏」⇒ **静默丢史且永不收敛**。
- 若 `source_earliest > inception`（源整体给不到的生命早期段），该段是**源不可达区间**，须**显式记录**（进 `sync_gap` 标记 `unreachable`），**不得**静默豁免——否则「源头就缺」与「我们拉漏了」再次同形。

### 5.4 新鲜度前置：stale ⇒ 「不确定」，禁报「无缺」

`inception` 是**派生数据**（来自快照族）。列表快照一旦过期（新上市标的未入），per-symbol 对账的**期望集本身就不完整** ⇒ 必须把「快照新鲜度」转成对账的**输出态**：快照 age 超阈 ⇒ 该轮对账输出 `stale_source`（「不确定」），**禁止**输出「无缺」。见 §九.1。

## 六、四条启发式的收编

| 启发式 | 类型 | 归宿 |
|---|---|---|
| `_PARTIAL_FREEZE_MAX_DAYS=10` | 被动冻结 | **删**——标的级对账既替代其功能，又消除粒度错配（全族游标退回 → 单标的差集） |
| `_TIER1_OVERLAP_DAYS=3` | 主动重叠 | **删**——日期级对账覆盖全区间，不再只回看 3 天 |
| `_CRYPTO_TAIL_GRACE=2` ＋ `_TIER1_LAG_TRADING_DAYS` | 发布滞后 | **并入 §5.1 的 publish_lag**（源属性，非 kind 属性） |
| `first_run_days` / `default_days=30` / `20050408` | 假首跑地板 | **换** `max(inception, retention, source_earliest)` |

**为什么「统一」不是「删一件事」**：四条分属三种类型、散在不同族。对 astock per-date 族是**加**日期级对账（它们连冻结都没有，比 crypto 更差，只有 3 天主动重叠兜迟发布）；只有 crypto 那 2 个族才是**删**。

## 七、分族治法与对账闭环

### 7.1 分族治法

| 族 | 粒度 | 期望集 | 治法 |
|---|---|---|---|
| per-date 整市场（`astock_daily` / `etf_daily` / `cb_daily`） | 日期 | `trade_cal` 交易日集合 | **日期级差集**：`SELECT DISTINCT trade_date` vs 预期，差集重拉。**判据已存在、无前置依赖** ⇒ 是同步主路径的收尾步骤（非独立维护任务） |
| **TIER1 族**（`margin_detail_sync` 等，`_make_tier1_handler`） | 日期 | 交易日集合（上界按 `publish_lag` 回推） | 同上（日期级差集）；**当前 handler 自算窗口，收编时须一并纳入**（§2.1 第四站点） |
| per-symbol（`bar_minute` / crypto bar / `pool_data` 财报股东） | 标的×日 | 每标的 `[max(inception, retention, source_earliest), end−lag]` | **标的级差集**：O(标的数)，低频或按需（现成 `_find_gaps`） |
| 快照（`static_list` / `industry_class` / `holder_structure`） | — | 上游当前全集 | 清表重灌；**无 reconciliation** |
| `trade_cal` | — | 年份区间 | 按年增量生成 |

**关键区分**：`astock_daily` 走 `pro.daily(trade_date=X)` **按日整市场**拉，上游只返当日存活标的 ⇒ **lifecycle 不产生缺口**；其洞是**整日失败**（连接抖动丢一天）⇒ 必须靠日期级差集。**lifecycle 只对 per-symbol 族是正解。**

### 7.2 对账输出闭环（缺口去哪、谁重拉、谁告警）

对账若只产报告、无消费者＝**等于没做**（双盲审 P1）。两类输出**分别定义消费者**：

| 粒度 | 输出 | 消费者 |
|---|---|---|
| **per-date**（主路径） | 本轮声称完成区间内的缺日 | **同步任务内联重拉**（补拉差集，幂等），**当轮收尾**；重拉仍缺 ⇒ 落 `sync_gap` ＋ 告警 |
| **per-symbol**（旁路） | 标的三元组 `(sync_id, symbol, 缺口区间)` | **落 `sync_gap` 表**（§四 定义层）＋ **告警** ＋ **限频重拉**（按缺口区间，幂等；重拉成功则闭合该行）；`unreachable`（§5.3）与 `stale_source`（§5.4）**单独标记** |
| 快照族 | — | 不对账（无「补历史」概念） |

**闭环判据**：`sync_gap` 每行必须能被三种方式之一终结——`closed`（重拉补齐）/ `unreachable`（源不可达，已记录）/ `stale_source`（快照不适格，待快照刷新）。**长期停留在 open 的行数**即「存量缺口」指标。

## 八、实施序（五步，含删除门）

1. **前置：源可达区间（硬契约）**——给 adapter 加 `available_range(kind) -> (earliest, latest)`，把散落的「源边界」收进来（`_TUSHARE_MIN_DATE=2010` 硬底 / 聚宽 `account_window()` / binance **日包**下界 `2019-09-08`（非月包 floor）/ okx 分页触顶）；`publish_lag` 一并由这里给出。
   - **硬契约**：所有**可拉** adapter **必须实现**，返回 `None` ⇒ **fail-loud**（CI 断言 pull-capable adapter 全覆盖）。否则新源漏实现即默认「today ⇒ 永不回补历史」，source_upper 变**软真源**。
   - **必须含 joinquant `account_window()`**（第三个起点站点）——否则换源 bug 残留在该类源（§九.3）。
2. **crypto perp 生命周期**——**扩 `security_master`（`market='crypto'`）并给 crypto bar handler 接 SM 填充链**，**inception 取真上币日**：OKX 取 `listTime`（已在响应内、现被丢弃）；**Binance 取 `exchangeInfo.onboardDate`；fapi 被墙时须另找可信来源，或显式写「inception 未知」——严禁用 `first_available_month` / 日包可达性冒充**（§2.6、§九.3）。
   - **连带**：`upsert_rows` 补 `session_id` 通道（＋显式传 `trade_phase='T+0'` 与真实 `multiplier` / `tick_size`）；**`_get_list_date` 现读 `asset_static_info` / `etf_basic_info` / `cb_basic_info`（engine.py:1862）、非 SM** ⇒ 须让 SM 成为这三表的真上游，或改 `_get_list_date` 读 SM，否则 **inception 双源**。
   - **这道门决定第 5 步能不能做。**
   - *排除「新建 perp 表」（造第二真源）与「从数据表 `min(ts)` 推导」——后者对「整窗 0 行」的标的天生失明（推导源为空 ⇒ 永不报缺），正是 OKX 7/485 的形状。*
3. **三方地板取 max**——`inception`（生命周期主档，**带新鲜度前置**，见 §5.4）＋ `retention`（`start_floor` 升格，engine 真读）＋ `source_earliest`（第 1 步），替换 `first_run_days` / `default_days` / `20050408`。
4. **分族对账 + 输出闭环**——per-date 族走日期级差集（内联重拉）；per-symbol 族走标的级差集（低频 / 按需），输出落 `sync_gap` ＋ 告警（§7.2）。
5. **删 `freeze_on_partial`**——**门控改为可观测判据**：连续 **N 轮** per-symbol 对账命中**同一缺口**且**零误报**；且 per-symbol 对账**已调度、自动重拉在跑**。**禁用**「对账在 prod 证明覆盖同一缺口」这类**无判据**表述。

**为什么删除是最后一步、且门控**：冻结今天**独家**护住「某标的整窗 0 行」（OKX 7/485）——该缺口**只有 inception 能检出**（无行 ⇒ 期望集为空 ⇒ 对账不可见）。在 crypto 有生命周期前删冻结 ＝ 重开此洞。过渡期并存只是**有界冗余**（全族重拉 11 天，幂等），**无正确性损失**，故安全。**但 F-1 提示**：crypto 族在 dev **从未闭合过游标、零成功记录** ⇒ 第 3 步「取 max」在 crypto 上等于**从零开始**，**验收必须覆盖「首跑即全史」这条路径**。

## 九、边界与风险

1. **🔴 依赖倒置**：inception 是**派生数据**（来自快照族同步项）。用时序族的完整性依赖快照族新鲜度 ⇒ **列表快照一过期（新上市股未入），时序族完整性就系统性静默漏报**。**闭合方式**＝§5.4：快照 stale ⇒ 输出 `stale_source`（「不确定」），禁报「无缺」。同族前科：清单驱动检测点不看 `enabled` ⇒ 停用数据源永 stale（P1-A）。
2. **🔴 源下界缺失**：模型若只有上界，适配器内部私自收窄起点 ⇒ 「模型窗口 ≠ 真实窗口」⇒ 对账不可信。**闭合方式**＝§5.1 第四边界 ＋ `available_range` 双返回 ＋ 第 1 步硬契约。
3. **🔴 inception 语义错配**：**源可得性 ≠ 生命起点**。用「源最早可得」当「上币日」＝把这个已知陷阱从「拉取起点」搬进「期望集下界」，错误性质从「拉不到」（看得见）恶化为「**不认为缺失**」（静默）。**闭合方式**＝§八.2 禁则；Binance 真上币日不可得时须**显式「未知」**，不得用可达性兜底（未知时对账按「不确定」处理，不报「无缺」）。
4. **只对 per-symbol 族有效**（§七）——不是通解。
5. **`_get_list_date` 是 tushare 专属**（§2.5）：硬编码 `_TUSHARE_MIN_DATE`（engine.py:1820，`SYNC_START_DATE` 默认 `20100101`）当回退 ＋ 下限 ⇒ 换源即错。升格前必须先落第 1 步。
6. **`index_daily` 无列表来源**（仅硬编码 `20050408`）⇒ 无 `inception`。该族只能靠 `retention`（＋源下界），须**显式声明**「此族无生命周期期望集」，不得默认按有 inception 处理。
7. **crypto 生命周期空白**（§2.6）——第 2 步不做，整个模型对 crypto 空转。
8. **分钟族 retention**：全区间逐日对账对高频族不适用（与 G-S1 系统资源包络冲突）⇒ 只能标的级、低频 / 按需。
9. **不做**：不重写游标契约（刚稳）；不把 full/incremental 压成一个 bool；不追求「所有设置都进 DB」。

## 十、待裁点与建议

> 建议**只按架构合理性**给——判据为**单一真源 / 依赖方向 / 职责层级 / 契约闭合**，不以实施成本或工作量论先后。下为助手意见，**待威廉姆裁定**。（A/B 的措辞经双盲审①修订；F/G 为本轮新增。）

| # | 待裁 | 选项 | 建议 |
|---|---|---|---|
| A | crypto perp 生命周期来源 | 新建表 ／ **扩 `security_master`** ／ 推导规则 | **扩 `security_master`（有条件）**——inception 须取真上币日（§八.2） |
| B | `retention` 落地形态 | **每任务列（`start_floor`）+ kind 默认** ／ 仅 kind 默认 | **任务列为准 + kind 默认作默认值来源**（＋同列两义逐行正名） |
| C | 对账调度频率 | 每轮 ／ 每日低峰 ／ 周级 | **不设全局值**，按族/kind 定义；**输出闭环（§7.2）为前置** |
| D | per-date 族对账优先级 | 与 per-symbol 同批 ／ **先 per-date** | **先 per-date** |
| E | 孤儿参数键闸门 | 立 ／ 不立 | **立**（列级 + 带理由豁免 + **CI 强制**） |
| **F** | Binance 真上币日不可得时的表达 | 显式「未知」/ 用日包下界近似并标注 / 用月包 floor | **显式「未知」**（禁近似冒充真值） |
| **G** | `inception` 单一真源 | SM 为 `asset_static_info` 等表的真上游 ／ 改 `_get_list_date` 读 SM | **二选一，须择一**（否则 inception 双源） |

### A. → 扩 `security_master`（**有条件**）

- **单一真源**：SM 已是系统**唯一跨市场标的元数据真源**（`vt_symbol` 主键；`_market_of_suffix` 已认 crypto；`covers()` 已声明「SM 未回填 ≠ 不可用」）。新建表 ＝ **第二真源**（同族前科：批 107 `etf_list.pg_table` 漂移）。
- **形状匹配**：crypto 永续需要的 `multiplier`（合约面值）/ `tick_size` / `fee_model_ref` / `session_id` / `trade_phase` **只有 SM 有列**；`list_date`（上币日）与 astock 上市日**同语义**，天然复用。
- **容器已备**：`market_hours` 有 `crypto_247`、`security_state` 已按 `vt_symbol` 组织 ⇒ 扩 SM 是「接进已有体系」，新建表要重接一遍。
- **排除「推导规则」是架构理由**：「从数据表 `min(ts)` 推」对**整窗 0 行**的标的天生失明 ⇒ 正是 OKX 7/485 的形状（见 §八 删除门）。
- **🔴 条件（双盲审① P0）**：**inception 只能取真上币日**——OKX `listTime`；Binance `exchangeInfo.onboardDate`；**禁用 `first_available_month` / 日包可达性冒充**。Binance fapi 被墙 ⇒ 按待裁 **F** 显式「未知」。
- **必须连带**：crypto handler 接 SM 填充链；`upsert_rows` 补 `session_id` 通道（现 12 列签名缺）；crypto 行显式传 `trade_phase='T+0'` 与真实 `multiplier` / `tick_size`；并按待裁 **G** 解决 `_get_list_date` 与 SM 的双源。

### B. → 任务列为准 + kind 默认作默认值来源

- **判据**「换任务才变 ⇒ DB」：retention 换任务就不同 ⇒ 必须**任务级可表达**；仅 kind 默认**表达不了**个别任务的差异。
- **值已存在**：`start_floor` 列在、且 crypto 项**已填**（§2.6）——缺的只是执行面读它。
- **不构成双真源**：kind 默认在**读入时合并**（列 NULL ⇒ 取 kind 默认），运行时只有一个有效值。前提：明写「**任务行为准**」。
- **须正名（同列两义，须逐行判）**：`binance_perp_daily=2019-09-08` 是**源下限**语义、`hourly/15min/1min` 是 **retention** 语义，**同一 provider 内部就混装**（§2.6）⇒ 正名**不可按 provider 一刀切**。且 `retention > 标的 inception` 时须按 §5.3 让 retention **同时封顶期望集**，否则永久缺口告警。

### C. → 不设全局值，按族/kind 定义

- **做成全局单选 ＝ 又开一个「没有家」的全局常量**（§一.2 的同构缺陷）。
- **per-date：每轮**——「本轮声称完成的区间必须真实完整」是**同步器的固有职责**（属主路径收尾，非独立节拍）；判据 `trade_cal` 已存在。
- **per-symbol：低峰 / 周级**——依赖 inception（第 2 步）、属**旁路深度修复**；**输出必须闭环**（落 `sync_gap` ＋ 告警 ＋ 限频重拉，§7.2），否则「周级报告」＝静默。
- **快照族：不对账**——无「补历史」概念。

### D. → 先 per-date

- **依赖闭合度**：per-date 判据 `trade_cal` 已存在、**不依赖 A / 第 1 步**；per-symbol 依赖 A（crypto 行）与第 1 步（跨源、源下限）⇒ per-date 是**可独立成立的最小完备子集**。
- **职责层级**：per-date 是**同步语义自洽**（主路径）；per-symbol 是**深度修复**（旁路）。主路径职责先于旁路工具。
- **收敛方向**：per-date 对账**替代正在起作用的 `_TIER1_OVERLAP_DAYS`** ⇒ 先替换在跑的启发式，使「启发式只减不增」，与 §六 收编方向一致。
- **非二选一**：两者治**不同类别**的洞（§七），是排序不是取舍。

### E. → 立（列级 + 带理由豁免 + **CI 强制**）

- **它是铁律一的可执行形式**（§三）：没有它，「声明必须被执行面消费」只是口号——实证即 §2.2 两列。同族先例：批 107 的对账门（注册表 ↔ 真源）。
- **列级粒度**：`sync_config` 的策略 / 声明列必须在 `src/**`（非测试）有读取点；运行态 / 审计列豁免。
- **豁免须显式 + 带理由**，否则退化成垃圾场（门就没有牙）。
- **须 CI 强制**（非仅「启红提示」）。
- **`start_floor` / `supports_backfill` 自身列入首批断言对象**：升格后 engine 必须真读；`supports_backfill` 派生后须有归宿（否则成新孤儿）；`start_floor` 历史 NULL 行须明确豁免 + 理由。

### F. → 显式「未知」（本轮新增）

- Binance `onboardDate` 被墙 ⇒ 若另行拿不到真值，**`list_date` 写 NULL ＋ 显式「inception 未知」**，**不得**用日包/月包可达性近似冒充真值（§九.3）。
- **未知时的窗口行为**：对账按「**不确定**」处理（不报「无缺」），与 §5.4 同机制；`retention` / `source_earliest` 仍可作下界（它们本来就与 inception 独立）。
- **理由（架构）**：语义污染一旦埋进主档，下游无法区分「真上币日」与「源可达近似」——**单一真源字段的可信度是资产**，不可用近似折价。

### G. → 择一并写死（本轮新增）

- `_get_list_date`（engine.py:1862）读 `asset_static_info` / `etf_basic_info` / `cb_basic_info`，而本稿要让 `inception` 来自 SM ⇒ **inception 双源**。二选一：**① SM 成为这三表的真上游**（列表同步同时写 SM，`_get_list_date` 改读 SM）／ **② 保留原表为真源、SM 的 `list_date` 视为其投影**。
- **判据（单一真源）**：无论选哪条，**同一事实只允许一个可写点**；实施序第 2 步必须在两者中**择一并写死在文档**，否则「修了 SM 却没改 `_get_list_date`」＝新双源。

## 十一、结论

**一句话**：同步窗口应从「游标单源 + 四条启发式兜底」改为 **`[max(inception, retention, source_earliest), source_latest − publish_lag]` 的四边界交集**；参数按「换任务才变 → DB、同类共享 → 代码 kind 默认、连源才需 → 接入层」三层归位；四条启发式分别**删 / 删 / 并入源边界 / 换真地板**；对账**输出必须闭环**（per-date 内联重拉、per-symbol 落 `sync_gap` ＋告警）。**冻结的删除是收尾步**，门控是**可观测判据**（连续 N 轮同缺口零误报），且**必须等 crypto 生命周期落地**——否则重开 OKX 那类洞。
