## 一、问题陈述

同步窗口的起点今天由**游标**（`last_sync_date`）单方面决定，而配置层里那个看起来像「数据起点」的字段（`start_floor`）**执行时不读**。由此三类问题：

1. **声明 ≠ 执行**：`start_floor` / `supports_backfill` 住在定义层，却只被前端读去渲染（回补日期下限、回补表单显隐）；`engine._get_config` 的 SELECT 里根本没有这两列。
2. **窗口策略没有家**：真正决定回看多远的是 engine 模块级常量（`first_run_days` / `default_days` / `20050408` / `_PARTIAL_FREEZE_MAX_DAYS` / `_TIER1_OVERLAP_DAYS` / `_CRYPTO_TAIL_GRACE`），不随任务、不随 kind、不可配；**且窗口起点有四处各自为政的站点**（§2.1）。
3. **自愈靠启发式堆叠**：四条互不知道的常量在各自领域打补丁（§2.3），语义重叠、边界不清，且都治不了「真实起点之外的老洞」——OKX 7/485 的 19 天洞即此症。

本稿要定的是：**同步窗口由哪些边界决定、这些参数各归哪一层、现有四条启发式如何收编。**

## 三、判据：一个参数该放哪一层

> **换一个任务就不同 ⇒ 定义层（DB）；同类任务共享 ⇒ 代码按 kind 给默认；连上某源才需要 ⇒ 接入层。**

两条铁律：

- **声明面必须被执行面消费**——只声明不读的键是装饰（§2.2 两列即反例）。**可执行形式＝E 闸门（CI 强制）**（§十 E）。
- **事实进代码，值进 DB**——能力/形状是**代码事实**（进 DB 即双真源、必漂移，如批 107 抓到的 `etf_list.pg_table` 漂移）；连接值/凭证是**运维事实**（进 DB）。
- **（本轮新增）下界须实测，未实证留 NULL**——源可达边界是**测量结果**，不是可推断/可臆造的声明；先例＝迁移 `0137`（§2.5）。

## 四、参数的三层归属（目标态）

### 定义层 · DB（系统数据）

| 承载 | 表 |
|---|---|
| 任务身份 / 调度 / 开关 / 交易日过滤 / provider / 游标 | `sync_config` |
| 结构 + **列形状**（kind/sub_kind/pg_table/列清单/rebuild） | `sync_kind_config` |
| **保留策略**（retention，现装在三义列 `start_floor` 里，须正名） | `sync_config`（升格，见下） |
| **对账缺口视图**（per-symbol 缺口行：同步目标 / 缺口区间 / 状态 / 重拉次数） | **新表 `sync_gap`**（§7.2，**派生视图、非权威**） |

使用方：scheduler（派发）+ engine（分派 / 写目标 / 窗口计算）+ 对账（§7.2）。
**升格**：窗口策略下沉——`first_run_days` / `20050408` 收成**按 kind 的默认表（代码）+ 任务行覆写（DB）**。默认跟 kind 走，因为「表有没有时间轴」由 kind 决定；个别源特殊才落任务行。

### 能力层 · 纯代码（绝不进 DB）

`adapter.capabilities`（sync_id 级）/ `capability_decls`（kind 级）/ `SYNC_ID_CAP_MAP`（归一）/ `_SUPPLY_PULL`（分派）。
使用方：写侧 `_validate_provider`（白名单）+ 前端 provider 下拉 + 域路由。
**理由**：能力是代码事实；进 DB ⇒ 双真源漂移。

### 接入层 · schema 代码 + 值 DB

`interfaces/*.py` 的 FIELD_SCHEMA / PARAMS_SCHEMA（**schema 是代码**）；`data_source` / `trading_account` 表的 credentials_encrypted / params（**值是运维事实**）；`proxy_binding`（出口）；**`adapter.available_range(kind)`（源可达边界，代码）**。
使用方：DataSource（get_client / 限速 / 熔断 / 用量）+ 组装时注入出口 + **窗口计算（§5.1 的源上下界）**。

## 五、窗口边界模型（目标态）

### 5.1 三个地板 + 一个源上限

```
窗口 = [ max(inception, retention, source_earliest) , source_latest − publish_lag ]
```

| 边界 | 含义 | 性质 | 落点 |
|---|---|---|---|
| **inception（产生时间）** | 数据**可能**存在的**最早**时点 | **事实**，每标的不同 | 生命周期主档（`security_master.list_date`，§八.2） |
| **retention（保留下限）** | 我们**关心**的**最早**时点 | **策略**，每任务 | `sync_config` 的保留策略列（`start_floor` 正名后，§十 H） |
| **source_earliest（源可达下界）** | 源**整体**能给到的**最早**时点（kind 级） | **源属性·须实测** | `adapter.available_range(kind)`（新建硬契约） |
| **source_latest − publish_lag** | 源**能给**的最晚时点（扣发布滞后） | **源属性** | 同上（双返回） |

**为什么要有源下界（双盲审① P0 病灶）**：只有上界时，适配器会**在内部私自收窄起点**（`binance_adapter._pull` :242-263 的省流阀即此），于是「模型窗口 ≠ 真实窗口」，**对账层无法信任上游**：模型认为该拉 `2019-09-08` 起，适配器实际拿不到更早的包，最终「拉回了空」与「源本来就没有」**同形**。

**为什么要有两个地板（inception / retention）**：全史都留时两者重合（所以看起来只需一个）；但分钟族不可能对「从 1990 起的每一分钟」都负有完整性义务——**这是职责范围的界定**。**正确做法是都显式化取 max**——`first_run_days=30` 正是「用一个假值同时冒充两者」的坏样本。

**🔴 粒度陷阱与绑定点（本轮修正）**：`available_range` 是 **kind 级**，而源可达性**逐标的不同**（2025 年上市者，包自 2025 起）。⇒ **不要断言「per-symbol 绑定只由 inception 承担」**——**绑定点可能是其中更晚的那一个**：
- **BTCUSDT（binance）**：上币 `2019-09-08`，源可达 `2019-12-31` ⇒ **由 `source_earliest` 绑定**，窗口下界 `2019-12-31`。
- **2025 年上市的永续**：inception `2025-xx`，源可达（kind 级）`2019-12-31` ⇒ **由 `inception` 绑定**。

**由源界绑定时的那一段 `[inception, source_earliest)` 是「存在但批量源不可达」**，必须按 §5.3 标 `unreachable`，**不得**当作我们的缺口。

**Binance 源级 earliest 的正确取值**：`2019-12-31`（主会话实测：日包 `2019-12-30`→404 / `2019-12-31`→200；月包自 `2020-01`）；**既非** `2020-01`（那是月包 floor，仅批量路径的优化边界），**更非** `2019-09-08`（那是**上币日**，批量源拿不到）。原 v2 稿写的 `2019-09-08` 会导致 §5.3 的 unreachable 条件对早上市标的**永不触发 ⇒ 永久 phantom gap**（双盲审② A2 P1-a）。

### 5.2 「缺」的定义随类别变

| 类别 | 「缺」＝ | 可否自愈 |
|---|---|---|
| 时序（incremental） | 预期日无数据（astock 用 `trade_cal`；crypto 用 **UTC 连续轴**——与 `bar_1D` 的 `ts`＝`00:00 UTC` 源原生日界一致） | **可**（差集重拉，幂等） |
| 快照（full_rebuild） | 与上游当前快照不一致 | 只能重跑，**无「补历史」概念** |
| `trade_cal`（生成族） | 覆盖 `[下限, 今天]` 的年份区间 | 按年增量生成 |

### 5.3 期望集下界 ≡ 窗口下界，且**封顶不得静默**

对上表「时序」类，**期望集下界必须等于窗口下界 `max(inception, retention, source_earliest)`**。三条**必守**规则：

1. **不许各算一套**：不能「拉取从 `retention` 起、期望却含更早」——那要么**永久缺口告警**、要么「对账认亏」⇒ **静默丢史且永不收敛**。
2. **🔴 retention 封顶必须可见（本轮新增，双盲审② A2/B2 共同指认）**：`retention > inception` 时，`[inception, retention)` 段是**我们主动不保留**，**不是「不存在」**。⇒ 该段须**显式登记为 `policy_discard`**（可见的排除声明，含理由），**禁止**由「下界取 max」隐式吞掉。**理由（架构）**：若静默，则「误种一个偏晚的 retention」＝**无声丢史**，且与「源头就没有」同形——**这是一条新静默阀**。先例风险：`okx_perp_daily` 的 `2020-01-01` 是**源下限**（0137 实测），若被当作 retention 使用，语义就错了（本例所幸源端本来 2019 全空、无实害，但**机制上未设防**）。
3. **源不可达段须登记**：`source_earliest > inception` 时，`[inception, source_earliest)` 标 `unreachable`（理由＝源可达性，**须实测**，见 §5.1 / 待裁 F）。**不得**静默豁免——否则「源头就缺」与「我们拉漏了」再次同形。

### 5.4 新鲜度前置：stale / 未知 ⇒ 「不确定」，且**抑制缺口主张**

`inception` 是**派生数据**（来自快照族）。两种情形必须转成对账的**输出态**，且**不只是「不报无缺」，而是不得主张任何缺口**：

| 情形 | 触发 | 对账输出态 |
|---|---|---|
| 列表快照过期 | 快照 age 超阈（新上市标的未入 ⇒ 期望集不完整） | `stale_source`（「不确定」） |
| `inception` 未知 | 真上币日不可得（待裁 F，如 Binance fapi 被墙） | `uncertain`（「不确定」） |

⇒ 两种态下 **per-symbol 对账不得输出「缺口」也不得输出「无缺」**（期望集不可信 ⇒ 一切主张无效），只登记该族为「不确定」。见 §7.2。

## 六、四条启发式的收编

| 启发式 | 类型 | 归宿 |
|---|---|---|
| `_PARTIAL_FREEZE_MAX_DAYS=10` | 被动冻结 | **删**——标的级对账既替代其功能，又消除粒度错配（全族游标退回 → 单标的差集） |
| `_TIER1_OVERLAP_DAYS=3` | 主动重叠 | **删**——日期级对账覆盖全区间，不再只回看 3 天 |
| `_CRYPTO_TAIL_GRACE=2` ＋ `_TIER1_LAG_TRADING_DAYS` | 发布滞后 | **并入 §5.1 的 publish_lag**（源属性，非 kind 属性） |
| `first_run_days` / `default_days=30` / `20050408` | 假首跑地板 | **换** `max(inception, retention, source_earliest)` |

**为什么「统一」不是「删一件事」**：四条分属三种类型、散在不同族。对 astock per-date 族是**加**日期级对账（它们连冻结都没有，比 crypto 更差，只有 3 天主动重叠兜迟发布）；只有 crypto 那 2 个族才是**删**。

## 七、分族治法与对账闭环

### 7.1 分族治法

| 族 | 粒度 | 期望集 | 治法 |
|---|---|---|---|
| per-date 整市场（`astock_daily` / `etf_daily` / `cb_daily`） | 日期 | `trade_cal` 交易日集合 | **日期级差集**：`SELECT DISTINCT trade_date` vs 预期，差集重拉。**判据已存在、无前置依赖** ⇒ 是同步主路径的收尾步骤（非独立维护任务） |
| **TIER1 族**（`margin_detail_sync` 等，`_make_tier1_handler`） | 日期 | 交易日集合（上界按 `publish_lag` 回推） | 同上（日期级差集）；**当前 handler 自算窗口，收编时须一并纳入**（§2.1 第四站点） |
| per-symbol（`bar_minute` / crypto bar / `pool_data` 财报股东） | 标的×日 | 每标的 `[max(inception, retention, source_earliest), end−lag]` | **标的级差集**：O(标的数)，低频或按需（现成 `_find_gaps`） |
| 快照（`static_list` / `industry_class` / `holder_structure`） | — | 上游当前全集 | 清表重灌；**无 reconciliation** |
| `trade_cal` | — | 年份区间 | 按年增量生成 |

**关键区分**：`astock_daily` 走 `pro.daily(trade_date=X)` **按日整市场**拉，上游只返当日存活标的 ⇒ **lifecycle 不产生缺口**；其洞是**整日失败**（连接抖动丢一天）⇒ 必须靠日期级差集。**lifecycle 只对 per-symbol 族是正解。**

### 7.2 对账输出闭环（缺口去哪、谁重拉、谁告警）

对账若只产报告、无消费者＝**等于没做**（双盲审① P1）。两类输出**分别定义消费者**：

| 粒度 | 输出 | 消费者 |
|---|---|---|
| **per-date**（主路径） | 本轮声称完成区间内的缺日 | **同步任务内联重拉**（补拉差集，幂等），**当轮收尾**；重拉仍缺 ⇒ 落 `sync_gap` ＋ 告警 |
| **per-symbol**（旁路） | 标的三元组 `(sync_id, symbol, 缺口区间)` | **落 `sync_gap` 表** ＋ **告警** ＋ **限频重拉**（按缺口区间，幂等；重拉成功则闭合该行） |
| 快照族 | — | 不对账（无「补历史」概念） |

**输出态四态（每行必须终结于其一）**：

| 态 | 含义 |
|---|---|
| `closed` | 重拉补齐 |
| `unreachable` | 源不可达（`[inception, source_earliest)`，§5.3-3） |
| `policy_discard` | 主动不保留（`[inception, retention)`，§5.3-2，**须带理由**） |
| `uncertain` | 期望集不可信（快照 stale / inception 未知，§5.4）——**此态下抑制一切缺口主张** |

**`sync_gap` **不是第二真源**（本轮明写，双盲审② B2 R3）**：它是**派生视图**——真源仍是「生命周期主档 ＋ 窗口边界规则」与「数据表本身」。⇒ **`sync_gap` 可随时重建、可清空重算**；**禁止**任何窗口/期望集计算读取 `sync_gap`（否则派生值回流成真源）。**「长期停留在 open 的行数」**即「存量缺口」指标。

## 八、实施序（五步，含删除门）

1. **前置：源可达区间（硬契约）**——给 adapter 加 `available_range(kind) -> (earliest, latest)`，把散落的「源边界」收进来；`publish_lag` 一并由这里给出。
   - **正确取值（须实测，禁臆造）**：`_TUSHARE_MIN_DATE=2010` 硬底（engine.py:1820）／聚宽 `account_window()`／**binance `2019-12-31`**（实测）／okx `2020-01-01`（0137 实测）／分页触顶。
   - **硬契约**：所有**可拉** adapter **必须实现**，返回 `None` ⇒ **fail-loud**（CI 断言 pull-capable adapter 全覆盖）。否则新源漏实现即默认「today ⇒ 永不回补历史」，source_upper 变**软真源**。
   - **必须含 joinquant `account_window()`**（第三个起点站点）——否则换源 bug 残留在该类源（§九.5）。
2. **crypto perp 生命周期**——**扩 `security_master`（`market='crypto'`）并给 crypto bar handler 接 SM 填充链**，**inception 取真上币日**：OKX 取 `listTime`（已在响应内、现被丢弃；真值形态见 0137 记录）；**Binance 取 `exchangeInfo.onboardDate`；fapi 被墙时须另找可信来源，或显式写「inception 未知」（待裁 F）——严禁用 `first_available_month` / 日包可达性冒充**（§2.6、§九.3）。
   - **连带（代码事实修正）**：`_pull` docstring（:246-249）与迁移 `0132:16` 的「日包更早 / 会静默丢掉 2019-09~12」**经实测为假**，须改写；`_pull` 的 `_FLOOR_DATE` 分支（:255-263）基于该假前提，会对 `start_floor=2019-09-08` 的长区间**静默发起约百次必 404 的日包请求**，须一并修（否则「省流阀」实为「费流阀」＋误导后人）。
   - **连带**：`upsert_rows` 补 `session_id` 通道（＋显式传 `trade_phase='T+0'` 与真实 `multiplier` / `tick_size`）；**`_get_list_date` 现读 `asset_static_info` / `etf_basic_info` / `cb_basic_info`（engine.py:1862）、非 SM** ⇒ 须按待裁 G 解决双源。
   - **这道门决定第 5 步能不能做。**
   - *排除「新建 perp 表」（造第二真源）与「从数据表 `min(ts)` 推导」——后者对「整窗 0 行」的标的天生失明（推导源为空 ⇒ 永不报缺），正是 OKX 7/485 的形状。*
3. **三方地板取 max**——`inception`（生命周期主档，**带新鲜度前置**，§5.4）＋ `retention`（升格，engine 真读）＋ `source_earliest`（第 1 步），替换 `first_run_days` / `default_days` / `20050408`；同时落 §5.3 的 `policy_discard` / `unreachable` 登记。
4. **分族对账 + 输出闭环**——per-date 族走日期级差集（内联重拉）；per-symbol 族走标的级差集（低频 / 按需），输出落 `sync_gap` ＋ 告警（§7.2）。
5. **删 `freeze_on_partial`**——**门控改为可观测判据**：连续 **N 轮** per-symbol 对账命中**同一缺口**且**零误报**；且 per-symbol 对账**已调度、自动重拉在跑**。**禁用**「对账在 prod 证明覆盖同一缺口」这类**无判据**表述。

**为什么删除是最后一步、且门控**：冻结今天**独家**护住「某标的整窗 0 行」（OKX 7/485）——该缺口**只有 inception 能检出**（无行 ⇒ 期望集为空 ⇒ 对账不可见）。在 crypto 有生命周期前删冻结 ＝ 重开此洞。过渡期并存只是**有界冗余**（全族重拉 11 天，幂等），**无正确性损失**，故安全。**但 §2.6 末行提示**：crypto 族在 dev **从未闭合过游标、零成功记录、`bar_1d` 仅 31 行** ⇒ 第 3 步「取 max」在 crypto 上等于**从零开始**，**验收必须覆盖「首跑即全史」这条路径**。

## 九、边界与风险

1. **🔴 依赖倒置**：inception 是**派生数据**（来自快照族同步项）。用时序族的完整性依赖快照族新鲜度 ⇒ **列表快照一过期，时序族完整性就系统性静默漏报**。**闭合方式**＝§5.4（`stale_source` / `uncertain`，且抑制缺口主张）。同族前科：清单驱动检测点不看 `enabled` ⇒ 停用数据源永 stale（P1-A）。
2. **🔴 源下界缺失**：模型若只有上界，适配器内部私自收窄起点 ⇒ 「模型窗口 ≠ 真实窗口」⇒ 对账不可信。**闭合方式**＝§5.1 第四边界 ＋ `available_range` 双返回 ＋ 第 1 步硬契约。
3. **🔴 inception 语义错配**：**源可得性 ≠ 生命起点**，有**两手实证**（OKX 差 ≈2 月、Binance 差 ≈4 月，§2.6）。用「源最早可得」当「上币日」＝把可达性坐进语义列，错误性质从「拉不到」（看得见）恶化为「**不认为缺失**」（静默）。**闭合方式**＝§八.2 禁则；Binance 真上币日不可得时按待裁 F **显式「未知」**，对账按 `uncertain` 处理。
4. **🔴 保留策略静默封顶**：`retention` 若可静默压掉早于它的真实历史，则「误种一个偏晚的 retention」＝无声丢史（§5.3-2）。**闭合方式**＝`policy_discard` 显式登记 + 理由。
5. **只对 per-symbol 族有效**（§七）——不是通解。
6. **`_get_list_date` 是 tushare 专属**（§2.5）：硬编码 `_TUSHARE_MIN_DATE`（engine.py:1820）当回退 ＋ 下限 ⇒ 换源即错。升格前必须先落第 1 步。
7. **`index_daily` 无列表来源**（仅硬编码 `20050408`）⇒ 无 `inception`。该族只能靠 `retention`（＋源下界），须**显式声明**「此族无生命周期期望集」，不得默认按有 inception 处理。
8. **crypto 生命周期空白**（§2.6）——第 2 步不做，整个模型对 crypto 空转。
9. **分钟族 retention**：全区间逐日对账对高频族不适用（与 G-S1 系统资源包络冲突）⇒ 只能标的级、低频 / 按需。
10. **既有代码事实错误未修**（§2.6 / §八.2）：`_pull` docstring ＋ `0132` 注释 ＋ `_FLOOR_DATE` 分支基于「日包可达 2019-09」的假前提；不修则**后人按错前提设计**＋每次长区间多烧约百次 404 请求。
11. **不做**：不重写游标契约（刚稳）；不把 full/incremental 压成一个 bool；不追求「所有设置都进 DB」。

- **必须连带**：crypto handler 接 SM 填充链；`upsert_rows` 补 `session_id` 通道；crypto 行显式传 `trade_phase='T+0'` 与真实 `multiplier` / `tick_size`；按待裁 **G** 解决 `_get_list_date` 与 SM 的双源。

### B. → 任务列为准 + kind 默认作默认值来源

- **判据**「换任务才变 ⇒ DB」：retention 换任务就不同 ⇒ 必须**任务级可表达**；仅 kind 默认**表达不了**个别任务的差异。
- **不构成双真源**：kind 默认在**读入时合并**（列 NULL ⇒ 取 kind 默认），运行时只有一个有效值。前提：明写「**任务行为准**」。
- **须正名（一列三义，逐行判）**：见 §十 H。
- **封顶须可见**：`retention > inception` 时按 §5.3-2 登记 `policy_discard`，**禁**静默。

### C. → 不设全局值，按族/kind 定义

- **做成全局单选 ＝ 又开一个「没有家」的全局常量**（§一.2 的同构缺陷）。
- **per-date：每轮**——「本轮声称完成的区间必须真实完整」是**同步器的固有职责**（属主路径收尾）；判据 `trade_cal` 已存在。
- **per-symbol：低峰 / 周级**——依赖 inception（第 2 步）、属**旁路深度修复**；**输出必须闭环**（落 `sync_gap` ＋ 告警 ＋ 限频重拉），否则「周级报告」＝静默。
- **快照族：不对账**——无「补历史」概念。

### D. → 先 per-date

- **依赖闭合度**：per-date 判据 `trade_cal` 已存在、**不依赖 A / 第 1 步**；per-symbol 依赖 A 与第 1 步 ⇒ per-date 是**可独立成立的最小完备子集**。
- **职责层级**：per-date 是**同步语义自洽**（主路径）；per-symbol 是**深度修复**（旁路）。
- **收敛方向**：per-date 对账**替代正在起作用的 `_TIER1_OVERLAP_DAYS`** ⇒ 使「启发式只减不增」，与 §六 收编方向一致。
- **非二选一**：两者治**不同类别**的洞（§七），是排序不是取舍。

### E. → 立（列级 + 带理由豁免 + **CI 强制**）

- **它是铁律一的可执行形式**（§三）：没有它，「声明必须被执行面消费」只是口号——实证即 §2.2 两列。同族先例：批 107 的对账门（注册表 ↔ 真源）。
- **列级粒度**：`sync_config` 的策略 / 声明列必须在 `src/**`（非测试）有读取点；运行态 / 审计列豁免。
- **豁免须显式 + 带理由**；**须 CI 强制**（非仅「启红提示」）。
- **`start_floor` / `supports_backfill` 自身列入首批断言对象**：`start_floor` 拆正名后 engine 必须真读 retention；`supports_backfill` 派生后须有归宿（否则成新孤儿）；历史 NULL 行须明确豁免 + 理由。

### F. → 显式「未知」（**先例已存在**）

- Binance `onboardDate` 被墙 ⇒ 若拿不到真值，**`list_date` 写 NULL ＋ 显式「inception 未知」**，**不得**用可达性近似冒充（§九.3）。
- **先例（不是新立规矩）**：迁移 `0136` **故意留 NULL**、`0137` 序言写「只填**已实证**下界、其余 NULL，**不臆造**」——本待裁点只是把这套既有纪律**从源下限推广到 inception**。
- **未知时的窗口行为**：对账按 `uncertain`（§5.4 / §7.2），**抑制一切缺口主张**；`retention` / `source_earliest` 仍可作下界（它们与 inception 独立）。
- **理由（架构）**：语义污染一旦埋进主档，下游无法区分「真上币日」与「源可达近似」——**单一真源字段的可信度是资产**。

### G. → 择一并写死

- `_get_list_date`（engine.py:1862）读 `asset_static_info` / `etf_basic_info` / `cb_basic_info`，而本稿要让 `inception` 来自 SM ⇒ **inception 双源**。二选一：**① SM 成为这三表的真上游**（列表同步同时写 SM，`_get_list_date` 改读 SM）／ **② 保留原表为真源、SM 的 `list_date` 视为其投影**。
- **判据（单一真源）**：无论选哪条，**同一事实只允许一个可写点**；实施序第 2 步必须**择一并写死在文档**。

### H. → 拆（一列三义必致误用）

- **证据**：`binance_perp_daily=2019-09-08`（**inception**）／`okx_perp_daily=2020-01-01`（**源下限**）／`binance_perp_hourly=2026-09-29`、`15min`/`1min=2026-10-05`（**retention**）。
- **拆法**：retention 留 `sync_config`（引擎真读）；源可达边界移入 `available_range`（接入层）；inception 归 SM（§八.2）。**列名/列数须显式**，不留「一列装载三种语义」。
- **理由（架构）**：一列三义下，**任何读取方都必须先猜语义**——「读到的值是什么」不可判定 ⇒ 契约不闭合。且历史值**无法用规则自动判语义**（同 provider 内部就有三种），只能逐行判。
- **不做**：不设「语义标列」这种软约定（软约定＝没约定，判据不可 CI 化）。

---

## 十一、结论

**一句话**：同步窗口应从「游标单源 + 四条启发式兜底」改为 **`[max(inception, retention, source_earliest), source_latest − publish_lag]` 的四边界交集**；参数按「换任务才变 → DB、同类共享 → 代码 kind 默认、连源才需 → 接入层」三层归位；四条启发式分别**删 / 删 / 并入源边界 / 换真地板**；对账**输出必须闭环**（per-date 内联重拉、per-symbol 落 `sync_gap` ＋告警，四态终结）；**源下界与 inception 都必须实测/取真值，禁以可达性冒充**；`start_floor` 一列三义须拆。**冻结的删除是收尾步**，门控是**可观测判据**（连续 N 轮同缺口零误报），且**必须等 crypto 生命周期落地**——否则重开 OKX 那类洞。
