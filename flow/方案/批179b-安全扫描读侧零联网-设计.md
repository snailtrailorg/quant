# 批179b · 安全扫描依赖版本：读侧零联网 + 三态真实映射

> 终态设计。**批179（`6adf6a3`）方案被推翻**：它改变了原来稳定的架构（把上游刷新从
> `dep_audit` 异步慢路径搬进用户手动 `security_scan` 的读路径），并引入 timeout（逐包
> `urlopen(10s)` 串行等待）→ 扫描卡死。用户裁定：不要这种方案。
> 本批只做「恢复 + 修正」——恢复批155 原架构，不新增网络路径、不引入超时、不动 `dep_audit`。
> 设计真源：`flow/方案/批155-依赖健康检测重构-设计.md` §3 判定引擎 / §4.4 rescan 契约；
> 批155 的设计本身未变，批179 是实现偏离。

## 1. 职责分离（唯一硬约束）

- **上游版本刷新只在 `dep_audit` 慢路径**：celery 异步、心跳续跑（`sec:dep_audit:beat`）、
  逐包 `pypi_versions_cached`（Valkey `sec:pypi:<name>` TTL 7d 恒读缓存）、按批 25 行落
  `security_component`、单包失败不炸轮。
- **用户手动 `security_scan` 只读**：读 `sec:dep_audit` 契约 + `security_component` 台账，
  零网络请求。缓存 stale 时由 `security_scan_trigger` **异步**派 `dep_audit.delay()`，本轮
  扫描照常读旧数据，不做同步等待、不就地补查。
- 系统包侧本就如此：`dnf repoquery --upgrades` 一次读本地全量 repodata、`rpm -qa` 读本地
  RPM DB，扫描侧从不逐包联网。PyPI 侧用 PEP 691 simple（per-project 端点，无「传一批包名
  返回各自所有版本」的批量接口），这只决定「刷新要逐包」，**不决定刷新可以放进请求关键路径**。

## 2. 读侧三态（真相映射）

`has_update_of(judge_class)` 服务端单源；`GET /api/security/snapshot` 的
`components_ledger`、`/dep-health` 分组、汇总共用同一判定：

| latest 情况 | judge_class | has_update | 页面 |
|---|---|---|---|
| `latest > cur` | actionable / in_constraint | `yes` | 有更新 |
| `latest == cur` | current（或 pinned / drift / unreachable 的明确判定） | `no` | 无更新 |
| `latest` 缺失 / 不可解析 | unknown | `unknown` | 未知 |

- **禁止把 `latest is None` 报成「无更新」**——没查到 ≠ 已确认最新。前端 `hasUpdateText`
  与三态筛选（是/否/未知）早已就绪，后端不得再吞掉 unknown。
- `unreachable`（本地 fork / 上游要求更高 Python）是**明确判定**，仍为 `no`。

## 3. 组件列表真源

`run_security_scan` 入台账的组件集 = **pip 安装集（`pip freeze` 全量）∪ SBOM ledger**；
`requirements.txt` 只用于 `judge` 判 pinned / `in_constraint_max`，**不决定谁上榜、也不决定
查不查上游**。SBOM 只做漏洞关联。

## 4. 守门（`server/tests/test_batch179_dep_latest.py`）

- 三态映射逐分支断言（latest 缺 / 高于 / 等于当前）；
- 静态守门：`security_collector.py` 不得出现 `pypi_versions_cached` / `_fill_missing_latest` /
  `dep_gap_filled` / `force=force`；`pypi_versions_cached` 签名不得有 `force`；
- 运行时守门：monkeypatch `urllib.request.urlopen` 抛错后 `_collect_components()` 仍返回 ok，
  且组件真源 = pip 安装集、`latest=None` 的行判 `unknown`。

## 5. 保持 `dep_audit` 原样（不改并发、不加超时）

批179 的教训是「动稳定架构」与「引入 timeout」两条都不能碰。`dep_audit` 的串行逐包、
心跳续跑、`done_names` 跳网、恒读 7d 缓存是既有稳定形态，本批**零改动**：只撤销读侧
新增的联网层。PyPI 逐包是接口选型的结果，靠缓存与续跑消化，不需要靠并发或超时参数
去「优化」；任何性能问题另立项，**不在扫描读侧解决**。
