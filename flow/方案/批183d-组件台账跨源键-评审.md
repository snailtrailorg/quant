# 批183d 组件台账「跨源同名」修复 · 评审

> 评审对象：`judged_map_of()`（键带 source）+ `_upsert_components` 查表改 `(source, name)`。
> 评审维度：是否只治标；数据模型与全链是否自洽；后续扩展（新生态/新采集通道）是否要改多处。

## 一、现象与根因（已实证）

页面「tzdata 有新版本，dnf 却无更新」。根因链：
1. `dep_health.rows` = **pip 行**（来自 `security_component source='pip'`）+ **OS 行**（来自 dnf 契约），
   两者**同名**（Python `tzdata` 2026.4 / rpm `tzdata` 2026a）拼接成一个 list。
2. 判定表原按 `_norm_key(name)` 单键构建 → 后追加的 OS 行**覆盖** pip 行。
3. 结果：pip 行 `managed_by` 被写成 `repo`（dnf 无更新），`latest_version` 仍是 PyPI 的 2026.6
   （audit 写的）⇒ 自相矛盾的一行。

同根因第二处：`_latm`（优先级刷新清单）也是 name→latest，OS 行 `latest=None` 会盖掉 pip 的。

## 二、当前修复评价

**方向正确，不是给 tzdata 打特例**：
- 没有硬编码任何包名；改的是**键的语义**（同一名字不同生态 = 不同实体），属数据模型层的正解投影。
- 收敛成单一工厂 `judged_map_of()`：原来 `_upsert_components` 的 `_gm` 与 `run_security_scan` 的
  `judged_map` 各写一套同样的字典推导，是漂移源（本次 bug 就只修了一处才发现另一处）；现在一个入口。
- 守门改为**行为断言**（pip 行不被 OS 行覆盖、双键各自命中）+ 「禁止再出现按名建表」，不是钉字面量。

**但只解决了「不互相覆盖」，没解决「同一实体两行」**——这是设计层欠账，见下。

## 三、结构性欠账（须立项，不宜塞进 hotfix）

### P1-1 `source` 字段承载两种语义
| 写入方 | source | 语义 |
|---|---|---|
| grype/syft 台账 | `pip`/`rpm`/`binary` | **生态**（包从哪来） |
| dep_audit OS 行 | `system` | **判定来源**（dnf） |
| dep_audit pip 行 | `pip` | 生态 |

后果：同一个 rpm 包在表里**两行**——`system`（版本+判定）与 `rpm`（SBOM 名字/版本）。
本次 `judged_map_of` 里 `group=='os' → ("system",k) + ("rpm",k)` 的**双写就是这条债务的显式桥接代码**。
只要 source 还混两个语义，桥接就删不掉。

**正解**：`source` 只表示生态（pip/rpm/binary）；判定来源已有列承载（`latest_source`/`judge_why`）。
OS 判定行与 SBOM rpm 行合一到 `source='rpm'`，读侧 `(source,name)` 天然唯一。
代价：迁移（system→rpm 合并，同名取 version 更完整者）+ GC 规则统一（现 `rpm`/`binary` **没有 GC**，
只剩 `system`/`pip` 有 3 天孤儿清理 ⇒ rpm 行会永久累积）+ 读侧口径复核。

### P1-2 展示未显式区分生态
`dep_health.rows` 直接拼接两源，前端按名渲染会出现两条 `tzdata`（PyPI 2026.4→2026.6 / rpm 2026a）。
不修的话，用户仍会问「到底哪个能升」。修法：行内携带 `source`（生态）并在 UI 以「PyPI / rpm」标签区分，
与 P1-1 同批做（属展示契约变更，前后端一起）。

### P2-1 `managed_by` 是派生常量，不该进判定契约
pip 行恒 `pypi`、OS 行恒 `repo`，却在判定表里来回传递，还经 `COALESCE` 回写表。
182d 已把「scan 从表读旧 judge 再回写」判定为写侧回环；`managed_by` 是同一形态的残留（当前值恒定所以无害）。
正解：由生态派生，不进 `judged`。

### P2-2 `group`(os/runtime/dev) 与 `source`(pip/rpm/binary/system) 两套词表并行
靠 `if group=="os"` 硬编码推断；加生态（cargo/npm）时两处都要改，且 `else → pip` 会**静默错**。
正解：dep_health 行直接带 `source`，删掉推断。

## 四、归口

| 项 | 归口 | 理由 |
|---|---|---|
| 键含 source + 单一工厂 + 行为守门 | **本批上产** | 纯 bug 修复，无表变更；不修则数据继续错 |
| `_latm` 换 `judged_map_of` | **本批**（1 行） | 同根因、零风险 |
| source 语义归一（system→rpm 合并）+ 统一 GC + 行带 ecosystem + UI 区分 + managed_by 派生 | **立项**（设计变更） | 涉表语义重定义、迁移、GC 规则、读侧与前端口径 |
| 任何按包名/按生态的白名单特例 | **不做** | 当前没有；加特例就是把结构债转成配置债 |

## 五、解法（已出方案稿）

三笔欠账的具体解法、迁移 0189、代码改动清单、实施顺序与验收见
`flow/方案/批184-组件台账归一-方案.md`。核心判断：`source` 在 A07 §四 本就定义为**生态**，
`system` 是批156 为「grype 未装机兜底」新增的第四个源、又被 schema2 扩成全量 rpm 副本——
本方案是**回归既定模型**，不是新造抽象。

## 六、结论

修复可作为 hotfix 上产：它把「按名覆盖」这类**同类 bug 的整类**（不止 tzdata）一次关掉，且用工厂收敛了
两处重复实现。但 `source` 一词两义是**上游病根**，本次只是让它不再造成数据错，不消除「同实体两行」——
需按 §四立项做模型归一，否则下一次新增生态/采集通道仍会在 `judged_map_of` 里长出新桥接分支。
