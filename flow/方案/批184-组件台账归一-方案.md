# 批184 · 组件台账模型归一（三笔结构债的解法）

> 上游：`flow/方案/批183d-组件台账跨源键-评审.md`（§三 P1-1/P1-2/P2）。
> 基线：`docs/architecture/A07-系统安全态势页.md` §四 已定义 `security_component` 唯一键
> `source+name`、**source=归源（pip/rpm/system）**。本方案不动这个键，只把 **source 的语义
> 收回到「生态」**，判定来源交给既有列 `latest_source`。

## 一、问题的一句话

`source` 同时表示两件事：**包从哪个生态来**（pip/rpm/binary）与 **谁做的判定**（dnf→system）。
批156 为「grype 未装机也滚动」引入 `system` 源，schema2 又把 OS 行从「8 个点名组件」扩成
**全量 rpm**，于是每个 rpm 包在表里有两行：`system`（有判定）+ `rpm`（SBOM 名/版本）。
183d 的 `("system",k)+("rpm",k)` 双键就是为这两行打的桥。

## 二、目标模型（回归 A07，不新增概念）

| 维度 | 取值 | 载体 |
|---|---|---|
| 实体 | (ecosystem, name) | `security_component` 唯一键（不变） |
| ecosystem | `pip` / `rpm` / `binary` | `source` 列（CHECK 约束锁死） |
| 判定来源 | `pypi` / `dnf` / `none` | `latest_source`（已有列） |
| 纳管方 | pypi/repo/none | `managed_by`：**由 ecosystem 派生**，迁移回填后只读，代码不再写 |
| 展示分组 | runtime/dev/os | `dep_health.rows[].group`：**只做 UI 分组**，不进判定路径 |

判定契约收缩为 `(latest_version, latest_source, judge_class, judge_why)`——`managed_by` 退出契约
（它是 ecosystem 的纯函数，182d 已把「从表读旧值再回写」定性为写侧回环，这是同形残留）。

## 三、迁移 0189（一次成型，可回滚）

1. **合并** `source='system'` → `rpm`：
   对每个 system 行 S，若存在同 `_norm_key(name)` 的 rpm 行 R：
   `R.version := S.version`（`rpm -q` 权威）、`R.latest*/judge_* := S.*`、
   `R.checked_at := GREATEST(R,S)`、`last_seen := GREATEST`，**删 S**；
   无 R 则 `UPDATE source='rpm'`。
2. **删 8 别名行**（`python/nginx/openssl/postgres/redis/pango/cairo/wqy-microhei`）：
   它们是 schema1 的点名探针别名，与真实 rpm 名（`python3.11` 等）不同名；
   schema2 全量行已覆盖，留着只会产生同名歧义（`python` 不是包名）。
3. **回填 `managed_by`**：pip→`pypi`、rpm→`repo`、binary→`none`。
4. **加约束**：`CHECK (source IN ('pip','rpm','binary'))`（禁止第四个源再长出来）。
5. **首次横扫**：`last_seen < today-3` 对所有生态删一次（原先只有 pip/system 有 GC，
   rpm/binary 无 GC ⇒ 永久累积）。首轮用 7 天阈值 + 删除量写日志，观察一轮再回到 3 天。

**dry-run 必产出两份清单**（迁移前跑、贴日志人工核对，不自动合并）：
- 同名 system/rpm 但 `version` 不同（取哪个？默认 system，逐条可复核）
- 仅 system 有、rpm 无（改名后是否与 syft 命名差异撞车，如 `libcom_err`/`libcom-err`）

## 五、实施顺序（一批两 commit，一次上产）

1. **0189 迁移 + 写侧**（后端）→ dev 往返（scratch schema upgrade/downgrade）+ 真库守门
2. **展示层**（行带 source + 前端标签 + i18n）
3. 上产 → 触发一次 scan，核对：`SELECT source,count(*) ... GROUP BY 1` 仅 pip/rpm/binary；
   `tzdata` 两行（pip 2026.4→2026.6 actionable ｜ rpm 2026a current），页面有生态标签

## 六、验收（守门，全部为行为断言）

1. `source` 值域 ⊆ {pip,rpm,binary}（DB CHECK + 真库断言）
2. 不存在 `source='system'` 行
3. `(source,name)` 内 `managed_by` = 派生值（断言三生态各一行样本）
4. `judged_map_of` 对同名跨生态返回不同键、同生态覆盖（现有 183d 守门升级为单键断言）
5. GC：对 pip/rpm/binary 三种源各注入一行 `last_seen=old`，全部被清（原 rpm/binary 不清理=回归点）
6. 迁移往返：0189 upgrade→downgrade→upgrade，行数与关键列等价

## 七、风险与取舍

- **version 冲突**：system 行 `rpm -q` 权威，rpm 行来自 syft（可能带 epoch/格式差异）。默认取 system，
  dry-run 清单逐条核对；无法判定的保留 rpm 原值并在日志点名。
- **首次横扫误删**：若某轮 SBOM 失败未刷 `last_seen`，3 天规则会删真实行。首轮用 7 天 + 删除量告警，
  稳定后回收 3 天。
- **不动的东西**：唯一键 `(source,name)`、`security_finding` 表、`latest_source` 语义、A07 五区展示结构。
- **为什么不做「读侧聚合」代替**：数据已按错键写坏，`DISTINCT ON` 只能遮住展示，判定列仍然串源；
  读侧聚合最多是归一后的补充，不能当替代。
