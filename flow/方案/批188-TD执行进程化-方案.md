# 批188 · TD 执行进程化（交易执行与策略任务解耦）· 方案

> 性质：架构级改造——把 TD 会话从"随 live_task 生灭"改为"按交易账号常驻独立进程"，
> 所有交易操作（策略单/撤单/清仓/手工单）经该进程的命令队列+回执统一承接；**下发路径判活整体退役**。
> 依据：`D26`（账号级 hub 拓扑）、`D32`（插件 TD builder）、`D12 §2.11`（急停终态）、`D15`（监控规则边界）、
> `risk.py`/`strategy.py`/`trading.py`/`hub_worker.py`/`main.py`/`scheduler`/`md_hub`/`health_monitor` 现状 + codegraph 实证调用图。
> 工作区：批187 已上产、干净；本方案独立开工。
> 审查轨迹（沿革/逐轮发现）在 `flow/审查/`，本文件只陈述终态设计，不留修订补丁。

## 0. 立项背景、目标与设计立场

**触发**：批187 上产后，prod 点"一键清仓"报 409"没有运行中的实盘任务"。根因是 TD 会话绑在
`quant-live-task@<tid>` 进程（`main.py:397/568`），没有 running 任务就没有 TD 执行载体，web 层无
TD 会话（批173 铁律），急停无法下发。

**根本裁定**：TD 执行能力常驻化后，执行载体恒在。进程不活只可能是系统级故障（systemd 自愈失败/机器宕），
由 systemd + 健康监控负责；**下发路径不再判活**——判活是"任务会生灭、需找活载体"时代的产物，
常驻化后它只剩"拦下本不该拦的急停"一个效果，正是 409 根因。

**设计立场（避免照搬错误）**：批187 的 `EmergencyWorker` 是为"每 runner 任务会生灭"设计的；本批账号常驻后，
执行载体、命令路由、账号集合都变了。本方案**只迁移其中仍然成立的部分**（线程执行模型、键族、三账链、状态机），
对不成立的假设（任务号段、任务维度路由、live_task 判活、行情链 Gate）**重新设计**，不照搬。

**目标**：
1. 每个交易账号一个常驻独立 TD 执行进程 `quant-td-exec@<account_id>`，持有该账号 TD 会话（唯一连接）。
2. 所有交易操作经命令队列+回执统一由执行进程承接；策略任务退化为纯信号计算（形态 X）。
3. 风控收拢到共同路径单次执行（执行进程内 `check_order → WAL → 合规校验 → send_order → 回执`），策略侧不判定。
4. TD 与行情账号解耦：下单价随命令带；清仓价读行情账号 hub 写的 tick 快照（td→quote 映射 + 持仓驱动订阅）。
5. 下发零判活：勾选账号直接写账号队列；进程健康交还 systemd + health_monitor。

## 4. 核心设计

### 4.1 TD 执行进程（systemd + SA4）

- 新单元 `quant-td-exec@.service`（参照 `quant-md-hub@.service`）：`Environment=ACCOUNT_ID=%i`，
  **`EnvironmentFile=/data/websites/snailtrail.cc/quant/shared/.env`（td_exec 需连 PG/Valkey——路径对齐
  `quant-live-task@.service:18`/`quant-md-hub@.service:13`，写错则进程起不来）**，
  `ExecStart=run-current -m src.td_exec.main`，`WatchdogSec=90`，`Restart=on-failure`，
  `RestartPreventExitStatus=0 78`，`RestartSec=30`，`MemoryMax=1G`，
  `OnFailure=quant-task-failed@%i.service`（写法对齐 `quant-live-task@.service:10`；`%n` 嵌套实例会失效）。
- 进程启动：读 `trading_account` 行（`account_id=%i`，含 `quote_account_id`——**取价映射在 td_exec 侧自查，
  命令无需携带**，避免下发侧拼装错误）→ 复用 `td_registry.build_td_runtime(provider, ..., client_id, order_prefix)`
  建 TD 会话（账号级号段 §4.5）→ 注册成交/委托回调（§4.4）→ `reconcile_orders` 补录宕机窗成交（§4.4）
  → 启动 TTL 心跳在场键（`HeartbeatWriter(ttl=90)` 范式）→ 进入命令消费循环 + 喂狗；优雅退出停止心跳。
- SA4 期望源（`scheduler/tasks.py:2035 _desired_units`）：第四源——`trading_account` 中
  `enabled=true` 且 `provider` 具备 **execution 能力**（`registry` token `execution`，
  `registry/__init__.py:27`；判定 `pick(DOMAIN_TRADING, provider, {"execution"}, "plugin")`，
  仿 `tasks.py:2071` 的 market_data 判定但换 token——hub 源才是 market_data，TD exec 是 execution，
  两者不同，勿混）的行 → `quant-td-exec@{id}.service`；与下发账号集共用 `exec_capable_providers()`（§4.7）。
- 切换不兼容旧任务：维护窗内先停全部 `quant-live-task@`（清 running 行，§7 runbook），再起 td-exec，原子切换。

### 4.2 命令通道与执行模型（统一承接）

**键空间约束**：批187 已建立回执/进度/终局/取消键族，大量读端依赖。本批**只换执行载体与下发判活，不换回执键名**
——td_exec 写同名键，三处读端与前端零改动。

**命令通道 = 真 List 队列（修复单槽覆盖）**：
- 写：`LPUSH td:cmd:{account} <cmd>`（每账号一队列，并发命令不覆盖）；
- 读：td_exec 主循环 `BLPOP td:cmd:{account} timeout=1` 阻塞取一条 → 投递到进程内 `queue.Queue` → 立即回环（不在读循环内执行）；
- 命令字段 = `{req_id, verb: place-order|cancel-all|close-all|manual-order, order|params, signal_id, operator,
  operator_uid, account_id, ts, bar_fingerprint}`——**不含 `quote_account_id`**（td_exec 自查，§4.1）；
  `req_id` 只在命令体与回执键中，命令队列本身不嵌 req_id（List 与回执键彻底解耦）。

**执行模型 = 主循环分流 + 单工作线程（饥饿根治的关键，逐行推演过）**：

事实基线：`EmergencyWorker._run`（`hub_worker.py:168-189`）只有**一个** daemon 工作线程：
`cmd = self._q.get()` → `self._handle(cmd)`。`_close_all_positions` 是 `while True`（`trading.py:756`，
仅取消键退出），工作线程一旦进入就**再也回不到 `_q.get()`**。因此"让工作线程在 close 期间 reject 其它命令"
在物理上不可能——写 reject 的执行者正被独占。这是前几版的致命盲点，本版从结构上解决：

- **主循环（`BLPOP td:cmd:{account}` 所在循环）持有 `business_redis`，具备独立写回执的能力**
  （`consume_risk_cmd` 现状即持有 `r`，`hub_worker.py:51-63`）。主循环维护一个**进程内标志 `closing_req_id`**
  （close 启动时置、终局时清，与 §4.7 取消键配合）。
- **分流规则（主循环内完成，不依赖工作线程）**：
  1. BLPOP 取命令 → 解析 `verb`/`req_id`；
  2. 若 `closing_req_id` 非空（close 进行中）且 verb 不是 close 自身的终局处理：
     主循环**直接写主回执** `risk:cmd:result:{req_id} = {accepted:false, reason:"系统处置中，请稍后或先取消当前处置"}`
     （用 `write_cmd_result` 同款格式），**不投递工作线程** → 调用方即时拿到 reject，零排队、零超时；
     **信号账不留孤儿**：策略 live 分支发命令前已写 `signal_log`（拿 signal_id），故主循环 reject 时**同时写一条
     `order_log(rejected, signal_id, reason=系统处置中)`**（`write_cmd_result` 之外补一个轻量落库；沿用 §4.4 的
     signal_id 关联键）——保证 signal_log 有对应 order_log，只是终态 rejected，F-4 三账链不因分流而断；
  3. 否则：置 `closing_req_id`（若 verb=close-all）→ 投递工作线程执行。
- **工作线程**仍单线程串行跑整轮急停（撤单/稳定窗/拒单窗/取价重试/终局/SSE）——但只处理"非 close 期命令"
  和"那一个 close 本身"，不会再有命令在它背后堆积等待（close 期的命令已被主循环分流 reject）。
- **stop 信号**：systemd 停机时主循环 BLPOP 超时检测到停止标志，向工作线程投 `_STOP_CMD`（`:749 drain`），
  若 close 在飞则限时 join、超时写 interrupted 终局。

**回执/进度/终局/取消键族（td_exec 写，键名沿用 trading.py 常量，读端零改动）**：
- 主回执 `risk:cmd:result:{req_id}`（`RISK_RESULT_KEY`）——`place_order` 2s 窗、两个 dispatch 5s 窗、
  `manual_order_result` 单查（`risk.py:417/749/808`）全读此键；**主循环分流 reject 也写此键**；
- 终局 `risk:cmd:result:{req_id}:final`（`RISK_FINAL_KEY`，TTL30min）——看板 `:final`/`:recent`/`:active`（`risk.py:550/567/605`）依赖；
- 进度 `risk:cmd:progress:{req_id}` + active `risk:cmd:active:{uid}`——每轮逐单进展（`trading.py:606` 迁入）；
- 取消 `risk:cmd:cancel:{req_id}`（`risk.py:706` 写 = `trading.py:598 RISK_CANCEL_KEY`，同名核对过）——
  web 取消按钮**直接写此键**，`_close_all_positions` 每轮检查（`trading.py:758/976`）并 `final:cancelled` 终止；
  **取消不经命令队列、不经工作线程**，故不受 close 独占影响，也不受主循环分流影响；
- 近终局索引 `risk:close:recent:{uid}`——跨页面重建用。

**"清仓独占"语义（明确的产品决策）**：清仓 = 熔断 + 撤单 + 卖持仓，熔断本就禁止一切下单。故 close 期间的
`place-order`/`manual-order`/`cancel-all` 由**主循环即时 reject**（`系统处置中`），符合熔断语义、非命令丢失；
停止清仓走独立取消键（不饿死）；close 终局（完成/取消/systemic）后主循环清 `closing_req_id`，命令恢复正常执行。
**关键：分流由主循环做，不占工作线程——这是饥饿从"换名未根治"到"结构性消除"的分界。**

- 策略 `place_order`（形态 X，live）：算信号 → 写 `signal_log` 拿 `signal_id` → `LPUSH` 命令 → 等
  `risk:cmd:result:{req_id}`（2s 超时）→ 拿 client_id 返回；**不调 check_order/合规/WAL/send_order**；
- 撤单/清仓/手工单同样发命令到本账号队列，**均不判活**（§4.7）。

### 4.3 共同路径风控 + 合规校验 + paper 分叉

执行进程内每条**实盘**下单命令按固定顺序：
`check_order(完整 order, account_id)` → reject 回执 rejected；adjusted 用 adjusted 值 →
WAL `order_log(submitting, adjusted, signal_id, bar_fingerprint)` →
`rules_for(...).validate(...)` 合规校验（`strategy.py:473-492` 迁来，reject 改本进程 order_log=`rejected` + 回执）→
`client_id=账号级号段` → `adapter.send_order` → 回填 vt_orderid/send_failed → 回执。

- `check_order` 读 `risk:halted`/开关/规则/快照（Redis+PG），不依赖策略进程；合规 provider 从 td_exec adapter 配置取；
- 实盘策略侧删除 `check_order`（`:463`）、合规校验（`:473-492`）、`order_log` 写入；
  `signal_id` 只关联 signal_log→order_log 创建；
- **`_log_signal_order` paper-aware**：`paper=True`/回测仍写 signal_log + order_log 双表并返回有效 order_id，
