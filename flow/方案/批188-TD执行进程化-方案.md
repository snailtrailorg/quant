# 批188 · TD 执行进程化（交易执行与策略任务解耦）· 方案

> 性质：架构级改造——把 TD 会话从"随 live_task 生灭"改为"按交易账号常驻独立进程"，
> 所有交易操作（策略单/撤单/清仓/手工单）经该进程的命令队列+回执统一承接；**下发路径判活整体退役**。
> 依据：`D26`（账号级 hub 拓扑）、`D32`（插件 TD builder）、`D12 §2.11`（急停终态）、`D15`（监控规则边界）、
> `risk.py`/`strategy.py`/`trading.py`/`hub_worker.py`/`main.py`/`scheduler`/`md_hub`/`health_monitor` 现状 + codegraph 实证调用图。
> 工作区：批187 已上产、干净；本方案独立开工。
> 审查轨迹（沿革/逐轮发现）在 `flow/审查/`，本文件只陈述终态设计，不留修订补丁。

## 0. 立项背景与目标

**触发**：批187 上产后，prod 点"一键清仓"报 409"没有运行中的实盘任务"。根因是 TD 会话绑在
`quant-live-task@<tid>` 进程（`main.py:397/568`），没有 running 任务就没有 TD 执行载体，web 层无
TD 会话（批173 铁律），急停无法下发。

**根本裁定**：TD 执行能力常驻化后，执行载体恒在。进程不活只可能是系统级故障（systemd 自愈失败/机器宕），
由 systemd + 健康监控负责；**下发路径不再判活**——判活是"任务会生灭、需找活载体"时代的产物，
常驻化后它只剩"拦下本不该拦的急停"一个效果，正是 409 的根因。

**目标**：
1. 每个交易账号一个常驻独立 TD 执行进程 `quant-td-exec@<account_id>`，持有该账号 TD 会话（唯一连接）。
2. 所有交易操作经命令队列+回执统一由执行进程承接；策略任务退化为纯信号计算（形态 X）。
3. 风控收拢到共同路径单次执行（执行进程内 `check_order → WAL → 合规校验 → send_order → 回执`），策略侧不判定。
4. TD 与行情账号解耦：下单价随命令带；清仓价读行情账号 hub 写的 tick 快照（td→quote 映射 + 持仓驱动订阅）。
5. 下发零判活：勾选账号直接写账号队列；进程健康交还 systemd + health_monitor。

## 4. 核心设计

### 4.1 TD 执行进程（systemd + SA4）

- 新单元 `quant-td-exec@.service`（参照 `quant-md-hub@.service`）：`Environment=ACCOUNT_ID=%i`，
  `ExecStart=run-current -m src.td_exec.main`，`WatchdogSec=90`，`Restart=on-failure`，
  `RestartPreventExitStatus=0 78`（优雅退出/配置错不重拉），`RestartSec=30`，`MemoryMax=1G`，
  `OnFailure=quant-task-failed@%n`（进程真起不来时告警——这是"系统崩了"的现成出口）。
- 进程启动：读 `trading_account` 行（`account_id=%i`）→ 复用 `td_registry.build_td_runtime(provider, ..., client_id, order_prefix)`
  建 TD 会话（xtp/emt，账号级号段见 §4.5）→ 注册成交/委托事件回调（§4.4）→ `reconcile_orders` 补录宕机窗成交（§4.4）
  → 写 `td:exec:{account}:alive` 在场键 → 进入命令消费循环 + 喂狗；优雅退出删在场键。
- SA4 期望源（`scheduler/tasks.py:2035 _desired_units`）：第四源——`trading_account` 中
  `enabled=true` 且 `provider` 属 trading 能力域的行 → `quant-td-exec@{id}.service`（与 hub 源并列，
  同 provider 集合判定逻辑 `tasks.py:2062-2080`）。账号停用/删除 ⇒ 期望移除 ⇒ reconciler 停单元。
- **切换不兼容旧任务**：维护窗内先停全部 `quant-live-task@`（清 live_task running 行，见 §7 runbook），
  再起 td-exec；测试环境原子切换，不留双 TD 共存。

### 4.2 命令通道（队列 + 回执，统一承接）

- 每账号一队列 `td:cmd:{account}`（Redis List + 短轮询）；命令 =
  `{req_id, op: place|cancel|close|manual, order|params, signal_id, operator, operator_uid, account_id, quote_account_id, ts, bar_fingerprint}`；
- 回执 `td:result:{req_id}`（TTL30min）= `{accepted, reason, client_id, order_row_id, vt_orderid, adjusted}`；
- 策略 `place_order`（形态 X，live 分支）：算信号 → 写 `signal_log` 拿 `signal_id` → LPUSH 命令
  （带 signal_id + order 意图 + quote_account_id）→ 等回执（2s 超时）→ 拿 client_id 返回；
  **不调 check_order/合规校验/WAL/send_order**；
- 撤单/清仓/手工单：同样发命令到本账号队列（web/急停/手工来源统一）；**均不判活**（§4.7）；
- 执行进程单线程串行消费命令（同账号 adapter 写归一线，零竞态——沿用 `EmergencyWorker` 线程模型，
  从"每 runner 线程"改为"每 td-exec 进程主线程"）。

### 4.3 共同路径风控 + 合规校验 + paper 分叉

执行进程内每条**实盘**下单命令，按固定顺序：
`check_order(完整 order, account_id)` → reject 发回执 rejected；adjusted 用 adjusted 值 →
WAL `order_log(submitting, adjusted, signal_id, bar_fingerprint)` →
`rules_for(...).validate(...)` 合规校验（`strategy.py:473-492` 迁来，reject 则改本进程 order_log=`rejected` + 发回执）→
`client_id=账号级号段` → `adapter.send_order` → 回填 vt_orderid/send_failed → 发回执。

- `check_order` 读 `risk:halted`/开关/规则/快照（Redis+PG），不依赖策略进程；合规校验的 provider 从执行进程 adapter 配置取；
- 实盘策略侧删除 `check_order`（`strategy.py:463`）、合规校验（`:473-492`）、`order_log` 写入；
  `_log_signal_order` 按 paper_mode 双行为（见下）；`signal_id` 只关联 signal_log→order_log 的创建；
- **`_log_signal_order` paper-aware**（双盲 P1 修复点）：
  - `paper=True`/回测：仍写 signal_log + order_log 双表并返回有效 order_id，保持
    `test_sc_orders.py:86`、`test_d32_p2_wiring.py:52` 对"它先于 send_order 被调用"的 patch 断言有效；
  - `live`：只写 signal_log（拿 signal_id），order_log 由执行进程写；策略进程不再调该函数写 order_log，
    但保留调用点形态（传 paper_mode）以兼容测试 patch 语义；
- **`paper`/回测分叉**：`place_order` 按 `paper_mode` 显式分支——
  `paper=True` 保留本地 `check_order(paper=True)` + stub adapter send_order + `paper_trade_log`（现状不变，
  paper 任务不建 TD exec）；`live` 才走命令通道。回测整体 monkey-patch `place_order`（`backtest.py:202`）免改；
- `risk_log` 每实盘单一执行侧产出；熔断放行 `is_flat_or_reduce`（`risk.py:23`）不变。

### 4.4 事件回调、三账对账与宕机回补

三账真实关联：`signal_log --signal_id--> order_log --vt_orderid/client_order_id--> trade_log`。
`signal_id` 只连第一段；成交/终态回写靠 `vt_orderid`/`client_order_id` 反查 order_log
（`trading.py:113-121/164-178`），不是 signal_id。

TD 会话迁入 td_exec 时，事件消费链一并迁入（同进程才有事件）：
- 复用 `td_registry.build_td_runtime`（`td_registry.py:51`）返回的 `exec_port` + `adapter` + `ee`；
- 在 td_exec 进程注册 `exec_port.subscribe_order(on_order)` / `on_trade`（`main.py:393`/`hub_worker.py:483`），
  回调内调 `trading.write_order_status` / `write_trade_log`（`trading.py:144/91`）；
- `_vt2cid` 映射（`trading.py:82`）与 adapter 同进程（td_exec），vt_orderid 反查 order_log 成立；
- `adapter.account_id` 在 td_exec 侧注入（写 trade_log 的 per-account 过滤真源）；
- 持仓快照 `_flush_positions`（`trading.py:194`）归 td_exec，仍按**交易账号**写 `position_snapshot`（§4.6）；
- **`reconcile_orders` 迁入**（双盲 P1 修复点）：`main.py:552-558 _reconcile → trading.reconcile_orders`
  （`trading.py:555`）随会话迁 td_exec，在**进程启动**与 **TD 重连沿**调用，补录宕机/断连窗内的成交
  ——F-4"宕机期间成交回补"链在 exec 进程内闭环，不能只剩事件回调。

崩溃窗口：order_log 由 exec 侧 WAL 先写 submitting，成交事件回写靠 vt 反查，宕机窗靠 reconcile_orders 补录
——认领链全在 exec 进程内，不依赖策略侧超时回执。

### 4.5 client_id 账号级号段（含 builder 注入点）

- 废任务号段 `runner_client_id(task_id)=(tid-1)%98+2`（`broker.py:128`）；
- 新 `td_exec_client_id(account_id)`：每账号独立 TD 进程、每进程单连接——client_id 只需"同账号内唯一"，
  账号间各自独立连接互不干扰，故每账号取固定号 2，XTP client_id 硬限 1-99（`broker.py:131`）满足；
- **builder 注入点**（双盲 P1 修复点）：`build_td_runtime`（`td_registry.py:33/51`）当前内部硬编码 tid 派生号
  （`:81 runner_client_id(tid)`、`:132-133 order_prefix=f"t{tid}"` 与 `(tid-1)%100+20`）。改为
  **签名增账号级入参 `client_id`/`order_prefix`**（编排层 td_exec 计算后传入），插件内部改用传入值——
  改的是 `td_registry` 编排层，providers/xtp/emt 插件内部逻辑零改动（D32 契约不变）；
- 保留 D26:104 session_slot NX fencing：重启过渡窗旧实例（XTP 无 logout，`td_registry.py:84`）未退时，
  新实例同号登录被 fencing 拒绝（NX 失败→退避重连），防双 TD 共存。

### 4.6 td→quote 取价（公共真相表语义不动）

`position_snapshot.account_id` **保持写交易账号（td）**——8 处消费者（§1.2）全为交易账号语义，零改动。
TD 与行情账号解耦后，取价链两端都对齐到行情账号（quote）：

- **映射配置**：`trading_account` 增 `quote_account_id` 列——alembic 迁移加列 + 回填
  `UPDATE trading_account SET quote_account_id=id`（PG 列 DEFAULT 不能引用 id，须显式回填存量行；
  不回填则反查空→不订阅→无 tick）；新增行由创建逻辑置 `quote_account_id=self`；td=quote 默认零行为变化。
- **订阅端**：行情 hub 持仓订阅源（`md_hub/main.py:346`）按映射反查——凡映射到本行情账号的交易账号，其持仓标的都订阅：
  ```sql
  SELECT DISTINCT symbol FROM position_snapshot WHERE volume>0 AND account_id IN (
    SELECT id FROM trading_account WHERE quote_account_id = %s   -- %s=本 hub 的 account_id（行情账号）
  )
  ```
  `IN` 天然支持多 td→单 quote 映射。
- **写端**：tick 写入键 = hub 自身 `hub:latest_tick:{quote}:{vt}`（`md_hub/parts.py:314` 用 hub 的 `ACCOUNT_ID` 写）。
- **读端**：清仓取价链 `_quote_price(sym, account_id)`（`trading.py:392/404`）→ `get_hub_tick(account_id)`
  （`hub_quote.py:39`）必须用 **quote 账号**——td_exec 执行清仓时按自身 account_id 查
  `trading_account.quote_account_id`，用 quote 账号调取价（命令带 `quote_account_id`）；`hub_quote.py` 本体不改。
  读键 `{quote}:{vt}` 与写键一致后才通。
- **订阅保证**：td 有持仓 ⇒ 映射的 quote hub 经反查订阅该标的 ⇒ 写 quote tick ⇒ 清仓按 quote 读到
  （15s diff/60s 重放窗内到位，平仓无限循环重试等到）；纯在途单撤单不需价；
- 取不到价（no_tick/valkey_down）：平仓循环继续重试（批187 无限循环已实现），systemic 才终止；
  验收含 td≠quote 实测（映射反查→订阅→取价→读键全链）；
- 映射只在 `trading_account.quote_account_id` 一处，hub 订阅与清仓取价同源读取。

### 4.7 下发路径判活整体退役

**裁定**：常驻进程由 systemd 保证在场（`Restart=on-failure`/`RestartSec=30`/`WatchdogSec=90`），
进程不活即系统级故障，由 systemd + 健康监控处理；**下发路径不做任何判活**。判活是"任务会生灭、需找活载体"
时代的产物（批171n/187），常驻化后载体恒在，判活只剩"拦下本不该拦的急停"一个效果——正是 409 根因。

- **`_dispatch_risk_cmd`**（`risk.py:316`）：删除 `live_running_tasks()` 枚举、`if not runners: raise 409`、
  400 `RISK_NO_MATCH_ACCOUNT`、skipped_accounts 三态分叉（`risk.py:357-370`）；勾选账号（或全部 enabled
  trading 账号）直接 LPUSH 到 `td:cmd:{account}`，返回 `{dispatched, req_ids}`；
- **`_dispatch_manual_cmd`**（`risk.py:717`）：同删 `_live_runners` 判活 + `MANUAL_NO_ACTIVE_RUNNER` 409
  （`:724-729`），直接写 `td:cmd:{account}`；CID 去重键 `manual:cid:{cid}`（`:736`）保留；
- **进程健康职责归位**：
  - systemd：`Restart=on-failure` 自愈 + `OnFailure=quant-task-failed@%n` 告警 + Watchdog（§4.1）；
  - 在场键 `td:exec:{account}:alive`：启动写、优雅退出删，供前端展示"执行进程离线"；
  - health_monitor：按 `td:exec:*:alive` 动态发现（同 `HUB_HB_PATTERN`/`collector.py:25` 范式，
    **不进静态 `CORE_UNITS`**——账号级动态单元），新增 `td_exec_down` 沿检测告警（服务/资源面，符合 D15 边界）；
- **前端 `Emergency.vue`**：`a.running`（live_task 判活）改为 `a.execAlive`（`td:exec:{account}:alive`），
  离线仅显示提示"执行进程离线"、**不 disable 勾选/按钮**（`Emergency.vue:8/26/111/121` 的 disabled 条件只看
  勾选数与 halted，与进程状态解耦）——命令进队列、进程自愈后消费；`RISK_NO_ACTIVE_RUNNER`/
  `MANUAL_NO_ACTIVE_RUNNER` 的 i18n 文案退役；
- **D12 §2.11** 整篇重写：无 409/无 skipped，下发即写账号队列；进程死活归 systemd + 健康监控；
- **测试涟漪**：`test_batch187_risk_progress_cancel.py` 三例 patch `live_running_tasks`（`:20/35/47`）移除
  （下发不再调用）；改钉"下发无判活 + 命令写账号队列"，`test_manual_order.py` 手工单同改。

## 7. 一次上产与边界

- 六面同一次提交、同一次上产；禁止"先上执行进程、策略下一轮"——策略发命令与执行进程必须同版生效。
- **切换 runbook（测试环境不兼容旧任务）**，维护窗内顺序：
  ① `UPDATE live_task SET status='stopped'`（先改 DB——否则 SA4 reconciler 每 300s 重拉，`tasks.py:2047`）；
  ② `systemctl stop 'quant-live-task@*'` + 确认进程退出；
  ③ 验券商侧 TD 连接已释放（XTP 无 logout，`td_registry.py:84`——靠 TCP 断链 + session_slot fencing NX 守卫重叠窗）；
  ④ 部署含新单元版本 → SA4 `_desired_units` 第四源拉起 `quant-td-exec@{account}` → 验 `td:exec:{account}:alive=up` → 开窗。
  逾期未释放告警、不开窗。切换后由执行进程承接全部交易 + 持仓写入 + 事件回调（§4.4）。
- **paper/回测边界**：paper/回测路径保留本地 `check_order(paper=True)` + stub + `paper_trade_log`，不进命令通道
  （paper 无 TD exec）；回测因整体 patch `place_order` 免改；`_log_signal_order` paper-aware（§4.3）。
- **进程失活边界**：下发零判活（§4.7）；进程不活的响应全在上层——systemd 自愈/`OnFailure` 告警、
  `td_exec_down` 动态告警、前端"执行进程离线"展示；**下发路径不得因进程状态拦截任何交易操作**。
- 不做：改 D32 插件内部契约（仅编排层注入号段）、改风控规则表、加密实盘（外部 gate 未开）、
  宣布 fencing 守卫退役、复用 live_running_tasks 做任何下发判断。
- **风险兜底**：执行进程崩溃 ⇒ systemd on-failure 重拉（30s，session_slot fencing 防双连接）⇒ 命令队列消息不丢
  （Redis 持久）⇒ 重启后 `reconcile_orders` 补录宕机窗成交 + 继续消费；order_log WAL 先写 submitting，
  成交事件回写靠 vt_orderid 反查（exec 进程内闭环）。
- **判定单源**：风控一次（执行进程）、合规一次（执行进程）、WAL 一次（执行进程）、号段一函数、
  映射一配置、取价读键一账号（quote）、下发零判活——禁第二真源。
- **制度符合性**：新增 systemd 单元进 SA4 期望源（非自创常开，不越权）；TD 连接走插件 builder（D32）；
  td_exec_down 进 health_monitor 动态发现（D15 服务面）；部署走 Ansible 管道（A06）；
  无新 sudoers/wrapper（执行进程 User=quant 不需特权）。
