# 批188 · TD 执行进程化（交易执行与策略任务解耦）· 方案

> 性质：架构级改造——把 TD 会话从"随 live_task 生灭"改为"按交易账号常驻独立进程"，
> 所有交易操作（策略单/撤单/清仓/手工单）经该进程的命令队列+回执统一承接。
> 依据：`D26`（账号级 hub 拓扑）、`D32`（插件 TD builder）、`D12 §2.11`（急停终态）、
> `risk.py`/`strategy.py`/`trading.py`/`hub_worker.py`/`main.py`/`scheduler`/`md_hub` 现状 + codegraph 实证调用图。
> 工作区：批187 已上产、干净；本方案独立开工。
> 审查轨迹（沿革/逐轮发现）在 `flow/审查/`，本文件只陈述终态设计，不留修订补丁。

## 0. 立项背景与目标

**触发**：批187 上产后，prod 点"一键清仓"报 409"没有运行中的实盘任务"——不是 bug，是架构必然：
TD 会话绑在 `quant-live-task@<tid>` 进程（`main.py:397/568`），没有 running 任务就没有 TD 执行载体，
web 层无 TD 会话（批173 铁律），急停无法下发。用户裁定：把 TD 执行能力常驻化，与策略任务解耦。

**目标**：
1. 每个**交易账号**一个常驻独立 TD 执行进程 `quant-td-exec@<account_id>`，持有该账号 TD 会话（唯一连接）。
2. 所有交易操作经**命令队列+回执**统一由执行进程承接；策略任务退化为纯信号计算（形态 X）。
3. 风控收拢到**共同路径单次执行**（执行进程内 `check_order → WAL → send_order → 回执`），策略侧不判定。
4. TD 与行情账号解耦：下单价随命令带；清仓价读行情账号 hub 写的 tick 快照（td→quote 映射 + 持仓驱动订阅）。

## 4. 核心设计

### 4.1 TD 执行进程（systemd + SA4）

- 新单元 `quant-td-exec@.service`（参照 `quant-md-hub@.service`）：`Environment=ACCOUNT_ID=%i`，
  `ExecStart=run-current -m src.td_exec.main`，`WatchdogSec=90`，`Restart=on-failure`，
  `RestartPreventExitStatus=0 78`（优雅退出/配置错不重拉），`MemoryMax=1G`，`OnFailure=quant-task-failed@%n`。
- 进程启动：读 `trading_account` 行（`account_id=%i`）→ 复用 `td_registry.build_td_runtime(provider,...)` 建 TD 会话
  （xtp/emt），号段用账号级固定号（§4.5）→ 注册成交/委托事件回调（§4.4）→ 进入命令消费循环 + 喂狗。
- SA4 期望源（`scheduler/tasks.py:2035 _desired_units`）：第四源——`trading_account` 中
  `enabled=true` 且 `provider` 属 trading 能力域的行 → `quant-td-exec@{id}.service`（与 hub 源并列，
  同 provider 集合判定逻辑 `tasks.py:2062-2080`）。账号停用/删除 ⇒ 期望移除 ⇒ reconciler 停单元。
- **切换不兼容旧任务**：维护窗内先停全部 `quant-live-task@`（清 live_task running 行，
  见 §7 runbook），再起 td-exec；测试环境原子切换，不留双 TD 共存。

### 4.2 命令通道（队列 + 回执，统一承接）

- 每账号一队列 `td:cmd:{account}`（Redis List + 短轮询）；命令 =
  `{req_id, op: place|cancel|close|manual, order|params, signal_id, operator, operator_uid, account_id, quote_account_id, ts, bar_fingerprint}`；
- 回执 `td:result:{req_id}`（TTL30min）= `{accepted, reason, client_id, order_row_id, vt_orderid, adjusted}`；
- 策略 `place_order`（形态 X，live 分支）：算信号 → 写 `signal_log` 拿 `signal_id` → LPUSH 命令
  （带 signal_id + order 意图）→ 等回执（2s 超时）→ 拿 client_id 返回；**不调 check_order/WAL/send_order**；
- 撤单/清仓/手工单：同样发命令到本账号队列（web/急停/手工来源统一）；
- 执行进程单线程串行消费命令（同账号 adapter 写归一线，零竞态——沿用 `EmergencyWorker` 线程模型，
  从"每 runner 线程"改为"每 td-exec 进程主线程"）。

### 4.3 共同路径风控 + paper 分叉

执行进程内每条**实盘**下单命令：`check_order(完整 order, account_id)` → reject 发回执 rejected；
adjusted 用 adjusted 值 → WAL `order_log(submitting, adjusted, signal_id, bar_fingerprint)` →
`client_id=账号级号段` → `adapter.send_order` → 回填 vt_orderid/send_failed → 发回执。
- `check_order` 读 `risk:halted`/开关/规则/快照（Redis+PG），不依赖策略进程；
- 实盘策略侧删除 `check_order`（`strategy.py:463`）与 `order_log` 写入；`_log_signal_order` 拆为：
  策略只写 `signal_log`（`strategy.py:550-555`），TD exec 写 `order_log`（`:556-562` 迁来），
  `signal_id` 只关联 signal_log→order_log 的创建；
- **`paper`/回测分叉**：`place_order` 按 `paper_mode` 显式分支——
  `paper=True` 保留本地 `check_order(paper=True)` + stub adapter send_order + `paper_trade_log`（现状不变，
  paper 任务不建 TD exec）；`live` 才走命令通道。回测整体 monkey-patch `place_order`（`backtest.py:202`）免改；
  `_log_signal_order` 在 paper/回测路径仍被调（保持 monkey-patch 有效）；
- `risk_log` 每实盘单一执行侧产出；熔断放行 `is_flat_or_reduce`（`risk.py:23`）不变。

### 4.4 事件回调与三账对账

三账真实关联：`signal_log --signal_id--> order_log --vt_orderid/client_order_id--> trade_log`。
`signal_id` 只连第一段；成交/终态回写靠 `vt_orderid`/`client_order_id` 反查 order_log
（`trading.py:113-121/164-178`），不是 signal_id。

TD 会话迁入 td_exec 时，事件消费链一并迁入（同进程才有事件）：
- 复用 `td_registry.build_td_runtime`（`td_registry.py:51`）返回的 `exec_port` + `adapter` + `ee`；
- 在 td_exec 进程注册 `exec_port.subscribe_order(on_order)` / `on_trade`（`main.py:393`/`hub_worker.py:483`），
  回调内调 `trading.write_order_status` / `write_trade_log`（`trading.py:144/91`）；
- `_vt2cid` 映射（`trading.py:82`）与 adapter 同进程（td_exec），vt_orderid 反查 order_log 成立；
- `adapter.account_id` 在 td_exec 侧注入（写 trade_log 的 per-account 过滤真源）；
- 持仓快照 `_flush_positions`（`trading.py:194`）归 td_exec，仍按**交易账号**写 `position_snapshot`
  （语义全链不变，见 §4.6）。

崩溃窗口：order_log 由 exec 侧 WAL 先写 submitting，成交事件回写靠 vt 反查——F-4 认领链在 exec 进程内闭环，
不依赖策略侧超时回执。

### 4.5 client_id 账号级号段

- 废任务号段 `runner_client_id(task_id)=(tid-1)%98+2`（`broker.py:128`）；
- 新 `td_exec_client_id(account_id)`：每账号独立 TD 进程、每进程单连接——client_id 只需"同账号内唯一"，
  账号间各自独立连接互不干扰，故每账号取固定号 2（或按 slot 分配），不需全局 2-99 去碰撞；
  XTP client_id 硬限 1-99（`broker.py:131`）仍满足；
- 保留 D26:104 session_slot NX fencing：重启过渡窗旧实例（XTP 无 logout，`td_registry.py:84`）未退时，
  新实例同号登录被 fencing 拒绝（NX 失败→退避重连），防双 TD 共存。

### 4.6 td→quote 取价（方案 B：公共真相表语义不动）

`position_snapshot.account_id` **保持写交易账号（td）**——8 处消费者（§1.2）全为交易账号语义，零改动。
TD 与行情账号解耦后，取价链两端都对齐到行情账号（quote）：

- **映射配置**：`trading_account` 增 `quote_account_id` 列——alembic 迁移加列 + 回填
  `UPDATE trading_account SET quote_account_id=id`（PG 列 DEFAULT 不能引用 id，须显式回填存量行；
  不回填则反查空→不订阅→无 tick）；新增行由创建逻辑置 `quote_account_id=self`；td=quote 默认零行为变化。
- **订阅端**：行情 hub 持仓订阅源（`md_hub/main.py:346`）按映射反查——凡是映射到本行情账号的交易账号，
  其持仓标的都订阅：
  ```sql
  SELECT DISTINCT symbol FROM position_snapshot WHERE volume>0 AND account_id IN (
    SELECT id FROM trading_account WHERE quote_account_id = %s   -- %s=本 hub 的 account_id（行情账号）
  )
  ```
  `IN` 天然支持多 td→单 quote 映射。
- **写端**：tick 写入键 = hub 自身 `hub:latest_tick:{quote}:{vt}`（`md_hub/parts.py:314` 用 hub 的 `ACCOUNT_ID` 写）。
- **读端**：清仓取价链 `_quote_price(sym, account_id)`（`trading.py:392/404`）→ `get_hub_tick(account_id)`
  （`hub_quote.py:39`）必须用 **quote 账号**——td_exec 执行清仓时按自身 account_id 查
  `trading_account.quote_account_id`，用 quote 账号调取价（命令亦可带 `quote_account_id`）；
  `hub_quote.py` 本体不改，只改调用方传参。读键 `{quote}:{vt}` 与写键一致后才通。
- **订阅保证**：td 有持仓 ⇒ 映射的 quote hub 经反查订阅该标的 ⇒ 写 quote tick ⇒ 清仓按 quote 读到
  （15s diff/60s 重放窗内到位，平仓无限循环重试等到）；纯在途单撤单不需价；
- 取不到价（no_tick/valkey_down）：平仓循环继续重试（批187 无限循环已实现），systemic 才终止；
  验收含 td≠quote 实测（映射反查→订阅→取价→读键全链）。
- 映射只在 `trading_account.quote_account_id` 一处，hub 订阅与清仓取价同源读取。

### 4.7 急停判活适配

- `_dispatch_risk_cmd`（`risk.py:316`）三态分叉/skipped/去重**仍基于** `live_running_tasks()` 枚举账号
  （保持 v6 审透口径，判活来源不变），只在"命令下发目标"上从 `risk:cmd:{tid}`（任务维度）改为
  `td:cmd:{account}`（账号维度）：`runners` 元组仍是 `(tid, account)`，SET 的键改为账号队列；
- `td:exec:{account}:alive` 仅作"执行进程在场"的可观测键（页面显示/告警），不参与 409 判定
  （常驻执行体恒在，409 自然消失，判活逻辑不动以免破坏三态分叉）；
- 测试涟漪：`test_batch187_risk_progress_cancel.py` 三例 patch `live_running_tasks`（`:20/35/47`）因判活来源不变
  继续有效；本批新增测试钉"命令写账号队列而非任务键"，验收补 `test_route_auth_gate.py`。

## 7. 一次上产与边界

- 六面同一次提交、同一次上产；禁止"先上执行进程、策略下一轮"——策略发命令与执行进程必须同版生效。
- **切换 runbook（测试环境不兼容旧任务）**，维护窗内顺序：
  ① `UPDATE live_task SET status='stopped'`（先改 DB——否则 SA4 reconciler 每 300s 重拉，`tasks.py:2047`）；
  ② `systemctl stop 'quant-live-task@*'` + 确认进程退出；
  ③ 验券商侧 TD 连接已释放（XTP 无 logout，`td_registry.py:84`——靠 TCP 断链 + session_slot fencing NX 守卫重叠窗）；
  ④ 部署含新单元版本 → SA4 `_desired_units` 第四源拉起 `quant-td-exec@{account}` → 验 `td:exec:{account}:alive=up` → 开窗。
  逾期未释放告警、不开窗。切换后由**执行进程**承接全部交易 + 持仓写入 + 事件回调（§4.4）。
- **paper/回测边界**：paper/回测路径保留本地 `check_order(paper=True)` + stub + `paper_trade_log`，不进命令通道
  （paper 无 TD exec）；回测因整体 patch `place_order` 免改。
- 不做：改 D32 插件契约、改风控规则表、加密实盘（外部 gate 未开）、宣布 fencing 守卫退役。
- **风险兜底**：执行进程崩溃 ⇒ SA4 on-failure 重拉（30s，session_slot fencing 防双连接）⇒ 命令队列消息不丢
  （Redis 持久）⇒ 重启后继续消费；order_log WAL 先写 submitting，成交事件回写靠 vt_orderid 反查（exec 进程内闭环）。
- **判定单源**：风控一次（执行进程）、WAL 一次（执行进程）、号段一函数、映射一配置、取价读键一账号（quote）——禁第二真源。
- **制度符合性**：新增 systemd 单元进 SA4 期望源（非自创常开，不越权）；TD 连接走插件 builder（D32）；
  部署走 Ansible 管道（A06）；无新 sudoers/wrapper（执行进程 User=quant 不需特权）。
