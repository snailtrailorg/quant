# 批190 · 安全三任务失败隔离与互斥（实施终态）

> 已上产 prod `202611260854-87da147`。本文=设计真源（安全扫描域无 D 系列专篇）。

## 0. 两条铁律的落地形态

| 要求 | 落地 |
|---|---|
| 失败不破坏上一次成功结果 | scan 整轮 ok 才覆盖快照；grype `state` 仅成功推进；dep 未取到上游的包只推 `last_seen` |
| 定时与手动不并行 | 三任务入口 `SET NX` 抢锁（唯一判定源）；路由只做快速 409 预检、不写锁 |

## 1. 互斥

三任务同一模式：

```
任务入口: SET <lock> <token> NX EX <TTL>  → 失败返回 {"status":"busy"}
          成功执行，finally 里 GET==token 才 DEL
路由:     GET <lock> 存在 → 409（仅快速反馈，不写锁）
```

| 任务 | 锁键 | TTL | 说明 |
|---|---|---|---|
| security_scan | `sec:scan_lock` | 2700s（>time_limit 2500） | 原仅路由写锁→beat 不查锁可并发，改为入口权威 |
| grype_db_update | `sec:grype_db_lock` | 2100s（>time_limit 1900，原 1800 短于时限） | 保持已有语义 |
| dep_audit | `sec:dep_audit_lock` | 173100s（48h+300） | 新增；beat 三态保留作进度/僵死诊断 |

**路由不写锁**的关键原因：route 先占锁会让随后入队的任务入口永远抢不到（自锁死）；且 delay 失败时锁残留=假忙。

**dep 僵尸锁回收**：锁在但 beat 终态 done 或心跳停 >10min（SIGKILL 无 finally）→ 清锁重抢一次。无 beat 时解析锁值内嵌 ISO 时间判龄（抢锁→首次心跳之间仍视为活）。否则 48h TTL 会让手动/beat 全部 409。

## 2. security_scan：整轮成功才覆盖

- `status == "ok"` 才执行 `INSERT ... ON CONFLICT (scan_date) DO UPDATE`。
- 非 ok：库内存在任一 `status='ok'` 行 ⇒ 不写快照（保留上次结果）；无任何 ok 行 ⇒ 落一行 degraded 供首诊。
- 非 ok 轮一律写 `sec:scan_last_attempt`：`{ts, scan_date, status, degraded_zones, n_fresh_vulns}`（7d），成功轮删除该键。
- `ai_summary` 仅在写快照的轮次回写（失败轮摘要不落到上次成功行）。
- 为什么必须做：读取侧用 `last_seen_at < snap.created_at` 判 fixed（`routes/security.py`），degraded 轮若推进 `created_at` 会把全部漏洞判成已修复=假清零。

## 3. grype_db_update：状态分层

`sec:grype_db_state`：
```json
{"state":"updated","ts":"<上次成功>","error":"","last_attempt":{"ts":"...","state":"update-failed","error":"..."}}
```
- `state/ts` 仅成功推进；失败只写 `last_attempt`。
- 从未成功过才把失败态写成有效态。
- 返回体仍带本轮 `state=update-failed`（任务层据此告警），不影响存储的有效态。

## 4. dep_audit：按包粒度

- 区分「确认无上游版本」（查询成功）与「本轮未取到」（异常/额度用尽）：后者该包只 `UPDATE last_seen=now()`，`latest_version/judge_class/judge_why/checked_at` 保持上次值。
- `_flush_batch` 两段 SQL：成功包 upsert；未取到包仅 last_seen。
- 契约 `last_complete` 仅 `ok=True` 写入（失败轮不推进切面锚）；枚举全挂时不覆盖契约。
