# 批190 · 安全三任务失败隔离与互斥（方案）

> 状态：待用户确认后实施。真源=本文件；D 系列无安全扫描专篇，落此。

## 0. 结论

用户两条要求各自命中的缺陷：

| 要求 | 现状 | 等级 |
|---|---|---|
| 失败不破坏上一次结果 | 三任务**都会**用失败结果覆盖上次成功结果（详见 §1） | P0（scan）/ P1（dep、grype） |
| 定时与手动不并行 | security_scan **任务入口没有任何锁**（beat 与手动可并发）；dep_audit 只有非原子 beat 判定 | P0 |

其中 scan 的覆盖是最严重的：同日失败重扫会把当天**全部漏洞判成已修复（假清零）**。

## 1. 现状证据（逐条可复现）

### 1.1 security_scan
- 入口无锁：`tasks.py:973-992` 的 `security_scan` 直接 `run_security_scan()`；`sec:scan_lock` 只由手动路由写（`routes/security.py:118`），beat 06:00 派发的任务不查锁 ⇒ **定时/手动可并行**，两个手动请求在 check→set 之间也可并行。
- 失败覆盖：`security_collector.py:1262-1272` 无条件 `INSERT INTO security_snapshot ... ON CONFLICT (scan_date) DO UPDATE ... created_at=now()`。
  - vulns 分区 degraded 时 `_upsert_findings` 被跳过（旧漏洞行保留），但快照 `created_at` 被推到最新；读取侧 `routes/security.py:79` 用 `last_seen_at < snap.created_at` 判 fixed ⇒ **全部漏洞显示已修复**。
  - 同时 `ai_summary` 写 NULL，清掉当日已生成摘要（`security_collector.py:1270`）。
- 同日成功→成功覆盖是正确语义（findings 同步刷新），不算破坏。

### 1.2 grype_db_update
- 失败覆盖状态：`security_collector.py:603-607` 无论 state 为何都写 `sec:grype_db_state`，失败时把上次的 `updated`+built_at 覆盖成 `update-failed`。本地 DB 仍是旧可用库，但所有读取方（scan 的 DB 卡、前端）都看到"库坏了"。
- 互斥：`tasks.py:1008` 任务入口 SET NX 有，路由预检有 ⇒ 基本合格；仅路由 delay 失败时锁残留（TTL 1800s 兜底）。

### 1.3 dep_audit
- 失败覆盖判定：`tasks.py:1172-1215` 单包上游查询异常/额度用尽 ⇒ `latest=None` ⇒ `_judge` 出 `unknown`，`_flush_batch`（`tasks.py:1146-1167`）无条件覆盖 `latest_version/judge_class/judge_why` ⇒ **昨日正确判定被降级为 unknown**。
- 失败覆盖轮次锚：`tasks.py:1361-1380` 即使 `ok=False` 仍写契约 `last_complete.ts=now()`；读取侧切面 `checked_at <= last_complete.ts`（`security_collector.py:333,396`）被推进到半轮，半更新行混入判定（有全表回退兜底，不会切空，但会混轮）。
- 互斥：仅 beat 三态判定（`tasks.py:1097-1110`）+ 路由预检（`routes/security.py:166-174`），非原子 ⇒ 两个并发任务可同时通过。

## 2. 修法

### 2.1 统一互斥（单一判定源：任务入口抢锁）

三任务同一模式，路由只做快速预检、**不再写锁**（消除 route-set/任务-释放的 token 分裂与 delay 失败残留）：

```
入口: SET lock <token> NX EX <time_limit+300>
      拿不到 → return {"status":"busy","reason":"<持锁值>"}
      拿到   → 执行；finally: GET==token 才 DEL
路由: GET lock 存在 → 409（仅快速反馈，非权威）
```

- `sec:scan_lock`（已有键，改为任务入口抢；TTL 2700 = time_limit 2500+200）
- `sec:grype_db_lock`（已有实现，保持）
- `sec:dep_audit_lock`（新增；TTL 172800+300，token=run_id）。beat 三态判定保留作**进度/僵死诊断**，不再作互斥依据。

### 2.2 security_scan：整轮成功才覆盖快照

- 判定：`status == "ok"` 才执行快照 upsert。否则：
  - 当日/历史存在任一 `status='ok'` 行 → 不写 snapshot（保留上次结果）。
  - 库中无任何 ok 行（首次即失败）→ 写一行 `status='degraded'` 供诊断（无旧结果可破坏）。
- 失败轮次一律写独立键 `sec:scan_last_attempt`：`{ts, status, parts, degraded_zones, n_fresh}`（TTL 7d）。前端"上次尝试失败"读它，不读快照。
- `ai_summary` 仅成功轮写；失败轮不碰。
- 结果返回体不变（`status` 等），加 `"snapshot_written": bool`。

### 2.3 grype_db_update：状态分层，成功才推进有效状态

`sec:grype_db_state` 改为：
```json
{"state":"updated","ts":"<上次成功时刻>","built_at":"...","last_attempt":{"ts":"...","state":"update-failed","error":"..."}}
```
- `state/ts/built_at` 仅在成功时更新。
- 失败只更新 `last_attempt`（保留旧 `state=updated`）；从未成功过才写 `state=update-failed`。
- 读取侧（scan DB 卡）原读 `state` 语义不变；新增暴露 `last_attempt` 供前端附注。

### 2.4 dep_audit：按包粒度「成功才写判定」

- 区分两种 None：
  - **确认无版本**（查询成功、versions 非空但解析后无/上游确无此包）→ 正常写 unknown。
  - **本轮未取到**（异常 / 额度用尽 /`_budget_out`）→ 该包只 `UPDATE last_seen=now()`，**不动** `latest_version/judge_class/judge_why/checked_at`。
- `_flush_batch` 拆两段 SQL：成功包走现有 upsert；失败包走仅 last_seen 的 UPDATE。
- 契约：`ok=False` 时不写 `last_complete`（保留上次完整轮锚），只更新 `ts/ok/errors/counts`；若 `pip_rows` 与 `os_installed` 全空（枚举全挂）→ 不写契约，只写 `sec:dep_audit:last_attempt`。

## 4. 六面 DoD

1. **数据契约**：无迁移（全部 Redis 键 + 现有表行语义）。`sec:grype_db_state` 新字段向后兼容（旧读者读 state 不变）。
2. **写入路径**：三任务入口抢锁；scan 成功判定闸；grype 状态分层；dep 按包写判定。失败一律留痕（`last_attempt`/errors）。
3. **读取展示**：前端安全页加"上次尝试失败（时间/原因）"一行，快照仍显示上次成功值；i18n 三语。
4. **可观测**：三个 `*_last_attempt` 键 + 日志；失败告警沿用现有。
5. **测试**：故障注入（见 §5）。
6. **文档**：本文件定稿；`flow/待办.md` 一行；完成后归档。
