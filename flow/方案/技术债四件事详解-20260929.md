# ① 上 ruff + pre-commit

## 1.1 一上来就会被打脸：20,247 条里 94% 是配置噪音

实测 `ruff check --select E,F,W,I,B,S,UP,SIM,C4,RET,ARG,PTH,RUF src` 报 **20,247 条**。但拆开看：

| 规则 | 条数 | 占比 | 性质 |
|---|---:|---:|---|
| RUF002 文档字符串含歧义 Unicode | 8,058 | 39.8% | **噪音** |
| RUF003 注释含歧义 Unicode | 5,956 | 29.4% | **噪音** |
| RUF001 字符串含歧义 Unicode | 1,435 | 7.1% | **噪音** |
| E501 行过长 | 3,205 | 15.8% | **噪音** |
| B008 默认参数里调用函数 | 405 | 2.0% | **噪音** |
| — 以上小计 — | **19,059** | **94.1%** | 全部由 3 个配置项造成 |
| 其余全部真实项 | **1,188** | 5.9% | 需处理 |

**三处噪音的成因，逐个说清**：

- **RUF001/002/003（15,449 条）**：这是中文项目的必踩坑。RUF 这三条规则把中文全角标点（`，。；：（）「」`）判定为「歧义的 Unicode 字符」——它们的本意是防 `а`（西里尔 а）冒充 `a`（拉丁 a）这类钓鱼式同形字，但中文标点是合法书写。**必须关闭**：`ignore = ["RUF001","RUF002","RUF003"]`。这条不关，ruff 直接废掉。
- **E501（3,205 条）**：他们的代码行「又长又密」——注释里塞满批号与理由。默认 `line-length=88` 对中文注释不现实（中文一字占两列宽，但 ruff 按字符数算，实际渲染 140 字符 ≈ 280 列）。建议 `line-length = 140`，仍超长的再单独讨论——**不要为了过 lint 去砍注释的信息量**，那是本末倒置。
- **B008（405 条）**：`function-call-in-default-argument`。FastAPI 的写法 `payload: dict = Depends(require_perm("read"))`、`body: dict = Body(...)` 天然触发这条。这是**行业标准误报**，官方解法是声明为「不可变调用」：
  ```toml
  [tool.ruff.lint.flake8-bugbear]
  extend-immutable-calls = ["fastapi.Depends", "fastapi.Body", "fastapi.Query", "fastapi.Path", "fastapi.Header", "fastapi.Cookie"]
  ```

关掉这三处后，真账 1,188 条。

## 1.2 最有说服力的证据：代码里已经有 17 处给「不存在的 linter」写的抑制注释

```
  10 处  # noqa: BLE001      ← BLE001 = flake8-blind-except（盲 except）
   7 处  # noqa: F401        ← 未使用 import

```

`BLE001` 属 `flake8-blind-except`，不在任何默认规则集里；`D102`/`D418` 属 `pydocstyle`。**这说明写代码时（很可能是 AI 协作时）已经按 ruff 的惯例在写抑制注释了，但仓库里从来没装过 ruff、也没有配置文件** —— 所以这 17 处注释在过去一段时间里**一行作用都没起**。

这是「规范与工具脱节」最干净的证据：抑制意图存在、抑制机制不存在。而且顺带被 `RUF100` 检出 14 处**已失效**的 noqa（其中 2 处是语法错误）。

**2 处 noqa 语法错误（顺手就能修）**：

```python
# src/data_platform/perms.py:12
from src.data_platform.db import get_conn   # noqa: F401（部分函数内再 import as _gc 同源）
#                                                      ↑ 代码列表后直接跟全角括号，无空格

# src/web_api/routes/im_bots.py:240
    from src.im_bot.credentials import save_bot_credentials   # noqa: F401（与创建语义对齐说明）
```

ruff 要求 noqa 代码列表以空白结束，`F401（部分函数内…` 被整体解析成代码名 → 报 `Invalid noqa directive`。**修法：代码列表后加一个空格** → `# noqa: F401 （…）`。

## 1.6 坑

1. **不要一次开满规则集**。`select` 先按上表，跑稳两周再加 `D`（pydocstyle）/ `ANN`（注解）/ `PL`（pylint）。一次开满会让存量清洗变成不可能任务。
2. **不要用 `ruff format` 全仓格式化**——他们的注释是信息载体（批号、理由、踩坑），格式化会打乱 `# noqa` 与代码的相对位置。初期只上 `ruff check`，`ruff format` 只对新文件。
3. **`RUF100` 会删掉那 14 处「失效 noqa」**——包括 10 处 `BLE001`。**先不要删**：应该先启用 `BLE001`（在 `select` 加 `"BLE"`），让那 10 处恢复作用，再看还剩几处真失效。
4. ruff 版本要 pin（`ruff==0.16.9`），否则规则默认集随版本变，某天 CI 突然红一片。
5. `requirements.txt` 里加 `ruff` 会进生产镜像——**ruff 只进开发依赖**，单独放 `requirements-dev.txt`（目前该文件不存在，需新建）。

## 2.2 为什么这是 P0（而不是风格问题）

因为**同一文件里已经存在正反两个样本**，9 行之隔。`strategy_runner/hub_worker.py`：

```python
def on_trade(event):
    trading.write_trade_log(event.data, adapter, sid, symbol)
    # 批 69a：SSE 信号帧（零内容——前端重拉 orders/position）
    try:
        from src.quant_common.eventbus import bus
        bus.publish_cross_process(0, "trade_update", {})
    except Exception:
        pass                                    # ← 205 行：无理由、无日志

ee.register(...)

try:
    r.xgroup_destroy(stream, gname)
except Exception: pass   # 组不存在（首启）属正常   # ← 214 行：有理由
```

214 行是**做对的**：吞掉异常，但用注释声明了「为什么可以吞」。205 行是**做错的**：SSE 推送（前端刷新的唯一触发）失败后**永久静默**——前端不会刷新，用户看不到任何异常，日志里也没有一行。

**这就是 09-28 那个 P0 的同形复现**：`_dispatch_async` 签名错配导致「外推链自 09-18 起全断十天」，根因也是告警链路被静默吞掉。同一个坑，换了个位置又埋了一个。

再补一个跨层的例子，`web_api/routes/trading.py:37-46`：

```python
try:
    import redis as _redis, os as _os
    r_ = _redis.Redis.from_url(...)
    for rid, *_ in rows:
        h = r_.hgetall(f"quant:hb:task:{rid}")
        if h: hb[rid] = h
except Exception:
    pass            # ← Valkey 挂了 → hb 全空 → 页面把所有实盘任务显示成"无心跳"
```

这是**读侧降级**：Valkey 不可用时任务列表静默显示为「无心跳」，用户侧的观感是「策略全死了」，而系统没有任何提示说明是监控通道故障。**误报 vs 漏报，这里选错了方向**——风控类系统应宁可报「心跳数据不可用」也不要假装它是空的。

## 2.3 判定规则（这条要写进规范）

> **规则**：`except` 块内必须有且仅有以下三者之一，否则视为违规——
> ① `raise` / `raise ... from e`（让上层处理）
> ② `logger.warning("...", exc_info=True)`（记日志但继续）
> ③ 一行注释明确写出「为什么可以吞」**且** 紧邻的 `pass` 带 `# noqa: S110  # <理由>`
>
> 三者皆无 = 违规。

**设计意图**：让「静默」从**默认行为**变成**需要显式声明的行为**。`# noqa: S110` 就是那份声明——它在 diff 里可见、可 review、可 grep。这比「靠人记住要写日志」可靠一个数量级。

## 2.4 三分类处置（附实际样本）

### (a) 合法忽略 → 补理由 + `noqa`

样本 1：`hub_worker.py:214`（已有理由，只需补 noqa 形式）
```python
except Exception: pass   # noqa: S110  # 消费组不存在（首次启动）属正常
```

样本 2：`health_monitor/collector.py:88-97`（**有降级路径，属于做对了的**）
```python
        for _, (ck, kind) in _CFG_KEYS["periods"].items():
            try:
                v = int(cfg.get(ck, _DEF_PERIODS[kind]))
                if v > 0:
                    periods[kind] = max(30, min(v, 86400))
            except (TypeError, ValueError):
                pass                      # ← 内层：单键值非法 → 保留缺省，合理
    except Exception:
        pass                              # ← 外层（94 行）：整体读配置失败 → 走下方回落
    if thresholds is None:
        thresholds, periods = _DEF_THRESHOLDS, _DEF_PERIODS   # ← 显式降级
```
**这处不用改语义，只需补理由注释**——注意它内层已经是收窄的 `except (TypeError, ValueError)`，而外层才用 `except Exception`，这个层次区分是正确写法，值得作为团队范式。

### (b) 应记日志 → 加 `exc_info=True`

- `hub_worker.py:205`（SSE 推送失败）
- `trading.py:45`（Valkey 心跳读取失败）
- `scheduler/tasks.py` 的 13 处（定时任务链，也是全仓最需要日志的地方）
- `health_monitor/collector.py` **全部 5 处** —— 最讽刺的一处：**监控组件自己出错时静默**，等于监控失效不会被发现。

改法：
```python
except Exception:
    logger.warning("on_trade: SSE trade_update 推送失败（前端可能不刷新）", exc_info=True)
```

`exc_info=True` 是关键——只写 `logger.warning("失败")` 等于把堆栈扔了，故障还是不可诊断。

## 2.7 坑

1. **不要用 `--fix` 批改 S110**——ruff 无法推断语义，自动修会删掉 `pass` 从而**改变控制流**（`except` 后空块是语法错误，但 ruff 的修法是把 `pass` 换成别的东西，可能引入行为变化）。这 92 处必须人工过。
2. **不要把 `except Exception` 随便收窄成具体异常**——收窄会把未知异常上抛，在定时任务里可能直接杀死 beat 进程。收窄只在明确知道会抛什么时做。
3. **不要给 `pass` 补 `logger.debug` 充数**——debug 级在生产默认不输出，等于没改。用 `warning` + `exc_info=True`。
4. **`# noqa: S110` 不要写成无理由的裸 noqa**——那就把「可 grep 的声明」退化成了「又一个静默点」，白做。建议 CI 里加一条：`# noqa: S110` 后面必须跟 `#` 和至少 8 个字符。

# ③ 依赖上锁 + 新路由禁 SQL

这两件事合并成一个任务，因为都是**防复发**——不改存量，只让问题不再增长。

## 3A 依赖上锁

### 3A.1 现状与风险

`server/requirements.txt` 37 条，**全部 `>=`，无 lock 文件**。风险不是抽象的——AGENTS.md 里已经记录了两次事故：

> 「vnpy 4.4.0 硬 pin `pyside6==6.8.2.1`，该版本 `requires_python <3.14`……resolver 回退 vnpy 4.0.0 与 vnpy_binance 2026.7.23 错配（`Exchange.GLOBAL` 缺失致 import 崩）」
> 「`pandas>=2.0`——原靠 vnpy/tushare 传递带入，上游一变即 ImportError」

他们已经踩过坑并把教训写进了注释。但**注释不是机制**——下一个人（或下一个 AI 会话）看到 `vnpy>=4.0` 还是会以为是安全的。

### 3A.2 关键约束：本地 3.10 / 服务器 3.11

AGENTS.md 明确：**服务器 3.11（venv 3.11.13），本地开发机 3.10**。锁文件必须在**目标解释器版本**下解析，否则解析出的依赖树可能不同（尤其是含 `python_requires` 分支的包）。

**做法二选一**：
- 在服务器同版本环境生成（推荐，最真实）；
- 或本地用 `--python-version 3.11` 显式指定（够用但不如上者精确）。

### 3A.3 具体做法

拆成两个文件——**人写意图，机器写断言**：

```
server/requirements.in     ← 人写。保留全部现有注释（批号、pin 理由）
server/requirements.lock   ← 机器生成，部署与镜像用，不做人工编辑
```

```bash
# requirements.in 内容 = 现在的 requirements.txt（含注释，一条不动）
# 生成 lock（在 3.11 环境）
pip install pip-tools
pip-compile --python-version 3.11 \
            --output-file server/requirements.lock \
            server/requirements.in
```

**部署链改动**（这步不会自己生效）：Ansible 管道里 pip 安装的目标要从 `requirements.txt` 切到 `requirements.lock`。按 AGENTS.md，部署走 `deploy/` 的 Ansible playbooks，所以这属于 release 剧本的改动，**必须走「彩排绿后跑 release.yml」的正常发布流程**，不能手工改。

### 3A.4 渐进路线（不建议一次全锁）

全锁会把 `akshare` / `tushare` 这类高频更新的数据源也冻住，与「数据源适配要跟上游」的需求冲突。**建议只锁关键链**：

| 优先锁 | 理由 |
|---|---|
| `vnpy` + `vnpy-*` + 传递来的 `PySide6` | 已出过两次事故 |
| `psycopg` / `sqlalchemy` / `alembic` | 数据库 Schema 正确性相关 |
| `fastapi` / `pydantic` / `uvicorn` | 接口契约相关 |
| `celery` / `redis` | 调度与队列行为相关 |
| **暂不锁**：`akshare` / `tushare` / `openai` / `httpx` | 需要跟上游走，用范围约束 |

实现上：`requirements.in` 里对「暂不锁」的包继续写 `>=`，`pip-compile` 会为它们解析出当前版本；如果想留活口，用 `--no-emit-index-url` 配合手工把这几条从 lock 中放出。**更简单的替代方案**：lock 只用于**生产部署**，开发机继续用 `requirements.in`——这是最小改动、最大收益的版本。

## 3B 新路由禁写 SQL

### 3B.1 现状

`server/src/web_api/` 下**没有 `services/` 目录**（现有：`auth.py` / `errors.py` / `main.py` / `models.py` / `redis_pool.py` / `terms.py` / `routes/`）。

`routes/` 14 个文件的 SQL 字面量实测基线（**这是白名单要用的数字**）：

| 文件 | SQL 处数 | | 文件 | SQL 处数 |
|---|---:|---|---|---:|
| `auth_routes.py` | 53 | | `im_bots.py` | 14 |
| `trading.py` | 28 | | `strategy.py` | 14 |
| `backtest.py` | 27 | | `stock.py` | 12 |
| `alerts.py` | 26 | | `sync.py` | 12 |
| `system.py` | 24 | | `quality.py` | 3 |
| `risk.py` | 18 | | `routing.py` | 3 |
| `mgmt.py` | 17 | | | |
| `chat.py` | 16 | | **合计** | **267** |

### 3B.2 核心决策：不重构，加闸门

**明确否决**「把 267 处 SQL 抽到 service 层」的大重构。理由：这 267 处分散在 14 个文件、与 FastAPI 的 `Depends(require_perm(...))` 权限链深度耦合（perm 与 SQL 在同一函数里交替出现），重构风险远大于收益，而且违反 AGENTS.md 的「a 会话一焦点」与「先 plan 后 act」。

**采用**：冻结存量 + 约束增量 + 随自然迭代收敛。

### 3B.3 具体做法

**新增 `server/tests/test_no_sql_in_routes.py`**：

```python
"""路由层 SQL 闸门：存量冻结，增量禁止。

设计：基线是「只许调低不许调高」的字典。任何想调高基线的改动
都会在 diff 里显式出现，等于强制一次架构决策 review。
"""
import os, re, pathlib

ROUTES = pathlib.Path(__file__).resolve().parents[1] / "src" / "web_api" / "routes"

_SQL = re.compile(r"(?i)\b(SELECT|INSERT\s+INTO|UPDATE\s+\w+\s+SET|DELETE\s+FROM)\b")

# 2026-09-29 实测基线（对应 flow/审计/2026-09-29-技术债体检.md）
_BASELINE = {
    "auth_routes.py": 53, "trading.py": 28, "backtest.py": 27, "alerts.py": 26,
    "system.py": 24, "risk.py": 18, "mgmt.py": 17, "chat.py": 16,
    "im_bots.py": 14, "strategy.py": 14, "stock.py": 12, "sync.py": 12,
    "quality.py": 3, "routing.py": 3,
}


def test_routes_sql_baseline_not_exceeded():
    over, unknown = [], []
    for p in sorted(ROUTES.glob("*.py")):
        n = len(_SQL.findall(p.read_text(encoding="utf-8")))
        if n == 0:
            continue
        if p.name not in _BASELINE:
            unknown.append(f"{p.name}: {n} 处（新文件必须为 0，请把 SQL 放进 web_api/services/）")
        elif n > _BASELINE[p.name]:
            over.append(f"{p.name}: {n} > 基线 {_BASELINE[p.name]}")
    assert not over, "路由层 SQL 超出基线，请改到 web_api/services/ 或显式下调基线：\n" + "\n".join(over)
    assert not unknown, "新增路由文件不得直接写 SQL：\n" + "\n".join(unknown)


def test_baseline_has_no_stale_entries():
    """基线只许调低：文件被删/清零时要同步收紧基线，防止基线烂掉。"""
    stale = [n for n in _BASELINE if not (ROUTES / n).exists()]
    assert not stale, f"基线存在已不存在的文件，请移除：{stale}"
```

**新增代码路径 `server/src/web_api/services/`**，并在 `server/tests/test_layering.py` 补一条约束：

```python
def test_services_not_imported_by_routes_reverse():
    """services 不得 import routes（组合根方向单向）。"""
```

**同时补一条防「服务层变成新的 SQL 垃圾桶」的断言**（可选，建议加）：

```python
def test_services_have_no_raw_sql_outside_repository():
    """services/ 下的 SQL 必须集中在 repository.py，其余模块禁止 SQL 字面量。"""
```

### 3B.4 为什么这条比大重构好

1. **把架构约束从文档搬进测试**。AGENTS.md 写「业务逻辑不寄生 HTTP 入口」但 `test_layering.py` 只断言 import 方向、不断言逻辑归属，所以拦不住。这条测试补上的正是缺的那一维。
2. **复用已有模式**。项目已有「防漂移闸」（`perm_registry` 键集守卫、router-walk 扫描），这条测试与它们同类，不引入新范式。
3. **零存量风险**。基线冻结 = 不碰一行生产代码。
4. **基线只许调低**的设计，让收敛变成**每次顺手改一点**，而不是一次性大工程。

## 3C 验收标准

| 检查 | 通过条件 |
|---|---|
| `server/requirements.lock` | 存在，且在 3.11 下可安装成功 |
| 部署管道 | Ansible release 剧本读 lock 文件；staging 彩排绿 |
| `test_no_sql_in_routes.py` | 全绿；人为在新路由文件插一句 `SELECT` 能被拦下 |
| `web_api/services/` | 目录存在，至少 1 个模块示范（建议先抽 `alerts` 或 `system` 里最简单的一个端点） |
| `test_layering.py` | 新增 services↔routes 单向约束 |

## 3D 坑

1. **lock 文件里的 hash 与安装方式强相关**（`pip-compile --generate-hashes`）。开了 hash 校验后必须用 `pip install --require-hashes -r`，否则会被 rpm/pip 混装绕开。建议先不开 hash，只锁版本。
2. **不要在服务器上跑 `pip-compile`**——AGENTS.md 铁律禁止直接 ssh；且服务器不该有编译工具链。在本地同版本环境生成后随部署工件下发。
3. **`server/venv/` 里已有装好的包与 lock 可能不一致**——这是既有事实，别试图对齐，只保证**新部署**走 lock。
4. **基线数字会漂**。有人改一个路由文件的行数不影响 SQL 计数，但若有人把两处 SQL 合成一处，基线就要下调。这个「下降也要改代码」的摩擦是**故意设计**的——它保证基线不腐烂。

# ④ 进展日志按月切分 + 恢复主谓宾

## 4.1 现状（实测）

| 指标 | 实测值 |
|---|---|
| `flow/进展.md` 体积 | **388 KB** |
| 行数 | 2,814 行 |
| 二级标题（一条交接） | **194 条** |
| 2026-08 条目 | 47 条 |
| 2026-09 条目 | 137 条 |
| 无日期条目 | 9 条 |
| **日期笔误** | 1 条：第 2744 行 `## 明日剧本（2028-08-18 接管会话从这里开始）` ——应为 2026 |

## 4.2 为什么是真问题（不是洁癖）

AGENTS.md「开工前必读」第 3 条：

> `flow/进展.md` **顶部一条** — 上一棒交接棒（做了啥 / 产出路径 / 下一步）

**规范要求读「一条」，但读取成本是「整个文件」**。每开一个新会话（人也好、AI 也好），都要把一个 388 KB / 2,814 行的文件加载进上下文，才能拿到最新那 20 行。137 条 2026-09 的记录里，有 130 多条与当前工作无关。

更麻烦的是**语言已不可解析**。实测顶部条目原文：

> 「**当班全弧**（方案 v2 **过门**→编码→**双盲 A/B** 全处置）……**施工自曝**（已修+列审单重点）：hset 位置参数被 mapping 形参吞→fail-open 静默吞回写（测试抓出）」

`当班全弧` / `过门` / `挂账` / `收编` / `典` / `圈` —— 这些自造压缩词对**没参与该会话的人**（包括三个月后的自己、以及下一个接手的 AI 会话）等价于密文。写的时候省了几个字，读的时候要用一整个上下文窗口去解码。

**这是「真相源在文件里」约定被推到极致的反噬**：文件确实承载了真相，但真相的**可访问性**被自己的写法破坏了。

## 4.3 切分方案

```
flow/
  进展.md                    ← 变索引：最近 3 条交接 + 月度归档链接（< 100 行）
  进展/
    2026-08.md               ← 47 条，归档，平时不读
    2026-09.md               ← 137 条，归档
    2026-10.md               ← 今后当月写入这里
```

**切分脚本**（按 `^## ` 二级标题切，处理无日期 bucket）：

```python
import io, os, re, pathlib

SRC = pathlib.Path("flow/进展.md")
OUT = pathlib.Path("flow/进展"); OUT.mkdir(exist_ok=True)
lines = io.open(SRC, encoding="utf-8").read().splitlines(keepends=True)

entries, cur = [], None
for l in lines:
    if l.startswith("## "):
        if cur: entries.append(cur)
        cur = [l]
    elif cur is not None:
        cur.append(l)
    # 头部前言（第一个 ## 之前）略过或保留到索引
if cur: entries.append(cur)

by_month = {}
for e in entries:
    m = re.match(r"##\s*(20\d\d)-(\d\d)", e[0])
    by_month.setdefault(f"{m.group(1)}-{m.group(2)}" if m else "_undated", []).append(e)

for month, es in by_month.items():
    p = OUT / f"{month}.md"
    p.write_text(f"# 进展归档 · {month}\n\n" + "".join("".join(e) for e in es),
                 encoding="utf-8")
    print(f"{p}  {len(es)} 条")
```

**索引文件 `flow/进展.md` 新结构**：

```markdown
# 进展（索引）

> 本文件只放最近 3 条交接。历史归档见 `flow/进展/`，需要回溯时 grep，不整体读。

## 归档
- [2026-09](进展/2026-09.md) — 137 条
- [2026-08](进展/2026-08.md) — 47 条
- 无日期条目 9 条，见 `_undated.md`（需人工补日期或归档）

## 最近交接
<最近 3 条原文>
```

**注意**：切分前先修 2 个数据问题——
1. 第 2744 行 `2028-08-18` → `2026-08-18`；
2. 9 条无日期条目 → 补日期或明确归入 `_undated.md`。

## 4.4 语言规范（比切分更重要）

切分只是把 388 KB 变成可管理，**可读性靠规范**。

写入 `flow/规范/` 的规则建议：

> **交接条目可读性三原则**
> 1. **主谓宾完整**。「双盲全处置」不是句子，「方案双盲发现 2 个 P1、7 个 P2，全部已处置」才是。
