## 二、三处会真出事的（P0）

### P0-1 · 根治点没碰：`.hooks/stop-doccheck.sh` 仍在往 `flow/进展.md` 追加

**这是本计划最重要的遗漏。**

实测 `.hooks/stop-doccheck.sh:21`，它的 hook reason 原文是：

```
② 交接:在 flow/进展.md 最上面追加一条进展(做了什么/为什么/怎么理解/产出路径/问题→解决/下一步)
并把这条贴在回复里给用户看,决策落 decisions.md、坑落 踩坑记录.md。
```

这是一个 **Stop hook——每个回合收尾触发一次**，自动指示 agent 往 `flow/进展.md` 顶部追加一条。

**388 KB 的成因就是它。** 也就是说：item 三（进度日志）的真正根因是一个**自动化写入机制**，而计划只处理了症状（物理切分文件），没动机制。

后果是可预测的：切分后 `flow/进展.md` 变成「索引 + 最近 3 条」（目标 < 100 行），**但因为 hook 还在指示"最上面追加"，新条目会继续写进索引文件**，索引重新膨胀，几周后回到 388 KB。等于白做。

而 AGENTS.md 自己写着：「解决问题从根本上解，不打补丁」。这个计划在这里正好违反了它。

**同样的约定还被写进了规范**——`flow/规范/工作流程.md:34`：

```
位置:`flow/进展.md`,**append、新的放最上面**。每个 Agent 干完一棒在顶部加一条;**顶部那条 = 当前交接棒**(`CLAUDE.md` 开工必读它)。
```

**必做**：改 `.hooks/stop-doccheck.sh:21` 的写入目标（改为写入 `flow/进展/<当前月>.md`，并更新 `flow/进展.md` 索引里的「最近 3 条」），同时改 `flow/规范/工作流程.md:34` 的约定。**这两处不改，item 三不成立。**

### 3.2 · `pip-compile` 上锁：命令与自述不一致 + 版本选错 + 防线可能失效

三个问题，逐个：

**(a) 说要哈希，命令没有。** 计划写「锁全部直接+传递依赖 + 哈希」，但命令是：
```
venv/bin/pip-compile requirements.txt --output-file requirements.lock
```
**缺 `--generate-hashes`。** 二选一：补上该参数（并注意启用后必须用 `pip install --require-hashes -r`，否则校验被绕开），或删掉「+ 哈希」的说法。

**(b) 在 3.10 生成、给 3.11 用——环境标记会按错误的解释器求值。**

计划写「3.10 解析，3.11 兼容（pyside6 6.8.2.1 双版本可用）」。但 pip-compile 在**当前解释器**下会求值环境标记（如 `python_version < "3.11"`）并可能丢弃标记分支，产出一份**在 3.11 上不成立或不是最优的锁**。「pyside6 6.8.2.1 双版本可用」只覆盖了一个包，不能支撑「整份锁 3.11 兼容」的结论。

**建议**：
```bash
pip-compile --python-version 3.11 --python-version 3.10 \
            --output-file requirements.lock requirements.txt
```
（多 `--python-version` 生成带标记的通用锁；至少也要给 3.11，因为**服务器才是 3.11**。）

**(c) 最要紧：锁不上部署路径 = 防线在真实场景失效。**

计划写：「部署仍走 requirements.txt（>=），lock 是审计/复现参考，不改变现有安装路径」。

**这句话让整个 item 二失去意义。** lock 存在的唯一理由就是防 vnpy/PySide6 那类漂移；而如果生产仍从 `>=` 解析，**下次部署照样会解析出漂移的版本**——事故条件完全不变。

**必须明确二选一**：
- **A（真防住）**：改 Ansible release 剧本读 `requirements.lock`。按 AGENTS.md，这属于发布链改动，须走「彩排绿后跑 release.yml」正常流程。
- **B（降级为开发侧）**：明说 lock 只服务开发/复现，**并同步修正文档措辞**——不要在任何地方把它写成「防上游漂移复发」，否则三个月后会有人以为它防住了。

**不能两个都要**（既不改部署路径、又宣称防复发）。

## 四、两处具体技术判断要修正

### 4.1 · 裸 `except:` 收窄不能一刀切——第二处会改行为

计划写：「裸 `except:` 2 处（`data_sync/pool_data.py:107/120`）收窄为 `(TypeError, ValueError)` + 注释」。实测两处语义完全不同：

**第一处（`pool_data.py:107-109`）——收窄安全：**
```python
elif c in core_map:
    v = row.get(core_map[c])
    try:
        vals.append(float(v) if v is not None and _is_num(v) else (str(v) if v is not None else None))
    except: vals.append(str(v) if v is not None else None)      # 兜底=字符串化
```
调用前有 `_is_num(v)` 守卫，且兜底是「转字符串」。收窄为 `(TypeError, ValueError)` 可接受。

**第二处（`pool_data.py:119-121`）——收窄会改行为：**
```python
def _is_num(v):
    try: float(v); return True
    except: return False
```
`float(v)` 除 `TypeError` / `ValueError` 外**还会抛 `OverflowError`**（例：`float(10**400)` → `OverflowError: int too large to convert to float`）。收窄为 `(TypeError, ValueError)` 后 `OverflowError` 会**上抛**，而 `_is_num` 是在写库循环（第 108 行）里被调用的 → 单个异常值会让整批 `sync_pools_data` 写入失败。

**结论**：`_is_num` 要么收窄为 `(TypeError, ValueError, OverflowError)`，要么保留宽 `except` 并配 `# noqa: S110  # 非数值一律视为非数字，含溢出`。**不能照计划机械收窄。** 这恰好是「批量改异常处理必须逐点读」的实例。

### 4.2 · 「F401/F841 `--fix` 会删掉 `Depends()` 参数 = 越权漏洞」——机制描述是错的

计划担心：
> FastAPI `Depends(require_perm(...))` 默认参数靠求值触发权限校验——F401/F841 `--fix` 若删参数 = 越权漏洞

**风险意识对，机制错**：
- `F841` = **局部变量**赋值未使用，不涉及函数签名默认值
- `F401` = 未使用 import；`Depends` 在签名里被使用了，不会被判未使用
- ruff 的 `--fix` **不会删除函数签名的默认参数**。会盯上这些的是 `ARG001/ARG002`（unused-argument），而它们的 fix 非自动应用——**且计划的规则集里没开 `ARG`，这个漏是对的**

**推论**：不必为「防 `--fix` 删参数」大面积加 `# noqa`（计划说「对含 `Depends(`/`Query(`/`Body(` 的文件全加 `# noqa` 保护」——**会无谓扩大 noqa 面积，反过来削弱 lint 价值**）。只需保留一条纪律：**永远不开 `ARG`**。

实测支撑：`ARG001` 131 + `ARG002` 68 = **199 处**，几乎全是 FastAPI 签名与 Celery 任务签名的天然形态。一开就是误报海。计划没开它——**请把这个决定显式写进 `ruff.toml` 的注释**，防止后人「顺手补上」。

### 4.3 · `scripts/audit_except_pass.py` 自研 AST 分类器：成本高于收益

计划要新建一个 AST 扫描器，按启发式给 92 处做 A/B/C 三分类（「机械启发式，不逐个读懂」）。

**问题**：ruff 已经能给出精确清单——`ruff check --select S110,S112 --output-format=json` 直接给出 file/line/col/rule，无需自建扫描器。**自研部分只剩「A/B/C 分类启发式」**，而：

1. 92 处的体量下，**逐条读比写+调试分类器快**；
2. 更根本的：**「用自动化代替理解」正是这次债的成因形态**——计划自己在 §三 里要解决的问题，就是历史上用流程/脚本代替工具/理解留下的；
3. 分类器一旦判错，后果落在交易系统的异常处理路径上（最坏情况：在 `os._exit` 清理路径里加 `raise`）。

**建议**：把 `scripts/audit_except_pass.py` 降级为一个 **20 行的「上下文导出器」**——对每个命中点输出 ±5 行源码，供人快速三分类。清单来自 ruff（免费），分类由人做（92 条，可控）。这既保留可重复性，又不把判断外包给启发式。

## 五、顺序：结论对，理由不成立（不阻塞，仅说明）

计划把 ruff（三）放最后，理由之一是「避免 ruff 的 F401 改 import 时连带动 SQL 冻结判定（四）」。

**这个理由不成立**：SQL 字面量位于函数体内部，`I001`（排序）/`F401`（删未使用 import）都不会触碰函数体里的字符串。唯一会动 import 行的是 `E402`，而 `E402` 恰恰**没有 autofix**（见 §3.4）。

**但结论仍然对**——「改动面最广的最后成批做」本身是合理的风险排序。这只影响效率，不影响对错，所以列为参考项。

> 若追求效率，把 ruff（三）提前有一个实打实的好处：**「100 处 except-pass」的精确清单就是 `ruff check --select S110,S112` 的输出**，三先做可省掉 §4.3 那个自研分类器。另外 `ruff` 一次运行就给出了真 bug（见 §六）。
