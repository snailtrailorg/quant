- **位置**：`server/src/strategy_runner/hub_worker.py:266-341`（`handle_msg`）
- **现状**（按行号顺序）：

- **建议改法**（需按此顺序想清楚再动手）：
  1. `xack` 从「无条件」改为「业务成功后」——或失败时只 ack 但不推进水位（二者必须同进退）
  2. 把 `state.max_ts` / `_mts_key` 的推进与 `history.append` 放进同一个「业务成功」分支
  3. 首根 bar 的锚点问题改用**显式初值**（启动时从 PG 暖机结果直接设锚），而不是靠「副作用提前」来规避
  4. guard 对 `handle_msg` 这类**有副作用契约**的 handler 应记录 + 计数，而不是纯吞（见 P1-2）
- **风险**：**高**。改的是实盘消费链核心顺序，涉及 ACK 语义与去重锚。改动前建议在 staging 用 `scripts/test-live-pipeline.sh` 跑一遍。
- **验收**：构造 `on_bar` 抛异常的用例 → 断言（a）该 bar 未被 xack 或可重放；（b）`state.max_ts` 未推进；（c）产生一条告警/错误日志。

### 原始分析（存档）

- **位置**：`server/src/web_api/redis_pool.py:12-21`、`server/src/feishu_bot/tasks.py:25-26`
- **现状**：
  ```python
  # redis_pool.py:12（业务池，注释说 db0）
  redis_pool = redis.ConnectionPool.from_url(
      os.environ.get("VALKEY_URL", "redis://127.0.0.1:6379/0"), ...)
  # redis_pool.py:17-19（飞书池，注释说 db4「与业务库隔离」）
  feishu_redis_pool = redis.ConnectionPool.from_url(
      os.environ.get("VALKEY_URL", "redis://127.0.0.1:6379/4"), ...)
  ```
  **两行相邻代码靠不同默认值区分目标库，却读同一个环境变量。**
  `feishu_bot/tasks.py:25` 是同一模式的第三份。
- **部署实况**（已核实）：
  - `server/.env:8` → `VALKEY_URL=...:6379/**0**`（业务库）
  - `server/.env.example:13` → `VALKEY_URL=...:6379/**4**`，且上方注释明确写「db 分配: safebox=db0 | quant: VALKEY=db4 …**绝不用 db0/db1/db2/db3**」
  - **两个文件规定相反**
- **为什么是问题**：三种情形全部坏掉——
  | 情形 | 后果 |
  |---|---|
  | 变量未设 | 隔离成立（唯一正确的巧合） |
  | 取 db0（当前 `.env` 实况） | **两个池都连 db0**，注释声明的隔离从未生效；飞书心跳与业务键混装，`scheduler/app.py:19` 的注释正警告过「一次故障全带走」 |
  | 取 db4（照 `.env.example` 部署） | **32 处业务连接点全落 db4** |
- **根因**：不是「漏改一处」，而是**用默认值来区分语义**。默认值只在环境变量缺失时生效，不可能可靠表达「这两个池必须不同库」。
- **建议改法**：
  - 拆变量：`VALKEY_URL`（业务）+ `FEISHU_VALKEY_URL`（飞书，默认 `.../4`），飞书侧独立读取
  - 或：飞书池不再从 URL 推导，改为复用连接参数 + 显式指定 `db=4`
  - 同时**统一 `.env` 与 `.env.example`**，并确认服务器实际 `.env`（需你在服务器上核实）
- **风险**：中等。改后飞书会切到 db4，**原 db0 里的飞书状态键会「消失」**（心跳/会话丢失，会自动重建，但首次切换会有一次重连）。选在非交易时段做。
- **验收**：加一条测试断言 `redis_pool.connection_kwargs["db"] != feishu_redis_pool.connection_kwargs["db"]`（在设置了 `VALKEY_URL` 的前提下）。
- **注意**：这是本轮 `VALKEY_URL` 34 处拷贝里**唯一已产生不一致后果**的一处；其余 32 处只是拷贝（见 P2-5）。

- **位置**：`server/src/data_platform/db.py:329`、`server/src/data_platform/db.py:342`

  - `:329` 函数签名 `-> list[date]`

- **建议改法**：模块顶部加 `from datetime import date`（一行）。同时删掉函数内的重复导入。
- **风险**：无。

# 附录 B · 扫描器自身的能力边界

两份扫描器都不是权威，用前须知：

1. **`audit-failure-modes.py --selftest` 必须先跑**，10/10 通过才算探针可信。开发过程中探针**先后 4 次给出自信的错误结果**：
   - `(?i)FROM` 正则**匹配到了 Python 的 `from src.xxx import`**（表名抓成 `src`）
   - 参数提取误命中行内逗号（`UPDATE ... SET enabled=%s, ... WHERE market=%s` 取成了 `updated_at`）
   - `sys.exit` 与 `os._exit` 混报（前者会走 atexit，不丢日志）
   - P7 输出满屏 `try:` 无法阅读（标签取块首行）
   **四类全靠反验才发现。没有 `--selftest`，它会持续输出看似正常的错误结果。**
2. **低置信模式（P3/P7/P8/P9，本次合计 1,073 条）需要人工分诊**，不要直接当账。高置信模式（P1/P2/P4/P5/P6/P10）本次合计 161 条。
3. **`audit-single-source.py` 的 B 项（51 处 `or` 兜底）绝大多数是展示文案**（`or '未知'`、`or '(空)'`、`or '{}'`），各调用点本就可独立措辞 → 默认不动。完整清单见 `flow/审计/单一真源扫描-20260929.txt`。
4. **查「同一个缺省值有几份」要 grep 配置键名，不是 grep 数值**。同一件事换锚点规模差十倍：`grep '0.6' server/src` → 3 处（1 处还是注释）；`grep 'VALKEY_URL'` → 34 处。
5. **工具会骗人，写工具的人也会犯同样的错**——「一条不合规就整体静默丢弃」这种毛病在扫描器里出现过（`(-1440, 1440, ...)` 首元素是 `ast.UnaryOp` 导致整张 bounds 表被跳过，不报错、给出看似正常的空结果）。这与 `trading.py` 那段写了等于没写的 `SELECT 1` 探测是**同一形状**。
