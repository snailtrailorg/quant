## 一、问题陈述

`sync_config` 是**一张平面注册表**（16 列 × 24 行），但现实里至少有 **6 种异质同步形态**：

| 形态 | 实例 | 本质差异 |
|---|---|---|
| ① 逐日全市场批量 | `margin_detail_sync` 等 7 项 | 「一天 = 一次调用」，按 trade_date 拉全市场 |
| ② 按标的增量 K 线 | `astock_daily` 等 6 项 | 「一只标的 = 一条序列」，按 ts_code 拉 |
| ③ 全量重建快照 | `namechange_sync`、`concept_sync` | DELETE 全表 + INSERT，**无游标语义** |
| ④ 静态清单快照 | `astock_list`、`etf_list` 等 5 项 | **无时间轴**，每次覆盖当前真相 |
| ⑤ 池内完整性驱动 | `pool_data`、`pool_data_full_calibrate` | 一条行背后 **10 张表**，按「标的缺不缺」驱动，不看日期 |
| ⑥ 日历专项 | `trade_cal` | 不是「同步数据集」，是「维护一张参照表」 |

后果有两类，且已经造成实际事故：

- **同一列在不同行代表不同东西** → 判据被滥用（`sync_mode` 当 UI 门 ⇒ `trade_cal` 该有入口却没有；`pool_data` 不该有却有一个点了不生效的假按钮）；
- **同一件事在不同层各写一遍** → 改一处漏一处（`float_cols` 代码/DB 双真源，已有挂账注记；日历改造只覆盖 tier1 7 表，漏了 `astock_basic`）。

**对架构设计的冲击（初版结论已由下节勘察修正）**

本稿 §三/§四/§六 的参数全部隐含「A 股时间轴」假设，crypto 逐条打穿：

| 参数 | A 股语义（本稿隐含） | crypto 语义 | 冲突性质 |
|---|---|---|---|
| ~~日期语义列~~ | `trade_date` / `ann_date` | 日界 = UTC 00:00 的连续序列 | ⚠️ **初版判「枚举不够」，已被修正**——该维度契约层已覆盖（`Temporality`），见下节 |
| `trade_day_filter` | none / workday / trade_day | **恒 none**（7×24 无休，日历过滤概念失效） | 取值域够，但归属须标注「仅交易日轴适用」 |
| `start_floor`（起点下界） | 静态日期：A 股 1990-12-19 = 数据诞生日 | **运行期能力**：交易所 K 线保留窗口（币安 1m 仅保留近期 N 天，更早须 REST 分页/第三方归档），**且随时间漂移** | **类型不同**——静态日期 vs 运行期探测，共用一列需加语义标记 |
| `lag`（可用延迟） | T+1（`margin_detail`） | 近实时（分钟级） | 缺省不能默认为 1 |
| 形态 | ①逐日全市场 / ②按标的 | **②的变体**：按标的 + 连续时间窗口分页（无「全市场单日」概念） | 形态 ① 对 crypto 不适用 |
| `provider` 限速模型 | HTTP 批量 + 每分钟次数 | REST/WS + 权重限速 + 分页游标 | 数据源层抽象须容纳两种限速模型 |

**结论（修正版）**：crypto 与 A 股的差异**不在「时态」**——契约层 `Temporality`（`historical`/`snapshot`/`streaming`）已能表达 crypto 的「历史 + 实时」组合（与 `bar_minute` 的 hybrid、`funding_rate` 的多时态同构）。真正仍无归属的是三件：①**交易时间表**（session：交易日 / 连续 / 无——`security_master` 用 `calendar='none'` 已在**运行时**处理 crypto，但未进配置契约）；②**起点下界**（运行期探测 vs 静态日期）；③**限速模型**（每分钟次数 vs 权重+分页）。

### 接口化现状：契约层已建成，运行时只接了半根线（威廉姆二次追问后勘察）

威廉姆问：「数据是系统定义的，获取数据的能力由外部注册的接口提供，我们可以定义这些接口，让注册的模块遵守这种接口（数据格式、配置格式）——是这样设计的吗？」

**答：是，而且比设想的更完整——契约层已经把这套机制写好了。真正的问题是：它只接了半根线，运行时用的是另一套词汇。**

### 分派键实测：抽象锚在两个不同地方（威廉姆三次追问后核）

威廉姆问：「同一种数据可能有多个外部接口提供，所以要抽象，**每一种数据都要定义一个抽象接口**，是不是这样？」

**答：方向对，但「每种数据一个接口」这半句会把粒度带偏。** 正确形态是**两个正交轴、两种不同粒度**：

| 轴 | 问什么 | 抽象键 | 实现机制 | 现状 |
|---|---|---|---|---|
| **数据种类轴** | 拉哪类数据 | `(kind, sub_kind)` | 统一端口 `BaseDataAdapter.fetch(req)` + 形状声明（`ContractFrame.columns` / `POOL_TABLE_SPECS` / `sync_kind_config`） | ◐ 部分接线 |
| **供应商轴** | 谁提供 | `(kind, temporality)` 能力声明 | `routing.resolve` → `CandidateChain` → 运行期选源 + failover | ◐ 仅消费面 + bar_daily 供给 pilot |

**`engine.py` 24 项的分派键实测**

| 路径 | 项数 | sync_id | 锚 |
|---|---|---|---|
| `_VIA_KIND_IDS` → `_sync_via_kind` → `adapter.fetch(req)` | 6 | astock_daily / etf_daily / cb_daily / index_daily / astock_minute / astock_minute_5min | ✅ **`(kind, sub_kind)`** |
| pool 两条 → `adapter.fetch`（`POOL_TABLE_SPECS`，挂在 `_HANDLERS` 只作编排） | 2 | pool_data / pool_data_full_calibrate | ✅ **`(kind, sub_kind=表名)`** |
| `_HANDLERS` 字面量 → bespoke 函数（模块内直 import `tushare_adapter`） | 7 | astock_basic / astock_list / cb_basic / etf_list / trade_cal / static_symbols / convertible_terms | ❌ **`sync_id`** |
| `_TIER1_BATCH` 工厂 → `importlib.import_module("…tushare_adapter")` | 7 | stk_limit_sync / moneyflow_sync / margin_detail_sync / top_list_sync / block_trade_sync / cyq_perf_sync / forecast_sync | ❌ **`sync_id` + tushare 硬编码** |
| `_TIER1_FULL` 工厂 → 同左 | 2 | namechange_sync / concept_sync | ❌ **`sync_id` + tushare 硬编码** |

**即：8/24 走契约端口，16/24 直连 tushare**（其中 9 个是 `importlib.import_module("src.data_platform.adapters.tushare_adapter")` 的**模块级硬编码**——provider 串根本不参与）。

**由此得两条硬结论**

1. **`sync_config.provider` 列对 16/24 项是摆设。** 唯一真读它的路径是 `_get_kline_adapter`（`engine.py:75`），且仅当 `routing_kline_pilot=on` **且** `sync_id` 以 `_daily` 结尾——只覆盖 bar 族 4 项。所以「同一数据换一个源」在**写入侧（供给）现在做不到**：要换源得改 handler 工厂里那行 import。
2. **`fetch` 的 docstring 已明写意图、且同层自相矛盾。** `base.py:58`：「分派键=(kind, sub_kind)（**DataKind 第一公民——sync_id 不复活**）」；可同文件的 `capabilities` 就是 `set[sync_id]`（20 个子串）。**同一层里两套词汇并存**——正是项层未对齐契约的直接投影。

**抽象粒度的判据（回应「每种数据一个接口」）**

- **不要**「每种数据一个 ABC」：24 项 → 24 个类、每类一个实现（tushare），抽象变成纯开销；加一种数据要动 类 + 注册 + 分派 三处。
- **要**「一族能力一个声明 + 一个统一端口」：数据种类的差异是**参数化**的（`kind` / `sub_kind` / `range_` / `freq` / `as_of`），不是**类型化**的。加一种数据 = 加一条 `CapabilityDecl` + 一个 spec 行，**不加类、不改签名、不动分派**。
- **供应商差异落在哪**：同一端口的多实现，差异收敛到 adapter 的映射方法（`to_source_symbol` / `to_source_adj` / `to_bar_rows`）——`base.py:88` 已预留（聚宽 `pre`→`fq='pre'`、Tushare `pre`→`qfq`）。这是**同一接口的不同实现**，不是**不同的接口**。

**收敛动作（并入期一）**：把供给面分派键从 `sync_id` 迁到 `(kind, sub_kind)`——让那 16 个直连 handler 也走 `adapter.fetch`。批 58 的 docstring 已写此意图（「同步引擎循环与消费面 DataBus **共用**，区别只在 req」），**只落了一半**。这一步做完，「同一数据多来源」才在两个面同时成立。

**架构判据（本轮最重要的结论）**

**不是重造，是接线。** 契约层已提供全部所需概念，工作量收敛为三件：
1. **项层退出能力判据**：`sync_mode` 不再当门，改查契约（`CapabilityDecl` 或 `kind × temporality`）；
2. **能力声明升级**：`capabilities: set[sync_id]` → `list[CapabilityDecl]`，让已备的 `validate_capability_decls` 钩子**真正执法**（当前零声明＝零执法）；
3. **补映射表 4 项缺口**，或改为由 `sync_config` 单向派生（消除双真源）。

## 三、判据：一个设置该放哪一层（三问）

| 问 | 若答案是… | 归位 |
|---|---|---|
| ① 它**随什么变**？ | 随数据源变（限速、并发、凭证） | **数据源层**（provider，已有 `params` jsonb） |
| | 随**数据品类**变（kind × temporality） | **契约层**（`quant_common/contract.py` **已有**，勿重复造第三套） |
| | 随数据族变（**交易时间表**、粒度、延迟、起点下界、落库形状） | **族层**（`sync_kind_config` 扩） |
| | 随调度意图变（何时跑、是否按交易日过滤） | **项层**（`sync_config`） |
| | 随环境变（部署、路径、开关） | **全局**（.env / settings） |
| ② 谁**读**它？ | 调度器 / handler / 落库层 / 仅 UI | 读它的人越多，越该往上收；**只有 UI 读 = 不是配置是标签** |
| ③ 写**错**了会怎样？ | 静默空转 / 漏数据 / 多调用 / 只是显示难看 | 前三种必须结构化 + 加校验；第四种可以留散文 |

判据 ③ 是本设计里最关键的一条：**它给「必须结构化」划了线**——不是所有设置都值得进 DB。

## 四、目标模型

```
┌─ 契约层 quant_common ──────────── DataKind × Temporality × CapabilityDecl   （**已建成**）
├─ 数据源层 provider ────────────── 限速 / 并发 / 熔断 / 凭证    （已有 params jsonb）
├─ 族层    sync_kind ────────────── 交易时间表 / 粒度 / 可用延迟 lag /
│                                   重叠 overlap / 起点下界 / 可回补?
│                                   / 落库形状 pg_table·pk·列类型·rebuild
├─ 项层    sync_item ────────────── id / name / kind_ref / enabled /
│                                   schedule / trade_day_filter / provider /
│                                   游标 last_* / 观测 last_*
└─ 运行层  族级运行约束 ─────────── timebox / dispatch expires
```

**一条铁律**：代码里**不许出现「哪一项怎样」**——一切 per-item 差异，要么声明在项层，要么由族层推导。

**配套的第二条**：能力必须**可查询**。UI 与调度器都要能问一句「这一项支持回补吗 / 它的交易时间表是什么」，而不是各自猜 `sync_mode` 或内省函数签名。

**第三条（本轮新增）**：**一切词汇复用契约层**——数据品类一律用 `DataKind` / `Temporality`，不得再让 `sync_mode` / `data_type` 这类自造标签充当判据。族层与项层的字段是契约层概念的**实例化**，不是平行定义。

## 六、分期路线

**期一 · 能力接线（低成本，解锁三个已发现病）**
本稿初版拟「族层新增 `supports_backfill` / `time_axis` / `start_floor` 三列」——**撤掉 `time_axis`**：该维度契约层已覆盖（`Temporality` + `KIND_TEMPORALITY`），新增即第三套词汇。期一改为四件：
1. 族层加 2 列：`supports_backfill`（bool）、`start_floor`（date，**可空**；NULL 语义 =「下界由数据源运行期决定」，即 crypto 的交易所保留窗口）；
2. **项层退出能力判据**：`sync_mode` 不再当 UI 门，改问契约（`CapabilityDecl` 或 `kind × temporality`）；
3. **能力声明升级**：`capabilities: set[sync_id]` → `list[CapabilityDecl]`，激活已备的 `validate_capability_decls` 钩子（当前零声明＝零执法）；
4. 补 `SYNC_ID_CAP_MAP` 缺的 4 项（或改为由 `sync_config` 单向派生）。
→ 一次性解掉：`trade_cal` 无入口、`pool_data` 假按钮（待办已挂双向表述）、`A股基本面` 未接交易日历（待办 98）——三者都是「能力未声明 / 未接线」的症状。

**期二 · 参数归位**
lag / overlap / start_floor / 日期语义列 / timebox / expires 从代码迁入族层（缺省值 = 现状值，行为零漂移）。迁完删代码常量；每迁一项加「缺省即现状」的回归钉。

**期三 · 收编双真源**
`float_cols` / `text_cols` 单源化（须先做数据语义清理，不能只改读侧）；`data_type` 退化为 kind 派生；`tushare_api` 的限速键职责显式化。

**期四 · 族内表可选独立（按需，不必现在做）**
`pool_data` 一条行背后 10 张表：只在「需要独立调度 / 独立观测 / 独立失败告警」时才拆成继承族能力的多行。**现在不拆**——拆分成本高、收益未证。

## 七、边界与风险

**不做**：
- 不重写 `sync()` 的游标契约（批 92/97 刚稳定）；
- 不为「统一」把 full/incremental 压成一个字段——它们是**不同形态**，正确做法是形态枚举 + 族能力，而不是一个 bool；
- 不追求「所有设置都进 DB」——按判据 ③，只把「写错会静默出错」的搬进去；
- **本稿只管配置抽象的形状，不负责 crypto 数据层落地**（数据源接入 / 采集器 / 回补 / 落库）——那是独立立项；但**形状必须现在就容纳 crypto**（时间轴枚举 + provider 限速模型），否则事后整体返工。

**风险**：
1. 族层参数进 DB ⇒ 必须配枚举闸 + 缺省值（否则 DB 少一列/多一个非法值就从「静默错」变「静默错得更远」）；
2. 迁移必须是 **expand 型**（加列/加表，不改现有列语义），保证可回滚（回滚只回代码不回 schema）；
3. 期三的单源化会改已入库内容语义 ⇒ 必须走真库往返验证，**不许只加测试**；
4. **crypto 空转死构件**：`data_increment_crypto` 每 15min 被 beat 唤醒、永远 `skipped`——不在本稿范围，但须独立挂账，**「落地或删除」二选一**（不留死构件）。

## 九、结论：这套机制「完善」了吗（威廉姆四问后的定论）

**一句话**：**设计层是完善的、甚至在同类系统里算高水准；落地层不完善——但需要的不是「重构」，是「接线」。**

逐层评级：

| 层 | 设计意图 | 落地实况 | 评 |
|---|---|---|---|
| **数据目录**（`DataKind` 27 词 / `Temporality` / `KIND_TEMPORALITY`） | 系统定义「有哪些数据」＋封死非法时态组合 | 完整；实测 `sync_kind_config.kind` **100% ∈ `DataKind`** | ✅ 完善 |
| **契约机制**（`CapabilityDecl` / `validate_capability_decls` / `register_adapter`） | 「注册即声明、声明即执法」 | 钩子装好、**锁没挂**——`capability_decls` **零 adapter 声明**；全契约唯一在跑的是 `is_legal`（`routing.py:254`） | ⚠️ 建好未接线 |
| **注册**（`_ADAPTERS` + `_REGISTRY` + `sync_config` + `data_source`） | 代码登记「能做什么」、DB 登记「实际做什么、用谁做」 | 两套词汇并行：能力用 `sync_id` 词、数据用 `kind` 词，无强制对齐 | ⚠️ 词汇分裂 |
| **抽象**（`routing.resolve` → `CandidateChain` 多来源选源 + failover） | 同一种数据多家供，上层不问供应商 | **只覆盖读取面**（消费面 DataBus）；**写入面 16/24 直连 tushare**（`importlib.import_module`），`provider` 列对那 16 项是摆设 ⇒ **换源做不到** | ❌ 半覆盖 |
| **配置**（散落 5 处） | 该结构化的结构化、加闸 | 真参数藏代码常量（lag=T+1）与散文；`data_type`/`kind` 两套分类词；映射表已漂两次 | ⚠️ 散落＋漂移 |
| **任务**（调度 → 锁 → 游标 → 分派 → 拉 → 存 → 记账） | 一次同步的全链路 | **生产在跑、稳**：批 92（游标语义）、批 97（交易日历）刚打稳；唯一脏点是 `sync_mode` 被当能力门 | ✅ 基本完善 |

**必须修的（会静默出错，不是「不好看」）**：
1. **写入面分派键** `sync_id` → `(kind, sub_kind)`，让 16 项也走 `adapter.fetch`。做完 `provider` 列才有效、「同一数据多来源」才在两面同时成立——**这是全稿最大的一块**；
2. **激活能力声明**（`capabilities: set[sync_id]` → `list[CapabilityDecl]`），`sync_mode` 退出判据 → 一次性解 `trade_cal` 无入口 / `pool_data` 假按钮；
3. **补 `SYNC_ID_CAP_MAP` 缺的 4 项**（或改成由 `sync_config` 单向派生，从根上消双真源）。

**跟手改就行的（乱，但不致命）**：参数归位（lag / overlap / start_floor / 日期语义列 → 族层）、`data_type` 退化为 `kind` 派生。**新功能、单独立项**：crypto 数据层 + `data_increment_crypto` 死构件处置。

**明确不做**：不重写游标契约（刚稳）、不把 full/incremental 压成一个 bool（它们是不同形态）、不追求「所有设置都进 DB」。

**比任何单点都重要的一条**：这仓反复出现**「机制建成、最后一跳不接」**——`data_increment_crypto` 死构件（每 15min 空转）、`capability_decls` 空转钩子、`pool_data` 假按钮、`provider` 摆设列、`ContractFrame` 半活（`databus.warmup` 有、快照读取方未接）。**这是同一个病的五次现身。** 所以除修实例外，建议加一道闸：**新机制上线必须带「消费者断言」测试**（无真实消费者的机制不许 merge，或显式标注「预留·未接线」并在 CI 亮黄灯）。修这一个习惯，比修上面任何一条都值。
