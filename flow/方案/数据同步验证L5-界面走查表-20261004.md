| 1 | 该接口三次请求**全 `200 OK`**（20:56 / 21:11 / 21:29，即走查时点的三次） | `quant-web-api@quant` journal |
| 2 | 同进程同时段另一全表查询直接 **500**，栈底 = `psycopg.errors.QueryCanceled: canceling statement due to statement timeout` | 同上（`/api/sync/symbols/astock_daily?size=9999` @21:14:00） |
| 3 | web-api 进程 **`statement_timeout = 10000ms`**（10 秒） | `server/scripts/systemd/quant-web-api@.service:15`；`db.py:48` 读取 |
| 4 | 接口 SQL 是**无界全表聚合** | `risk.py:353` |
| 5 | 异常被**静默吞**、返回结构与「真无数据」**逐字相同** | `risk.py:355-356` |

**为什么这条 SQL 必超时**（`risk.py:353`）：

```sql
SELECT symbol, count(*), min(ts AT TIME ZONE 'Asia/Shanghai')::date, max(...)::date
FROM bar_1D GROUP BY symbol ORDER BY symbol
```

- `bar_1d` = 全市场 5000+ 标的 × 多年日线 ≈ **千万级行**；
- **时区转换被包在 `min()` 里面** ⇒ 每行都要算表达式 ⇒ 用不上 `idx_bar_1d_symbol_ts(symbol, ts DESC)` / `idx_bar_1d_ts` 的 index-only scan ⇒ **全堆扫描**；
- 10s 内跑不完 ⇒ PG 取消 ⇒ `except` 吞 ⇒ 返回空。

**三重危害**：

1. **前端假装「没有标的」**——`except` 返回的 `{items:[], summary:{total:0,...}}` 与「表真的空」逐字相同，**无法区分「查询失败」与「没数据」**。
2. **前端已备好的错误条被架空**：`DataIntegrity.vue:6/64` 的 `loadFailed` + 重试按钮**永远不会显示**（后端给的是 200 正常体）。
3. **「管理标的」页（齿轮）同样炸**：`sync.py:175` `/api/sync/symbols/{sid}?size=9999` 同一超时 → 500（它没吞异常，反而诚实）⇒ 本表 B3 建议的「单标的回补」路径**也断了**。

⇒ **能力影响**：生产「数据面人工验证」的**唯一入口**（`quant-dbro` 只收 3 固定动作、无任意 SQL）——现在 **integrity 页不可用、管理标的页 500** ⇒ **数据面验证能力实际归零**。这是本轮最重的发现（**P1**）。

**修复方向（供任务文件用）**：

- **① 让失败可见（最优先）**：`risk.py:355` `except` 补 `logger.exception(...)`，返回体加 `"error"` 让前端 `loadFailed` 生效。⇒ **可观测性缺陷，与 OBS-1 同族**。
- **② 让 SQL 跑得完**：`min(ts AT TIME ZONE 'Asia/Shanghai')::date` → **`(min(ts) AT TIME ZONE 'Asia/Shanghai')::date`**（时区转换移出聚合函数 ⇒ 索引可用）；必要时加时间窗，用 `EXPLAIN ANALYZE` 实证。`sync.py:175`（`size=9999` 无界）同族处理。
- **③ 兜底**：度量类只读接口单独放宽超时（`SET LOCAL statement_timeout`），不与业务查询共用 10s。

> **⚠️ 更正**：本表 **B 节（判 Q1 主战场）与 B3（管理标的回补）当前不可用**，须待接口修复后再执行。C / D / E 节不依赖此接口，仍可走。
