## 三、已发现缺陷（实证，2026-10-03）

### ✅ P1-A（已定案＝停采，2026-10-03）：`concept_sync` 长期失败——**上游接口下线**，非本仓缺陷

- **现象**（本地 dev 库实证）：
  ```
  sync_id=concept_sync  status=error  rows_pulled=0
  error: 查询数据失败，请确认参数！... Error 1054 (42S22): Unknown column 'name' in 'field list'
  ```
  最近一次成功 = **2026-09-14**（写入 1353 行）；此后 1873 次运行**全红**。
- **上游隔离实测（2026-10-03 当日，真调 TUSHARE_TOKEN）**：
  - `pro.concept()`（不带参） → `必填参数, trade_date` ⇒ 上游把「可选」参数改成了**必填**（契约变更）；
  - `pro.concept(trade_date='20261002')` → `查询数据失败... Error 1054 (42S22): Unknown column 'name' in 'field list'`；
  - `pro.concept(trade_date='20251002')`（**过去日期**） → **同样 1054**。
  ⇒ 连历史日期都 1054，且错误话术是 tushare 平台侧标准文案（「可以反馈管理员协助您排查」）
  ⇒ **不是本仓用法错**（`pull_concept` 只做 `pro.concept(**kwargs)`、无 fields 参数），是**该接口在上游服务端已不可用**。
  旁证：官方文档页 `doc_id=125`（老式「概念股分类」接口，字段 `code/name/src`）**现已 404**，只有第三方镜像还留着。
- **裁定＝停采（`enabled=false`，迁移 `0129`），不换 `dc_index`**：
  1. **换 `dc_index` 不是修 bug，是新产品需求**：`dc_index` 输出 15 字段（行情/领涨股/涨跌家数…），本仓 `concept` 表**只有 `ts_code+name` 两列**——schema 装不下，须新建表 + 新 sync_config + 新 handler + 新落库映射，不该挂「修 P1-A」名下。
  2. **停采代价 ≈ 0（零消费者，逐点验过）**：全仓唯一引用＝`data_platform/data_source.py:140` 的限流配置（0.3s）；前端 `web/src` **零引用**、无组件；无 API 端点、无因子、无策略消费。
  3. **消掉的是残余噪音**：P1-B 前它每 300s 触发一次（风暴）；批 90（P1-B）已退避为「每周一 07:00 一次失败+告警」；本迁移再进一步停采，把这条也消掉。
- **连带修（本批新发现的同型缺陷）**：断流检测 `scheduler/tasks.py::_check_tier_freshness` 与指标采集 `health_monitor/collector.py::collect` 原**硬编码遍历 `TIER1_SYNC_IDS`、不查 `enabled`** ⇒ 停采后 `concept_sync`（无 success 行）**永久 stale**（语义噪音）。⇒ 改为**尊重 `enabled`**（已禁用即不参与断流告警/新鲜度指标），并带 **fail-open**（读不到任何 enabled 行退回全量，宁误报不静默——对齐 `_tier_alert_filter` 立法）。
- **过渡态 `TRANSITION-0129`**：`concept_sync` **保留**在 `TIER1_SYNC_IDS`（维持一档 9 表分级语义）+ `enabled=false`。收口条件二选一：① 确认放弃 → 从清单移除（哨兵撤）；② 上游恢复或改 `dc_index` 重设计 → 改回 `enabled=true`（检测自动回归监控）。

### ✅ P1-B（已修并上产 2026-10-03）：异常型失败不推进 `last_sync_ts` ⇒ **每 5 分钟重试风暴**（G-S3 覆盖漏洞）

- **机制**（代码静态可证 + 双向实证）：
  - `sync()` 的 `except` 分支（`engine.py:319-323`）只 `_mark_running(False)`，**不调 `_update_sync_state`**；
  - G-S3 修复（`engine.py:285`，注释明写「调度器以旧 ts 算 next_run 会连发重试」）**只覆盖「handler 正常返回 + failed_dates」路径**，漏了「handler 抛异常」路径；
  - 调度器 `base = last_sync_ts`（旧值不动）⇒ `croniter.get_next` 恒返回已过去的到点 ⇒ **每 300s 触发一次**，无限循环。
- **实证**：
  - 本地（打桩 handler 抛异常）：`sync('concept_sync')` ⇒ `last_sync_ts` **不变**、sync_log +1、status=error；
  - 本地（真调）：耗时 **1159ms**、status=error、`last_sync_ts` 仍停在 2026-09-25；
  - 生产：`data_sync_scheduler` 日志 `triggered: 2` + skipped 列表 20 条（不含 concept_sync）⇒ 未被 skip 的正是 **pool_data + concept_sync**，即 concept_sync **每 5 分钟被调度触发**（24h = 238 轮，吻合）。
- **危害**：触发侧无限重试（本地已积 1873 条 error 行）；`last_sync_ts` 永不推进 ⇒ 调度器永远认为「过期」⇒ 永不停歇。
- **⚠️ 生产执行侧已复验（§3.4）**：上产后 `concept_sync` 首轮触发一次（0.94s 真调）即退避，次轮转 `skipped(未到周期)`——**风暴止于首轮**，生产危害面=「每 5 分钟一次失败调用与告警噪音」，修复后消除。
- **修复（已落 2026-10-03）**：`except` 分支补 `_update_sync_state(sid, cfg["last_sync_date"], 0, "failed")`（游标写回旧值，只刷 `last_sync_ts`）+ `_alert_sync_failure`（异常型此前零告警——正是 P1-A 被埋 1873 条无人知的直接原因）。回补模式沿用「不碰游标/ts」现状（与返回路径 `_advance=None` 同源）。
- **断言组**（`tests/test_sync_cursor.py::TestExceptionPathBackoff`，5 例）：① 异常后写终态（等价 ts 推进）② 游标=旧值 ③ 游标 NULL 时写回 None 不污染 ④ `_mark_running` 顺序 `[True, False]`（G-S2 不回归）⑤ 异常告警 status=failed ⑥ 回补异常不碰游标。
- **真库实证（2026-10-03）**：真调 `concept_sync`（上游 Error 1054 必失败）前后对比——`last_sync_ts` **2026-09-25 → 2026-10-03 12:44（推进 8 天）**、游标 `20260925` 不变、status `idle→failed`、sync_log +1。**修复前该 ts 恒定不变**（=风暴根因）。

### ✅ OBS-1（已修并上产 2026-10-03）：调度可观测性缺陷（**曾卡住 §3.4 的定位**）

- `data_sync_scheduler` 原返回 `{"triggered": len(triggered)}`（**仅数量**），**不打印 id 与 result**。源码里 `triggered.append({"id": sid, "result": result})` 已经带上了 id/result，只是 `return` 时被 `len()` 抹掉。
- **后果（实证）**：生产每轮日志只留「triggered: 2」，无法判断第二个被触发的任务是谁、返回了什么（`skipped`？`error`？），只能靠 skipped 列表反推 ⇒ 本次诊断在此绕了数轮。
- **修复（已落 2026-10-03）**：返回 `{"triggered": [{"id", "result"|"dispatched"}...], "n_triggered": N, "skipped": [...]}`——明细含 id 与 handler 返回值（error 摘要亦在内），保留计数键供聚合/监控。全仓确认无消费方依赖旧整型（消除破坏面）。断言组：`tests/test_sf1_longtail.py::test_scheduler_returns_triggered_detail` + `..._async_dispatch_detail`。

### ✅ 3.4 生产执行侧行为（**已复验收敛，2026-10-03 上产后**）

- **原观测**（`quant-journal` 只读日志，24h 窗）：238 轮里 3 轮 >0.5s（1.38s / 1.68s / 15.59s）、其余 235 轮 0.15–0.22s；本地同代码真调需 1159ms ⇒ 曾疑 `SyncLock` 被间歇占用（`engine.py:248` 秒回路径）。
- **收敛结论（OBS-1 上产后实测）**：真因是 **P1-B 的 ts 不推进** ⇒ 每轮恒到点、恒触发；被触发后 handler 行为分两类（真调 ~0.9s / 快速失败 ~0.2s），**并非锁占用**。
  ```
  21:33:42  n_triggered=2  triggered=[concept_sync{...}, pool_data(async)]   0.94s  ← 真调
  21:38:41  n_triggered=1  triggered=[pool_data(async)]                      0.04s  ← concept_sync 落 skipped(未到周期)
  ```
- **修复后行为**：21:33 触发一次失败 ⇒ 20261003 `last_sync_ts` 推进 ⇒ 21:38 起 `concept_sync` 恒 `skipped(未到周期)`，直到下个 cron 点（周一 07:00）——**风暴止于首轮**。
- **遗留（不阻塞）**：旧代码下 235 轮 0.2s 秒回 vs 3 轮真调的差异，随修复失去复现场景，未再深追。
