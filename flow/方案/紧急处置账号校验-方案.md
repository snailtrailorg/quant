## 3. 重发设计（v5 核心 · 两条 P0 的正解）

### 3.1 幂等锚（跨 worker 重启）

**用现成 Redis 回执键，不用内存表**：
- `RISK_RESULT_KEY = risk:cmd:result:{req_id}`（`trading.py:376`，TTL 10min）；
- `RISK_FINAL_KEY = risk:cmd:result:{req_id}:final`（`:377`，TTL 30min）；
- 两键由 `write_cmd_result(req_id, result, final=)`（`trading.py:565-579`）写，worker 重启仍在。

**状态机（单源，用回执键承载 phase）**：
1. web 首次下发：`SET RISK_RESULT_KEY = {"phase":"dispatched", ...}`（新增 `write_cmd_ack(req_id)`，
   TTL 10min），再 `SET risk:cmd:{tid}`（含 req_id）；
2. worker `GETDEL` 取命令 → 执行前**原子**检查回执键：
   - `phase == "executing"` 或已有最终结果 ⇒ **不执行**，只把现存回执重写一遍（重发 = 重查）；
   - `phase == "dispatched"` ⇒ 原子改为 `"executing"`，再执行；
3. 执行完成：`write_cmd_result` 写真实结果（覆盖 phase）；
   close-all 另写 `:final`；
4. worker 崩溃在 executing：重发看到 executing ⇒ 不重跑、明示"未确认，需人工查持仓"——
   **宁可不执行，也不重复平仓**（XTP 异步持仓未回更时重复卖单=超卖，正是 171o A-P1-4 要防的）。

### 3.2 重发契约（端点 / 请求体 / 触发点）

- **端点**：`POST /api/risk/retry`（perm=`halt`）；
- **请求体**：`{"verb": "close-all"|"cancel-all", "req_ids": {"<tid>": "<req_id>"}, "skipped_accounts": [...]}`；
  `req_ids` 直接来自首次下发的响应（`risk.py:400` 已返回 `req_ids` 映射），**不新生成 req_id**；
- **服务端**：按映射重新 `SET risk:cmd:{tid}`（同 req_id、同 verb/operator），
  cmd 载荷带 `skipped_accounts`；返回 `{"status":"dispatched","req_ids":...}`；
- **FE 触发点**：`onCloseAll`/`onCancelAll` 收到 `status=dispatched` + `pending_runners` 时，
  显示「重试未确认命令」按钮；点击调 `riskRetry(...)`，
  **禁止再走 `riskCloseAll`/`riskCancelAll`**（那会 `uuid4()` 新 req_id）；
- **上限**：重发 N 次（配置项，建议 2）仍无回执 ⇒ 明示"未确认"，交人工，不无限重试。
