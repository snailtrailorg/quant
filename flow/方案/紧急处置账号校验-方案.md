## 0. 三问（前置 · v4 更新）

1. **真源层**：分两个语义，不再混用——
   - **下发判活**（本方案）= `live_task.status='running'`（DB 行集，**不看心跳**）。
     理由：心跳停通常意味着进程忙/卡/队列堵，而这正是最需要急停的时刻；
     用心跳拒绝下发＝越危险越失灵。
   - **展示健康度**（保留现状）= `risk_exposure.running`（DB running ∩ 心跳 30s），
     只用于页面显示"进程在但心跳老"，**不参与是否下发命令的判断**。
2. **全部消费者**（逐个核实，v4 补回执/重发面）：
   - 前端勾选/投影/提交：`Emergency.vue:4/221-225/235/267`、`utils/emergency.js:3`
   - 后端预校验与分叉：`risk.py:326-343`（DB-only 预校验 + `:337` 判定）
   - **下发枚举（新）**：`config_store.live_running_tasks()`（`config_store.py:176-182`）——
     v4 把它从"被否定的错误口径"提升为**急停下发的正确口径**
   - 命令载体与去重：`risk.py:362-366`（写 `risk:cmd:{tid}`，TTL 10min）、
     `hub_worker.py:47-55`（**GETDEL 取命令——取走即删**）
   - 回执与终局：`risk.py:279-294`（回执聚合）、`:378-400`（5s 回执窗 / pending）、
     `risk.py:512-566`（`:final`/recent 端点）、
     `hub_worker.py:242-311`（worker 写主回执 + `:final`）
   - 手工下单（**不在本方案范围，但不得破坏**）：`risk.py:594/600` 仍用
     `_live_runners`（DB ∩ 心跳），`tests/test_manual_order.py:62/84`
   - 回执渲染：`Emergency.vue:103-136`（`fmtResult`）/`:147-168`（`fmtFinal`）
   - 审计：`risk.py:389-390`；文案：`locales/index.js:1180/2645/4416`、`api.js:30-39`
   - 测试：`test_batch171o.py:75-82`、`test_batch171n.py:262-282`
3. **既有机制**：
   - `live_running_tasks()` 现成就是"DB running 行集"——**回归它作为下发判活**；
   - `GETDEL` + `req_id` + 5s 回执窗 + `:final`/recent + FE 短轮询**都已存在**——
     重发要复用这套，不另造通道；
   - **缺口**：worker 无 `req_id` 去重，web 无重发逻辑——这是 v4 必须补的两处。

## 3. 新裁定语义

1. **下发**：`accounts` 勾选集 ∩ `live_running_tasks()`（DB running 行集）→ 对每个 tid 下发命令。
   **不看心跳、不看 `exposure.running`**。
2. **未处置明示**：勾选集 − 下发集 = `skipped_accounts`，原因 = "无运行任务"（新裁定下
   不再有"心跳死"这一原因——因为心跳根本不参与下发判定）。
3. **回执定结果**：5s 窗内收到回执 → 汇总结果；未收到 → `status=dispatched` +
   `pending_runners`，FE 按 req_id 短轮询。
4. **重发（幂等铁律）**：
   - **复用同一 req_id** 重发命令（`risk:cmd:{tid}` 用同 id 重新 set）；
   - **worker 侧新增已处理 req_id 去重表**（内存 + TTL 10min，与 cmd TTL 一致）：
     命中已处理 id ⇒ **不重复执行**，直接重写原回执（结果缓存于去重表）；
   - 重发上限与间隔配置化（建议 2 次 / 每次间隔按现有 5s 回执窗），
     超限仍未回执 ⇒ 明示"未确认"，交人工，**不无限重试**。
   > 不做"换新 req_id 重发"——那会让平仓重复下单（违反 171o A-P1-4 按账号去重防双发的立法）。
