## 3. 重发设计（v6 核心）

### 3.1 幂等：独立 phase 键，绝不与回执键共用

- **键**：`risk:cmd:phase:{req_id}`（**新建**，TTL 30min），值 = `dispatched` / `executing` / `done`；
- **为什么独立**：`risk:cmd:result:{req_id}`（`trading.py:375`）会被 web 轮询 `risk.py:384-387`
  GET 后 **DELETE**——共用会导致首轮把 phase 当结果吞掉、锚被删（v5 P0）；
- **流程**：
  1. web 首次下发：`SETNX risk:cmd:phase:{req_id}=dispatched`（TTL30min）→ `SET risk:cmd:{tid}`；
  2. worker GETDEL 取命令 → 执行前对 phase 键 **Lua/GETSET 原子翻转**：
     - `executing` 或 `done` ⇒ **不执行**，只把既有回执/`:final` 重写一遍（重发=重查）；
     - `dispatched` ⇒ 翻 `executing`，执行；
  3. 执行完成 `write_cmd_result`（主回执 + close 的 `:final`），phase 写 `done`；
  4. worker 崩在 executing：重发见 executing ⇒ 不重跑、明示"未确认，需人工查持仓"——
     **宁可不执行，也不重复平仓**（XTP 异步持仓未回更时重复卖单=超卖）。
- **web 轮询不改语义**：仍 GET+DELETE 回执键拿首轮结果；**phase 键不参与、不得删除**。

### 3.2 重发契约（端点 / 触发 / 持久化）

- **端点**：`POST /api/risk/retry`，**`Depends(require_perm("halt"))` 包裹**（路由守门强制）；
- **请求体**：`{"verb": "close-all"|"cancel-all", "req_id": "<原 req_id>", "tid": "<原 tid>", "skipped_accounts": [...]}`——
  **复用原 req_id，禁止新建**；
- **服务端**：按 tid 重 `SET risk:cmd:{tid}`（同 req_id、verb、operator），cmd 载荷带 skipped；
  返回 `{"status":"dispatched","req_id":...}`；audit_log 记重发次数；
- **未确认持久化（解决 P1-6）**：下发时写 `risk:cmd:pending:{uid}`（list of
  `{tid, req_id, verb, skipped, ts}`，TTL 30min）；新增 `GET /api/risk/pending`（halt 键）供 FE
  刷新后重建重试入口；成功回执到达后从 list 移除；
- **FE 触发点**：`onCloseAll`/`onCancelAll` 收到 `status=dispatched` + `pending_runners` ⇒
  显示「重试未确认命令」按钮 → 调 `/api/risk/retry`（**禁止再走 close-all 新 req_id**）；
  页面刷新后由 `/api/risk/pending` 重建该按钮；
- **上限**：重发 N 次（配置项，建议 2）仍无回执 ⇒ 明示"未确认"，交人工，不无限重试。
