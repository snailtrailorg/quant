## 题面（三问，作答时不看标准答案）

**问题 1**：一次发布分几步、每一步谁在守（什么机制保证每步不出错/出错过不了关）？

**问题 2**：改依赖、改 wrapper、改 nginx 配置，各要动哪些文件、各要跑什么闸门/动作才算安全？

**问题 3**：发布到一半失败了，会发生什么？（分「切换前」与「切换后」两种情形说明）

---

## 标准答案（验收员持）

### 问题 1 标准答案

发布两步走：**先彩排（staging）后上产（prod）**——staging 与 prod 同路径同权限同配置，staging 绿了 prod 大概率绿。

一次发布内部的阶段与守门人：

1. **preflight 预检**：交易窗（盘中拒绝启动）、磁盘余量、前端构建、wrapper 在位等断言——**零触碰目标机**，不过即停。
2. **切换前段（同步→编译→导入冒烟→DDL 门→装依赖→迁移）**：破坏性 DDL 门拦危险迁移、pip dry-run 拦坏依赖、导入冒烟拦语法错——**守门者是各阶段自身**，炸了删半成品即停，线上未动。
3. **切换后段（翻链→波次重启→验证）**：dwell 稳定窗盯单元连续稳定、healthz/readyz 探活、**版本收敛断言终判**（所有进程必须都在跑新版本）——不过则**自动回滚**（指针拨回上一版+重启+复验）。
4. **退出码**：失败一律非零退出+告警——**CI 门不吃假绿**。

（加分项：波次顺序 web→celery→feishu→task→hub 不可乱；GC 只在成功路径跑。）

### 问题 2 标准答案

| 动作 | 要动的文件 | 闸门/动作 |
|---|---|---|
| **改依赖** | `server/requirements.lock`（+`requirements-dev.txt` 工具链） | lock **必须带 hash**（`--require-hashes`，丢 hash 被 pip 预检拦停）；dev 文件须进 `deploy_slices`+同步白名单（双写），否则 venv 永不装、扫描恒 degraded。改完正常走彩排→上产即被 req_changed 指纹捕获 |
| **改 wrapper** | `deploy/wrappers/quant-*` 本体；动白名单时连带 `sudoers-quant-deploy.j2` | **不进 release 管道**——仓库改了不等于机上生效，须 **michael 重跑 bootstrap 装位**（手工 install=违规）；staging 与 prod 双机各装一次；SQL 相关须过 `test_deploy_blast_radius.py` |
| **改 nginx conf** | `server/scripts/nginx/quant.conf`（模板真源）；同步到服务器 `/etc/nginx/conf.d/quant.conf` | **管道外输入**——手工替换+`nginx -t`+reload+四安全头 curl 核验；勿启用 security-rules.conf（伤探针与 DELETE 端点） |

共性纪律：**改任何输入前先查 A06 §11 输入→消费者地图**（每行=输入×下游×必查×闸门），查表可得全部下游。

### 问题 3 标准答案

- **切换前失败**：自动删掉本次半成品目录（releases/<新id>/），**立即停止——线上完全没被碰过**。唯一残留：venv 可能已装入新依赖（无害）。若 DDL 豁免实际生效（allow_contract 放行过破坏性迁移）则 staged 保留、转人工处置——不自愈、显式化。
- **切换后失败**：**自动回滚**——把 server/web 链接拨回上一版 → 重启受影响的服务波 → 再验证一遍 → 退出码非零+告警。**注意：数据库 schema 不自动回退**（代码回旧版、schema 留新版）——成立前提是 expand-only 迁移纪律，破坏性迁移被切换前的 DDL 门拦住。
- 盘中（交易日 08:55-11:35 / 12:40-15:05）启动被闸拦；紧急可 `-e force=true`（自担风险、留痕）。
- **回滚成功 ≠ 万事大吉**：进程 crash 后被 systemd 拉起会解析新链接自动滚到新版——收敛断言就是防这个的终判。
