### P1-1 · break 分支注释失实（pool_reconcile.py:214-215）

注释宣称：「日历失效（陈旧守卫返原值）——**不回退**，宁可误报不静默」。实证行为不符：

- `_nearest_trade_day` fail-open 三态（无行/异常/陈旧守卫）**全部返回原值 upper_str，从不返回 None**（pool_data.py:144-158）。
- 回退循环输入恒为 `tbl_expected` 前一自然日 s；日历失效时 NTD 返 s 本身，`not prev` 为假、`prev >= tbl_expected` 也为假（s < tbl_expected 恒成立）⇒ **不 break，tbl_expected 被回退到前一自然日**——与「不回退」宣称相反。
- break 两条件实际均不可达（NTD 返值恒 ≤ 输入 < tbl_expected）：break 是死代码。
- 功能定性：无危害。日历失效场景下 expected 本身已是原值（废锚），回退自然日与否都在误报面内、方向一致。**危害在误导**：注释宣称了一个不存在的守卫语义，后续维护（尤其 lag>1 扩展时）会据此错判。
- 修法（二选一）：① 删 break+注释，如实写「NTD fail-open 返原值 ⇒ 回退自然日（废锚场景，与 expected 同废）」；② 真实现守卫：`if prev == <循环输入>（NTD 返原值即日历失效）: break`。推荐①（简单、与实际行为一致）。

### 判定：**有条件过门**

条件=P1-1 注释修正（一行注释改动，随批带上）。逻辑本身正确、测试钉有效、消费面干净。

### P0-1 · requirements.lock 丢失 `pillow==13.0.0 ; python_version >= "3.11"`

**事实**（git show HEAD vs 工作区全量 diff）：
- HEAD（批 139，64cff03）：lock 含双 pin——`pillow==13.0.0 ; python_version >= "3.11"`（83 行 hash 块）+ `pillow==12.3.0 ; python_version < "3.11"`。
- 工作区（本次 lock-sync.sh 重编译）：**仅剩 12.3 档**，13 档整块消失。requirements.txt 的 Pillow 双行声明未动。
- 根因推断：lock-sync.sh 用控制机 3.10 venv 的 pip-compile 重编译——`>=3.11` marker 分支在 3.10 解释器下不适用被剔除。批 136/139 的双 pin lock 是当时双 dry-run 工序（含手工/半手工）保住的，本轮全量重编译冲掉了。

**后果链**：
1. 本次上产**不立即爆**：pip 对 marker 不匹配的行只是跳过（不装不卸），prod venv 现有 pillow 13 保持不动；且部署管道对 pillow 无直接断言。
2. **lock 作为「venv 重建自包含真源」已损坏**：未来 bootstrap/venv 重建在 prod 3.11 上将**不装任何 pillow** ⇒ akshare/tushare/jqdatasdk/vnpy/weasyprint 依赖链全断。
3. **批 136 安全修复静默丢失**：pillow 13 的图像解码 CVE 修复在重建后消失——正是批 136 血证「安全修复假绿」的镜像形态（那次是版本钉旧、这次是整档蒸发）。

**闸门为何没拦**（test_requirements_lock_consistency.py，19 例全绿——实测复现盲区）：
- 包名闸门：只比名字存在性，pillow==12.3 在册 ⇒ 绿。

**修法**（上产前必须）：
1. 补回 13 档 hash 块：`git show 64cff03:server/requirements.lock` 的 2154-2240 行整块恢复（brotli 块不受影响，与本次新增行无交叠）。
