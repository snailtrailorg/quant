## 发现

### 批 145

**P0-145-1 · bind=True 与「签名不变」自相矛盾，字面实现=任务每小时崩**
- 问题一句话：产出 1 要求装饰器改 `bind=True, …`，接口契约节又承诺 `data_continuity_check() -> dict` 签名不变——bind=True 时 celery 以 bound task 调用 `run(self, …)`，函数保持零参签名 ⇒ 每次触发 TypeError。
- 锚点：任务文件产出 1 + 接口契约节；现码 tasks.py:550-551（零参 def）；仓内 bind 先例（:640/:713/:892）全部带 self 参数。
- 修法建议（二选一）：① 去掉 bind=True，只加 `soft_time_limit=2400, time_limit=2700`——与本批自引先例 data_gap_reconcile（tasks.py:1723-1724，**无 bind**）同制，改动最小；② 保留 bind=True 但签名改 `def data_continuity_check(self) -> dict` 并同步接口契约节。推荐 ①。
- 定级理由：实现者忠实照任务文件做（只改装饰器行）即产运行时崩，属「会导致错误实现」。

**P2-145-1 · 现状机制表述方向反了**
- 问题一句话：现状 #2「任务代码未捕则直达完成」应为「被体内 except Exception 捕获（SoftLimitExceeded 继承 Exception）⇒ 记 issue 继续跑完」；未捕获才会 failed。
- 锚点：任务体多处宽 except（tasks.py:576/:630/:677 区域）；实证 29 次告警零失败支持「被吞继续」。
- 修法建议：改一句表述；不影响结论与修法。

### 批 144

**P1-144-1 · last_sync_ts 的第二消费面未论证（next_run base）**
- 问题一句话：调度器 cron base 同样读 last_sync_ts（tasks.py:823 `base = last_sync_ts.astimezone(TZ_CN)`），任务文件未论证刷 ts 对它的影响。
- 锚点：tasks.py:823；running 分支 :782 起 continue 在 cron 计算之前。
- 修法建议：任务文件现状表或产出补一句「已核：last_status='running' 行在僵尸判定段 continue（tasks.py:782-805），cron base 计算（:823）不可达 ⇒ 运行中刷 ts 对 next_run 无影响」。（本人已实核该结论成立——running 行恒 continue，修法与 next_run 无冲突；补论证是防后续者在非 running 路径扩大刷 ts 面时无案可查。）
- 定级理由：结论不受影响但方案未闭合该交互面，一行补齐即消。

### 批 146

**P1-146-1 · 空 pk 交集 ⇒ drop_duplicates(subset=[]) 直接 ValueError**
- 问题一句话：产出 1 的容错「pk 缺列容错=交集，防上游再改版」在交集为空时自身崩——pandas 2.3.3 实测 `df.drop_duplicates(subset=[])` 抛 `ValueError: not enough values to unpack`。
- 锚点：任务文件产出 1；实测命令（本机 venv pandas 2.3.3）。
- 修法建议：`inter = [c for c in pk if c in df.columns]; df = df.drop_duplicates(subset=inter, keep="last") if inter else df`——交集空时跳过去重，让后续 INSERT 形状层 fail-loud（错误归因更准），本批两键（namechange 3 列健在/concept 窄投影保证 ts_code 在）均不触发该分支。
- 定级理由：目标场景闭合，边界（上游彻底改列名）按现方案仍崩且崩因更晦涩（ValueError 而非形状错误）；fail-loud 不劣化数据，故 P1 非 P0。

**P1-146-2 · C_STALE_DAYS int→dict 只写了判定处，:231 文案行必崩**
