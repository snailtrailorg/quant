## 严重（P1）

### P1-1（批 112）探针 `actual` 的 schema 域未钉死——`table_schema='public'` 是静默漏检的分水岭

- `verify_schema`（`db.py:434-437`）的 `actual` 显式 `WHERE table_schema='public'`，这才是防漂移的关键；任务书产出 1 只写「与 information_schema.columns 做 expected ⊆ actual」，**未钉 schema 域**。
- **可复现构造**：库中残留 `chain_scratch`（生成命令 `db.py:394` 建后若未 DROP）或任何非 public schema 同名列 ⇒ 探针若不带 `table_schema='public'`，`actual` 取并集 ⇒ 被删列误判 `ok` ⇒ **false compatible = 静默漏检（恰是批 84 要治的病）**。
- 任务书「复用解析」只复用 txt 格式解析（`" :: "` 切分，`db.py:408-411`），**schema 域在查询里、不在解析里**——引用的批 84 有「同构 verify_schema」四字，但产出 1 正文未携带。须在契约中钉 `WHERE table_schema='public'`。

### P1-2（批 112）「复用 verify_schema 解析」表述失实——探针是 bash/psql wrapper，不能直接调 in-process 函数

- `verify_schema` 是 `src/data_platform/db.py` 内进程函数（吃 `get_conn`/整 app 栈）；`quant-hbcheck` 是 bash wrapper（`sudo -u quant` + psql peer 通道，见 wrapper 头）。**两条腿不同**：要么 bash/psql 重写解析（格式极简、可做），要么嵌 python heredoc import app 栈（脆弱，违背 wrapper 最小依赖）。
- 结论：可行但**是重写一套解析、非复用**；任务书「复用这个解析」过度承诺，编码期定位会漂。须写明落点＝bash 解析 或 独立 python 脚本（复用格式），并补 `schema_expectations.txt` 缺失时的 fail-closed 语义（见 P1-3）。

### P1-3（批 112）探针对「期望文件缺失」语义未定义——默认可能 fail-open

- 回滚到极旧 release（无 `schema_expectations.txt`）时，探针无清单可比。若缺省 rc=0（「无可检」当「兼容」）＝**跳过校验**，同病根。`verify_schema` 对缺失是 `expectations_missing: True` 哨兵（fail-soft），但探针契约「有 miss 才 rc≠0」未覆盖「文件缺失」分支。须钉：文件缺失 → rc≠0 + 「无法校验，须人工」。
