判据：八步法步 1/2、任务模板、D27、decisions.md 2026-10-10 两条立法。只读评审，全部锚点实开文件核对。

## 总评

方向正确（消静默错误、声明驱动供给、糖兼容），现状表 7 条锚点全部实证为真，无编造前提。
但**核心语法 needs: dict 在最大用户面（Web 自定义因子）无持久化闭环**——契约不闭合，P0 一枚须返工修订；
另有词汇漂移（bar_1d/static 非 DataKind 词）、回测一致验收不可执行、拒启/冷启动边界未定死等 5 项 P1。

## 致命（P0）

**P0-1 needs 声明无持久化闭环——自定义因子路径断裂，重启后静默降级单频糖**
- 证据链：`factor_def` 列＝`id,name,category,description,code,params,created_at,updated_at,needs_history:int,type`
  （`schema_expectations.txt:38`，无 needs JSON 列）；写侧 `register_custom_factor(..., needs_history: int)`
  （`factor.py:241`，INSERT/UPDATE 只写 int，`factor.py:284/290`）；重载侧 `load_factors_from_db`
  （`factor.py:188-236`）只读 needs_history int 进注册表；Web 校验 `_int_or(needs_history, 0, 5000)`
  （`web_api/routes/strategy.py:244/358`）。
- 构造复现：用户经 Web 创建 `needs={"bar_1d":60}` 自定义因子 → 无列可存（或塞 params 污染 compute
  命名空间——spec 未裁定）；runner 重启 `load_factors_from_db`（`main.py:337`）重建注册表 → needs dict
  丢失 → 聚合只见糖映射 bar_minute。**多维声明对 DB 因子静默失效——正是本批要消灭的静默语义丢失形态**。
- 产出/限定范围列了 factor.py 但未列 alembic 迁移与 Web 路由改造，也未显式把自定义因子划出范围。
  修法（任选其一，须用户裁定）：① factor_def 加 needs JSON 列（迁移+写/读/Web 三侧）；
  ② 显式 de-scope「本批仅预置因子可多维声明，DB 因子沿用糖」写进限定范围与验收。

## 严重（P1）

**P1-1 needs 键词汇漂移＝第二真源风险**：产出/验收用 `"bar_1d"`、`"static"`（表名列表），DataKind 词表
（`contract.py:25-40`）是 `bar_daily`/`static_list`；同一 bullet 内自相矛盾（「对齐
KIND_TEMPORALITY["bar_daily"]」却写 `needs["bar_1d"]`）。须钉死：needs 键≡DataKind 字面量，或给单源映射表。

**P1-2 回测一致验收不可执行**：引擎存在（`backtest.py:131`；入口 `scheduler/tasks.py:1049`）——非编造前提；
但回测管道**只喂日线**（`tasks.py:1092-1094` kind="bar_daily" freq="1D"），实盘喂 1min。bar_minute 因子
「回测/实盘首算值逐位一致」在现管道上不可达；「同一暖机函数复用**或同构实现**」的"或"是逃生舱，钉子无构造
（无 pytest 路径/无 fixture/未定义"首算"取哪根 ts）。违反八步法「验收可验性预审」。

**P1-3 拒启/冷启动边界未定死 + 退出码档位错配**：产出 3 同一谓词（实际供给<声明）在「启动⇒拒启 EX_CONFIG」
与「首算前⇒告警+degraded」两处并存，时序上首算紧随启动，边界判据缺失；验收「三分支（足/不足/超声明）」
分支语义不明。EX_CONFIG＝永久配置错不重启（`main.py:41`），而新标的日线未同步是**瞬态数据滞后**——
构造：新上市标的 T 日、bar_1d 同步滞后，needs={"bar_1d":60} 任务每日 EX_CONFIG Failed 人工——
decisions.md 2026-10-10 立法同型病（闸门开合取决于数据管道启动时序）。数据完整性归同步层告警体系，
不归启动闸门代偿（立法第 4 条）。

**P1-4 现状"两处常量"漏计，真源化范围不全**：100/窗常量实际≥4 处——`main.py:80`（默认 100）、
`main_worker.py:256` 之外还有 `main.py:96`（`[-min(n,500):]` 500 帽）、`hub_worker.py:245`
（xrevrange count=240）、`hub_worker.py:403`（环形 `len>100 pop`）。needs>500 时 PG 侧恒供给 500
（30 天窗内 1min 约 5 千根，500 帽是绑定约束）→ 启动闸门会响亮拒（不静默）但 needs∈(500,5000]
（Web 允许 5000）永不可启，spec 未裁定（扩帽/声明期校验拒）。

**P1-5 范围与契约缺口**：限定范围 5+ 改面（factor/strategy/main/hub_worker/回测/bar_1d 通道）违模板
「≤3 文件」硬约束，未声明拆批或偏离理由；「叠加策略自身声明」的声明语法未入接口契约；needs 未知键
（拼错如 "bar_1min"）的校验行为未定义——不定义即静默不供给＝回退到静默错值老路。

## 一般

- 步 1 四要素之「回滚」未写（糖兼容+默认 100 零漂移即天然回滚面，宜一句话写明）。
- daily_history/static 刷新节奏未定（盘中随 rewarm 刷？日界沿才刷？——影响首算一致钉口径）。
- 性能：`hub_worker.py:396` 每 bar `list(history)` 浅拷贝 O(n)，n=500 量级 µs 级、dict 引用共享，
  非阻塞；扩窗不放大复制语义（浅拷贝引用不复制 dict）。BarContext 构造同量级。结论：性能不构成改动理由。
