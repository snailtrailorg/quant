## P0

**P0-1 特权命令通道缺失（采集器核心功能在 prod 不可用）**
- 任务文件 §产出 1 列出 `dnf --security`、`sshd -T`、`ss -tlnp` 三类命令，但采集器随 celery worker 跑（`quant-celery-worker@quant`，quant 用户），**只字未提执行通道**。
- 实证权限边界：`deploy/wrappers/` 12 只特权 wrapper（alembic/dbro/flip/pip/svc 等）无任何 dnf/sshd/ss 通道；`server/scripts/systemd/49-quant.rules` polkit 只放行 `quant-live-task@*`/`quant-feishu-bot@*`/`quant-md-hub@*` 三族 unit 管理——**无 dnf/polkit-1 通行证**。CLAUDE.md 铁律「禁直接 ssh」，服务器操作唯一通道=ansible。
- 逐命令评估（可降级路径存在但方案必须显式声明）：
  - `dnf --security`：需 root。降级可行——quant 用户可读 repo 元数据缓存时 `dnf --security --cacheonly check-update` 仍需读 /var/cache/dnf（默认 root:root 755，子目录不可读，**大概率仍失败**）；更稳路径：由部署管道（Ansible root 面）定期落一份安全更新计数文件，采集器只读该文件（采集/特权分离，符合三权分立）。
  - `sshd -T`：需 root（且多数版本要求 -C 连接参数才输出完整）。降级可行——直接解析 `/etc/ssh/sshd_config` 文本（全局可读 644），grep PasswordAuthentication/PermitRootLogin 两键即可，语义足够（有效配置=文件+include，本机审计同口径）。
  - `ss -tlnp`：`-p` 显示进程名需 root（非 root 下 process 名列为空，**静默丢进程归属**）。降级可行——`ss -tln` 不带 -p 对监听端口清单零损失（端口/地址全在），进程归属本来也不是基线 diff 判据（判据=端口集变化）。
- 结论：**P0 设计缺口**——三条命令均有降级路径，但任务文件必须改写为降级方案+显式声明权限边界（W6 制度符合性），否则步 3 编码时必然撞墙或静默产出空数据（违反八步法「超时必须可观测」同族的静默落空禁令）。

**P0-2 pip-audit prod 可达性：依赖声明不实 + 网络行为未定义**
- 任务文件锚点 3 称「pip-audit 已装（本机 venv）」——措辞已限定本机，但 §产出 1 直接把「pip-audit 输出」写成 prod 每日采集项，而 `server/requirements.txt` 全文 grep **无 pip-audit**（prod venv 不装，部署管道 release.yml 阶段 2/5 只认 requirements.txt/lock——不加依赖装不上）。**采集项引用了 prod 不存在的工具**。
- 本机实测（2026-10-11）：`./venv/bin/pip-audit -r requirements.txt --format json` 在 120s timeout 内**未完成**（exit 124，无输出）——OSV 在线逐包查询对 486 行 lock 的依赖解析+网络往返远超 beat 任务全局 `task_soft_time_limit=300`（app.py:132）的一半；且 prod 服务器外网可达性与本机不同（OSV=Google 域，大陆网络环境存疑）。任务文件**无网络依赖声明、无超时/失败语义**（fail-soft 只写了 LLM，未写 pip-audit 网络失败时是「空结果」还是「任务失败」——pip-audit 网络异常默认非零退出+stderr，若采集器吞掉错误落空表=把证据缺失当零漏洞）。
- 修法（返工须落进任务文件）：pip-audit 进 requirements-dev 或独立工具链+采集器探测二进制存在性；显式声明 OSV 网络依赖+失败语义（失败=当日漏洞分区标 unavailable+告警一次，绝不落「0 漏洞」假象）；评估在采集器内 per-call timeout（如 subprocess timeout=240）+ 全局软限独立声明（同批 110 data_gap_reconcile 显式 1800/1980 范式，tasks.py:1719 有现成立法先例）。

## P1

**P1-1 severity 数据源未定义，验收条款不可执行**
- §产出 5-C 与验收「severity 降序/分色」依赖 severity 列，但 pip-audit 默认输出无 severity（Name/Version/ID/Fix）——OSV JSON 有 severity 数组但 pip-audit 不透出；dnf --security 输出亦无 severity。任务文件未写 severity 从哪来。三选一须裁定：a) OSV API 逐漏洞单查（网络+限速，叠加 P0-2 风险）；b) 本地映射表（第二真源，违反本批「不重复造 CVE 库」自身立法）；c) **弃 severity，改 first_seen 停留天数排序**（数据全在本表，零新增依赖，推荐）。不裁定则 C 区/置顶逻辑/A 区分色点三处验收全部悬空。

**P1-2 AI 摘要注入面与渲染面未声明**
- 注入：CVE 描述/包名（外部数据，OSV 描述含任意文本）直接入 prompt，任务文件未提注入防护；LLM 摘要员虽无工具权限（判定归确定性规则已立法，缓解），但输出含「建议动作」文本，注入可诱导错误建议。
- 渲染：`ai_summary` 前端展示方式未声明——仓内先例 AIChat.vue:54 是「v-html 前全程 HTML 转义」自制 mini-md；安全 Tab 若复用必须显式引用该范式，若纯文本必须写明。安全页自身被 XSS 是最讽刺的失效模式，契约里应有一行。

**P1-3 新增包告警抑制缺失：正常部署将每日误报**
- 部署管道 release.yml 阶段 2 判定 requirements 变更即 pip 真装（app.py 附近 tasks 亦有 pip-wrapper 先例）——**每次带依赖变更的部署次日必触发「新增包」告警**，违反自身「静止绿不扰民」目标，狼来了效应会淹没真实漂移告警。仓内已有 `requirements.lock`（486 行）可作比对真源：venv 实测包集 vs lock 允差（部署后未跑 pip 的窗口期）或部署指纹（release 版本号）标注「预期变更」。任务文件未提任何机制。
