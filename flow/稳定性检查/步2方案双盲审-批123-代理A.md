# 批123 方案双盲审 · 代理A（2026-10-14）

评审对象：`flow/任务/批123-漏洞源重构.md`。判据：八步法步1/2、任务模板、仓内注册先例、
security_collector/0145/A07 现状。全部结论带一手证据。

## 总评

方向正确（severity 正道/台账一等表/插件注册制=仓内惯例），但方案有一个 **P0 级通道死锁**：
装机通道以「本机网络好时下载」为前提，而 2026-10-14 实测**本机 GitHub 同样不可达**，
方案未给任何备选通道与解锁判据——步骤 3 的「grype 装机」在当前网络态下不可执行，
验收 1（prod 一轮扫描）全部下游塌陷。P0 不闭门不得进编码。

## P0

### P0-1 装机通道死锁：唯一通道前提失效，无备选、无解锁判据
任务文件§二.1 全部装机动作锚在「本机（网络好时）下载 grype/syft linux_amd64 tar.gz」
（批123文件:24）。实测（2026-10-14 本机，多轮）：
- `github.com`/`objects.githubusercontent.com`/`grype.anchore.io`/`anchore.com`/
  `toolbox-data.anchore.io`/`release-assets.anchore.io` 全部 000（连接不可达）；
- spe 代理通道同断：`spe curl -v https://github.com` → `socks5://localhost:12345
  connect refused`（代理后端 127.0.0.1:12345 未监听——代理本身也挂）；
- ghproxy 类中继（mirror.ghproxy.com/gh-proxy.com/ghfast.top）全 000；
- 通的只有：`mirrors.aliyun.com` 301/200、`gitee.com` 200。
即**当前网络态下「网络好时」这个前提在本机不成立**，且 anchore 自有域名不放二进制
（grype.anchore.io 是文档站，404 探查记录在案），grype 官方分发唯一渠道就是 GitHub
releases——没有「绕开 GitHub 的官方替代源」。方案缺三样：① 备选通道（gitee 镜像仓/
网络恢复窗口/可联网第三方机）；② 通道就绪的可验证判据（如 `curl -I
https://github.com` 200）；③ 通道不可达时步骤 3 的重排规则（迁移/wrapper 补采/前端
修正先行，装机解耦）。**修法**：§二.1 补「装机前置闸」小节，装机步与其余施工步解耦，
其余步骤不被装机阻塞（迁移 0146+dnf 补采+前端修正均不依赖 grype 二进制）。

## P1

### P1-1 `syft scan dir:<release>` 扫错对象：venv 不在 release 树内
§二.2 说 SBOM 覆盖「venv site-packages + rpmdb 一体」，但扫描目标是
`dir:<release>`。实测布局：venv 在 `shared/venv`（管道外，inventory/group_vars/
all.yml:18「shared/.env 与 shared/venv 管道外」；DEPLOY.md:69 shared/ 与 releases/
同层），release 树白名单只有 src/migrations/scripts/requirements*/vendor
（all.yml:23-32）。即 **dir:<release> 根本扫不到 site-packages**——实际会扫到的
Python 证据是 `requirements.txt`/`requirements.lock`（**声明≠已安装**，SBOM 语义失真：
lock 声明 155+ 包但 venv 实装 192 dist-info，且 pip-audit 线已在扫 lock，等于重复源）
+ src/ 源码树（无 setup.py/pyproject，仅 ruff.toml——syft 不会产包清单）。本机
server/venv 实测：`site-packages/*.dist-info` 192 个、egg-info 0、egg-link 0——
syft 对 Python 的识别正是靠 dist-info METADATA/RECORD（目录凭证），扫
`dir:.../shared/venv/lib/python3.11/site-packages` 才能得到真实已装包集。
**修法**：§二.2 扫描目标改为显式双目标：`syft scan dir:<shared>/venv/lib/python3.11/
site-packages`（pip 层）+ rpmdb（OS 层 syft 自动发现），release 树不进扫描面；
版本路径 python3.11 用解析式获取（模板律：环境事实禁硬编码）。

### P1-2 severity 词表映射未定义：RH 词表≠CVSS 词表，真源悬空
§二.4 只说「增采 errata severity 写入 finding（source='dnf' 行补 severity）」。
dnf errata 用 RH 词表（Critical/Important/Moderate/Low），§二.2 定义的列词表是
grype 原生 CVSS 词表（Critical/High/Medium/Low/Negligible/Unknown）。两词表并存且
不等价（Important↔High、Moderate↔Medium 是约定映射不是天然同名），前端 C 区
「严重度列有色」（§二.5）按词表取色——**映射函数缺位则 dnf 行的 Important 在
CVSS 词表里查无此词**，要么渲染崩要么吞色。且 0145 立法「source 词表在代码=避免
第二真源」，severity 同理需要单一真源。**修法**：§二.4 补一行契约：映射函数落
security_collector（写入侧归一——dnf 采集时即翻译成 CVSS 词表入库，DB 只存一种
词表），映射表 Critical→Critical/Important→High/Moderate→Medium/Low→Low 写明
并注明「RH 官方语义对齐」，前端零映射逻辑。

### P1-3 alinux3 识别验证「SBOM 阶段验」太晚——应前移为步骤 3 第一闸
§六 把「grype 对 alinux3 rpmdb 识别质量」列为风险、验证时机=「SBOM 阶段」。
但§二.6 切换判据、验收 1/2 全部押在 grype 覆盖面上；若 rpm 识别弱在装完机、
写完采集器之后才发现，方案退化（「OS 层保留 dnf 源」）会反攻表结构与前端设计。
syft/grype 对非主流发行版的处理是已知短板：distro 识别失败时降级为 unknown
distro，OS 包匹配**全漏或按通用 CPE 撒网**（grype 官方 issue 大类）。该验证
**零编码成本**：装机后第一条命令 `syft scan dir:/ -o table | head`（或
`grype distro:alinux3` 探针）即可判死活，结果直接决定走全量方案还是退化方案。
**修法**：§五 步骤 3 装机后立即「alinux3 识别冒烟」设为硬闸，闸不过则先按退化
方案（pip 层 grype + OS 层 dnf 补采）施工，避免返工。

## 一般

- **N-1 DB 更新成本账缺 06:00 任务的重叠核算**：§六 只问「全量 vs 增量」。已知机制：
  grype v5 DB 每日构建单 tar（listing.json 指针切换），无官方增量——即「日更=每日
  全量 296MB/106s」基本坐实（待文档确认，但应按全量做预算）。安全扫描 06:00 触发、
  pip-audit 段 300s timeout 之上再叠加 syft 扫描+grype 比对+106s 下载，单轮预算须
  写进§三；「限频隔日」会直接放大 CVE 盲窗（A07 §三「CVE 源日级更新」的自洽性），
  建议明确取舍而不是留「或」。
- **N-2 台账 UNIQUE(source,name) 与验收 2 的口径**：system 组件（nginx/pg/redis）
  版本探测分属多通道（rpm/二进制 --version），source 列枚举 'pip'|'rpm'|'system'
  的归属规则未写（pango 走 rpm、redis 走 --version 填哪个）。一行规则即可闭。
- **N-3 模板偏离声明缺失**：任务文件非八字段模板形态（现状/方案/验收结构），且§二.6
  「重叠度极低 ~3%」引用 A07——A07 原文并无此数字（A07 通篇无 3%/重叠度表述，
  2026-10-14 通读核实），引用锚点失实，须改挂真实出处或删数字。
- **N-4 限定范围表缺**：模板要求「只改 A/B/C 明确不碰 D/E/F」；本批改动面大
  （迁移+wrapper+采集器+API+前端+A07），§四「不做」是反向清单但无正向范围表，
  越界风险高于常规批（违反「限定范围 ≤3 文件+引用 ≤2 份」的模板硬约束——本批
  引用 0 份设计文档章节，应补 A07 §锚点引用）。
