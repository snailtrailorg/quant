## P1

### P1-1 「天然去重」表述误导——唯一键不跨源去重（红队头条坐实）
- **证据**：任务:76「finding 表按 (source,pkg,vuln_id) 天然去重」；0145:70 唯一键
  `UNIQUE (source, pkg, vuln_id)`——**含 source 维**。grype 报 GHSA-xxxx、pip-audit
  报 PYSEC-xxxx（同一 CVE 两 ID 体系）⇒ 键不等 ⇒ **两行并存，无任何去重发生**。
  grype findings（source='grype'）与 pip-audit findings（source='pip-audit'）的
  pkg 命名域也不同（syft SBOM name vs requirements.lock name——如 `pyyaml` vs
  `PyYAML`），连 pkg 相等性都未定义。
- **后果链**：A 区"活跃漏洞总数"（SecurityTab.vue:197 `activeFindings.length`）
  并存期**必然双计**——总数=grype 行+pip-audit 行+dnf 行之和；新洞告警
  （security_collector.py:492-495 `security.vuln_new`）同一漏洞从两源各响一次。
  「天然去重」四字把"不去重"说成了"已去重"，与八步法"验收可验性预审"冲突。
- **修法（待裁点①）**：三选一——(a) aliases 归一层（grype JSON 有 `relatedVulnerabilities`
  字段可归一到 CVE 号）；(b) 接受双行+前端按 CVE 前缀聚合展示；(c) 唯一键改造
  （vuln_id 归一列+source 降为属性）。**任一都须写进任务文件**——现状句是错的。

### P1-2 security_component 表设计缺口
- **(a) source 域重叠**：`'pip' | 'rpm' | 'system'`（任务:47）——alinux3 rpm 库含
  `python3-pip`/`python3-setuptools` 等（syft SBOM "venv+rpmdb 一体"扫描必然同时
  报同一包），pip 域与 rpm 域 name 冲突双行；且 venv 里 pip 装的包与 rpm 装的
  python3-xxx 库在 SBOM 里 type 不同但 name 可能同形。需归源规则（syft 的
  `source`/`type` 字段映射到哪个 source 域）——任务未写。
- **(b) first_seen/last_changed 语义纠缠**：冷启动日全表 first_seen=last_changed=
  当日；新装包两者也恒等——两列仅在"旧包升级版本"场景才分化。语义上
  first_seen="该 (source,name) 首次入台账"、last_changed="当前 version 首见日"。
  建议注释里写明三列各自的判定语义（任务:50-51 只写了一半），否则步 4 必返工。
- **(c) 系统组件来源归属**：现 D 区 8 组件（nginx/openssl/pg/redis/python/pango/
  cairo/wqy）中 postgres 可能非 rpm（PG18 官方源 dnf 装则 rpm、源码装则否）、
  python=venv 解释器（rpm 装的 python3.11）。`'system'` 域与 SBOM 产出（pip/rpm
  两域）的映射规则未定义——SBOM 之外的组件谁写台账？任务未答。
- **(d) 172+ 包数与现实现 179 不符**：任务 §三.2 说"172+ pip 包"，A07:22 与
  pip freeze 实现为 179——数字无锚点（应写 `pip freeze | wc -l` 实测或去掉具体数）。

## 一般

- G1 **插件注册细节留白**（待裁点②）：§二.6"插件注册制（md_gateway 同款）"——
  md_gateway 是 dict 注册无优先级语义（md_gateway.py:115-117），im_bot 的顺序靠
  显式 `_PROVIDER_MODULES` 元组+order 映射（im_bot/base.py:142-143）。任务说
  "注册顺序决定优先级"（§二.6 未明说但切换语义需要）——若照抄 md_gateway 则无
  序；须显式 priority 属性或顺序元组（同 im_bot 惯例）。available 探测时机
  （每轮扫描 vs 模块导入）、三插件全退时 vulns 分区状态（应=degraded 非空表 ok，
  0145 立法"绝不静默空表"）——建议任务文件补两行明确。
- G2 **severity 回填账**（待裁点③ 关联）：存量 finding 行（pip-audit/dnf 历史行）
  severity 恒 NULL；dnf 补采只覆盖新行 ⇒ 切换期 C 区"未评级"占比可能 100%，
  severity 列信息价值在冷启动周≈0。可接受（7 天观察期后 grype 行全带 severity），
  但任务应写明该预期，防验收 1（"severity 非全 NULL"）被判读者误解为全量覆盖。
- G3 **验收 2 冷启动悖论**（待裁点③）：台账首建日全部 first_seen=last_changed=
  当日，"对一已知变更包（如本轮部署的任意升级）验证 last_changed 精确"——部署
  升级发生在台账首建**之前**，该包首行即当前版本，无"变更"可验。应降级为
  「机制验证」：staging 人工 UPDATE 一行模拟版本变更后复跑 UPSERT，断言
  last_changed 推进（模板 §四 mock 纪律的天然适用场景）。
- G4 **grype DB 更新频率与部署窗**：§六 已识别（296MB 全量 vs 增量）但未给判据
  「首查 grype 文档」的落点（验收几？哪一步？）——挂在风险节无主。建议归入
  步 3 grype 装机的准出条件。
- G5 **`dir:<release>` 扫描对象表述**：§二.2 说扫 `dir:<release>`——release 目录
  含 server/ 全树；requirements.lock 语义（A07:23"扫的是部署真源"）被替换为
  "扫装机现场"——两者差异（venv 里 `pip install` 后的解析树 vs lock 钉死清单）
  未论证。非阻断，但 A07 §二更新时应写明这个真源切换（读 A07:81-83「真源对齐」
  支柱受影响）。

| 待裁点 | 我的结论 |

| ① 跨源去重机制 | **推荐 (c) 唯一键改造的反向轻量版**：保留 (source,pkg,vuln_id) 键不动（存量零迁移），**采集侧归一**——grype findings 入库时用 `relatedVulnerabilities` 抽 CVE 号写入 vuln_id（GHSA/PYSEC 均 alias 到 CVE），pip-audit 侧 OSV 返回的 aliases 同理；source 保留溯源。若实测 alias 覆盖不全，退化 (b) 前端聚合。**不建议 (a) 独立归一层**（新表+新查询面=过度工程，与"台账直读"初衷相反）。 |
