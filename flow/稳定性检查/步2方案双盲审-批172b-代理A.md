### P0-2 翻译层落在 `_guard` 之外 ⇒ 任一翻译异常直接杀死 vnpy 事件线程（静默失聪且继续下单）

**证据链（两条都在本仓/venv 内）**

1. `server/venv/lib/python3.11/site-packages/vnpy/event/engine.py:68-80`：

       def _process(self, event):
           if event.type in self._handlers:
               [handler(event) for handler in self._handlers[event.type]]   # 无 try/except
       def _run(self):
           while self._active:
               try: event = self._queue.get(...); self._process(event)
               except Empty: pass                                        # 只接 Empty

   handler 抛任何异常 ⇒ 穿出 `_process` ⇒ 穿出 `_run` ⇒ **线程永久退出**。
2. `src/quant_common/guard.py:13` 的注释就是这条立法：「vnpy 事件线程零保护，F-26——一次异常=线程静默死亡=永久失聪」。

**方案现状**：`main.py:358-366` 与 `hub_worker.py:445-455` 的 handler 整体被 `@_guard("worker.on_order")` /
`@make_guard("hub.on_trade", _alert)` 包住——今天 `adapter` 未绑定（NameError）、`event.data` 缺字段等异常
**全被守卫吃掉并告警**，线程存活。方案改成 `port.subscribe_order(cb)` 后，端口内部必然是
`ee.register(EVENT_ORDER, wrapper)`，而 `wrapper = cb(translate(event.data))`——`translate` 在 `cb` **之前**执行，
被守卫包住的只有 `cb` ⇒ 翻译异常落在守卫之外。

**必坏路径**（任一即触发，且现实）：
- `main.py:336-366` 的结构本身就是风险面：EE 先起、handler 先注册、`build_td_runtime` 后才有 `adapter`。
  方案把 `adapter_getter` 放进这条链 ⇒ EMT RESTART 当日重放在 `build` 期间投递 EVENT_ORDER 时，
  `adapter_getter()` 抛 NameError（闭包自由变量未绑定）——**正是方案声称要保住的场景**。
- 任一 `OrderData/TradeData` 缺 `vt_orderid`/`status`/`vt_tradeid`（EMT 合成对象、SDK 升级字段改名）⇒ `AttributeError`。

**后果**：进程活着、心跳正常、策略继续下单，但 `order_log` 终态与 `trade_log` **永久停更**（账实分离），
且没有任何告警（守卫没参与）。这是本仓最忌讳的形态：静默 + 继续动作。

**建议**：ACL 的每个 `ee` handler 自带守卫（`subscribe_*` 内
`ee.register(EVENT_X, guard("legacy_port.on_order", alert=_alert)(wrapper))`），或把 `translate` 移进 `cb` 内部；
验收补一条行为断言：喂缺字段事件 ⇒ 线程存活 **且** 有 warning/告警留痕（钉「静默错必须留痕」，不能只钉「不抛」）。

## P1

### P1-1 「查询→撤销闭环」只在同一会话内成立；重启 / EMT EOD 重建后 client_id 解析链断

- `adapters.py:334-337`：`_vt2cid/_cid2vt` 在 `send_order` **返回之后**才写；`adapters.py:363-366` `get_vt_orderid` 读同一份进程内 dict。
- `adapters.py:949-953`（`EmtAdapter._check_eod`）：交易日变更重建时 **`_cid2vt.clear()` / `_vt2cid.clear()`**；
  RESTART 重登（`adapters.py:583-600`）同理。
- `adapters.py:339-361`：`cancel_order` 收到非纯数字串（如 client_id）时**主动放弃**
  （"盲撤错单比不撤更危险"）。

⇒ 方案 D 段与 D32 §6 的「`query_orders` 必带 `client_id`（查询→撤销闭环）」，在恢复场景（正好是 `query_orders`
存在的理由）不成立：translate 只能从被清空的 `_vt2cid` 反填，得 `client_id=""`；随后 `port.cancel("")` →
`get_vt_orderid("")`=None → `adapter.cancel_order("")` → 非数字 ⇒ 放弃。
老路径 `_cancel_working_orders` 用 `od.vt_orderid` 在同样场景**能撤**。

**P1b 本身不坏**（方案明写撤单仍用 `od.vt_orderid`），但它把一条**假的闭环**写进了 P3 的契约地基。
**建议**：契约改为「`query_orders` 的 `client_id` 为 best-effort；`cancel` 必须**先解析后撤**——
`_cid2vt` → 查询缓存（`_orders` 里按 client_id 反查 vt_orderid）→ 都失败则**计 failed 并留痕**」，
并让 P1b 的 ACL 当场写对（否则 P3 直接继承错误）。

### P1-2 `status_of` 把「未知/缺失状态」默认映射成 `NOT_TRADED` ⇒ 撤单在场集扩大（旧码跳过）

- 方案 §B：`NOTTRADED/UNKNOWN→NOT_TRADED`。
- `trading.py:290-302`：在场集 `{SUBMITTING, NOTTRADED, PARTTRADED}` → 新集 `{SUBMITTED, NOT_TRADED, PARTIAL}`。
- 旧码 `getattr(od,"status",None) in working`：`None`/未知值**不在**在场集 → 跳过。
- 新码若 `status_of` 对 `None`/未知回落 `NOT_TRADED` ⇒ 变成**在场** ⇒ 对状态不明的委托发撤单。

venv 实测 vnpy 4.5 的 `Status` **没有 UNKNOWN 成员**，所以方案里的 `UNKNOWN→NOT_TRADED` 是凭空的；
真风险是 `getattr(d,"status",None)` 为 `None`（EMT 合成对象缺字段、paper/stub、未来 SDK 升级）——
此时 `requested` 计数与真撤单都会多算，而急停回执直接喂 web UI 的"已请求撤销 N 笔"。

**建议**：`status_of(None/未知)` 必须 fail-closed（raise 或映射到新 `UNKNOWN`，后者要走 D32 §12.2 契约变更），
**不得默认成在场态**。

### P1-3 `_cancel_working_orders` 的逐条 translate 失败被外层 except 吞成 `failed=0`（急停回执少报）

- `trading.py:288-310`：`try:` 包住整个 for 循环，`except Exception as e: logger.error("撤单流程异常: %s", e); return out`。
- 方案把 translate 放进循环内 ⇒ 第 2 条翻译抛异常时：`requested` 已 +1（第 1 条），**`failed` 恒 0**，函数正常返回。
- 基线 C3 语义是「requested=请求已受理」、单笔异常计 `failed` 且不中断循环。新形态下**"翻译崩了"与"全部撤成功"
  在返回值上不可分辨**——正是本仓要求的"路径不可分辨"的**反面**。

**建议**：translate 放进**单笔 try**（与 `cancel_order` 同级），失败计 `failed` + warning；
矩阵补「第 2 条 translate 抛 ⇒ requested=k, failed=1，且第 3 条仍被处理」。

### P1-4 `trade_ref` 空值由 `NULL` 变 `""` ⇒ 撞 `ux_trade_log_ref` 唯一索引，后续成交被 `DO NOTHING` 静默丢弃

- 基线 `trading.py:158`：`getattr(d, "vt_tradeid", None) or None` ⇒ 空值写 **NULL**。
- 方案：`Trade.tradeid = d.vt_tradeid or d.tradeid`、`trade_ref=d.tradeid` ⇒ 两者皆空时写 `""`。
- `server/migrations/versions/0039_order_trade_reconcile.py:28`：`CREATE UNIQUE INDEX ux_trade_log_ref ON trade_log (trade_ref)`。
  PG 唯一索引对 NULL 不去重、对 `""` **去重** ⇒ 第一笔空 ref 成交入库，此后全部 `ON CONFLICT DO NOTHING`
  且 `cur.fetchone()` 无行 ⇒ **连"成交入库"日志都没有**（`trading.py:160-162`）。

触发面窄（需 `tradeid` 为空），但纯损失无收益，且无用例覆盖。
**建议**：写入侧保留 `... or None`（与基线同值），矩阵补「空 trade_ref 连续两笔 ⇒ 两行」。

### P1-5 `write_trade_log` 的 cid 命中但无行时，回落语义发生漂移（旧码**不**回落）

- 基线 `trading.py:137-150`：`if cid: <按 client_order_id 查>` / `elif vt: <按 vt 反查>` —— **互斥**；
  cid 命中但查不到行 ⇒ `order_db_id=None`，**不**再试 vt。
- 方案 D 段：「先 `d.client_id`（空则 `_vt2cid` 反查）**再** `d.orderid` 反查」——读起来是**顺序回落链**。
- 若照字面实现：cid 有值但 `order_log` 无行（跨进程单、order_log 清理、历史数据）时额外认领到 vt 行 ⇒
  `trade_log.order_id` 从 NULL 变成某 id、`strategy_id` 随之变化（影响按策略统计的成交归属）。

基线矩阵无此用例，写错也抓不到。
**建议**：任务文件把 SQL 顺序写成硬契约（「vt 两步查询顺序不变；`client_id` 仅作**空值**时的回退源」），
补「cid 有值 + 无行 ⇒ 不回落到 vt」用例。

### P1-6 `providers/xtp/translate.py` 一文件两义，且让编排层直依赖插件包（分层闸咬不住）

- D32 §4 依赖规则只有 `应用→端口`、`编排→端口+注册表`、`插件→端口+规格`，**没有**"编排 → 插件"这条边；
  §9.6 可插拔验收：「新增 provider 不允许修改 `strategy_runner/`」。方案让 `strategy_runner/legacy_exec_port.py`
  与 `trading.py` 都 import `providers/xtp/translate.py`——核心硬指向**具体插件包**。
- `tests/test_layering.py:20-21`：`providers:2`、`strategy_runner:3`，规则是"下层不得 import 上层"⇒ 3→2 合法，
  **守门不会红**（这次架构回退无人拦）。
- 语义上也不是一件事：P1b 的 translate 译的是 **vnpy ExecutionAdapter 对象**（`OrderData/TradeData`），
  P3 的 `providers/xtp/translate.py` 要译的是 **XTP SDK 对象**。同一路径承载两种翻译，
  P3「删除 LegacyExecutionPort」时必须从该文件摘一半，文件变成混合体。

**建议**：迁移期翻译层放 `strategy_runner/legacy_translate.py`（随 ACL 在 P3 一起删），
`providers/xtp/translate.py` 留给 P3 真插件；若坚持放 providers 下，则必须同时把
「`strategy_runner` / `trading` 不得 import `providers.*`」写进守门，否则这条边界必然复发。

### P1-7 ACL 的非事件面（send / cancel / query_account / connected）零验收，且 `connected` 在 adapter 侧无来源

- `adapters.py` 的 `ExecutionAdapter` 只有 `send_order/cancel_order/query_position/query_account/query_orders/query_trades/get_vt_orderid`

- `query_account` 返回 `list`（`adapters.py:414-425`），端口签名为 `AccountState | None`。折叠规则（求和？取首？）

  带未定义语义 + 零测试交出去，等于把风险推到改动面更大的 P3。

**建议**：至少补 `isinstance(port, ExecutionPort)` 结构断言（`@runtime_checkable` 只查属性存在，能过但语义未验），

3. **S8 结构断言是同义反复**：`strategy_runner` 今天就没有任何 `MarketDataPort` 引用（全仓 grep 只在 `ports/` 自身），

   按 D32 §十四"守门自检"要求应配**突变复测**（往 `md_hub/main.py` 塞一行 `from src.ports import ExecutionPort` 必须红）。
4. **`query_account` 折叠规则未定义**（见 P1-7）：`AccountState.frozen` 存在但无人说 `available` 是
   `sum(max(0,b-f))` 还是 `sum(b)-sum(f)`；融资账户负可用时两者不同。
5. **对账告警文案变化**：`trading.py:786` `getattr(o.direction,'value','?')`。vnpy `Direction.LONG.value == "Long"`，
   domain `Direction.LONG.value == "direction_long"` ⇒ 告警正文从 `Long` 变 `direction_long`。基线 C5 只钉标题，抓不到。
   属"等价改写"，但基线 §5 第 3 条要求分类留痕，应显式记入任务文件。
6. **`EventEngine.register` 按 handler 身份去重**（`vnpy/event/engine.py:113-120`）：`__init__` 预注册 + 外部再
   `subscribe_*` 会各生成**新闭包对象** ⇒ 双双注册 ⇒ 双回调（双 SSE 帧、双 UPDATE）。
   方案须写明：**唯一注册点是 `subscribe_*`，构造函数禁止注册**，且 `subscribe_*` 幂等。
7. **等价矩阵缺口**（除上文已指出的 4 条）：
   - 三事件的**错误路径**：translate 抛 / 回调抛 ⇒ 线程存活 + 留痕（对应 P0-2）；

## 对"两套事件并存 / 双写"的直接回答

**DB 双写：在"每个 commit 内原子替换 handler"的前提下不产生**——`order_log`/`trade_log` 的写入方各只有一处，
`XTPAdapter`/`EmtAdapter` 里注册的 `EVENT_ORDER/TRADE` 只填缓存不落库（`adapters.py:274-286`、`:744-762`）。
**但存在三条"第二真源"缝隙**，方案必须显式关掉：
① 构造函数预注册 + `subscribe_*` 再注册（P2-6）；
② `ctx.get("exec_port")` 回落直注册（P0-1②）；
③ `Trade.client_id` 这个**字段**与 `adapter._vt2cid` 这份**进程内存**是同一身份的两次快照——
翻译时刻冻结 vs 消费时刻读取，基线是后者；`_vt2cid` 会被 `EmtAdapter._check_eod` 清空（`adapters.py:949-953`），
冻结值可能比读取值"更新"也可能"更旧"。方案写"先 `d.client_id`（空则反查）"= **优先信快照**，
基线语义是**用现值**。建议：两个写函数保持"现值优先、`d.client_id` 只作最后兜底"，
并在基线 §2.5 补一条"身份键读取时刻"的语义条目。
