## P1

### P1-1 `_cancel_working_orders` 会漏撤「状态可读、其他字段不全」的在场单（基线不会）

- 现行为（`trading.py:288-310`）：判据只有两件事——`getattr(od,"status") in working` 与 `od.vt_orderid`。**不读 symbol/direction/volume，因此没有失败面**。
- 方案 §D：`_cancel_working_orders`「逐条 translate；单条翻译失败 `failed += 1` + warning + 继续（不增 requested）」；而 `to_domain_order` 需要 `orderid/vt_orderid/symbol/direction/status/volume/traded/price` 八个字段（`quant_common/domain/order.py:37-49`）。**任一字段缺失/类型异常 → 该在场单被跳过，不撤**。
- 这不是臆测：仓内既有桩形态就是「只有 status+vt_orderid」——`tests/test_trading.py:257-258` 的 `_order()` 只造这两个字段，正是撤单三态用例的输入。
- 影响面：熔断沿撤单（F-41）、一键撤单（`hub_worker.py:200/211`）共用本函数；「撤不动却没撤」是资金面语义，比计数错更重。且 `failed` 被计入急停回执（见 P2-7），人工会误判为「撤单被券商拒」。
- **修法**：撤单路径把「在场判定」与「全量翻译」解耦——`status_of(od)` 单独判工作态，工作态即 `adapter.cancel_order(getattr(od,"vt_orderid","") or od.orderid)`，其余字段不参与；只有 `status_of` 本身失败才计 `failed` 并 warning。等价用例补一条「8 字段只给 2 个字段的在场单仍被撤」。

### P1-2 `reconcile_orders` 的方向告警文案：方案写错了基线

- 代码（`trading.py:785`）：`f"{o.symbol} {getattr(o.direction,'value','?')} ..."`。vnpy `Direction.LONG = _("多")`（venv `vnpy/trader/constant.py`，`_()` 默认中文）→ **现网文案是「多/空/净/」**，不是 `Long/Short/Net`。
- 方案 §D 写「告警方向文案保持 legacy `Long/Short/Net/?`（domain 值需回译，禁止出现 `direction_long`）」——**描述与代码不符**。按文档实现（回译成英文）即改变行为；按 domain 直取 `.value` 又变成 `direction_long`（方案自己禁止）。两种写法都不等于基线。
- 后果：等价测试如果照任务文件写期望值，会与基线不一致而被判「回归」；实现者也可能顺手改成英文，把一条中文告警静默改版。
- **修法**：在契约里写死映射表 `{LONG:"多", SHORT:"空", NET:"净"}`、未命中 `"?"`，并注明「`_()` 本地化若切换语言则文案随之变，等价测试以当前 locale 为准」。

### P1-3 早到事件窗口只解决了一半：cb 拿不到 adapter 时「丢事件且无告警」

- 时序确认（**这部分方案是对的**）：现状 `main.py:352/366` 注册早于 `build_td_runtime`（`:370`），`XTPAdapter.__init__` 自己在 `adapters.py:257-260` 注册缓存 handler，也是 build 之后 → 端口在 build 前订阅，**handler 先后顺序与现状一致**（口述「能保住」成立）。
- 但 `on_order` 闭包里的 `adapter` 要到 `main.py:414` 才有值。方案只说了 `adapter_getter` 返 None、翻译照做，**没说 cb 怎么拿到 adapter**。若无 holder，`write_order_status(d, None, ...)`：
  - vt 命中行时能回写（cid 分支才碰 adapter）→ 比现状（`UnboundLocalError` 整条丢）**更好**；
  - vt 未命中 → `trading.py:98` `with adapter._lock` 抛 `AttributeError` → 被 `:114` 的 never-raise 吞成一条 warning → **事件静默丢失，且比现状少一条 guard 告警**（现状 `main.py:299-303` 的 `_guard` 会 `_alert`）。
- `write_trade_log` 侧同窗口会写 `account_id=None`（`trading.py:159` `getattr(adapter,"account_id",None)`）——这是基线既有窗口，不算本批回归，但方案应写明「不修」。
- `port.send`/`cancel`/`query_*` 在 adapter 未绑定时行为同样未定义（见 P2-4）。
- **修法**：方案写明「main 用可变 holder（`[None]`/dict）传给 `adapter_getter`，cb 也从 holder 取 adapter（不得闭包未绑定局部量）」+「早到事件」等价用例一条（断言：vt 路回写成功 / cid 路一条可分辨 warning、且不被 guard 吞成无名异常）。

### P1-4 S8 角色隔离守门：验收要它，产出没有它

- D32 `:526`/`:566`：S8 = 「P1b 结构断言（消费者不引用跨角色端口）」，出口条件写在 P1b 行（`:480`）。

- 但产出 8-12 只有 `test_d32_p1b_equivalence.py`，**没有 S8 测试文件**；`tests/` 现有 D32 守门只有 S1/S2/S3（`test_d32_s1_vnpy_boundary.py`/`s2`/`s3`），无 S8。
- 手工「塞一行再删掉」不可回归、也不在 CI 里。**修法**：产出增 `tests/test_d32_s8_role_isolation.py`（扫 `md_hub/` 不引用 `ExecutionPort`、`strategy_runner/` 不引用 `MarketDataPort`；带 allowlist 文件 + 「扫描目标非空」自检，防扫描面静默失效），突变复测写进该文件注释与验收。

## P2

1. **`orderid = d.vt_orderid or d.orderid or ""` 引入基线没有的查询分支**：`trading.py:126-134` 只用 `vt_orderid`，空即不查。新式在 `vt_orderid` 为空时用**原始 orderid** 去查 `order_log.vt_orderid`，是基线的超集（若某 adapter 存过裸 id 可能误命中）。建议保持「只 `vt_orderid`」，把 fallback 留到 P3 由插件填 `client_id` 时再说。
2. **`guard_factory: Callable[[str, Callable], Callable]` 与 `main._guard` 不匹配**：`main.py:299` 是柯里化 `_guard(name) -> deco`。main 侧必须写 `lambda n, f: _guard(n)(f)`，极易写成 `_guard` 直传后 TypeError。建议契约改用 `make_guard(name, fn)` 的适配形式并给出 main 侧调用样例。
3. **`connected` 必须是 `@property`**：`ports/execution.py:20-21` 冻结为 property。若 `LegacyExecutionPort.connected` 写成普通方法，`if port.connected:` 恒真（bound method 恒 truthy）。另 `connected_getter` 默认 `lambda: True` 是 fail-open 默认值，未绑定时建议 False。
4. **`port.send` 必须逐调用解析 `adapter.send_order`**：`main.py:513` 的 `adapter.send_order = _gated_send` 是 sticky 冻结 + `buy_ok` 新鲜度的唯一咽喉（`main.py:495-513`）。若端口构造期缓存 bound method 且早于 `:513`，则**绕过安全门**。方案需写死「每次调用 `getattr(adapter, "send_order")`」，并加一条「send 经过 _gated_send」的等价用例。
5. **测试盲区**：`hasattr(MagicMock(), "_vt2cid")` 恒 True → 「adapter 无 `_vt2cid`（P3）才用 `d.client_id`」这条分支**永远测不到**。验收第 6 条请用 `SimpleNamespace`（显式无该属性）覆盖。
6. **产出 11 漏列改动点**：`tests/test_trading.py:257-258` 的 `_order()` 必须改 domain `OrderState`（否则撤单三态用例全红，`:266` 的 `cancelled == ["x.1","x.3"]` 会被「顺手放宽」）；`tests/test_batch69.py:18/24` 是 `inspect.getsource` 源码钉（钉 `bus.publish_cross_process(0,"trade_update",{})` 等字面量），**SSE 发布行必须原地留在 `on_trade/on_order` 体内**，不能挪进端口，否则红。
7. **`failed` 语义扩张**：急停回执 `{requested, failed}`（`hub_worker.py:200`，`trading.py:288-310`，基线 C3 = 「撤单异常」）新增「翻译失败」，用户面读法变了。要么单列 `untranslatable` 键，要么在模块契约里明写扩张后的定义。
8. **`n_new` 计数**：`trading.py:791-796`「补录当日成交 N 笔」按 `query_trades` 条数计；翻译跳过时是否仍计未定 → 日志会虚高。另 `to_domain_account` 在 P1b 无任何生产消费者（死代码），可留但别在文档里声称「能力闭合」。

## 逐条结论（对应指派重点）

| # | 问题 | 结论 |
|---|---|---|
| 1 | LegacyExecutionPort 注册时序能否保住线程且不漏事件 | **部分**。注册顺序与现状等价（端口在 `build_td_runtime` 前 → 早于 `XTPAdapter._on_order`，同 `main.py:366 < :370`）；线程存活由 guard 保住。但「不漏事件」不成立：cb 侧的 adapter holder 未规定，cid 路会在 never-raise 里静默丢且无告警（P1-3）。并发窗口无新增死锁：`_lock` 两处顺序获取、无嵌套。 |
| 2 | `subscribe_*` 幂等 / EventEngine 去重是否足够防双回调 | **够，但有前提**。vnpy `register` 按 handler 身份去重（`vnpy/event/engine.py:113-120`），而每次 `subscribe_*` 新建 wrapper → **端口必须按原始 cb 去重缓存 wrapper**；方案写了「同一 cb 幂等」但没写「按 cb 键」与「断言 ee.register 只被调 1 次」，需补。另注意 `XTPAdapter` 自身也注册同事件（`adapters.py:257-260`），那是缓存面不是回调面，不构成双回写。 |
| 3 | `status_of` fail-closed + 单条 try 是否漏/误撤 | **漏撤会**（P1-1）。误撤不会（fail-closed 不会把未知态当在场态）。与基线 C2/C3 逐条对齐：判据集合一致、`requested/failed` 语义扩张未在契约里声明。 |
| 4 | cid/vt 互斥、`trade_ref or None`、`_vt2cid` 当前值是否与基线逐字等价 | **等价**（`trading.py:130-145` `if cid: ... elif vt:` 确是互斥；`vt_tradeid or None` → `tradeid or None` 等价；当前值读取与基线同刻）。**未覆盖分支**：`d.orderid` fallback（P2-1）、adapter 无 `_vt2cid` 分支无测试（P2-5）。 |
| 5 | 既有 5 文件改法能否保住守门力 | **大体能，但清单不全**。`test_order_status_write` 的 `assert_not_called` 与 `ORDER BY id DESC LIMIT 1` 断言可原样保留；`test_trading` 除 `_trade()` 外还有 `_order()`（P2-6）；`test_batch69` 的源码钉必须原地保留（P2-6）。真正的盲区：MagicMock 恒有 `_vt2cid`（P2-5）。 |
| 6 | v3 是否引入新范围/验收矛盾；D32 与任务是否自洽 | **有 1 处硬矛盾**（P0-1：产出/限定范围 vs「全绿」验收）与 1 处缺项（P1-4 S8）。与 D32 §12.1/§12.2 其余项自洽：`client_id` 末位、`PORT_CAPS`、`EVENT_LOG` 不迁、`md_hub` 归 P3 均对齐。 |
