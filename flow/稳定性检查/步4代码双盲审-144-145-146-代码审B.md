### 发现

无 P0。两条 P1（处置后不阻塞过门）：

- **P1-146a · 窄投影对「重名列出现在 ts_code 上」的变形不设防，INSERT 仍会撞 1054**：投影取列交集用 `c in df.columns`，而 pandas 重名列下 `"name" in df.columns` 恒 True（duplication 不影响 membership）——当前实测形态（重名在 name）下取 `df[cols]` 会返回**两列 name**（`df[["ts_code","name"]]` 在重名时返回所有匹配列）。也就是说：`~df.columns.duplicated()` 若真收到上游重名列 df，去重先发生、后续投影安全；**但若上游列名面再变形**（例如 ts_code 与 name 都重名、或上游返回的列序变化导致交集非前缀），交集逻辑仍稳，真正破的是 `test_project_12col_with_dupname` 的构造方式——它用 pandas 折叠构造「重名 name」实际得到的是**单列 name**（pandas 构造即去重），并未真实复现 12 列重名形态。**测试钉强度不足=自证**：真实重名 df 需 `pd.concat([df1, df2], axis=1)` 构造。修法：测试改为 concat 构造真重名 df；或同时补断言「投影输出列数==len(cols)」防多列漏网（`assert out.shape[1] == 2`）。**但产线代码本身正确**：`duplicated()` 先滤后投影的顺序保证任何重名形态下输出恒 ≤2 列。**产线无需改**。
- **P1-146b · `_handler` 未 catch fetch/写库异常即冒泡，concept_sync 复位(enabled=true)后首轮仍可能 error 闭环外**：任务文件产 3 复位 concept_sync 后依赖 07:00 周一轮自愈；若上游再改版（如列再变），fetch_supply 窄投影后空列交集 `cols=[]` → `df[[]]` 空 df → 早退「空数据」failed_dates，**不炸但也不 success**——该形态已由空数据分支兜住，无实害；真正的越界风险是 fetch 抛网络异常时 handler 冒泡→sync 层 error→last_status=error，与现状同态（非本批引入）。**核实后降级为观察项**：无新引入缺陷。

另 P2 一条（随手）：

- **P2-146 · `test_split_thresholds` 的 rows 元组 arity 与 SQL 列序耦合**：构造 rows=`(sid, "idle", ts)` 三元组对应 SELECT 三列，正确；但断言依赖中文可读名（「交易日历」「A股列表」）——若 FAMILY_C 改名文案，钉即脆断。可接受（文案即契约），仅备注。
