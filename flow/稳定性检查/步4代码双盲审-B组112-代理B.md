**P1-1 · SCHEMA_CODE_SPLIT 只有「人眼在场」一条告警通道，机器可检索面为零。**
`rollback-tasks.yml:173-185`：`failed_when: false` + `register: rb_compat` 后**全仓无任何消费**（`grep -rn rb_compat deploy/` 仅命中注册行自身）。词条进 shell 的 stderr ⇒ ansible 默认 callback 只在终端回显一行 `⚠ SCHEMA_CODE_SPLIT…`，落不进任何文件/告警中心/journal 可检索锚点：

**P1-2 · compat 解释器 `shared/venv/bin/python`（quant-hbcheck:79）与批 111 依赖方向律不一致。**
批 111 在 `release.yml:380-387` 明文立法：「本模块自称纯 stdlib ⇒ 不该依赖应用 venv；目标机必有 python3 ⇒ 非新增依赖」，且 `test_release_playbook_has_no_ddl_logic.py` ⑻ 全文守卫把 playbook 内解释器锁死 `/usr/bin/python3`（该守卫诚实声明局限 (ii)：wrapper 内部不归它管——所以此处违规**静默**）。compat 的 PYEOF 只用 `sys`，纯 stdlib，按同判据应写 `/usr/bin/python3`。本次未爆的原因是身份巧合：两处调用（rollback-tasks.yml:176、release.yml:684）都 `sudo -u quant` 跑，quant 能读 `shared/venv`（0700 quant:quant）。但注意 **:150 既有 hub 心跳 PYEOF import redis 必须用 venv——同文件两段 PYEOF 解释器不同会成新坑源**（工程一致性问题：下次有人照抄 :79 或照抄 :150 都是错一半）。越界性检查：无 sudoer/身份逃逸（`quant_hbcheck_cmd` 全链无覆盖定义，default 即 `sudo -u quant`；sudoers QUANT_DEPLOY_QUANT 白名单只放行无参/任意参形态的 wrapper 本体——`deploy/templates/sudoers-quant-deploy.j2:18-22`，新增子动作复用既有白名单行，无 sudoers 改动需求，合规）。
