## 严重（P1）

- **P1-1 DSL 因子 needs 持久化往返断裂（load 侧丢多维声明）**
  `factor.py:315`（load dsl 分支）`"needs": merge_needs(None, n)`、`needs_history: n`——n=表达式静态窗口，**DB 里存的多维 needs（final_needs）被整体丢弃**。写侧 `register_custom_factor` dsl 分支（`:419`）注册表却写 `final_needs`（含合并多维）且落库。后果：DSL 因子声明 `{"bar_minute":300,"bar_daily":5}`（表达式窗口 20）→ 写侧 needs_history=300 落库 → 重启 load → needs={"bar_minute":20}、needs_history=20——**正是本批立项要杀的「重启静默降级」失效模式**，且两处口径不一致。测试缺口：`test_roundtrip_multikind_needs` 只测 python 类型，DSL 多维往返无钉。修复=load dsl 分支改用 final_needs（与 python 分支同形）。
- **P1-2 judge_supply 换算系数对 crypto 低估 ~9 倍，注释方向写反**
  `main.py` `_BARS_PER_DAY=240`（A 股 4h/日）：crypto 分钟线 24h/日=1440 根。公式 `(d1-d0).days*240//365` 估「上市以来可得根数」对 crypto 系统性低估 ~9 倍 ⇒ 分支②b 误拒（例：上币 5 天声明 1000 根，实得可 7200 根，公式估 720<1000 ⇒ reject「真不可满足」，实为瞬态缺数据应 degraded）。注释称「crypto 24h 偏保守=不误拒」「高估可得根数 ⇒ 误拒少」——**方向恰相反**（是低估 ⇒ 误拒）。误拒是 fail-closed 方向（拒启+EX_CONFIG 人工可见，不带病运行），且 crypto 实盘 gate 未开（币安/OKX API 未开通），故非 P0；但注释误导后人、crypto 接入即咬。修复=按 market 分系数或注释纠偏+挂待裁。
