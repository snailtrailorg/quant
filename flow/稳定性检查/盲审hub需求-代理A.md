# 共享行情 Hub 架构 · 稳定性需求清单（独立审计）

范围：针对「每任务独立进程持 MD+TD」→「单 hub 持 MD 聚合分发 + N 个轻量 worker 只持 TD」改造，盲态枚举。现状事实已对照 `server/src/strategy_runner/main.py`、`strategy_framework/adapters.py`、`risk_control/risk.py` 核实（F-8 bar 幂等、F-24/F-25 重订阅、SC2 启动对账、SB1/SB2 fail-closed、Valkey 心跳等既有机制为基线，新架构不得丢它们）。传输层未指定，需求按传输无关表述。

## A. 消息分发语义（丢失/重复/乱序/陈旧）

| 编号 | 需求 | 验收判据 |
|---|---|---|
| A1 | 至少一次投递 + worker 端按 (symbol, bar_ts) 去重实现"恰好一次效果"；去重不得沿用现有"仅比对上一条 ts"逻辑（非连续重复投检测不出） | 重放同一 bar 100 次（含夹杂新 bar 的非连续重放），strategy.on_bar 恰好执行一次 |
| A2 | 每流单调序列号，worker 可检测丢条；检出到 gap 后进入修复/降级，且盘中修复可能无源（Tushare 分钟线盘后才可得），必须定义为"补不上即冻结该标的交易直至人工确认"而非静默继续 | 人为丢弃一条消息，worker 下一秒内识别 gap、告警，补不上时该标的拒发新单 |
| A3 | 按 symbol 严格 FIFO；跨 symbol 不要求全序但需成文；worker 拒收 ts ≤ 已处理最大 ts 的陈旧 bar | 注入乱序/回退 bar，worker 拒收并告警，不进入因子窗口 |
| A4 | 消息同时携带交易所时间戳与 hub 发布时间戳；新鲜度与"数据陈旧拒单"判定基于发布时间戳，防止 hub 重放补齐被当作新数据触发交易 | hub 回放当日历史 bar 补齐时，worker 因子更新但零下单 |
| A5 | 端到端延迟预算成文（分钟收齐→worker 收到），开盘全订阅突发为压测场景 | 9:30 突发压测 p99 分发延迟 < 预算值，超限自动告警 |
| A6 | 慢消费者隔离：单 worker 卡顿（GC/慢因子）不得拖慢 hub 或其他 worker；每 worker 有界队列 + 明确溢出策略（断开+告警，禁止无界堆积） | 一个 worker 人为 sleep 60s，其余 worker 分发延迟不变、hub 内存不涨 |
| A7 | 重连补齐：worker 断连重连后能拉回错过的 bar（通道自带回放，或 hub 环形缓冲按 seq 拉取）；禁止选无回放能力的传输（如裸 Redis pub/sub）当默认语义 | 盘中断连 30s 后重连，零 gap、零重复处理，因子状态与不断连等价 |
| A8 | 分钟边界显式化：vnpy BarGenerator 靠下一分钟 tick 推——收盘最后一根（15:00）、真空分钟、集合竞价段必须有显式 flush/空洞策略 | 15:00 收盘 bar 在 15:00:05 前投递；无 tick 分钟有明确标记而非永久缺失 |
| A9 | 跨断线分钟 bar 失真处理：XTP 断线不回补行情，跨断线的分钟 bar OHLCV 不真——hub 必须丢弃或标记不可信并触发补采/冻结 | 10:00:30 注入 MD 断线，10:00 bar 被标记或被补采值替换，策略不消费失真值 |
| A10 | hub 重启后序列纪元（epoch/seq 重置）显式通知，worker 不误判为乱序或 gap | 盘中重启 hub，worker 无缝续流，日志零 gap/乱序误报 |

## B. hub 故障与恢复（单点/脑裂/重启）

| 编号 | 需求 | 验收判据 |
|---|---|---|
| B1 | hub 单点 fail-closed：hub 失联时 worker 在明确时限内检测（心跳/数据新鲜度双通道）并停发新单；在场委托处置策略（撤/留）成文 | 盘中 `kill -9` hub，全部 worker ≤ 规定时限停止新下单并告警，TD 会话保持存活 |
| B2 | 防脑裂/单写者：分布式锁 + fencing token 进每条消息；第二个 hub 实例（部署重叠/手工误启）不得发布、不得占第二个 XTP MD 会话互踢 | 双 hub 并起测试：worker 拒收旧 token 消息，XTP 侧仅一个 MD 会话 |
| B3 | hub 自动恢复：重启后自动重登录、重订阅全聚合集、重建合约表、广播 epoch 重置（B10/A10）；恢复时长预算成文 | 盘中 OOM 重启，从死亡到恢复分发 < 预算，期间 worker 行为符合 B1 |
| B4 | hub 看门狗三件套从旧 runner 迁移：systemd WATCHDOG、事件线程死亡检测、交易时段 tick 新鲜度（含"今日已收过 tick 才升级"防节假日误判） | 挂死 hub 被 systemd ≤ WatchdogSec 内重启；节假日静默重启零误告警 |
| B5 | 重启窗口治理：计划内重启/升级禁止落在 9:15–15:00；冷启动耗时（含合约表拉取）实测并小于盘前余量 | 部署/重启脚本带时段闸门拒绝盘中计划内操作；冷启动耗时记录在案 |
| B6 | hub 侧幂等重订阅：交易时段周期性重放订阅（对冲 XTP 重连不恢复订阅），覆盖全部聚合订阅 | 拔线 30s 恢复后订阅自动找回，全程无重启、无人工介入 |
| B7 | hub 职责纯化：无下单路径、无风控决策；若持久化 bar，PG 写必须异步隔离，DB 抖动不得反压分发线程 | 代码审查 hub 无 risk/order 调用；停 PG 30s，分发延迟不上涨 |
| B8 | hub 可观测性：登录态/订阅数/tick 速率/每 worker 队列深与分发 lag 全部落指标，一条命令可查"某 worker 最后收 bar 时间" | kill 测试中，运维 ≤ 1 次查询定位断点是 hub 侧还是 worker 侧 |

## C. worker 侧行为（失联交易/暖机/幂等）

| 编号 | 需求 | 验收判据 |
|---|---|---|
| C1 | 失联交易策略成文并覆盖**所有下单路径**：bar 驱动天然安全，但时钟驱动型（尾盘平仓、定时再平衡）在无数据时也可能触发——任何 send_order 前置统一数据新鲜度 gate | hub 断链状态下，人为触发定时器路径下单被 gate 拒绝并告警 |
| C2 | worker 禁止私连行情兜底（否则 400–600M/进程 问题原样回归）：进程内零 XTP MD 会话，纳入巡检项 | netstat/网关登录审计确认 worker 无行情连接；巡检脚本检出即告警 |
| C3 | 盘中暖机：worker 重启后从 PG/hub 回补当日 bar，因子状态与连续运行一致（不能只回补 T-1 历史） | 黄金测试：盘中重启 worker，恢复后 N 根 bar 内信号与连续运行的对照组一致 |
| C4 | 全局唯一 client_order_id：现为进程内 `c{seq}`，N worker 必冲突（order_log 唯一索引 + vt→cid 映射错认）——需 task 前缀 + run epoch | 双 worker 同日下单无唯一键冲突，成交回报能归属到正确 worker |
| C5 | TD 断线重连对账：启动对账（SC2）逻辑必须在 TD 会话重连后重跑，不限进程启动时一次 | 盘中踢 TD 会话，重连后 60s 内完成在场委托核对+成交补录并告警差异 |
| C6 | hub 重启不连带 worker：systemd 依赖设计保证 hub 单独重启不杀 worker（避免 TD 会话反复掉线重登+对账风暴） | 连续重启 hub 5 次，worker TD 会话断开次数为 0 |
| C7 | 停止语义保留：Web 停任务 → worker ≤60s 退出、零新单、在场委托处置有审计记录 | 盘中停止任务，order_log 无停后新单，处置动作有日志+通知 |
| C8 | 事件线程防护迁移：`_guard` 异常拦截 + EventEngine 线程死亡检测必须复制进 worker（TD 事件仍走 vnpy 事件线程，F-26 在 worker 依旧成立） | 向 worker handler 注入异常，线程存活、事件不丢；杀死线程被检测并重启 |
| C9 | 熔断沿传播到全部 worker：各自 ≤5s 检测熔断、撤在场委托、拒新单（SB2 语义在 N 节点下不回退） | 一键熔断测试：全部 worker 在时限内撤单+拒新单，告警聚合不风暴 |

## D. 订阅管理 / TD 会话 / 内存容量

| 编号 | 需求 | 验收判据 |
|---|---|---|
| D1 | 聚合订阅引用计数：同 symbol 多任务一份订阅；最后一个退订才真正退订，防订阅泄漏 | 两任务同标的停一个，存活方行情不断；全停后 XTP 订阅数归零 |
| D2 | 订阅确认时序：worker 启动 → hub 确认订阅（或回放当日已聚合 bar）之后才算"就绪"，消除启动竞态窗口 | 10:30 新起任务，history 窗口无缝衔接，启动期零"等 bar 空转"告警 |
| D3 | TD client_id 唯一分配 + 券商并发 TD 会话配额确认（同账号同 client_id 互踢是已知坑；**N 会话是否放行属外部确认项**，不放行则架构前提坍塌） | N worker 全天在线零互踢；券商书面/实测确认并发 TD 会话上限 ≥ N |
| D4 | 配额实测成文：XTP 单 MD 连接订阅上限、TD 会话上限、单会话报单频率，容量规划按 80% 上限设计 | 满配额 80% 压测一个交易日稳定，上限值写入容量文档 |
| D5 | worker 合约元数据来源：worker 无 MD 无合约表，下单所需 tick size/涨跌停/数量单位必须由 hub 分发引用数据快照并版本化 | worker 零合约表状态下委托不被拒单；hub 引用数据更新后 worker 侧版本同步 |
| D6 | 总内存预算实测：hub(400–600M) + N×worker(vnpy+TD .so 实测 RSS) + PG/Valkey/FastAPI/Celery ≤ 1.8G+swap 的 N_max 成文，不得线性外推 | N_max 配置下 soak 3 个交易日零 OOM、零 swap 抖动导致的分发延迟超标 |
| D7 | OOM 牺牲顺序预案：oom_score_adj 定级 + systemd MemoryMax，内核 OOM 不随机杀 | 内存压力注入测试，被杀进程与预案一致，其余进程按 B1/C1 降级 |
| D8 | hub 内存有界：回放环形缓冲按 symbol×条数封顶，禁止任何无界队列/缓存 | 连续一周运行 hub RSS 平稳（斜率≈0），无缓慢爬升 |
| D9 | 若 Valkey 兼任分发通道：交易流所在 DB 禁止 eviction 策略（eviction 静默丢 bar 比崩溃更危险） | 配置审查 noeviction + maxmemory 打满测试中交易消息零丢失 |

## E. 迁移与回滚

| 编号 | 需求 | 验收判据 |
|---|---|---|
| E1 | 双模式共存灰度：任务级开关切新架构，旧进程模式保留；共存期旧进程 MD 连接与 hub MD 并存是否触发行情会话互踢需实测 | 1 任务新 + N 任务旧共存一个交易日，零互踢、零行情劣化 |
| E2 | 影子对比门禁：切换前 hub 聚合 bar 与旧进程 BarGenerator bar 逐根 diff（OHLCV+volume 全等）连续 ≥5 个交易日为 0 差异 | 5 日 diff 报告全零，否则不切换 |
| E3 | 一键回滚：任务级退回旧模式有脚本化路径，回滚后启动对账承接在场委托 | 盘中回滚演练一次成功，无委托丢失、无重复记账 |
| E4 | bar 持久化职责界定：hub 模式下盘中 bar 是否写 PG 成文；(symbol,ts) 幂等且与 data_sync 盘后补采不冲突 | hub 重启零重复 bar 行；补采与实时写同日共存无覆盖冲突 |
| E5 | 监控面同步切换：心跳升级为 hub+worker 两级，看板/巡检/告警路由同步改 | 停 hub 后看板 ≤90s 变红；停单 worker 精确定位 |
| E6 | systemd 拓扑与自愈顺序：quant-hub 与 worker 单元的 After/PartOf/WATCHDOG 设计，服务器整机重启后 PG→Valkey→hub→worker 顺序自愈 | 整机重启演练一次，开盘前全链路自动恢复 |

## F. 冷门需求专节（设计者最容易忽略）

| 编号 | 需求 | 验收判据 |
|---|---|---|
| F1 | **vnpy_xtp 网关 MD/TD 一体耦合**：gateway.connect() 同时连行情+交易，"worker 只保留交易连接"不是现成能力——空行情地址的行为未验证，可能需裁剪网关，且裁剪版 worker 不能顺手把合约表又拉回来吃掉内存 | worker 进程持有 XTP MD 会话数 = 0，TD-only 连接行为有实测记录 |
| F2 | **告警责任反转**：hub 死时它自己无法替自己告警——必须由 worker 承担"hub 死亡"告警责任，且 N worker 同时告警需聚合抑制防风暴 | kill hub 一次，收到恰好 1 条聚合告警而非 N 条 |
| F3 | **account_snapshot 多写者竞态**：N worker 同账户各自每 60s 写快照——daily_pnl 基准竞态+风控读到互相覆盖的值；需单一 owner | 双 worker 同账户运行一日，account_snapshot 每 60s 恰好 1 行 |
| F4 | **max_trades_per_day 跨 worker 竞态**：读-计数-下单-写窗口在 N worker 并发下可突破上限；护栏需原子化 | 并发压测 N worker 同时触发限额边缘下单，实际成交数 ≤ 上限 |
| F5 | **同 bar 同步开火的自我冲击**：N worker 同标的同信号同时下单——流动性差标的自我对敲/排队互踩，可能需错峰或汇总执行层 | 双 worker 同标的同信号场景实测，委托到达时间差 ≥ 设定抖动 |
| F6 | **监控语义升级：从"进程活"到"数据流活"**：worker 活着但收不到 bar 是新架构特有的静默半死态——必须有 per-worker last-bar-age 指标 | 断开某 worker 的订阅通道但保持进程存活，监控 ≤ 90s 告警定位 |
| F7 | **回测/实盘聚合口径对齐**：hub 的分钟归属必须与 Tushare 分钟线（回测数据源）口径一致，否则因子系统性偏差且影子对比都发现不了 | 抽样 20 个交易日逐根对比 hub bar 与 Tushare 同分钟 bar 全等 |
| F8 | **零 tick 窗口不误杀**：午休/停牌/半日市——tick 新鲜度/看门狗/断流告警必须感知交易日历与停牌 | 午休时段重启 hub 不触发断流升级；停牌标的整天零断流告警 |
| F9 | **引用数据盘中变更分发**：新券/停复牌/涨跌停调整需版本化主动推送到 worker | 盘中合约表变更事件注入，全部 worker 在下一笔下单前用上新版本 |
| F10 | **hub 本地安全面**：分发 socket 任意本地进程可读（合规）或可伪造 SUBSCRIBE 洪水打爆配额——需 socket 权限+控制面限流/鉴权 | 无权限用户连接分发与控制通道被拒；洪水订阅被限流 |
| F11 | **退路保留判定**：hub 定型后 tick 级/盘口策略被永久排除——业务范围收缩型决策须显式记录并获用户确认 | 决策记录在案（含未来 tick 路径预案），用户书面确认 |
| F12 | **收益核算前置**：TD-only worker 实际 RSS 可能仍有 100–300M，N_max 可能小到让改造不划算；实测数据应作为是否继续的 gate | 单 worker RSS 实测报告 + N_max ≥ 目标任务数结论先行 |
