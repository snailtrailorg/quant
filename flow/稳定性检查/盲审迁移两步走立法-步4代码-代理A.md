# 盲审迁移两步走立法-步4代码-代理A

> 独立盲审（只读）。基线 a46f625。一手复核：pytest 三闸门 63 passed、ruff All checks passed、
> 全仓扫描、临时目录复现。下列结论均来自本人复核，未引用对方产物。

## 总评

代码整体工程质量高：单一真源模块干净（纯 stdlib、两用）、封闭式 `failed_when` 正确、
受管集内容指纹差集到位、三闸门 pytest 全绿。但**契约闭合在 prod 侧存在真实断点**——
`check_release` 对受管集内 legacy 文件「可见不阻断」、而唯一能拦「白名单外新建 legacy」的
仓内闸门④**不在部署路径上**，于是「新破坏性迁移标 legacy」在 prod 静默放行且无留痕（比
`allow_contract` 更危险，因后者至少留 `var/ddl-gate-bypassed`）。另有一处契约倒置（异常→rc=1
被 allow 当命中豁免）与一处 guard 作用域局限（判定入口唯一性只扫 release.yml）。**无 P0 级
设计不可实施；建议 3 条 P1 处置后过门**。

无。

## 严重 (P1)

**P1-1｜legacy 自声明洞（prod 静默绕过，闭合断点）**
- 现象：新迁移文件 `# EXPAND-CONTRACT: legacy` + 含破坏性 op，部署门阶段 4 放行。
- 可复现：`migration_policy.py --check-release <new> <prev空目录>` 对 `legacy+op.drop_table`
  新文件返回 **rc=0**，stdout 仅一行 `ℹ ...`（无 `✗ 破坏性 DDL 命中`，不进 rejects）。
  实跑证据见临时目录复现（rc=0）。
- 证据：`migration_policy.py:275-285`（`if decl["legacy"]: ... continue`，不 evaluate、不 reject）；
  闭合所依赖的 `test_migration_expand_contract.py:133-145`（白名单外新建 legacy ⇒ fail）属
  仓内闸门，**W6 第 1 条已承认不在部署路径**。三环（check_release 分流 / evaluate 单文件拒 /
  闸门④白名单）**闸门④不在 prod 路径 ⇒ 不成闭环**。
- 为何 P1 非 P0：该形态需开发者**故意**把新迁移标 legacy（违反规范硬规则①），且 PR 期 pytest
  可拦；但 prod 机械强制点（阶段 4）对其**零拦截、零留痕**——是「看起来对、实际不拦」的最
  危险单点。建议：分流时区分「已存在于 prev 的 legacy（可见不阻断，保留现状）」与「prev 无此
  文件的新建 legacy（必须拒，rc=1）」，堵住死锁修复引入的旁路。

**P1-2｜异常退出码契约倒置（门崩溃被当命中豁免）**
- 现象：`check_release` 仅对 `managed_set` 包了 `except OSError`；per-file `read_text`/
  `evaluate` 未包。任一未捕获异常（如受管文件非法 UTF-8、权限错）⇒ Python **rc=1**（已复现
  真实退出码=1）。而 `failed_when=not(rc==0 or rc==3 or (rc==1 and allow))`：rc=1 且
  `allow_contract=true` ⇒ **不 fail ⇒ 放行**。
- 证据：`migration_policy.py:260-263`（仅包 managed_set）、`:270-290`（循环内无保护）；
  `release.yml:388-390`。复现：非法 UTF-8 受管文件 ⇒ 退出码 1 + traceback。
- 为何 P1：设计稿宣称「门不可用（非 0/1/3）恒红」，但崩溃实际落 **rc=1** 而非契约值 **2**，
  与 allow 叠加即失效。需把整段 `check_release` 包进 `try/except` 使意外错误恒返 2（既有的 2
  =内部错分支），方与封闭式补集前提自洽。

**P1-3｜判定入口唯一性 guard 作用域局限（可经 include_tasks / lookup 逃逸）**
- 现象：`test_release_playbook_has_no_ddl_logic.py` 只读 `release.yml`，且只抽阶段 4 的
  `shell:` 体（`:40-46`）与全文件 needle 计数（`:116-129`）。把 DDL 判定挪到
  `include_tasks: other.yml` 或 `lookup('pipe', 'grep ...')`/`vars`/`set_fact` 内联，则
  release.yml 内 `migrations/versions`/`migration_policy.py` 计数仍=1 ⇒ 测试绿，但第二判定
  路径已存在（且不在白名单扫描内）。
- 证据：`test_release_playbook_has_no_ddl_logic.py:23,40-46,116-129`。
- 为何 P1：终态已用「引用任务恰 1 个」替代自相矛盾的原「≤1 次」（裁定③正确），但守卫只覆盖
  单文件单段，重定向到被包含文件或 pipe-lookup 即逃逸。建议把判定文件清单扩展为
  `release.yml` + 其 `include_tasks` 目标，并对 `lookup('pipe'...)` 同样纳入白名单扫描。

**P1-4｜孤儿 expand 断言与文档语义自相矛盾（脆性）**
- 现象：`test_orphan_expand_reported_not_red` 名为「允许孤儿、只报告不红」，体却
  `assert not orphans`（`:126`）。一旦存在合法的进行中两步走（expand 已上产、contract 未发），
  该测试**直接红**——与规范 §4「expand 上产→观察窗→contract 跨发布」及闸门③「孤儿允许、不红」
  冲突，会误卡正当半成品。
- 证据：`test_migration_expand_contract.py:112-126`（函数名与 `assert` 语义相反）。
- 为何 P1：守卫把「当前无孤儿」错当成「孤儿永不该存在」。建议去掉硬 `assert`，改为报告 + 校验
  orphan 的 pair 指向尚未上产的 id（防误标），或至少重命名以匹配真实语义。

## 一般 / 陷阱核对

- **同行排除潜在陷阱**：`scan_unsafe_lines` 行级「先排除后命中」，整行豁免。全仓实测 3 处
  `op.drop_constraint` 与宽口径 `op.drop_\w+` 共存（`:100/:116` 等），但**均为排除项自身、
  无真正破坏性 op 被掩** ⇒ docstring「本仓无此形态」**成立**。隐患是未来若一行同时写
  `op.drop_constraint(...)` 与 `op.drop_table(...)` 会掩掉 drop_table——属潜在陷阱，非现状。
- **裸 SQL 大小写敏感**：`DROP/RENAME/ALTER COLUMN` 正则全大写，当前迁移实写大写（16 命中已
  验证全部捕获），无现状绕过；但 `op.execute("drop table x")` 小写会漏检，建议正则加 `(?i)`
  或对原始 SQL 段做 casefold，消除潜在逃逸。
- **受管集 glob 非递归**：`_digests` 仅 `*.py` 顶层（`migration_policy.py:234`），子目录/
  非 `.py` 迁移本就不被 alembic 加载，影响面小；手工 SQL 已在已知边界声明豁免，非缺陷。
- **首部署 + 逃生门双豁免**：`rc=3` 跳过 + allow 叠加 ⇒ prod 零机械覆盖，W6 第 4 条已诚实声明，
  属已知边界，非缺陷。

## 过门判定

**过门（无 P0）**。P1 四条均有处置结论：P1-1 需区分「新建 legacy 必拒」；P1-2 需把 `check_release`
整体包 `try/except` 恒返 2；P1-3 需把 guard 覆盖扩展至 `include_tasks` 目标与 `lookup('pipe')`；
P1-4 需去掉 `assert not orphans` 改报告+校验。建议 P1-1/P1-2 在合入前修复（prod 面闭合与契约
自洽），P1-3/P1-4 可在后续批次加固。
