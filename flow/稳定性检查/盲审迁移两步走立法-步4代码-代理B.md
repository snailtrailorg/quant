# 盲审迁移两步走立法 · 步 4 代码 · 代理 B 独立评审

> 基线 commit `a46f625`。只读复核；以下每条结论来自本人一手 grep/实测/读码，未引用对方审件。

## 总评

代码实现与设计稿（v2.3.1/v2.3.2）高度一致，三闸门 `pytest` 63 passed、`ruff check .` 绿、声明面与执行面基本闭合。**但发现 1 个 P0**：v2.3.2 编码裁定①让部署门（`check_release`）对 `legacy` 文件**永久分流为「可见不阻断」**，而唯一 prod 机械强制点就是部署门——新文件标 `legacy`+破坏性 op 在部署路径上被静默放行（rc=0），设计所依赖的「closure 归仓内闸门④」因④不在部署路径上（W6#1，已认）**在 prod 上不成立**。此即「门可被绕过致 prod 无保护」。另 4 条 P1（行级整行豁免逃逸、orphan 测试自相矛盾、rc=1 语义混淆、ruff 不扫 tests）。**过门判定：存在 P0，需返工后方可过门。**

## 致命 (P0)

**P0-1 · legacy 自声明洞（部署路径上 prod 无保护）**
- 现象：一个新迁移文件写 `# EXPAND-CONTRACT: legacy reason="x"` 且含破坏性 op，部署门阶段 4 返回 rc=0（ℹ 可见不阻断），不拒。
- 可复现构造：见下「事实核查」已实测 `/tmp/rel_new/9999_evil.py`（`legacy`+`op.drop_table`）→ `python migration_policy.py --check-release /tmp/rel_new /tmp/rel_prev` 退出码 **0**。
- 证据：`migration_policy.py:275-285`（legacy 分支 `continue`，不调 `evaluate`）；`test_migration_expand_contract.py:133-145`（④ 检测白名单外 legacy，但 W6#1 明示 pytest **不在部署路径**）；`release.yml:379-390`（prod 唯一强制点）。
- 为何 P0：设计稿声称「legacy 合规性归仓内闸门④」并据此在 `check_release` 跳过 legacy（`migration_policy.py` 注释 line 276-285）。但④仅在开发期 `pytest` 跑，部署链零 pytest（已证）。⇒ 该 closure 在 prod 上是空转；攻击者/疏忽者标 `legacy` 即可让破坏性迁移过部署门。v2.3.2 裁定①的死锁（15 个 legacy 文件加声明行→sha 变→受管集必含→若拒即拦死本批上产）**只在引入声明的那一次发布成立**，据此做**永久**跳过是过度且危险的解法。

## 严重 (P1)

**P1-1 · 行级「先排除后命中」整行豁免 → 注释/同句逃逸（静默漏检）**
`scan_unsafe_lines` 对每行先判 `EXPLICIT_EXCLUSIONS`，命中即**整行 exempt**（`migration_policy.py:128-129`）。一行上若破坏性 op 与排除关键字同现（含注释），整行静默放行。构造：`op.drop_table('secret')  # DROP CONSTRAINT is safe` → `scan_unsafe_lines` 返回 `[]`（已实测）。当前仓内无此形态（grep 验证），但机制**不结构阻止**。修复：排除判定应限定到「该 op 自身的 token 范围」而非整行。

**P1-2 · orphan 测试自相矛盾（脆性）**
`test_orphan_expand_reported_not_red` 文档语义＝孤儿 expand「允许、不红」（`test_migration_expand_contract.py:112-113`），却 `assert not orphans`（line 126，要求「当前必须无孤儿」）。合法进行中的两步走（expand 已上产、contract 未产）会令该测试红，与「允许」语义直接冲突——把「允许」写成了「禁止存在」。应改为：孤儿只进报告，不构成失败（除非白名单收口要求）。

**P1-3 · 退出码 rc=1 语义混淆（崩溃被当命中豁免）**
`check_release` 仅对 `managed_set` 包 `try/except OSError`（`migration_policy.py:260-263`）；循环内 `read_text`/`evaluate` **未包**。模块未捕获异常 ⇒ python 退出 1，与「真命中拒」同码。当 `allow_contract=true` 时，封闭式补集把 rc=1 一律当「命中豁免」→ **崩溃被静默放行**。修复：循环体内层 try，异常走 rc=2（门不可用恒红）。

**P1-4 · ruff 不扫交付测试（质量无门）**
`ruff.toml` `extend-exclude` 含 `tests` ⇒ `ruff check .` 绿但三测试文件不受约束（如 `test_release_playbook_has_no_ddl_logic.py:122/127` 的 E741 歧义变量 `l`）。非阻断，但交付物测试质量缺机械门。

## 一般 / 陷阱核对

- 判定表大小写敏感：`RENAME COLUMN`/`DROP TABLE`/`ALTER COLUMN … TYPE` 均大写匹配；未来 lowercase raw SQL（`rename column`）逃逸。本仓未见。
- MySQL `RENAME TABLE a TO b` 不被 `\bRENAME\s+TO\b` 命中（Postgres 仓无此形态，低风险）。
- 受管集仅 `glob("*.py")` 单目录：子目录/非 .py/versions 外 SQL 不在覆盖（与文档边界一致，已知）。
- A06 同步抽查一致：行 268（「已由『唯一放行通道』降级为」）、427、431、452 已收口且措辞正确，**无遗留陈旧断言**。
- 封闭 `failed_when`：除 `{0, 3, (1 & allow)}` 外一切码（2/126/127/130/137/255）恒红——成立，无 rc 误判放行（P1-3 的 rc=1 混淆是模块侧，非 `failed_when` 侧）。
