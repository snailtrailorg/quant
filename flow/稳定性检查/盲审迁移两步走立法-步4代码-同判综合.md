## 结论一句话

**不过门** —— 存在 **2 个 P0**：① 部署门对迁移头 `legacy` 标记**零验证、零拦截、零留痕**（prod 唯一机械强制点被一条注释绕过）；② 模块内部错误伪装成退出码 `1`，与「真命中」同码，叠加 `allow_contract` 后被逃生门当「命中豁免」静默放行。
**最强理由**：设计花四轮把 `allow_contract` 硬化为「带 `contract_reason` + `var/` 留痕」的**声明式旁路**，却把**效果完全相同、却无人看守**的 `legacy` 文件标记留成**裸通道**——声明面（迁移头）↔ 执行面（部署门）在 legacy 这条路径上**未闭合**。

## 三、分歧与仲裁

### 分歧 1 —— legacy 洞是 P0 还是 P1？（A:P1 · B:P0 ⇒ **仲裁 P0**）

A 的两条降级理由**均不成立**：
- 「需开发者**故意**标 legacy」——`allow_contract` 同为「故意」，且它被四轮硬化；**故意性不能区分两者**。
- 「PR 期 pytest 可拦」——**设计 W6 第 1 条已自认部署链零 pytest、无 CI、无钩子**（三审一手采证）。「PR 期可拦」是**未落地的假设**，与 A 自己引用的 W6#1 冲突。

**仲裁 P0 的架构判据（成本不列）**：
1. **声明面被执行面消费（失效）**：设计目标原文＝「部署门据声明**自动放行合规 contract、拒未声明者**」。对 legacy，门**消费了声明却不执行裁断**（信任）⇒ 该路径声明↔执行未闭合。
2. **单一真源（被破坏）**：判定「哪些 legacy 合法」的冻结集 `_LEGACY_EXPECTED` 住在**测试文件**里，而执行侧模块**对此一无所知**⇒「谁知道谁是合法 legacy」与「谁在 prod 上执行」**是两个地方**（详见 M3）。
3. **职责层级 / 模块自洽（被破坏）**：同一模块内，`evaluate`（单文件判定）**明说** legacy+命中＝拒（`:185-190`），`check_release`（部署入口）**拒绝采用该判定**（`:275-285` 直接 `continue`）。这不是设计的信任边界，是**模块内两函数自相矛盾**（M2）。
4. **与既有制度硬冲突**：设计因「裸开关不可接受」而硬化 `allow_contract`（reason + 留痕 + 🔖）；`legacy` 标记达成**同一效果**（破坏性 op 过门）却**零 reason 校验、零留痕、零旗标**⇒ 安全模型不一致，且**更易达的那条路无人看守**。
5. **诚实边界自证**：设计侧原文「legacy 合规性归仓内闸门④」——但 ④ 不在部署路径（W6#1）⇒ 该 closure 在 prod 上**空转**。

### 分歧 2 —— rc=1 契约倒置是 P1 还是 P0？（A:P1 · B:P1 ⇒ **主会话上调 P0**）

上调依据（**三审先例 + 契约自洽**）：三审把 P0-α（`failed_when` 合取式致 `allow_contract=true` 时**门崩溃/`rc=2` 不 fail**）判为 **P0**，判据原文＝「门不可用（任何非 0/1/3 的码）在任何情形下都必须亮红」。本项形态**与 P0-α 同构**：`allow_contract=true` 且**门崩溃**（只是崩溃恰落 `rc=1`）⇒ 不 fail ⇒ 放行，且旁路告警**谎报**「门已检测」。
设计自述「解释器缺失（127）等异常码亦不失真 ⇒ 由封闭式 `failed_when` 兜住」——该论证**只考虑了模块外的异常码**（127/137），**未考虑模块自身崩溃会落 `1`**。⇒ 封闭式补集的前提「`rc=1 ⇔ 真命中`」**被生产侧推翻**，补集不成立。

### 分歧 3 —— A 独有：判定入口 guard 作用域（**裁断 P1-c**）

A 正确：guard 只读 `release.yml`（`_PLAYBOOK`），`include_tasks: <其它文件>` 或 `lookup('pipe', …)` 内的第二判定路径可逃逸。B 未提。**裁断 P1-c**（现状无逃逸实例，属加固）。

### 分歧 4 —— B 独有：ruff 不扫 tests（**裁断 一般**）

B 正确且已复现（单跑三文件 = 2×E741）。但 `ruff.toml` 的 `extend-exclude` 含 `tests` 是**项目级既有约定**，改动会牵出全仓既有告警，**超本批限定范围**⇒ 裁为**一般**：本批只需**手改新文件的 E741**，是否放开全仓 tests 留独立批次。

## 四、主会话独立复核（**仅新增证据**，不引用 A/B）

- **M1（精度更正，双方都错在此）**：可达触发路径**不是**权限错/TOCTOU（A/B 猜测）。实测：受管文件权限 `000` ⇒ `_digests` 的 `read_bytes()` 先失败 ⇒ 被 `check_release` 的 `try/except OSError` 兜住 ⇒ **rc=2（正确）**。**真正的可达路径是解码失败**：`_digests` **只读 bytes 不解码**（`:235`）⇒ 非法 UTF-8 文件顺利进受管集；循环内 `read_text(encoding="utf-8")`（`:274`）抛 `UnicodeDecodeError`——它是 `ValueError` 子类、**非 `OSError`** ⇒ 不被捕获 ⇒ **实测退出码 = 1**。
- **M2**：`evaluate` 的 legacy 分支（`:185-190`）在**部署路径上是死代码**——`check_release` 对 legacy 从不调用 `evaluate`。模块对同一事实持两种立场。
- **M3**：冻结 legacy 集 `_LEGACY_EXPECTED` **只在测试文件**（`test_migration_expand_contract.py:35-51`）。模块＝「判定唯一真源」却**不含**「合法 legacy 清单」⇒ 真源被切成两半，执行侧那半不存在。
- **M4**：`evaluate` 自身 `except OSError`（`:177`）**同样漏** `UnicodeDecodeError`——实测 evaluate 直接抛出。⇒ 影响不止部署门，仓内闸门亦会崩。
- **M5**：`parse_declaration` **无互斥校验**——`# EXPAND-CONTRACT: legacy phase=contract pair=0116` 实测同时得 `legacy=True, phase='contract'`；`evaluate` 短路 legacy ⇒ phase 被完全忽略。这是 P0-1 的一个变体（一行即得双通道）。
- **M6**：`ruff check --no-cache tests/…三文件` ⇒ `Found 2 errors`（E741 `l`，`test_release_playbook_has_no_ddl_logic.py:122,127`）。

## 五、必修清单

### P0（门——修完方可复审）

**P0-1 · legacy 自声明洞：部署门对 `legacy` 标记零验证**
- 现象：**新**迁移文件写 `# EXPAND-CONTRACT: legacy`（**连 `reason` 都可省**）+ 破坏性 op ⇒ 阶段 4 返回 **rc=0**、仅一行 `ℹ`（已实测复现）。
- 修复方向（**架构判据：单一真源 + 声明面被执行面消费**）：**把冻结 legacy 集从测试搬进模块**（`_LEGACY_EXPECTED` → 模块常量，测试改为 `import`），`check_release` 对受管集内 legacy **分流为二**：
  - 名在冻结集 ⇒ 「ℹ 可见不阻断」（保留本批 15 文件加声明行的自洽，死锁不复发）；
  - 名**不在**冻结集 ⇒ **拒（rc=1）**，拒因文本须与 `✗ 破坏性 DDL 命中:` 接口兼容或另立接口并由沙箱新增用例覆盖。
- ⚠ **这会改写 v2.3.2 编码裁定①**（由「永久分流」→「仅冻结集内分流」）⇒ **属设计变更，须用户拍板**。
- 残留（须诚实声明）：改动**已部署** legacy 迁移的**函数体**（违反「迁移不可变」）仍不在门覆盖内——单列已知边界。

**P0-2 · 模块内部错误伪装 rc=1（逃生门豁免门崩溃）**
- 现象：`check_release` 仅对 `managed_set` 包 `try/except OSError`（`:260-263`）；循环内 `read_text`/`evaluate` 未包 ⇒ 非 `OSError` 异常（可达：`UnicodeDecodeError`）**实测退出码 1** ⇒ 与「真命中」同码 ⇒ `allow_contract=true` 时被当命中豁免 + 告警**谎报**「门已检测」。
- 修复方向：**把 `check_release` 整体（或 `main` 的调用点）包进 `try/except Exception` ⇒ 任何非预期异常恒返 `2`**（既有的「内部错」档）；`evaluate` 的 `except OSError` 一并放宽（`:177`）。使「`rc=1 ⇔ 真命中`」在生产侧**重新成立**——这是封闭式补集**成立的前提**。

### P1（须给处置结论）

**P1-a · 行级整行豁免逃逸**（`:128-129`）：一行内「破坏性 op + 排除关键字（含注释）」⇒ 整行静默放行（三例实测漏检）。处置方向：排除判定**收窄到 op 自身 token 范围**（先剥行尾注释；并按 `;` 切分语句后逐语句豁免），使排除项不再「整行赦免」。现状仓内无此形态（双方已 grep 证实），属**未来形态的预防性收窄**。

**P1-b · orphan 测试自相矛盾**（`test_migration_expand_contract.py:112-126`）：去硬 `assert not orphans`，改为「报告 + 校验孤儿 pair 指向的 id 确未上产（防误标）」；维持规范 §4 / 闸门③「孤儿不红」。现测试靠「当前无孤儿」侥幸通过，**会误卡正当进行中的两步走**。

**P1-c · guard 作用域**：把判定文件清单由 `release.yml` 扩为 `release.yml + 其 include_tasks/import_tasks 目标`，并把 `lookup('pipe'…)` 一并纳入阶段 4 白名单扫描。

### 一般（记录，不阻断）

- **P1-d/E741**：手改 `test_release_playbook_has_no_ddl_logic.py:122,127` 的 `l` 变量名（本批交付物不应带 lint 错）；是否放开全仓 tests 的 ruff 排除＝独立批次。
- **大小写敏感**：`DROP/RENAME/ALTER COLUMN` 正则全大写，小写 `op.execute("drop table x")` 逃逸；建议加 `(?i)`（低风险）。
- **MySQL `RENAME TABLE a TO b`** 不被 `\bRENAME\s+TO\b` 命中（本仓 Postgres，低风险）。

## 六、附带发现（主会话复核出、A/B 均未提）

- **模块内两函数立场冲突**（M2）——已并入 P0-1 判据 3。
- **真源被切成两半**（M3）——已并入 P0-1 判据 2；亦是 P0-1 修复方向（把清单搬进模块）的**依据**。
- **`evaluate` 亦漏解码异常**（M4）——P0-2 修复须**同时**覆盖 evaluate，否则仓内闸门仍会崩。
- **`legacy` + `phase=` 可并存无互斥**（M5）——P0-1 修复时应在 `parse_declaration` 或 `evaluate` 加互斥校验（legacy 与 phase 不得同现）。
