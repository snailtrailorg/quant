## 一、致命（P0）

**P0-1 · 排除项「整语句赦免」⇒ 同语句内的破坏性 op 被静默洗白（非本轮引入，但属本批立法对象的直接失效）**

- 现象（实测，`server/src/data_platform/migration_policy.py:216` 的 `continue` 是整语句级）：
  | upgrade 语句 | 现命中 | 期望 |
  |---|---|---|
  | `op.execute("ALTER TABLE t DROP CONSTRAINT ck_x, DROP COLUMN c")` | **0** | 1（`DROP COLUMN`） |
  | `op.execute("ALTER TABLE t ALTER COLUMN c SET DEFAULT 1, DROP COLUMN d")` | **0** | 1 |
  | `op.execute("ALTER TABLE t DROP CONSTRAINT ck_x, RENAME TO t2")` | **0** | 1 |
  | 同上但 `;` 分两句 | 1 | 1 ✔ |
- 复现：`cd server && ./venv/bin/python - <<<'…'` 调 `scan_unsafe_lines(_mig(upgrade=<上表语句>))`（我自跑，见事实表 R6）。
- 为什么是 P0（三条，任一成立即 P0）：
  1. **静默漏检 + 不可逆**：rc=0 且无输出，破坏性 op **不需要任何声明**就随发布真执行 ⇒ 正是 2026-09-24 分裂事故那一类。
  2. **契约不闭合**：规范 §1.3 声明豁免的对象是**形态**（`DROP CONSTRAINT` / `op.drop_constraint`），执行面豁免的是**整语句**；模块 docstring:193-197 虽写了「逐语句」，但 **docstring 不是规范**，规范 §6 已知边界未列 ⇒ 对规范读者仍属「未声明即静默」（P0-B 的同款教训）。
  3. **不是边角写法**：PG 支持 `ALTER TABLE … DROP COLUMN b, DROP CONSTRAINT uq_a` 多动作同句；contract/清理步正是「一句清多件」的场景。
- 为何不是「本轮换说法」：本轮**未触及**该行；`9fa0e7f` 同样漏。但**本轮 `DROP\s+\w+` 宽口径扩大了它的杀伤面**（原本只吞 `TABLE|COLUMN|INDEX`，现吞 `DROP <任意对象>`）。
- 修法（我已验证可行，3 行）：排除项由「整语句 `continue`」改**减法**——
  `rest = st; for rx,_ in EXPLICIT_EXCLUSIONS: rest = re.sub(rx, " ", rest, _MATCH_FLAGS)`，再对 `rest` 匹配 unsafe。
  实测：① 上表三句由 0 ⇒ **1**；② `alter table t drop constraint ck_x` 仍 0；③ **全仓 141 迁移仍是 16 文件 / 33 处，且精确＝`LEGACY_FROZEN`(15) ∪ {`0122`}**（零假红）；④ 0116 / 0062 仍 0（反证钉⑤ 不破）。

## 二、严重（P1）

**P1-1 · 冻结集校验的作用域＝「受管集 ∩ 冻结集」，而非「冻结集」⇒ 冻结集文件「改名 / 从本版消失」零告警**
- 实测（隔离临时目录，`prev` 含已上产冻结文件；`0098` 为已上产 expand）：
  - ⑨ 冻结文件改名到非冻结名（`0131_x.py`，体内 `revision="0010"` 保 alembic 链不断）+ 重标 `phase=contract pair=0098` ⇒ **rc=0，无任何行**。
  - ⑩ 冻结文件从 new 目录整体删除 ⇒ **rc=0，无任何行**（`managed_set` 只迭代 new，删除不可见）。
- 判据：规范 §5.1 与模块 docstring:45-46 都写「**名在冻结集内 ⇒ 一律逐字比对 upgrade 段**」，实现只在「名在冻结集内 **且** 落进受管集」时比 ⇒ 实现 ⊂ 规范。
- 为何不是 P0：该路径下破坏性 op **到不了 prod**——alembic 从不重跑已应用的 revision（改名保 `revision="0010"` 时链不断但也不重跑），故是「不可变约束未覆盖面」而非「破坏性 op 静默执行」。
- 处置（建议就地修，勿挂账）：冻结集校验**以 `LEGACY_FROZEN` 为主体循环**，与受管集解耦——`for name in LEGACY_FROZEN: if (prev/name).is_file(): 要求 (new/name).is_file() 且 upgrade 段逐字一致`，否则拒「冻结集文件在本版消失」。

**P1-2 · 「rc=1 语义唯一＝有命中且拒」已被本轮扩张打破（契约表述失真）**
- 实测：冻结集文件 body 微改（`SELECT 1`→`SELECT 2`，**零破坏性 op**）+ 重标 contract ⇒ **rc=1**，而该文件 `scan_unsafe_lines` = 0 命中。
- 冲突点：模块 docstring:432-433「所有拒均发生在有命中的前提下」、规范 §6:82「`rc=1` 语义唯一＝有命中且拒」**均为假**。
- 影响面：**无安全影响**（内部错仍恒 rc=2，见事实表 R4；`allow_contract` 豁免 rc=1 是设计内行为）。但这条不变量是 P0-2 的立论基石，失真会让下一轮复审误判。
- 处置：不改代码（fail-closed 方向对），**改表述**为「`rc=1` ⇔ 拒（有命中 **或** 冻结集不可变违规）；内部错恒 `rc=2`」。

## 三、一般 / 陷阱核对

1. **宽口径 + `re.I` 的假红面（已查，仓内为零）**：`re.I` 让裸 Python 标识符落入网——`for drop in items:` 实测 OLD=0 / **NEW=1**（`DROP\s+\w+` 无前导 `\b` 之外的标识符约束）；`drop = 2`、`backup_drop = 1` 不命中。仓内 141 迁移零实例。建议加 `(?<![A-Za-z0-9_])` 前视收窄（仍挡不住 `for drop in`，可接受 fail-closed）。
2. **规范 §1.1 说明版未同步宽口径**：仍写「`DROP TABLE` / `DROP COLUMN` / `DROP INDEX`」，而代码已吞 `DROP <任意对象>`。规范自称「两者不一致时以代码为准」⇒ 说明失真，建议同步为「`DROP <任意对象>（TABLE/COLUMN/INDEX/SCHEMA/VIEW/TRIGGER…）`」。
3. **排除表注释「后两条」指错条目**（`migration_policy.py:96-98`）：实测 0062 依赖**第 1 条**裸 SQL `DROP\s+CONSTRAINT`、0116 依赖**第 2 条** `op\.drop_constraint\(`（逐条删除验证，见 R3）。应写「前两条」。
4. **空 expand 可过门**：`phase=expand` 体为 `SELECT 1` 的「假 expand」能上产，随后任意 contract 以它为 pair 即合规。门只验「pair 已上产且声明 expand」，不验 expand 是否真建新结构 ⇒ 建议在 §6 显式声明为已知边界（或挂账）。
5. **死代码**：`_upgrade_body`（`migration_policy.py:163`）全仓零引用（含测试）。
6. **守卫面未退化**：`test_release_playbook_has_no_ddl_logic.py` 的语料＝`release.yml` + 其 include/import 目标（封闭 allow-list），不含 `run_scenarios.sh`；本轮 S7j/S7k 新增的 `grep -q "发生变化"` / `grep -q "破坏性 DDL 命中"` 是**对门输出的断言**，非 bash 侧判定；`write_mig` 第 4 参只是道具落点 ⇒ **无 DDL 判定逻辑挪到 bash**。
