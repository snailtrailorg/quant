# 交付彻底性（一次做到底）

> 单点任务拖成八九轮上产，上下文爆表且结构越改越乱。本文是可执行闸，不是原则宣言。

## 二、动手前三问（写进任务/回答里，≤5 行，不写不许改）

1. **真源层**：这条事实的唯一真源在哪一层？（数据 / 判定 / 展示 / 告警）
2. **全部消费者**：谁读它？（用 grep/codegraph 列出**文件名+行号**，不许凭印象）
3. **既有机制**：现有体系是否已经表达它？（有 ⇒ 复用/扩展；无 ⇒ 才新建；新建要说明为何不能复用）

## 三、六面 DoD（缺一项不许提交）

| 面 | 必须回答 |
|---|---|
| ① 数据/契约 | 字段/表/迁移/双写/兼容期；破坏性变更是否两步走 |
| ② 写入路径 | 谁写、写什么、幂等、失败留痕 |
| ③ 读取/展示 | API 投影字段（**逐字段核对白名单**）、前端列/标签、i18n 三语 |
| ④ 可观测/告警 | 状态在哪可见、runbook 条目、恢复沿、是否与既有规则重复 |
| ⑤ 测试 | 行为断言优先于静态断言；覆盖失败路径；真库项标记 skip |
| ⑥ 文档 | 设计真源（D/A 文档）、规则表、待办挂账、进展 |

## 四、上产前验收（必须是一条**可执行证据**）

- 模板：`curl <端点> | 断言 <字段>=<期望>` 或 `psql -c "<SQL>" | 断言 <行/值>`
- **不接受"全量测试绿"作为唯一证据**——测试只证明代码能跑，不证明用户看到对的东西。
- 无法观测 ⇒ 说明不可交付：先补可观测，再上产。

## 五、一次上产原则

- 同一功能的六面**同一次提交、同一次上产**；禁止"先上后端、前端下一轮"。
- 唯一例外：法规强制的破坏性迁移两步走（expand→contract）。此时**第一步必须功能等价**
  （双写 + 读侧切换 + 展示不缺项），第二步只在任务文件标注，不留用户可见缺口。

## 六、反修补闸（用户指出问题时）

顺序固定：**三问 → 影响面清单（含同类点）→ 修法结论（修一处 / 改设计 / 整段重写）→ 用户确认 → 一次改完**。
禁止"听到哪里不对就立刻改那一处"。若结论是设计错，就整段重写并同步真源文档，不叠补丁。

## 七、提交前自审一问

> 页面/接口上出现的 `—` / `unknown` / `未定义` / `没数据`，有没有一处是我这次改动造成的？

有 ⇒ 不算完成。

## 八、上下文预算

- 同一文件**第 3 次**改动 ⇒ 停下来重读整段，不再凭片段打补丁。
- 结构性问题第一跳用 `codegraph_explore`，一次拿全消费者，替代多轮 grep/Read。
- 一条主线做完再开下一条；不并行改两个不相关的面。
