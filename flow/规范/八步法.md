# 八步法（强制交付流程，2026-08-26 用户定稿）

> 适用：重构批 3 起的所有批次与后续正式功能交付。审核方式一律**独立双盲**
> （两名独立审稿人同章程互不可见，主会话做同判比对与分歧仲裁）。
> 违反顺序=返工：任何一步未过不得进下一步（尤其：未过双盲审不得编码、未过测试不得提交、
> 未过审核不得部署）。

## 八步（顺序强制）

| 步 | 内容 | 产出 | 过门判据 |
|---|---|---|---|
| 1 方案 | 设计稿（任务文件/契约/风险面） | docs/任务/<批>-*.md 或设计文档 | 覆盖目标/契约/验收/回滚四要素 |
| 2 审核① | **方案的独立双盲审** | 两份审报告+同判综合 | 双同无 P0，P1 有处置结论 |
| 3 编码 | 按过审方案实现 | 代码变更 | 不越方案范围（越界=回到步 1） |
| 4 审核② | **代码的独立双盲审** | 同上 | 同上 |
| 5 单元测试 | 全量绿+pyflakes 零新增+分层绿 | 测试报告 | `pytest tests/ -q` 全绿 |
| 6 提交代码库 | git commit（原子、可回滚） | commit 序列 | 步 2/4/5 证据齐 |
| 7 部署到服务器 | 管道化部署（批 3 起走 Ansible release） | 部署记录 | 管道门全绿+盘外 |
| 8 集成/系统测试 | 生产观察+postverify+一交易日无事故 | 收官记录 | 无事故=批次完成（完成定义） |

## 与既有制度的关系
- 四道门（G1 单测/G2 真机冒烟/G3 事务化部署/G4 盘外）并入步 5/7/8 对应位置
- 「每批完成=生产一交易日无事故」= 步 8 的验收标准
- 「审核由用户触发」修订：**双盲审核由执行者在步 2/4 主动发起**（不再等用户催），
  用户保留终审与抽查权
- 收工流程（进展/踩坑/decisions）不变，在步 8 后

## 施工与交付守则（2026-08-30 web 重设计通宵批复盘后增补，W1-W7）

> 缘起（伞因）：通宵批把用户"不要停"误读为"须宣称全部完成"——形成**标题报全/脚注藏缺**
> 的报账结构：43 项施工只做了各页核心增量，进展条却记"Phase 0-3 完成"、绕开清单凭记忆
> 列 9 项（实际缺口 29 个验收点，事后机器扫描坐实）。双盲复盘修正：验收标准从未漂移
> （任务卡验收列一直在），缺的是**收工回读动作**与**运行时验证**这两个流程位置。

- **W1 完成声明=逐行对照验收**（并入步 6 过门/步 8 复核）：宣称"完成"必须附任务卡验收列
  的逐条状态（通过/绕开/未做）；"绕开清单"必须从任务卡**全文扫描**生成，禁凭记忆归纳。
  豁免：单文件/纯文案批可声明"无验收列"跳过，防拖死小任务。
- **W2 前端运行时冒烟门**（并入步 5）：build 绿≠完成——前端改动须本地全栈起
  （`scripts/dev-start.sh`）+登录+逐页加载+核心 API 状态断言后才算过步 5（自动化承接：
  `bash scripts/smoke-web.sh`，B5 2026-09-01——登录+20 端点状态/形状）。断言只打
  HTTP 状态/JSON 结构/登录流，**不打具体数据值**（防本地 DB 形态漂移导致红）。
  脚本沉淀 `scripts/smoke-web.sh` 随 web 批维护（P1-2 立项）。
- **W3 设计对照律**（并入步 2/4 审单+步 3 自检）：页面归位/菜单调整/权限可见性变更，
  必须引用设计文档（03/05 号等）具体节为依据；盲审报"不可达/藏死"类问题时，修法选项
  须对照信息架构定义选择，禁就近塞壳（前科：用户管理塞集成中心）。
- **W4 多段手术原子化**：已并入上方"四条原则"第 4 条。
- **W5 命令五要素**（CLAUDE.md 协作约束同步）：给用户执行的命令必须标【机器/账号/
  密码（写指针如 server-info.md，禁明文入对话史）/前置】。
- **W6 任务卡五要素**（步 1 四要素扩五）：+**制度符合性声明**——涉权限/通道/部署制度的
  变更，方案须先陈述"符合/偏离哪条制度"（前科：quant_root 常态密码通道违背三权分立）。
- **W7 大改造切批**（适用范围增补）：>10 项任务的大施工按 Phase 切批、分批完整走验收
  交付；"一会话一焦点"对通宵批是硬约束——宁可"完成 X 项+如实交剩余清单"，不可虚报
  完成度换进度观感。
- **W8 后台任务禁 sleep-poll**（2026-09-01 用户第三次纠正规约）：`run_in_background` 的任务完成时
  **自动发通知**——发出后什么都不做，等通知到达再处理结果。**禁止 `sleep N && tail`**（用户实测
  纯浪费 7 min/次）。判断：命令预计 >600s（如 staging+prod 双环境部署 ~14 min）→ 直接
  `run_in_background: true`，不发 sleep、不轮询、不预测结果。同理适用 agent 调用：子代理完成
  会通知，不等不等。

## 验证与演练守则（2026-08-27 G4 复盘后增补）

> 缘起：G4 过程病三发，根子同一——**用假设代替观测**。sleep 等待是它在代码里的形态
> （等时间猜任务完成），演练犯错是它在过程里的形态（猜参数/猜时序/拿"已给命令"当"已执行"）。

### 四条原则
1. **等条件不等时间**：等待耦合到状态本身；时间只承担轮询间隔与超时兜底。禁裸 sleep
   猜任务完成、"等 X 分钟后查"式时钟点等待（=把轮询间隔放大到分钟级+把判断外包给时钟）。
2. **超时必须可观测**：超时是异常路径，返回布尔/抛异常/标注 partial——禁止静默落空
   把部分数据当全量（adapters `_wait_update` 前科：XTP 慢时静默返回持仓子集当全量）。
3. **读状态不猜状态**：动手前读真实配置（`systemctl cat` + `show -p Restart*,StartLimit*`），
   变更后当场回读（EXISTS/is-active）并带时间戳记录。
4. **多段手术原子化**（W4，2026-08-30 web 重设计复盘：三起"assert 中断=内存替换丢失/
   部分落盘"事故）：长脚本多段修改先**全段只读匹配**（dry-run 确认每个锚点命中次数），
   通过后一次执行；执行后 grep 验证落点与计数。dry-run 拦不住"中断丢内存"——原子性靠
   "先全验后一动"，验证靠回读。

### 等待原语选型三问（何时事件化、何时轮询是正解——逐处判断，不整体套用）
1. **事件源存在吗**：进程内回调→Event/Condition；跨进程消息→Redis pub/sub；无事件源
   （systemctl 状态/分布式锁 SET NX/跨权限边界）→**轮询是唯一解，不是病**。
2. **耦合成本值不值**：订阅机制复杂度 vs 轮询实际伤害（SSE 0.5s 非阻塞轮询跨进程进度
   ≈零伤害，为它上 pub/sub 生命周期不值——保持轮询）。
3. **语义对得上吗**：协议约束优先于优雅（XTP 逐行推送无完成信号，"收齐"须稳定窗推断
   ——事件化须去抖重臂，naive 首事件即退=O-S1 回归）。

### 演练/验证条目
- **预检单（step 0）**：目标单元真实配置+账号权限边界+证据源指认（journal/celery 结果/notifications 表）
- **结论挂证据指针**（task_id/date_done/结果字典/SQL 行）；隔离测试不充分时明示"不可下结论"
- **记账门槛**：子验收全有证据才"过"，部分=「过/未验」分列；注入物清理+复验完成才许写"已清理"
- **环境事实禁硬编码**进任务文件（db 号/IP/路径）：写解析式命令+附实测值
- **验收可验性预审**：步 1/2 评审每条验收问"按给定方法测得到吗"

## 前端交付规约（2026-09-10 批11D 双 P0 复盘后增补）

> 背景：批11B-D 连续三天，前端两个 P0（TabsShell prop 漏声明/IM 分支丢失）+ 多处方案承诺落空
> （组件抽取不做/owner 列不做/smoke 断言事后补）——同根因：**前端没有后端 pytest 等价的硬门**，
> 加之用脚本 replace 改模板放大风险。规约对齐后端严格度。

### 三条铁律

1. **模板结构性改动禁用脚本 replace**：改 Vue 模板的分支/嵌套/组件结构，必须用 Edit 工具
   （old_string 匹配失败即报错，天然防静默）或整文件重写。shell/python 的 str.replace 无匹配
   不报错=静默失败（批11D 两个 P0 的直接根因）。locales 等配置文件同理——replace 后必须
   `assert 新内容 in 文件` 自检。
2. **UI 验收两级制（不依赖多模态）**：
   - 机器级：smoke-ui 断言升级——关键改动点要**结构断言**（元素层级/组件类名/交互后状态），
     非仅文字存在性；交互路径（点击流）端到端断言；flaky 重跑两次以上必须查根因，禁止靠重试磨绿。
   - 人工级：**视觉验收=用户本人**（大模型不承担视觉判断——执行模型可能非多模态）。
     交付时给用户"验收入口清单"（页面 URL+改动点+操作步骤），用户过目后批算收。
3. **方案清单=承诺**：任务文件范围表列的组件/文件项是硬承诺；砍项必须显式回写任务文件并
   在进展条声明"砍了什么为什么"，不允许默默不做（盲审抓到才算数=失职）。

### 附：验证脚本质量（批11D 连续 flaky 教训）

puppeteer 验证脚本等待不足导致的假失败连续 5+ 次，每次归咎"时序"未查根因——规则：同一脚本
重跑第 2 次必须 dump 页面状态（URL/body/console）定位，第 3 次仍 flaky 禁止再跑，改脚本
（显式 waitFor 而非 sleep 竞猜）。
