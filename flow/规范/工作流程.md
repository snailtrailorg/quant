# 任务生命周期（工作流程）

> 一个任务从「有个想法」到「进了生产」，走几个环节、每步产出落到哪个文件——这是「活儿怎么流动」的详规。

---

## 零、四份规范的分工（先看这张表，避免读串）

| 规范 | 管什么 |
|---|---|
| **本文件** | 任务的**流程**：环节顺序、每步产出落哪、收口动作 |
| `任务模板.md` | 任务文件的**写法**：字段、引用规则、粒度、mock |
| `文档维护SOP.md` | **真相源文档**（`CLAUDE.md` 体系）该写什么、不该写什么 |
| `八步法.md` | **交付门禁**：双盲审 / 测试 / 部署的强制顺序 |

术语见 `术语表.md`；规范总索引见 `flow/规范/README.md`。

## 一、四环节主循环

```
新任务
  ↓
① 立项分析 ── 判断类型：纯实施 ｜ 还是 设计/契约变更？
  ↓
② 设计先行（仅设计变更）── 改设计文档，重写整篇使其自洽（§二）
  ↓
③ 任务文件 ── flow/任务/批xxx-描述.md，引用②的章节，只写实施步骤
  ↓
④ 待办挂行 ── flow/待办.md 加一行索引（概要一句话 + 指向任务文件）
  ↓
⑤ 执行 ── 门禁走 八步法.md（方案双盲审→编码→代码双盲审→单测→提交→部署→集成测试）
  ↓
⑥ 收口 ── 待办删行 ｜ 进展写简述+引用 ｜ 任务文件归档 docs/obsolete/任务归档/
```

### ① 立项分析

先判断这个任务属于哪一类，决定后面走哪条路：

| 类型 | 判据 | 后续路径 |
|---|---|---|
| **纯实施** | 设计已定，只改实现 | 直接进 ③ |
| **设计变更** | 契约 / 结构 / 取舍要动 | **必须先进 ②**，再进 ③ |
| **纯运维 / 例行检查** | 不改代码 | 抄 `flow/规范/` 里的手册（如 `观察日三查.md`），不进本循环 |

### ② 设计先行（仅在改动设计时）

**顺序是硬的：设计文档先改，任务文件后写。**

反过来（先写任务文件、设计文档后补）会立刻产生「任务文件里一套方案、设计文档里另一套」——两处真源，漂移从此开始。

改法见 §二「重写制」。

### ③ 任务文件

`flow/任务/批<编号>-<描述>.md`，按 `任务模板.md` 写。要点：

- **正文只写**：目标 / 范围（做什么 + 明确不碰什么）/ 实施步骤 / 验收命令 / mock 方式。
- **设计一律引用**：写「见 `docs/architecture/A0x-…md` §N」，**不复制**方案段落。
- 为什么：设计文档是方案的真源。任务文件复述一遍＝造第二个真源，改一处忘一处即失准。

### ④ 待办挂行

`flow/待办.md` 是**索引层**，一行 = 一个未闭合项：

```
| # | 事项（一句话） | 状态 | 方案 | 任务文件 |
```

**禁止**把实施细节、上产记录、裁定推理写进待办——那些各有归宿（见 §三）。

### ⑤ 执行

门禁走 `八步法.md`：顺序强制，未过双盲审不得编码、未过测试不得提交、未过审核不得部署。

### ⑥ 收口

| 动作 | 落在哪 |
|---|---|
| 任务完成 → **删掉待办那一行**（不留行内史） | `flow/待办.md` |
| 完成史：一句话简述 + 引用（任务文件 / 设计文档 / commit / release id） | `flow/进展/<ISO周>.md` 顶部 |
| 任务文件归档 | `docs/obsolete/任务归档/` |
| 过程中的裁定与理由 | `flow/decisions.md` |
| 过程中的坑与教训 | `flow/踩坑记录.md` |

## 二、两制式：什么该追加，什么必须重写

**这是本体系最容易出错的地方，单独立法（2026-10-04 用户裁定）。**

| 制式 | 适用 | 文件 | 为什么 |
|---|---|---|---|
| **追加制**<br>（append，新的放最上面） | 流水 / 事件 | `flow/进展/<周>.md`<br>`flow/踩坑记录.md`<br>`flow/decisions.md` | 它们是**时间线**——追加就是它们的正确形态，历史本身就是内容 |
| **重写制**<br>（改就重写整篇） | 状态 / 规则 | `docs/architecture/`<br>`docs/design/`<br>`flow/方案/`<br>`flow/规范/`<br>`CLAUDE.md` | 它们是**当前状态的快照**——追加会把它变成「反反复复的时间线」，读者要拼才能得到真相 |

### 重写制怎么操作

- ❌ 在末尾加一节「> 2026-10-05 更新：……」，让新旧说法并存
- ✅ **重读全文，把变化揉进正文各处，删掉被取代的旧表述**，让整篇自洽

允许保留**一行时态声明**（如「现行：… ｜ 挂起待实施：…」）——那是状态标注，不是变更日志。

**判据**：一个新会话第一次读这份文档，能不能**直接**得到「现在的真相」？

- 能 → 合格
- 要翻时间线、要比对前后版本才能拼出来 → 不合格，重写

**变更史去哪了？** `git log`。文档不承担变更史职责。

## 三、分层归属（内容 → 归宿）· 单一真源

| 内容 | 归宿 |
|---|---|
| 技术方案 / 勘察推理 / 设计取舍 | `docs/architecture/`（架构级）· `docs/design/`（模块级 D 系列）· `flow/方案/`（待定稿方案） |
| 实施步骤 / 验收清单 / 限定范围 | `flow/任务/批xxx-描述.md` |
| 完成史（上产 / 五证 / 交付数） | `flow/进展/<ISO周>.md` + git log |
| 裁定与理由 | `flow/decisions.md` |
| 问题与教训 | `flow/踩坑记录.md` |
| 例行检查 / 运维手册 | `flow/规范/` |
| 已完成任务文件 | `docs/obsolete/任务归档/` |

**一句话判据**：协调 / 推进项目的 → `flow/`；要交付的内容 → `docs/`（知识）或 `server/src/`（代码）。

> 本表是**唯一真源**；`flow/待办.md` 表头只引用不复制（复制＝两处真源）。

## 四、三个核心机制

### A. 进展日志 = 接力棒

位置 `flow/进展/<ISO周>.md`（周号 `date +%G-W%V`），**追加、新的放最上面**；`flow/进展.md` 只留索引 + 「最近 3 条」。**最近一条 = 当前交接棒**（`CLAUDE.md` 开工必读）。

每条字段：**做了什么 / 为什么 / 怎么理解 / 产出（路径）/ 问题→解决 / 下一步**。

**铁律：只带「指针 + 增量」**——指向真实产出（给路径）+ 这一棒新增，**不重抄内容**；接手方顺指针回源文件读。

（为什么是一个 append 文件而不是 N 张卡或覆盖快照：N 张卡会堆爆；覆盖会丢历史、没法接力。append 一个文件 = 留历史 + 不爆 + 顶部即棒。）

### B. 共用入口 = 运行时合同

`CLAUDE.md` 每个会话自动加载、是**两个工具共用的规则通道**。精要规则、约束、目录地图、指针必须写在它里面。`AGENTS.md` 软链到它，写一次两端生效。

### C. 跨模型评审

主控（持上下文 / 编排）+ 独立第二双眼。何时：每次交付前、高风险逻辑、设计岔路口。强制形态见 `八步法.md`（一律独立双盲）。

## 五、目录归属

| 文件夹 | 放什么 |
|---|---|
| `flow/` | 控制层：`charter.md`（章程）· `plan.md`（里程碑契约）· `待办.md`（索引）· `进展/`（append 日志）· `任务/`（进行中任务规格）· `方案/`（待定稿方案）· `decisions.md` · `踩坑记录.md` · `规范/` · `审计/` · `稳定性检查/` |
| `docs/` | 内容层：`architecture/`（架构真相 + 契约）· `design/`（模块设计 D 系列）· `manual/`（使用手册）· `reference/`（外部资料）· `obsolete/`（归档） |
| `CLAUDE.md` | 运行时合同（见机制 B） |
| `server/src/` · `web/src/` | 代码产物本身 |

**判据**：这份东西是**协调 / 推进项目**的 → `flow/`；是**项目要交付的内容** → `docs/`（知识 / 文档）或 `server/src/`·`web/src/`（代码）。

控制层**指向**内容层：任务文件 / 进展条里的「产出（路径）」就是 `docs/`·`server/src/` 路径。
