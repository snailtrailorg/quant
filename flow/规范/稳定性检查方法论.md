# 稳定性检查方法论（SOP）

> 2026-08-17 制定。背景：实盘链路验证通过当天暴露 7 雷，均为"撞上才发现"；用户决定 XTP 改共享行情进程架构（实时性换内存），稳定性要求更高。
> 本文回答一个问题：**怎么检查才能不遗漏**。先定方法，再执行检查（检查执行计划见 §7）。
> 配套：`docs/architecture/12-实盘稳定性设计.md`（第一轮经验驱动清单，本文是其系统化升级的基准）。

## 1. 适用范围（in-scope 清单——"无遗漏"的锚点）

无遗漏是相对**固定清单**而言的。被检对象全集：

| 类 | 对象 |
|---|---|
| 进程 | quant-web-api@quant / celery-worker / celery-beat / feishu-bot@N / **live-task runner**（现状）/ **行情 hub + 轻策略 worker**（共享架构改造后） |
| 存储 | PostgreSQL（quant 库）/ Valkey（db2/db3）/ 文件（bar 表、avatar、celerybeat schedule、journal） |
| 外部依赖 | XTP 行情/交易服务器、SMTP、飞书开放平台、Tushare/AkShare、（未来）币安/OKX |
| 配置 | systemd unit ×6、polkit rules、.env、fstab、nginx、alembic 链 |
| 工具链 | quant-deploy.sh、deploy-server.sh、dev-start.sh、verify.sh |
| 数据流 | tick→bar→on_bar→signal→order→trade→position→snapshot→API→前端；同步任务→PG→回测 |
| 变更操作 | 部署、迁移、unit 变更、策略启停、配置修改、服务器运维（swap/内核参数） |

## 2. 防遗漏的元原则（怎么知道清单本身没漏）

1. **枚举空间固定化**：所有检查项落在"组件 × 故障轴 × 生命周期"矩阵里（§3），矩阵空格必须显式标注"不适用+理由"，不许留白跳过——空白就是遗漏的藏身处
2. **多源交叉，不靠单脑**：每类检查项至少两个独立来源——①官方文档章节目录反推 ②本项目踩坑库 ③社区/上游 issue 故障库 ④红队攻击性枚举（"怎么让它亏钱/失控/失明"）⑤第二视角独立评审（Codex 或独立子代理盲审后合并）
3. **从真实故障时间线反推**：把 12 号文档 7 雷 + 踩坑记录全部映射进矩阵，验证矩阵表达力（表达不了的失败模式 = 矩阵缺轴）
4. **变更也是故障源**：检查不只覆盖"运行时"，一切会改变系统状态的操作（§3E）都在枚举内

## 3. 枚举框架（五轴）

### A 组件轴
§1 清单，逐个过 B/C/D 轴。

### B 故障模式轴（每组件的标准故障集）
crash / hang（不崩但停转）/ 变慢 / 部分失败（半成功）/ 网络断连与分区 / 资源耗尽（内存·CPU·磁盘·fd·连接数）/ 状态损坏 / 时钟异常（跳变·时区·夏令时）/ 依赖级联失败 / 权限与配额（polkit·cgroup·OOM 选择）/ 原生库异常（segfault·abort·死锁）。

### C 生命周期轴（每个实体全状态转移）
进程：install→start→running→degrade→fail→restart→stop→disable。
连接/会话：建立→认证→活跃→心跳丢失→断开→重连→**重连后状态恢复**（重订阅/重查询/对账——历史雷区）。
订单：意图→WAL→提交→部分成交→终态（成交/撤/拒）→**对账闭环**。
任务：pending→running→stopped/error→删除→**残留清理**（unit/缓存/订阅）。
DB 事务/Valkey key：创建→使用→过期/泄漏。

### D 时间尺度轴
秒级（下单窗口/崩溃窗口）→ 分钟级（bar/快照/心跳）→ 日级（交易时段开闭·收盘对账·日志滚动）→ 周级（数据回补·备份·保留）→ 变更时刻（部署/迁移与运行中任务的交叠）。

### E 变更轴
部署、alembic 迁移、unit/polkit 变更、策略启停、配置热改、服务器级操作（升配/内核/网络）。每项检查：变更窗口保护、部分失败回滚、与运行中实盘任务的互斥。

## 4. 检查手段（四层递进，L1→L4）

### L1 代码静态深读（读法，不是 grep）
- **线程模型图**：vnpy EventEngine 线程 / runner 主循环 / uvicorn 线程池 / celery prefork——画出所有**跨线程共享状态**，逐一核对锁与可见性（重点：runner 里 event 线程回调 `on_vnpy_bar` 与主循环 `history` 列表的并发访问）
- **异常审计**：每个 `except` 三问——吞掉的异常谁会知道？该失败的操作有没有留下状态残留？外层调用者拿到的语义对吗
- **资源关闭审计**：连接/文件/子进程/gateway 的关闭路径 × 正常退出/异常退出/被杀 三种方式
- **状态机推演**：订单/任务/XTP 会话三张状态机图，标注所有转移的实现位置，找缺失转移（如：委托发出后连接断开，回报丢失，状态机停在哪？谁推进？）
- **崩溃一致性标注**：每个"外部副作用+本地记录"对标注顺序（发单 vs 写库、订阅 vs 登记、通知 vs 落库），非原子窗口逐个定性

### L2 工具设计研究（各工具要研读什么，产检查项）
- **systemd**：Restart×StartLimit 交互语义、After/Requires/Wants 真实行为、Watchdog 协议、KillMode/KillSignal、cgroup 内存记账（MemoryMax 是否含 swap、MemoryHigh 节流行为）、OnFailure 触发条件、模板实例化规则（今天幽灵实例的机制要彻底搞清并文档化）
- **vnpy**：EventEngine 队列模型（丢事件？阻塞行为）、gateway 断线通知与重连语义（重连后是否自动重订阅）、MainEngine.close 做什么不做什么
- **XTP SDK**：TD 单会话约束、行情断线重连要求、订单回报可靠性（会丢吗）、查询接口的节流限制
- **PostgreSQL/psycopg**：连接中断的事务语义、DDL 锁与时长、statement_timeout 配置、连接数上限
- **Valkey**：TTL 精度、持久化配置（重启丢哪些 key）、maxmemory 策略
- **polkit/journald**：规则加载时机、日志保留与磁盘上限
- 方法：读官方文档对应章节 + 本地实验验证关键语义（不猜）

### L3 业界基准对照（联网 spe curl 核实，WebSearch 不可用）
- Google SRE 四金信号（延迟/流量/错误/饱和度）→ 映射到本系统每组件
- AWS Well-Architected 可靠性支柱检查表 → 逐条对照
- Chaos Engineering 原则：先建"稳定行为假设表"，实验验证假设（假设=检查项的可证伪形式）
- 券商柜台/量化系统惯例：启动对账、fencing（防旧进程复活双活）、幂等重试、四账核对
- vnpy/XTP 社区已知故障库（GitHub issues、社区帖）排雷

### L4 故障注入实测（dev 环境 + 测试账户）
标准注入清单：kill -9 于订单状态机各阶段 / 进程挂死（SIGSTOP）验看门狗 / 断网（断 XTP/PG/Valkey）验重连与降级 / 内存填充验 OOM 行为与受害者选择 / 双启动同任务验唯一性与 fencing / 时钟跳变 / 部署与运行任务交叠 / PG 锁表 / journal 塞满磁盘。
每项记录：预期行为（来自假设表）vs 实际行为。差异即发现。

## 5. 覆盖率验收标准

1. 矩阵空格清零（每个空格 = 组件×故障模式 的处置结论：已有机制/发现缺陷/不适用+理由）
2. 双盲交叉：第二视角（Codex/独立子代理）在不见我清单的前提下独立枚举，合并时**只有对方有我没有的项**逐条补入——差异项是金子
3. 历史雷全回归：12 号文档 7 雷 + 踩坑记录全部能被矩阵定位（定位不了的补轴）
4. 每个发现可证伪：附注入实验或代码行号证据，不收"感觉"
5. 每个坑固化测试（今天 7 雷只有部分有测试）

## 6. 产出物

1. 检查矩阵（覆盖表，带处置结论）
2. 检查报告（发现按灾难/严重/一般分级，每条附证据与修复建议）
3. **共享行情架构稳定性需求书**（新失败面：hub 单点、hub↔worker 通信丢消息/乱序/延迟、hub 重启时 worker 行为（禁止在陈旧数据上交易）、bar 序号连续性校验、fencing token 防旧 hub 复活、worker 退出对 hub 的清理）——直接喂给架构设计
4. 修复批次待办（并入 ST 批次，按 P0/P1/P2）

## 7. 执行计划（方法论审定后执行）

| 阶段 | 内容 | 产出 | 预估 |
|---|---|---|---|
| P-1 | 建矩阵骨架（§1×§3），映射历史雷 | 矩阵初稿 | 0.5 会话 |
| P-2 | L1 代码深读（runner/adapters/strategy/web_api 启停路径） | 状态机图+并发图+崩溃一致性表 | 1 会话 |
| P-3 | L2 工具语义研究（systemd/vnpy/XTP 优先，本地实验验证） | 工具语义备忘（进踩坑/记忆） | 0.5-1 会话 |
| P-4 | L3 业界对照（spe curl 联网）+ 双盲交叉评审 | 基准差距表+差异项 | 0.5-1 会话 |
| P-5 | L4 故障注入实测（dev+测试账户） | 假设表 vs 实测记录 | 1 会话 |
| P-6 | 汇总报告 + 共享架构需求书 + 修复批次 | §6 四件套 | 0.5 会话 |

约束：P-5 注入只在本地 dev / 服务器测试账户+非交易时段；服务器注入需用户在场。
