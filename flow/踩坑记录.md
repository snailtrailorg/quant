## 2026-08-27 · systemd StartLimit 窗口内 reset-failed 后 start 仍被拒（G4 ④a 实证）

**现象**：hub 5 杀 124s 打穿 StartLimit（Burst=5/Interval=300s）→ failed。L3 首轮 beat（窗口过期前 31s）reset-failed+start → start 被拒（l3_failed，新进程未拉起）；第二轮 beat（窗口过期后）重试成功。

**根因**：`systemctl reset-failed` 清 failed 态，但**不清窗口内已计数的 start 尝试**——StartLimitIntervalSec 未过期时 start 仍报 "Start request repeated too quickly"。3a 沙箱已遇同款（quant-svc wrapper 前置 reset-failed 的原因），本次产上再证。

**防御**：L3 按设计未记退避（l3_failed 分支不计 attempts），300s 后自然重试即自愈——**不要**在 l3_failed 后立即手动反复 start（每试一次都重新计数续窗）。若人工介入：等窗口过期（Interval 从最后一次 start 尝试起算）再 start。

**附带缺口（P2）**：l3_failed 分支不记 stderr 不告警——持续失败会静默每 300s 重试；待补日志+告警。

## 长事务锁链闷死 DDL 与部署管道自伤（2026-08-20 锁链事件）

- **现象链**：14:29 手动触发 astock_basic 同步（逐行 INSERT 长事务）→ 15:0x 部署跑 alembic `CREATE INDEX`（要锁）排队等事务 → 部署侧三次中断（闸门差 1 分钟/timeout/`| head` SIGPIPE 杀 rsync）→ 每次"僵尸 alembic"在 PG 侧持锁滞留（pkill 客户端≠PG 释放锁，TCP 半开连接默认等 keepalive 数小时）→ 7 个 CREATE INDEX 排队 + 19min idle in transaction → 后续部署全部"卡在 migrate"。
- **诊断钥匙**：`pg_stat_activity` 按 `xact_start` 排序看事务龄——`Lock/relation` 等锁者+最早一条 `Client/ClientRead` 长事务=源头；`pg_terminate_backend(pid)` 精确清 9 条解锁。**kill 客户端进程不清 PG 锁**，PG 侧 terminate 才是终点。
- **通用教训 1**：**同步任务事务里禁跨网络拉取**（Tushare 慢=49min 事务）；批量写要分段提交（N 行/事务）。→ 已立项数据库操作统一规划（18 号文档）根治。
- **通用教训 2**：**DDL 无限等锁=部署闷死**——alembic/迁移要带 `lock_timeout`；索引上生产用 `CREATE INDEX CONCURRENTLY`。
- **通用教训 3**：**部署命令禁接 `| head`**（SIGPIPE 杀 rsync 半途）；输出重定向文件再 grep。部署超时转后台时,rsync 可能已完成而服务未重启——指纹对比的是"服务器文件"非"进程代码",形成"文件新+进程旧"死循环（重启被指纹跳过）——`--force` 语义扩展为强制重启即为此解（用户审核后同步 michael 版生效）。
- **通用教训 4**：`idle in transaction` 是池化会话事务边界失管的信号（SELECT 完归还未 commit）——PG 侧 `idle_in_transaction_session_timeout` 该设（入 DB 规划）。
- **权限三权分立实证**：bernard 的 sudo 白名单精确到"以 michael 跑 quant-deploy.sh 单命令"——`--preserve-env`/`sudo -u michael cp` 均被正确拒。脚本同步 michael=用户专属步骤，勿试任何绕过。

## 断流守卫基线必须时段作用域；重启不是疗法（2026-08-18 hub 晨间自杀案）

- **现象**：hub 每晨 09:31:02 必自杀重启（journal：`hub tick 断流 34627s`）。根因链：`first_tick_today`/`last_tick_wall` 是**进程生命周期**变量，昨夜 23:54 回放最后 tick 把基线钉在昨天；09:31 `in_session()` 翻真瞬间 stale=9.6h>300s → 按设计自杀。注释里"防假日误判断流"的保护恰被此击穿。
- **通用教训 1**：任何"staleness/新鲜度"基线必须**会话/时段作用域**（进入沿清零），进程累计值跨日必污染。三所规则不一（沪深收盘竞价/北交所无、可转债临停零 tick 合法）+券商平台偏差（夜间回放），把时段预期编进守卫触发器必在边界翻车。
- **通用教训 2**：**重启只解决进程自身问题**（死锁/内存/内部状态机）；平台/网络问题重启无效且重启风暴有害。守卫动作只认事实信号（连接回调/线程状态/watchdog/unit 状态），数据节奏异常→告警+消费端冻结，不自杀。
- **修复**（15-服务监控设计.md）：删两处自杀改告警；基线改时段内；BUY 安全判定挪 send_order 时刻（`buy_ok_check`），日历从动作路径清零。

- **现象**：服务器 .env 早配了 `CELERY_BROKER_URL=db5/CELERY_RESULT_BACKEND=db6`，但 `app.py` 直连 `VALKEY_URL`——配置静默失效，celery 实际与业务键混装 db4。

## clear-redis 默认值与服务器实际分库错位（2026-08-17）

## 第十坑+第十一坑：rollback 波次缺口 + hub Prevent 含 3/4 部署炸弹（2026-08-27）

- **第十坑（rollback 波次缺口）**：rollback.yml 独立入口缺 dbro 波次采集（release 有 pre_tasks 而 rollback 没有）——live/feishu 清单恒空 → 任务 8/feishu 不被回滚波次重启 → 收敛断言抓"钉新版"。修 f16c4e5。
