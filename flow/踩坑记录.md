## 2026-08-10 · Codex exec 调 Ark coding 端点返 400（function calling invalid escape + 52万token循环）[Codex/Ark 坑]

- **现象**：`mcp__subcodex__run` 派 D2（L2+workspace-write），Codex 跑 11 分钟后 exit 1，零文件改动。输出 1MB 全是 `ReasoningSummaryDelta without active item` / `OutputTextDelta without active item` noise，末尾 `codex_api::endpoint::responses: error=http 400 Bad Request: InvalidParameter "Invalid request body"`（Ark ark.cn-beijing.volces.com/api/coding/v3）。
- **根因**：用户直接 `codex` CLI 跑 hello 正常（不触发工具调用）。subcodex 用 `@openai/codex-sdk` 的 `runStreamed(prompt)` 跑复杂任务（读文件/改码/跑 pytest 多工具调用）暴露 Ark model function calling bug：rollout 末尾 `function_call_output: "failed to parse function arguments: invalid escape at line 1 column 128"`（Ark 生成的工具调用 arguments JSON 有 invalid escape）-> Codex 解析失败 -> 重试循环 -> 上下文累积到 **52 万 input token**（cached 46 万=大量重复重发）-> Ark 拒超限请求体 -> 400。config.toml: model=ark-code-latest, reasoning_effort=high, wire_api=responses, base_url=Ark coding 端点。
- **解决**：根因在 Ark model function calling 不稳（非 Contract/非配置错）。绕过：① 换 function calling 稳定的 model（cc-switch 切 Anthropic/OpenAI 直连）；② 本会话豁免 full-subagent 铁律，Claude Code 直接做 D2（材料已预热，增量约 5-10K token vs Codex 52万，且不生成 arguments JSON 避开 Ark bug）。
- **教训**：① subcodex 跑出 stream noise（ReasoningSummaryDelta/OutputTextDelta without active item）是 codex_core 状态机 bug 的 noise，**非根因**；真正根因看 rollout 末尾（~/.codex/sessions/<date>/rollout-*.jsonl）的 function_call_output / API error。② Ark coding 端点 function calling 在复杂任务下不稳，简单对话 OK；subagent 模式（多工具调用）慎用 Ark。③ 诊断 Codex 失败：看 rollout JSONL（完整会话）+ ~/.claude/codex-logs/progress-L2-*.log（subcodex 轨迹），比 1MB 的 mcp result 噪音有用得多。

## 2026-08-10 · analysis.py 里箭头字符是 U+2192（非 ASCII 的 - + >），Edit 多行匹配失败 [工具坑]

- **现象**：Edit `server/src/astock_analysis/analysis.py` 的 MinuteAnalysisEngine.on_bar（old_string 含 docstring `K 线 -> 实时研判`），报 `String to replace not found`。python `repr()` 显示看起来正常，但 `old in s` assert 失败。
- **根因**：文件里 docstring/注释的箭头是 **U+2192（单字符右箭头）**，非 ASCII 的 `-`+`>`（0x2D 0x3E）。python repr 对可打印 Unicode 不转义（显示原字符），终端字体 fallback 也显示成 `->`，**肉眼无法区分**。Edit old_string 输入 ASCII 箭头不匹配 U+2192。注意：函数签名行 `def on_bar(...) -> dict:` 的箭头是 ASCII（Python 语法必须），只有 docstring/注释里的箭头是 U+2192。
- **解决**：python 脚本从文件**精确读取** old 段（`s.find("def on_bar")` 到 return 行末），用读到的字符串做 `s.replace(old, new)`，不手写 old。new 内容不含箭头字符（docstring 改用"实时研判（bar+history 因子计算）"不用箭头）。`ast.parse` 验证语法。
- **教训**：① Edit 多行含中文文档失败 + repr 看起来正常 -> 警惕 U+2192/全角空格等不可见差异；用 `ord(c)` 查 codepoint 或 python find 定位。② 改文件优先 Edit；Edit 多次失败改用 python `s.replace`（old 从文件读，精确匹配），带 `ast.parse`/`assert in` 验证。③ 写新代码 docstring 里别用箭头字符（用"返回"/"到"代替），避免 U+2192 混入。

## 2026-08-09 · Bash 工作目录持久跨调用（cd 后不自动复位）[工具坑]

- **现象**：`cd /home/bernard/Projects/quant/web && npm run build` 后，后续 `venv/bin/python -m pytest`（相对 server）报 `No such file or directory`--CWD 仍是 web，不是 primary（server）。
- **根因**：Bash 工具工作目录**跨调用持久**（"Working directory persists between calls"），`cd` 在 compound command 改 CWD 后不自动复位到 primary。
- **解决**：跨目录操作后，后续命令显式 `cd /home/bernard/Projects/quant/server && ...`，或用绝对路径（`/home/bernard/Projects/quant/server/venv/bin/python`）。
- **教训**：① 涉及 `cd` 到其他目录（web/scripts）后，下一个 server 命令记得 `cd` 回来。② 优先用绝对路径避免 CWD 依赖。③ pytest/venv 命令默认 CWD=server，cd web 后必复位。

## 2026-08-04 · 飞书 API 返回结构不一致，取字段前必须 dump 返回 [已解决]

- **现象**：`/bot/v3/info` 返回 `{'bot': {'app_name': '量化助手'}, 'code': 0}`，取 app_name 先猜 `data.app_name`（空）、再猜 `data.bot.app_name`（空）、最后才 `bot.app_name`（对）。往返 3 次，浪费 token + 时间。

## 2026-08-03 · 参考文档可能是 AI 生成的不准确方案（飞书扫码旧版）+ 核实方法论 [已弃旧版]

- **现象**：旧版飞书扫码方案声称调 `oauth/v2/device/authorize` 端点拿 app_id/app_secret。但 OAuth 设备授权（RFC 8628）返回 access_token（用户授权），**不返回 app_secret**（应用凭证）--违反 OAuth 安全模型。文档含糊（"以实际 API 为准""可能需额外请求"）+ 参考项目（LobsterAI/cc-connect）可能不存在。
- **核实方法**：联网 spe curl 飞书文档（SPA 拿不到正文）+ GitHub code search（需认证）都失败。最终**本地 inspect SDK** 确认：`venv/bin/python -c "import lark_oapi; print(hasattr(lark_oapi,'register_app'))"`--直接看 SDK 有没有该方法，最可靠。
- **结果**：升级版用官方 SDK `lark_oapi.register_app`（v1.7.1 真实存在 + 官方文档背书），可信。旧版已弃。
- **教训**：
  1. 参考文档可能是 AI 生成的不准确方案，用**安全模型/协议标准**可判断（app_secret 不通过 OAuth 授权流程返回是 OAuth 2.0 铁律）。
  2. 联网核实失败时（SPA/需认证），**本地 inspect SDK/库**（hasattr/dir/inspect.signature）是可靠 fallback。
  3. 用户给"升级版"要重新评估（可能修正了），不固守旧判断。

## 2026-08-03 · vnpy 4.0 查询事件驱动（无同步 query_position 返回）[设计约束，已适配]

- **现象**：vnpy 4.0 `MainEngine` 只有 `send_order`/`cancel_order`，**没有** `query_position`/`query_orders`/`query_trades`/`query_account`。`XtpGateway` 有 `query_position()`/`query_account()` 但返回 None（异步触发，结果通过 `EVENT_POSITION`/`EVENT_ACCOUNT` 推送）。`query_orders`/`query_trades` 网关层没有（靠 `EVENT_ORDER`/`EVENT_TRADE` 推送收集）。
- **根因**：vnpy 设计是事件驱动--调 `gateway.query_position()` 触发 SDK 异步查，结果通过 EventEngine 推事件。不是同步返回。
- **适配**：XTPAdapter `__init__` 注册 `EVENT_ORDER/TRADE/POSITION/ACCOUNT` 监听收集到缓存（dict）；`query_position()` 调 `gateway.query_position()` 后轮询等缓存更新（`_wait_update`，超时 2s）；`query_orders()`/`query_trades()` 直接从缓存读。
- **教训**：vnpy 查询非同步，封装 adapter 时要 (1) 注册事件监听收集，(2) query 触发后轮询/等事件，(3) 带超时防卡死。

## 2026-08-03 · deploy health check 误报失败（sleep 2 太短，uvicorn+vnpy 启动慢）[已解决]

- **现象**：连续两次 `deploy-server.sh` 末尾 `⚠️ health check 失败（服务可能未就绪）`，但 `curl http://120.24.235.98/health` 实测返回 `{"status":"ok","version":"0.1.0"}`——服务实际是好的。
- **根因**：`quant-deploy.sh` 的 `restart_server()` 重启 `quant-web-api@quant` 后只 `sleep 2` 就 `curl :8001/health`。uvicorn 启动 + vnpy/PySide6 import + PG 连接 > 2s，curl 时服务还没 ready → 误报失败。脚本 `quant-deploy.sh:323 sleep 2` + `:324 curl -s`（无 `-f`，失败也不显式报错，靠 `||` 兜底打 warning）。
- **解决**：`restart_server()` 改轮询重试——`for i in seq 1 15: curl -sf :8001/health; 通了 break; 每次 sleep 2`，最多等 30s。通了打 `✅ health ok（第 N 次尝试，约 Xs）`，超时才真报失败并提示 `journalctl -u quant-web-api@quant`。
- **教训**：部署后 health check 不能单次 curl + 短 sleep——服务启动有延迟（尤其拖 vnpy/PySide6 的）。用轮询重试（带超时上限），既不误报又能抓真崩。`curl -sf`（`-f` 失败返回非 0）比 `curl -s || echo` 更可靠。

## 2026-08-03 · 服务器 XTP 连接成功 + 本地连不上中泰（出口网络）+ vnpy subscribe 单 req 非 list [已解决]

- **现象**：本地手动编译 vnpy_xtp cp310 后跑 `test_xtp_connect.py`：vnpy 代码层全通（import/MainEngine/connect/subscribe 调用都成功），但行情+交易都报 `connect server failed.[OS:115]Operation now in progress`（TCP 握手 10s 没完成）。`ping 119.3.103.38` 通（32ms 0% 丢包），本地对外 TCP 正常（baidu:443/服务器:22 通），唯独中泰 6002/6102 不通。
- **根因**：本地出口网络对中泰测试服务器 TCP 端口的 SYN-ACK 回程受限（SYN 到达服务器——XTP 后台记录了访问，但握手没完成）。**不是 IP 白名单**（用户确认测试账号未设白名单）、**不是非交易日**（用户纠正）、不是代码问题。
- **解决**：服务器跑同一脚本 → 行情+交易登录成功，账户 `253191001822 balance=1000000.0`（100 万对得上），SZSE 合约推送。确认本地连不上纯本地网络问题，实盘走服务器。
- **附带坑**：vnpy 4.0 `MainEngine.subscribe(req: SubscribeRequest, gateway_name)` 是**单个 SubscribeRequest**，不是 list。传 list 会报 `'list' object has no attribute 'exchange'`（list 被当 req 传到 gateway）。改循环 `for req in reqs: me.subscribe(req, "XTP")`。
- **教训**：
  1. 连不上券商服务器时分层诊断：`ping`（IP 可达性）+ `bash /dev/tcp`（TCP 端口）+ 对外基线（baidu:443）。ping 通 + TCP 不通 = 端口/防火墙问题，非 IP 不可达。
  2. 本地能验代码层（import/调用），网络层实盘验证走服务器（本地出口网络常受限）。
  3. vnpy 4.0 的 subscribe/connect/send_order 等多带单个 Request 对象，传 list 要自己循环。

## 2026-07-26 · 类型级同步卡 running + 回补历史 NaN 崩溃 [已解决]

- **现象1**：astock_daily `last_status=running` 卡住不释放，后续同步全被防重跳过返回 skipped。
- **根因1（劣质修补）**：`sync()` 用 `if last_status=='running'` 防重，进程被杀后状态死无对证，永远卡死。第一版我加了"running 超 30 分钟判僵尸自动重置"——**被用户否决**：固定时间阈值是拆东墙补西墙，误杀长任务或漏判卡死，本质在猜时间。
- **根本解1**：`src/data_sync/sync_lock.py` 新增 `SyncLock`（Valkey 心跳锁）。`SET NX EX` 抢锁 + token 校验，后台线程每 20s 刷 TTL（60s TTL 留 40s 余量）。进程被杀->无人刷新->TTL 自然过期->下次 sync 能抢到。**不猜时间，靠 TTL 自然过期，分布式锁标准做法**。`last_status` 退化为展示用，不再作防重依据。实测：进程被 kill 后 65s 锁自动过期，自愈可继续触发。
- **现象2**：astock_basic 回补 `start_date=19800626`（用户填了 1980 起），大量日期 failed：`TypeError: float() argument must be a string or a real number`。
- **根因2**：1991-1999 早期 daily_basic 数据 `pe/pb/turnover_rate` 等字段是 Python `None`（非 NaN）。`save_daily_basic` 第 254 行 `float(r.get("turnover_rate", 0))`——`.get(key, default)` 的 default 只在 key 不存在时用，key 存在但值 None 时返回 None，`float(None)` 抛 TypeError。`close`/`turnover_rate` 裸 float 无保护，其余字段有 `pd.notna()` 保护所以没事。
- **解决2**：加 `_safe_float(v, default)` 工具（None/NaN/空串/非法 -> default），统一替换 `to_save_rows`/`to_save_rows_min`/`save_daily_basic`/`engine._daily_to_rows` 所有裸 float。实测 1991 年 8 行历史数据入库不再崩。
- **教训**：
  1. 防重/状态机不能只靠进程自己写的 DB 字段，进程被杀就死无对证。用进程外可见的活信号（Valkey 锁 + TTL）才是根本解。时间阈值是劣质修补。
  2. `dict.get(key, default)` 的 default 只在 key 缺失时生效，key 存在但值为 None 时返回 None。`float(None)` 必崩。pandas 数据入库统一走 `_safe_float` 之类工具，杜绝裸 float。
  3. 回补时填超早起始日（如 1980）会拉到 Tushare 早期缺字段数据，触发隐藏的 NaN 崩溃——数据清洗必须防御性。

- **解决**：①生产用分钟线需升积分档（5000+）提频次；②或 AkShare 免费拉东财分钟线补量（非官方、不稳）；③或实盘时直接用 XTP 实时行情，不走 Tushare 历史分钟。
- **教训**：Tushare 积分解锁的是"接口权限"，"调用频次"是另一个维度，按积分档递增。设计分钟线管线时要考虑频次瓶颈，做批量+缓存。

## 2026-07-23 · init-db.sh 在 HBA_FILE 检测行静默退出 [已解决]

- **现象**:`sudo bash scripts/init-db.sh` 看似"执行完了"但 pg_hba.conf 没被改、quant 仍要密码。`bash -x` 显示脚本在 `HBA_FILE=$(ls ...)` 赋值行后立即退出，后续步骤全没跑。
- **触发条件**:`set -euo pipefail` + `ls /var/lib/pgsql/*/data/pg_hba.conf` 的 glob 无匹配。本机 PGDATA 是 `/var/lib/pgsql/data/`（不在版本子目录），glob 不展开成字面量，`ls` 把它当路径找不到报非零，`pipefail` 让 `ls|head` 管道非零，`set -e` 在**赋值语句**（命令替换的退出码=赋值的退出码）处直接杀脚本，且无报错输出。
- **试过没用的**:
  - `sudo -u postgres psql` 直连 —— 本机 pg_hba `local` 是 `md5`/scram（非 peer），连超级用户都要密码，进不去（这是另一个坑，脚本已用 temp-trust 绕开）。
  - 改 `all all` → trust 永久版 —— 影响共用此 PG 的其他 app，改回定向 quant 专属 trust。
- **根因**:`ls <非匹配glob>` + `pipefail` + `set -e` 三者叠加，在命令替换赋值行静默退出。`2>/dev/null` 只压报错不改变退出码。
- **解决**:`scripts/init-db.sh` 的 HBA_FILE 检测改用 `find /var/lib/pgsql -name pg_hba.conf -type f -print -quit 2>/dev/null || true`（无 glob、无管道、无 SIGPIPE、`|| true` 兜底），不触发 set -e。
- **教训 / 怎么避免**:在 `set -euo pipefail` 脚本里，**命令替换赋值 `var=$(cmd)` 的退出码 = cmd 的退出码**，cmd 失败会让 `set -e` 静默杀脚本且无输出。避免用 `ls <glob>` 做存在性/路径检测；用 `find ... -print -quit` 或 `for p in ...; do [ -f "$p" ] && ...; done`。关键命令加 `|| true` 或用 `if` 包裹。
